# 《SSE流式解析与异步执行》

> 原文链接：https://t.zsxq.com/QHX9s
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

流式 Chat 不只是“把同步 HTTP 放进线程池”：它需要正确解析 SSE 事件边界，定义完成、错误和取消的互斥终态，并让取消、背压、缓冲上限和资源清理贯穿整个异步生命周期。

## 核心内容提炼

- 原文的 `doStreamChat` 构造 `stream=true` 请求并声明 `Accept: text/event-stream`，创建上游 HTTP call 后提交到专用执行器，立即向调用方返回取消句柄。
- `StreamCallback` 提供 `onContent`、`onThinking`、`onComplete`、`onError`。原文约定完成和错误互斥，用户主动取消时不再回调完成或错误。
- `OpenAIStyleSseParser` 逐行读取 `data:`，识别 `[DONE]`，从 `choices[0].delta` 提取 `content` 或 `reasoning_content`，必要时兼容 `message` 字段和 `finish_reason`。
- `StreamAsyncExecutor` 把阻塞读取从 Web 请求线程移到专用线程池；任务被拒绝时取消上游并回调错误，避免 HTTP call 已创建却无人消费。
- 取消采用两层机制：`AtomicBoolean` 提供业务取消信号，`Call.cancel()` 中断正在阻塞的网络读取；取消动作通过 CAS 保证幂等。
- 读取循环在 `[DONE]` 或明确完成原因时结束；提前 EOF、网络异常和解析异常需要转为终态。单条脏事件是否跳过，应取决于它是否影响流完整性。

## 关键概念/术语

- **SSE 事件**：由字段行组成、以空行结束的一条事件；不能等同于 TCP chunk 或单个 `data:` 行。
- **异步终态**：`COMPLETED`、`FAILED`、`CANCELLED` 等互斥且只能到达一次的生命周期结果。
- **取消传播**：从浏览器/调用方一路传到订阅、上游 HTTP 请求和资源持有者。
- **背压**：下游按处理能力请求数据，避免上游无限向内存缓冲写入。
- **有界缓冲**：限制事件数和字节数的队列或探测区，超过上限必须明确失败或施加背压。

## 与 xrag 项目的关系

- xrag 目前只有同步 Spring MVC 与 `RestClient`，没有现成流式客户端。Step C 应明确选择：
  - `WebClient` / Reactor：天然具备异步流和背压，但会引入新的编程模型；
  - 阻塞 HTTP + 专用线程池：实现改动较小，但必须自行定义线程容量、有界队列、取消和资源释放。
- 无论选择哪一种，验收都应覆盖：CRLF/LF/CR、多个 `data:` 行、注释、空行事件边界、未知事件、UTF-8、跨网络 chunk、提前 EOF、取消竞态和资源释放。
- 内部事件模型不应只包含文本，还要为思考、工具参数增量、完成、错误和 usage 留出明确类型。Provider 适配器负责把供应商事件归一化。
- 浏览器断开、用户停止、首包超时、流空闲超时、总截止时间和应用关闭都必须传播到上游；调用方取消不计入 Provider 熔断失败。
- 诊断至少记录流式标记、chunk 数、首事件/首有效块/下游提交耗时、是否已提交、终止原因和 Provider 请求 ID。

## 值得注意的设计取舍/坑

- **原文按行处理 `data:` 是教学简化，不满足完整 WHATWG SSE 语法。** 多条 `data:` 要在空行处拼成同一事件；冒号开头是注释，不能当业务数据。
- **专用线程池只是隔离，不自动提供背压。** 如果下游处理慢而上游持续产生事件，无界队列仍会耗尽内存。
- **取消语义必须显式。** “取消后不回调任何终态”虽然简单，但调用方可能无法区分主动取消和连接静默消失；内部应至少记录 `CANCELLED`，对外契约再决定是否发送事件。
- **不能一律吞掉解析异常。** 非关键未知字段可跳过；破坏事件结构、终止信号或业务 JSON 的错误应结束流并留下诊断。
- **终态后不得继续发送。** 完成、失败、取消需要原子保护，所有路径都应关闭响应体、归还连接、释放许可和清空缓冲。
