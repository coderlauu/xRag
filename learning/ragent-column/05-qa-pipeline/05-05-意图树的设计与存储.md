# 《四分类撑不住 20 个知识库，为什么要设计意图树？》

> 原文链接：https://t.zsxq.com/NuEaK
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

扁平四分类只回答了"做什么"（知识检索/工具调用/闲聊/澄清），回答不了"**去哪找**"——知识库从 2 个涨到 20 个时，"知识检索"这一类里塞了全部候选；解法是一棵三级意图树，叶子节点直接绑定执行目标（Collection / MCP 工具 / 系统模板），**且只有叶子参与打分**。

## 核心内容提炼

- **四分类的三处失效**：分不清该查 20 个库里的哪一个；有多个 MCP 工具时不知道调哪个；分类完还要再加一层路由，**分类与路由割裂**。

- **暴力全库搜索算过账，不划算**：20 个库各取 Top-5 = 100 条候选，Cross-Encoder 精排的计算量约为单库的 20 倍，延迟从几十毫秒飙到秒级。更要命的是**质量反而下降**——跨境物流的 chunk 和 3C 数码的 chunk 放在一起做全局排序，Reranker 会被语义上"都沾点边"的文档迷惑，把不相关的排到前面。

- **三级结构 DOMAIN → CATEGORY → TOPIC，但深度不固定**。"商品信息""售后维修"在 CATEGORY 层就是叶子（知识集中，没必要再拆）；"跨境物流"下面有海外仓/清关/运费三个方向，才需要 TOPIC 层。**层数取决于知识库的粒度需求，两层分支和三层分支可以共存。**

- **只有叶子节点参与匹配**，中间层仅用于组织与导航。三个理由：
  1. **中间层没有可执行目标**——命中"跨境物流"也不知道该干什么；
  2. **中间层参与打分会让分数语义崩坏**——"国内物流"(CATEGORY) 0.8 分、"配送方式"(TOPIC) 0.7 分，该走哪个？走高分的？但它不可执行；
  3. **减少 LLM 要评估的节点数**——16 个节点里叶子只有 11 个，Prompt 更短、更快、更便宜。

- **三种 `IntentKind` 共存一棵树**，用同一套打分机制路由：

  | Kind | 叶子的关键字段 | 命中后 |
  |---|---|---|
  | KB | `collectionName` | 去对应 Collection 做向量检索 |
  | MCP | `mcpToolId` | 触发工具调用链 |
  | SYSTEM | `promptTemplate`（可选） | 跳过检索，直接调 LLM 或返回预设回复 |

  收益是**一步到位**：不需要先判类型再判具体意图，LLM 一次打分同时考虑所有叶子。

- **`IntentNode` 一个节点承载三层职责**：匹配（`description` + `examples`）、路由（`collectionName` / `mcpToolId` / `topK`）、生成（`promptTemplate` / `promptSnippet` / `paramPromptTemplate`）。**意图树不只是分类结构，它是整个 RAG 链路的路由表。**

- **`isLeaf()` 只看 `children` 是否为空，不看 `level`。** 这是"深度不固定"能成立的前提。

- **`promptSnippet` 与 `promptTemplate` 的分工有讲究**：单次问答命中多个意图时没法用某一个节点的专属完整模板，但个别节点又有必须遵守的规则（如"回答时提醒保修凭证有效期"），这时注入短片段而非整套模板。

- **持久化用扁平行而非嵌套 JSON**：每行一个节点，`parent_code` 表达父子关系，加载时在内存重建树。理由是可以单节点增删改查、可以用 SQL 条件查询（如"所有 KB 类型的叶子"）、ORM 支持更好。

- **重建树的四步**：查出 `deleted=0 且 enabled=1` 的扁平行 → DO 转内存对象（`intent_code`→`id`、`parent_code`→`parentId`）→ 按 `parentId` 挂到父节点 children → 递归填充 `fullPath`。**找不到父节点的孤儿节点兜底当作根节点**，宁可结构不完美也不让节点在加载中消失。

- **Redis 缓存整棵树而不是单个节点**：意图分类需要一次性拿到全部叶子来构建 Prompt，缓存单节点就得 scan 遍历再组装。一个 key、一次 get、反序列化就是完整的树。7 天 TTL + 写时主动失效。**意图树变更频率极低、读取频率极高，缓存命中率天然很高，不需要复杂的双写一致性方案。**

- **父停子不停会造成"看起来下线了其实还在匹配"**：停用 CATEGORY 但叶子仍启用时，LLM 看的是叶子，照样打分照样命中。所以批量停用/删除时强制校验子节点一致性，不满足直接拒绝操作。

## 关键概念/术语

- **意图树**：DOMAIN / CATEGORY / TOPIC 三级（深度可变）的意图组织结构。
- **叶子绑定**：叶子节点直接绑定一个可执行目标——向量集合、MCP 工具或系统回复模板。
- **`IntentKind`**：KB / MCP / SYSTEM 三种意图类型，共存于同一棵树。
- **`fullPath`**：从根到当前节点的路径串（「物流与配送 > 跨境物流 > 清关流程」），用于日志与歧义引导展示。
- **写时失效（Cache-Aside）**：管理端改动后主动清缓存，下次读取自动从库重建。
- **子节点一致性校验**：禁止父节点停用/删除而子节点仍处于启用状态。

## 与 xrag 项目的关系

- **`collectionName` 这个字段在 xrag 不成立，必须替换。** 原文绑定的是 Milvus Collection，而 xrag 的向量存储是 **pgvector**（Phase 0 检查点已锁定），知识库是 `knowledge_base` 表里的一行。意图叶子应当绑定 **xrag 的知识库 ID**，检索时按该 ID 过滤向量表，而不是切换 Collection。这不是改个字段名的事——**"一个知识库一个物理集合"与"一张向量表按知识库 ID 分区"是两种不同的检索形态**，会直接影响多通道并行检索的实现（第 10 篇）。

- **意图树是 Phase 3 最该形成 ADR 的决策。** CLAUDE.md 明确写着"检索策略尚未形成 ADR，遇到相关问题不要假设已有定论"。三级树 vs 扁平分类 vs 向量化路由是有真实取舍的选择，且一旦落库就有迁移成本，应当在 Step C 写成 ADR 而不是散落在技术方案里。

- **术语要进 [CONTEXT.md](../../../CONTEXT.md)。** 那里已经定义了「意图」「检索通道」「检索表达」，但没有「意图树」「意图节点」「叶子绑定」。Phase 3 Step B/C 要补上，否则 PRD 与技术方案会各叫各的。

- **`enabled` + `deleted` 双字段与 xrag 既有约定完全一致**：逻辑删除是全系统约束（[知识库 PRD §7.6](../../../docs/prd/2026-07-25-knowledge-base-prd.md)），而 `enabled` 用于动态启停——Phase 2 的 `ai-models.yml` 里 deployment 也是这个模式。可以直接沿用。

- **Redis 缓存这一层同样要按单实例假设重新论证**（[ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md)）。原文用 Redis 是为了集群下多实例共享失效信号；xrag 单实例下本地缓存 + 写时清空即可。**但要注意与 Phase 2 的一处差异**：模型 catalog 是启动时快照、改配置必须重启（无热更新），而意图树需要管理后台在线增删改后立即生效——**两者的一致性要求不同，不能照搬 catalog 的做法**。

- **意图树需要管理界面**，这意味着 Phase 3 的 Step B 除了问答对话页，还要出意图树维护页的 `ui-spec.md` 与可点击原型。这一条会显著影响 Phase 3 的工作量估算，应当在 Step A 检查点里明确提出来让所有者裁决——**是本期就做管理界面，还是先用 SQL/初始化脚本维护**。

- **`topK` 挂在节点上**（节点级检索条数，未配置时用全局默认）这个设计可以直接借鉴。它与 Phase 1 知识库的分块策略是同一类"全局默认 + 单体覆盖"的模式。

## 值得注意的设计取舍/坑

- **"只有叶子参与打分"是这套设计的承重墙。** 一旦允许中间层也参与，分数就失去了可比性——高分的不可执行、可执行的分不高，路由逻辑必须引入一堆特判。这条规则要写进规格，不能只留在代码里。

- **`description` 的质量直接决定匹配准确率**，它是 LLM 判断的核心依据。这意味着意图树的**运营成本**被低估了：加一个知识库不只是建表建索引，还要写一段能让 LLM 准确区分它与兄弟节点的描述。描述写得含糊，整条链路的路由都会飘。

- **孤儿节点兜底当根，是"宁可结构错也不丢数据"的取舍。** 值得学的是这个优先级排序：加载阶段丢节点会导致某类问题**静默地永远无法被路由到**，而结构不完美至少是可见、可修的。

- **父停子不停这个坑很隐蔽。** 管理员在界面上停用了一个分类，界面显示已停用，但用户提问照样命中下面的叶子——**界面状态与实际行为不一致**，而且没有任何报错。校验必须放在写入端，事后审计发现不了。

- **`BeanUtil.toBean` 不保证映射所有字段，`@Builder.Default` 在 setter 路径上不生效。** 原文显式补设了 `mcpToolId`、`paramPromptTemplate` 并手动初始化 `children`。xrag 用 JdbcTemplate + 显式 RowMapper，天然避开这类问题——Phase 2 工单 17 就记过教训：`queryForMap` 对 timestamptz 返回 `java.sql.Timestamp`，强转会运行时炸，所以改用显式 RowMapper。**这条经验在 Phase 3 继续适用：不要用反射式的自动映射。**

- **缓存整棵树 vs 缓存单节点，选择依据是读取形态而不是数据形态。** 意图分类每次都要全部叶子，那就整棵缓存；如果访问形态是"按 ID 取单个节点"，结论会反过来。设计缓存粒度时先问"谁在读、怎么读"。

- **7 天 TTL 在这里更像兜底而不是策略。** 真正保证新鲜度的是写时失效；TTL 的作用是防止某次清缓存失败导致脏数据永久驻留。这个双保险的思路值得保留，但 TTL 具体取值意义不大，不必纠结。
