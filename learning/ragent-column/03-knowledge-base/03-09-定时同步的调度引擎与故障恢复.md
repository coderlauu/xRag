# 《AI大模型Ragent项目》——定时同步的调度引擎与故障恢复

> 原文链接：https://t.zsxq.com/e9kKG
> 所属分组：03-knowledge-base AI知识库建设
> 系列下篇（讲运行时），上篇见 03-08（讲设计）

## 一句话概括

承接 03-08 的架构设计，这篇讲定时同步真正"跑起来"的样子：调度引擎用一条"到期+无锁"合一的SQL周期扫描任务、生产者-消费者模式异步执行；一次完整刷新分"准备（值不值得跑）→执行（两层防并发+两次锁失效检测）→收尾（按 Phase 精细化清理文件）"三阶段；再加上"锁自动过期 + RUNNING状态定时恢复"的双重故障兜底。核心心法是：**先判断值不值得跑，再决定跑到哪一步失败该怎么收拾**。

## 核心内容提炼

- **调度引擎的扫描SQL是全文设计精妙之处**：`WHERE enabled=1 AND (nextRunTime IS NULL OR nextRunTime<=now) AND (lockUntil IS NULL OR lockUntil<now) ORDER BY nextRunTime ASC LIMIT 20`——**一次查询就把"到期判断"和"锁判断"合并**，直接筛出"现在该跑且没人正在跑"的任务，不需要先查到期任务再单独判断锁状态。`LIMIT 20` 防止一次扫描太多任务打满线程池。

- **扫描到任务后不是直接执行，而是"抢锁→提交线程池"两步**：抢锁失败（`tryAcquire`返回`null`）直接跳过、不等待——这正是租约锁的特点（不排队等待，抢不到就放弃，等下一轮扫描）。**一个容易被忽略但很重要的补偿细节**：如果线程池已满导致任务提交失败（`RejectedExecutionException`），必须**立刻释放刚抢到的锁**，否则这个任务会白白卡住直到锁过期（默认15分钟），期间没人能接管。异常处理不能只是记日志，还要做补偿动作。

- **为什么扫描线程和执行线程要分离**：刷新逻辑（下载+分块+上传）可能耗时几秒到几分钟，如果在扫描线程里同步执行会阻塞后续扫描；用线程池异步执行是典型的"生产者-消费者模式"，扫描线程是生产者只管找任务提交，线程池是消费者负责真正干活，两者解耦、互不阻塞。

- **一次完整刷新的三阶段流程**（`ScheduleRefreshProcessor.process()` 是总编排者）：
  1. **准备阶段（判断值不值得跑）**：① 启动心跳（第一步就启动，因为后面所有操作都可能耗时，不启动心跳锁会过期；心跳启动失败要立刻释放锁终止执行）；② **重新校验任务合法性**——即使任务是扫描阶段找出来的，真正执行时环境可能已经变了（schedule/文档可能被删、文档可能被禁用、来源可能从URL改成文件、定时同步可能被关闭、cron可能变得非法），任一前提不成立就调用 `disableIfOwned()` 自动禁用而不是硬着头皮往下跑——**"不要假设环境不会变，执行前要重新确认"**是这里的核心工程原则；③ 先插一条 RUNNING 状态的 exec 记录（哪怕中途失败也能追溯到停在了哪一步）；④ **变更检测**（复用 03-08 的两级策略）——这是准备阶段最关键的一步，**90%以上的触发都会在这一步直接返回 SKIPPED**，只有真正检测到文件变化才进入执行阶段。这里的核心心法是："定时到了不等于要刷新，是定时到了先判断值不值得刷新"。
  2. **执行阶段（真正开始刷新，两层防并发+两次锁检测）**：⑤ 第一层防并发——检查文档当前状态，如果已经是 RUNNING（可能有手动分块正在跑），直接跳过；⑥ 第一次锁失效检测（抢占文档运行权之前）；⑦ 第二层防并发——**CAS抢占**文档RUNNING状态（`ne(status, RUNNING)`），标记 `phase=DOC_OCCUPIED`——**为什么要两层**：第一层检查和第二层CAS之间有时间差，其他线程可能在这个间隙抢先把文档占了，CAS操作本身保证原子性兜底；⑧ 上传新文件到对象存储——**关键设计：先上传、先分块，最后才切换文档主记录的文件元数据**（不是上传完立刻切换）；⑨ 第二次锁失效检测（执行分块之前，因为分块是最耗时的操作，上传阶段可能已经耗掉一些锁的租期）；⑩ 执行分块——**直接复用 03-07 篇的 `documentService.chunkDocument()`**，不单独造一套"定时同步专用分块流程"，设置 `UserContext` 为系统用户表示这是自动触发；⑪ 分块结束后**重新查一次文档状态确认真的是 SUCCESS**（不能假设分块流程没报错就等于真的成功了）；⑫ 确认成功后才 `applyRefreshedFileMetadata()` 切换 `docName`/`fileUrl`/`fileType`/`fileSize` 到新文件，标记 `phase=FILE_SWITCHED`。**为什么"先上传先分块最后切换"**：如果上传完立刻切换但分块失败了，用户看到的文档元数据已经是新文件，但检索不到任何chunk——这个中间态比"保持旧文件直到新文件真正可用"要糟糕得多。
  3. **收尾阶段（按 Phase 精细化清理，全文最见工程功力的部分）**：`markSuccessIfOwned()` 写回结果（同样锁感知，不匹配就只更新exec不更新主表）；异常处理按 Phase 分两种——文件还没切换成功（`phase != FILE_SWITCHED`）就正常标记失败；**文件已经切换成功但写回状态时才出错**，这种情况**不能**把文档标记为FAILED（因为分块和切换其实都成功了），只更新 exec 记录+打日志等人工介入；`finally` 块按 Phase 决定清理策略——**这是 Phase 枚举存在的真正价值**：
     - `FILE_SWITCHED`（新文件已生效）→ 删旧文件（安全，新的已经在用了）
     - `< CHUNK_COMPLETED`（新文件还没真正用上）→ 删新文件（避免浪费存储）
     - `>= CHUNK_COMPLETED && < FILE_SWITCHED`（分块成功但主记录还没切过去）→ **保留新文件+打告警**，因为 chunk 和向量已经写入数据库指向这个新文件了，删掉会导致数据不一致，宁可多占点存储也不能删。

- **定时任务的生命周期和文档操作联动**：创建（`startChunk` 的事务回调里 `upsertSchedule`，只处理URL来源，`enabled` 综合判断文档启用+cron非空+scheduleEnabled+间隔达标）；更新（文档启用/禁用时 `syncScheduleIfExists`，`allowCreate=false` 只更新已有记录不额外新建）；删除（文档删除时先删 exec 记录再删 schedule 主表，在事务里完成——**先删子表再删主表**是因为 exec 记录在业务逻辑上依赖 schedule 记录）。

- **RUNNING 状态恢复（双重故障保障的第二重）**：锁虽然会自动过期（15分钟）让其他实例能接管**任务**，但**文档状态**不会跟着自动恢复——如果文档一直卡在 RUNNING，用户既看不到结果也没法重新触发。所以每分钟单独扫描一次，把卡在 RUNNING 超过阈值（默认30分钟，最小10分钟）的文档批量重置为 FAILED。**这个机制的定位很清楚**："目的不是精确判断任务一定已经死了，而是做一个工程上的安全兜底"——不追求完美，追求兜底。

- **五个核心配置项**（`rag.knowledge.schedule` 前缀）：`scan-delay-ms`（10000，扫描间隔）、`lock-seconds`（900，锁持有时间）、`batch-size`（20，每次扫描批量大小）、`min-interval-seconds`（60，cron最小间隔）、`running-timeout-minutes`（30，RUNNING超时阈值）。

## 关键概念/术语

- **生产者-消费者模式（在调度引擎里的体现）**：扫描线程（生产者）只管找任务提交，线程池（消费者）负责真正执行刷新逻辑，两者解耦。
- **Phase 枚举**（`INIT→DOC_OCCUPIED→CHUNK_STARTED→CHUNK_COMPLETED→FILE_SWITCHED`）：追踪长流程执行到了哪一步，为异常清理提供"可靠坐标"。
- **两层防并发**：文档状态检查（粗筛，非原子）+ CAS抢占（细筛，原子）组合使用，弥补两次检查之间的时间差风险。
- **锁自动过期 + RUNNING定时恢复**：故障恢复的双重保障，一个管"任务级别的重新调度"，一个管"文档级别的状态复原"，缺一不可。

## 与 xrag 项目的关系

- **这篇和 03-08 合起来，是目前整个 03-knowledge-base 分组里对 xrag 实际编码阶段最具直接指导意义的两篇**——03-08 给出静态设计（表结构、组件划分、锁机制、检测策略），本篇给出动态流程（扫描逻辑、三阶段执行、Phase驱动的清理策略、故障恢复）。技术方案阶段应该把"三阶段流程 + Phase清理表"原样作为 xrag 定时同步模块的骨架。
- **"先判断值不值得跑，再执行"这个心法应该被提炼成 xrag 所有类似定时/批处理任务的通用设计原则**——不只是知识库定时同步适用，未来任何"周期性重复检查是否需要真正动作"的场景（比如评测报告的周期生成、模型健康检查）都应该套用这个模式。
- **"分块成功但主记录切换失败时保留新文件、打告警等人工介入"这个取舍**，体现的是"宁可多占资源也不能留下数据不一致"的一贯原则（和 03-01/03-06/03-07 篇里反复出现的类似取舍一脉相承）——xrag 技术方案里遇到类似"多步骤操作中间某一步失败"的场景，都应该按这个原则设计降级策略：优先保数据一致性，其次才是资源整洁。
- **由于 xrag 是单实例部署（个人项目），"锁自动过期让其他实例接管"这部分机制的实际价值会打折扣**（本来就只有一个实例，谈不上"接管"），但 **RUNNING 状态定时恢复这个机制无论单/多实例都有价值**（进程重启、异常退出都可能导致状态卡死），应该保留在 xrag 的设计里；数据库锁本身也仍然值得实现（防止同一进程内的手动分块和定时刷新并发冲突，这一点和实例数量无关）。

## 值得注意的设计取舍/坑

- **执行阶段的两次锁失效检测容易被简化成一次**，但原文明确指出两次检测的时机不同（抢占运行权前 vs 执行分块前），中间隔着"上传文件"这个可能耗时的操作，只检测一次会漏掉这段时间窗口内锁失效的情况。
- **变更检测阶段"每次都写一条 exec 记录（哪怕是SKIPPED）"是一个显式的取舍，不是没想清楚**：原文自己承认这样做"可追溯但数据会比较多"，并给出了两个可选优化方向（不变化就不写记录 / 定时清理旧记录），但明确说"如果文件不多，基本不需要"——这提示 xrag 在实现时也不必一开始就上优化，先按"全记录、可追溯"的简单方案来，等真的出现数据量问题再优化，不要提前优化。
- **"分块流程执行完不能假设一定成功，必须重新查一次状态确认"**——这是一个容易被跳过的校验步骤（直觉上"调用完成=成功"），但异步/长流程里"调用返回"和"业务真正成功"是两回事，必须显式二次确认。
- **线程池满了要主动释放锁这个补偿动作，是最容易被漏掉的边界情况**——大多数人写"抢锁→提交线程池"时只会处理"提交成功"的路径，容易忘记"提交失败也要释放已经拿到的资源"，这是需要在 code review 阶段专门检查的一类坑（资源获取后的所有分支路径都要能释放资源，不只是正常路径）。
