# 界面规格：AI 知识库建设模块

- `status`: approved（`2026-07-25`）
- `related_docs`: [API 契约](api.md)、[架构方案](architecture.md)、[数据模型](data-model.md)、[测试矩阵](test-matrix.md)、[PRD](../../docs/prd/2026-07-25-knowledge-base-prd.md)
- `prototype`: [可点击原型](../../prototype/knowledge-base/index.html)（自带演示控制台，可切换文档状态 / 空态 / 错误提示，逐条核对本文档的规则）

这份文档的目标是让前端照着实现而不需要回来追问需求。它不规定视觉风格（配色、圆角、字号），只规定**信息结构**和**状态规则**——后者散落在实现里就必然前后不一致：同一个 `RUNNING` 状态，列表页禁用了删除按钮、详情页忘了禁用，是这类模块最典型的 bug。

所有文案都是**确定的成品文案**，不是占位描述。写"给出明确提示"等于没写规格。

## 1. 页面结构

三个页面，两层导航深度。分块管理是文档页的子页面而不是独立顶级页面——分块脱离文档没有意义（[CONTEXT.md](../../CONTEXT.md)：分块"不能脱离源文档和文档版本独立存在"）。

```
/knowledge-bases                          知识库列表
  └─ /knowledge-bases/{kbId}              文档列表（页头显示所属知识库）
       └─ /documents/{docId}/chunks       分块管理
```

面包屑始终展示完整路径：`知识库 / 产品文档库 / 产品手册.pdf / 分块`。理由是分块页看到的是一堆文本片段，没有面包屑用户会不确定自己在编辑哪份文档的内容。

## 2. 文档状态的展示规则

四种状态是这个模块最核心的信息，它们的中文表述必须全局统一，任何一处出现同义词都算 bug。

| `status` | 中文表述 | 语义色 | 图标语义 | 用户此刻该做什么 |
|---|---|---|---|---|
| `PENDING` | **待处理** | 中性（灰） | 静态 | **需要点"开始处理"**——这是唯一需要用户主动动作的状态 |
| `RUNNING` | **处理中** | 进行中（蓝） | 旋转 | 等待，可轮询查看进度 |
| `SUCCESS` | **已完成** | 成功（绿） | 静态 | 无需操作，可查看分块 |
| `FAILED` | **处理失败** | 危险（红） | 静态 | 看失败原因，修正后重新处理 |

**`PENDING` 是最需要设计投入的一个状态。** 上传接口返回后文档并没有被分块（[api.md §3](api.md)、PRD §7 决策 1），如果界面只显示一个灰色的"待处理"标签，用户很容易以为系统正在后台自动处理，然后一直等下去。因此：

- 上传成功的 toast 文案必须点明下一步：**"上传成功，文档尚未处理。点击「开始处理」后才会切分并写入向量库。"**
- 文档列表里 `PENDING` 的行，操作区第一个按钮就是**「开始处理」**，且是主按钮样式（其他状态下这个按钮是次要样式的「重新处理」）。
- 知识库下存在 `PENDING` 文档时，文档列表顶部显示一条提示条：**"有 N 篇文档待处理，处理后内容才能被检索。"**

同一个触发接口在不同状态下的按钮文案不同，因为用户的心智不同：

| 文档状态 | 按钮文案 | 样式 |
|---|---|---|
| `PENDING` | 开始处理 | 主按钮 |
| `SUCCESS` | 重新处理 | 次要按钮 |
| `FAILED` | 重试 | 次要按钮 |

后端不区分这三种情况（[api.md](api.md)：都走同一条路径），但界面必须区分——对用户来说"第一次处理"、"重做一遍"和"失败后重试"是三件不同的事。

### 状态轮询

文档处于 `RUNNING` 时轮询 `GET /api/v1/documents/{docId}`，间隔 2s，进入 `SUCCESS`/`FAILED` 后停止。

离开页面必须停止轮询。列表页有多篇 `RUNNING` 文档时，轮询列表接口一次而不是为每篇文档各发一个请求。

`RUNNING` 期间**不显示百分比进度**。后端只提供 `phase`（阶段），不提供百分比，编造一个假进度条比诚实地显示"处理中"更糟。可以显示当前阶段：**"处理中 · 正在计算向量"**（`phase` 映射见 §4）。

## 3. `RUNNING` 时必须禁用的操作

`RUNNING` 是唯一的排他状态。后端对这些操作一律返回 `409 DOCUMENT_PROCESSING`，但界面不能靠"点了才报错"来传达这件事。

| 位置 | 操作 | `RUNNING` 时 |
|---|---|---|
| 文档列表 / 详情 | 删除文档 | 禁用 |
| 文档列表 / 详情 | 编辑文档（名称、分块参数、同步配置） | 禁用 |
| 文档列表 / 详情 | 开始处理 / 重新处理 / 重试 | 禁用 |
| 文档列表 / 详情 | 启用 / 禁用文档 | 禁用 |
| 分块页 | 新增分块 | 禁用 |
| 分块页 | 编辑 / 删除单个分块 | 禁用 |
| 分块页 | 批量启用 / 禁用 | 禁用 |

禁用按钮必须挂 tooltip，统一文案：

> **文档正在处理中，请等待处理完成后再操作。**

这句话与后端 `409 DOCUMENT_PROCESSING` 的 `message` **逐字相同**（见 [api.md §1](api.md)）。一致性在这里有实际价值：万一竞态导致用户还是撞上了 409（界面上按钮已灰但状态是 2 秒前的快照），用户看到的是同一句话，不会以为遇到了两种不同的问题。

分块页在文档 `RUNNING` 时整页显示一条横幅，而不是让用户去逐个发现按钮都灰了：

> **文档正在重新处理，当前分块即将被替换。处理完成后请刷新。**

这条措辞点明了"即将被替换"——重新处理会逻辑删除旧分块、写入新分块（[architecture.md §3.2](architecture.md)），用户此刻看到的内容马上就不存在了。只说"请稍候"会让人以为编辑还有意义。

## 4. `phase` 的中文映射

`phase` 让"失败了"变成"在哪一步失败了"，这是 CONTEXT.md 对「入库任务」的明确要求。不映射成中文，它对用户就是五个无意义的英文单词。

| `phase` | 处理中文案 | 失败文案 |
|---|---|---|
| `DOWNLOAD` | 正在读取文件 | 读取文件失败 |
| `EXTRACT` | 正在提取文本 | 文本提取失败 |
| `CHUNK` | 正在切分内容 | 内容切分失败 |
| `EMBED` | 正在计算向量 | 向量计算失败 |
| `PERSIST` | 正在写入 | 写入失败 |
| `null` | 处理中 | 处理失败 |

失败时展示形式是 **`{阶段失败文案}` + 折叠的 `errorMessage` 原文**：

> ⚠ **向量计算失败**　　[查看详情 ▾]
> ```
> Embedding API 返回 429：rate limit exceeded
> ```

`errorMessage` 原文默认折叠但必须可展开。它经常包含供应商的原始错误（配额耗尽、Key 失效、限流），这些是用户能自己解决的问题；把它藏起来只显示"向量计算失败"，用户只能反复重试碰运气。

`phase` 为 `null` 的失败（尚未进入任何阶段就失败，或超时/重启回收）走兜底文案。**回收产生的失败要能与真实失败区分**——它们的 `errorMessage` 分别写明"进程重启"和"心跳超时"，界面直接展示原文即可，不需要额外的状态位。

## 5. 入库任务历史与 `SKIPPED`

文档详情页展示最近一次任务摘要（`latestRun`），并提供"查看全部处理记录"入口打开完整历史列表。

| `ingestion_run.status` | 中文表述 | 语义色 |
|---|---|---|
| `QUEUED` | 排队中 | 中性 |
| `RUNNING` | 处理中 | 进行中 |
| `SUCCESS` | 成功 | 成功 |
| `FAILED` | 失败 | 危险 |
| `SKIPPED` | **内容未变化，已跳过** | **中性（灰），绝不能用警告或危险色** |

`SKIPPED` 是最容易被做错的一个。它不是失败，是"检查过、内容没变、无需处理"——**这是定时同步正常工作时最常见的结果**。如果把它标成橙色警告，用户每天早上打开界面看到一排橙色，会以为同步一直有问题。

`SKIPPED` 的历史行不显示"重试"入口（没什么可重试的），但显示检查时间，让用户确认调度确实在跑。这正是 `SKIPPED` 必须落库的原因（[architecture.md §3.3](architecture.md)）：没有它，用户看到"同步开着但从来没有执行记录"，无法区分"检查过没变化"和"调度根本没跑"。

定时同步区块的完整展示：

```
定时同步　　[已开启]
  同步规则　　每天 03:00　（0 0 3 * * ?）
  下次执行　　2026-07-26 03:00
  上次执行　　2026-07-25 03:00　内容未变化，已跳过
  ⚠ 最近 10 次记录中有 2 次失败　　[查看全部记录]
```

"最近 N 次中有 M 次失败"这一行只在确实存在失败记录时出现。PRD §5 要求同步配置"不是配置完就看不见"，而"有没有失败历史"是这里唯一真正需要用户注意的信号——单看"下次执行时间"完全看不出这个同步其实每次都在失败。

`syncCron` 同时展示人类可读描述和原始表达式。只给 `0 0 3 * * ?` 大多数用户读不懂；只给"每天 03:00"则无法核对自己填的表达式是否正确。

## 6. 分块管理页

### 布局

分块管理是文档页下的**独立子页面**（不是弹层）。PRD §5 的理由是需要展示分块在原文中的顺序上下文；弹层的高度约束会让"上下文"变成只能看见一两条。

```
产品手册.pdf · 分块（142）                          [新增分块]
─────────────────────────────────────────────────────────
[ ] 全选　　已选 3 项　[批量启用] [批量禁用]      筛选：全部 ▾
─────────────────────────────────────────────────────────
[ ] #0   987 字符 · 约 640 token          [已启用]  [编辑] [删除]
        第一章 总则……
─────────────────────────────────────────────────────────
[✓] #1   1012 字符 · 约 660 token         [已禁用]  [编辑] [删除]
        1.2 适用范围……
```

- 按 `chunkIndex` 升序，与后端排序一致（[api.md §4](api.md)）。序号显示为 `#{chunkIndex}` 而非行号——它是分块在原文中的位置，删除中间某块后序号出现空缺是正常的，**不要重新编号**。
- `chunkIndex` 允许重复（手动新增分块时可指定已存在的序号）。两条同号分块相邻展示即可，界面不做去重也不报错。
- `tokenCount` 展示为 **"约 N token"**。它是启发式估算，只用于展示、不参与任何逻辑判断（[architecture.md §5](architecture.md)），加"约"字是为了不让用户拿它去核对账单。
- 内容默认折叠为 2 行，点击展开全文。

### 分块的启用状态

| `enabled` | 标签 | 含义提示（hover） |
|---|---|---|
| `true` | 已启用 | 参与检索 |
| `false` | 已禁用 | 不参与检索，向量已清理 |

"向量已清理"这句要写出来，因为重新启用会**重新计算向量**（[api.md §4](api.md)），也就是会再花一次 Embedding 的钱。用户有权在点之前知道这件事。

**父文档被禁用时**，分块页顶部显示横幅，且所有"启用分块"操作禁用（对应后端 `409 INVALID_STATE`，见 CHK-26）：

> 文档已禁用，其中所有分块都不参与检索。**请先启用文档**，再单独调整分块。

注意这里的不对称：**禁用分块不受父文档状态限制，启用才受**（[api.md §4](api.md)）。所以横幅期间"批量禁用"仍然可用，只有"批量启用"禁用。这个不对称不解释清楚，前端很容易图省事把两个按钮一起灰掉。

### 编辑分块

编辑用弹层（只改一段文本，不需要整页）。保存后：

- 内容确实变了 → toast **"已保存，向量已更新。"**
- 内容与原来完全一致 → toast **"内容未变化，未重新计算向量。"**

第二种情况后端直接返回不做任何向量操作（[api.md §4](api.md)：省下按 token 计费的调用，也避免删旧插新期间的检索空窗）。界面把这件事说出来，用户才知道系统"聪明地什么都没做"，而不是怀疑保存没生效。

### 批量操作反馈

选中若干分块点击「批量禁用」，**先弹确认框**，文案由前端根据已加载的列表本地算出：

> 已选中 **12** 个分块，其中 **9** 个将从「已启用」变为「已禁用」，**3** 个已是目标状态、不会变化。
>
> 禁用后这些分块的向量会被清理，不再参与检索。
>
> 　　　　　　　　　　　　　　　[取消] [确认禁用]

操作完成后 toast 用后端返回的**实际**数字（`{requested, changed, alreadyInTargetState}`）：

> 已处理 12 个分块，其中 9 个状态已变更，3 个原本就是该状态。

确认框用本地估算、toast 用后端实测，两个数字都要展示。它们通常一致；**不一致就说明在用户确认的这几秒里数据被别处改动了**，此时用户看到的是真实结果而不是自己以为的结果。

批量选择的两条约束要在界面上体现，而不是等后端报 400：

- 选中数超过 **500** 时禁用批量按钮，提示 **"单次最多操作 500 个分块，请分批处理。"**（对应 CHK-31/CHK-32）
- 未选中任何分块时禁用批量按钮。不提供"全选所有页"——那个需求应该用文档级的启用/禁用（[api.md §4](api.md) 约束 1）。

## 7. 错误提示文案

后端错误码到用户文案的映射。四种"用户能自己解决"的错误必须有专属文案——统一显示"请求失败"会让用户完全不知道下一步该做什么。

| HTTP | `error` | 用户提示 |
|---|---|---|
| 413 | `FILE_TOO_LARGE` | **文件超过 50MB 上限，无法上传。** 请压缩或拆分后重试。 |
| 415 | `UNSUPPORTED_FILE_TYPE` | **不支持这种文件格式。** 目前支持 .txt、.md、.pdf、.docx。 |
| 429 | `UPLOAD_BUSY` | **当前上传任务较多，请稍后重试。** 系统同时最多处理 3 个上传。 |
| 409 | `DOCUMENT_PROCESSING` | **文档正在处理中，请等待处理完成后再操作。** |
| 400 | `INVALID_REQUEST` | 直接展示后端 `message` |
| 404 | `NOT_FOUND` | **内容不存在或已被删除。** 请返回列表刷新后重试。 |
| 502 | `EMBEDDING_FAILED` | **向量计算服务暂时不可用。** 请稍后重试；若持续失败请检查模型服务配置。 |
| 409 | `INVALID_STATE` | 直接展示后端 `message`（见下） |
| 无 | 网络失败 | **无法连接到服务器。** 请确认后端已启动、网络正常后重试。 |
| 其他 | 其他 | **操作失败，请稍后重试。** 副文案取后端 `message`，没有则显示"服务端返回 {status}。" |

413/415/429 的文案里都写进了**具体数字或清单**（50MB、四种格式、3 个并发）。只说"文件太大"，用户不知道要压到多小才行。

最后两行是兜底，`2026-07-25` 实现工单 04 时补入。**网络失败必须与 HTTP 错误分开**：前者没有状态码，说"操作失败请重试"会让用户在后端根本没启动的时候反复点重试；后者至少能把服务端的话透出来。

文案里的 50MB / 3 个并发与后端 `application.properties` 的 `UPLOAD_MAX_FILE_SIZE`、`UPLOAD_MAX_CONCURRENT` 耦合，改配置时这张表和 `frontend/src/api/errors.ts` 要一起改。

> ### `INVALID_STATE` 必须由后端给出具体文案
>
> 这是写这份规格时发现的一个 API 契约细节。`409 INVALID_STATE` 在 [api.md](api.md) 里对应至少三种完全不同的情况：
>
> 1. 给禁用文档触发分块
> 2. 给禁用文档新增分块
> 3. 启用分块但父文档处于禁用
>
> 它们的用户动作各不相同，但**前端从错误码上无法区分**。两种解法：给每种情况分配独立的 `error` 码，或让后端在 `message` 里写清具体原因。
>
> **选后者**：这三种情况的共同修复动作其实是同一个（先启用文档），前端并不需要按码分支处理逻辑，只需要把话说清楚。为此拆出三个错误码，前端要写三个分支来显示三句文案，与直接展示 `message` 的效果完全一样，只是多了一层映射表要维护。
>
> 因此对后端的硬性要求：**`INVALID_STATE` 的 `message` 必须是可以直接展示给用户的完整句子**，不能是 `"invalid state"` 这类开发者向的字符串。三处的成品文案：
>
> | 场景 | `message` |
> |---|---|
> | 给禁用文档触发分块 | 文档已禁用，无法处理。请先启用文档。 |
> | 给禁用文档新增分块 | 文档已禁用，无法新增分块。请先启用文档。 |
> | 启用分块但父文档禁用 | 文档已禁用，无法单独启用其中的分块。请先启用文档。 |
>
> 这个要求已同步进 [api.md](api.md) 的错误响应约定。

## 8. 空态

三处空态各有不同的引导，因为用户此刻缺的东西不同。

| 位置 | 文案 | 引导操作 |
|---|---|---|
| 知识库列表为空 | **还没有知识库。** 知识库是文档的归属边界，同一业务范围的资料放在一个知识库里。 | [创建知识库] 主按钮 |
| 文档列表为空 | **这个知识库还没有文档。** 上传本地文件，或添加一个可定时同步的文件链接。 | [上传文件] [添加链接] 两个并列按钮 |
| 分块列表为空（`revision = 0`） | **文档还没有处理。** 处理后会切分成分块并写入向量库，届时可在此查看和编辑。 | [开始处理] 主按钮 |
| 分块列表为空（`revision > 0`） | **这份文档没有切出任何分块。** 可能是文件内容为空或无法提取出文本。 | [重新处理] 次要按钮 |

最后两条必须分开。同一个"分块为空"，`revision = 0` 是"还没处理"（正常，需要用户动作），`revision > 0` 是"处理过但切不出内容"（异常，多半是空文件或扫描版 PDF 提取不出文字）。合并成一句话，第二种情况的用户会一直点"开始处理"而永远得不到分块。

筛选后为空是另一回事，不要用空态：显示 **"当前筛选条件下没有内容。"** 加一个「清除筛选」链接。把它做成空态会让用户以为数据没了。

## 9. 二次确认清单

只在这些操作上做二次确认。删除是逻辑删除、技术上可恢复，但界面上**没有**恢复入口，对用户而言就是不可逆的，所以照不可逆处理。

| 操作 | 确认文案要点 |
|---|---|
| 删除知识库 | 点明连带影响：**"将同时删除其中 N 篇文档和 M 个分块，且无法在界面上恢复。"** |
| 删除文档 | **"将同时删除该文档的 N 个分块，且无法在界面上恢复。"** |
| 删除分块 | 单条删除不做确认弹层——影响面小、可手工重建，弹层的打扰成本高于收益 |
| 禁用文档 | 点明代价：**"该文档全部内容将不参与检索。重新启用时需要重新计算向量。"** |
| 批量禁用分块 | 见 §6 |

"无法在界面上恢复"这个措辞是准确的：数据确实还在库里（逻辑删除），但界面不提供恢复功能。写"永久删除"是撒谎，写"可以恢复"会让用户误以为界面上有恢复入口。
