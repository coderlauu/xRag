# 数据模型：AI 知识库建设模块

- `status`: approved（`2026-07-25`）
- `related_docs`: [架构方案](architecture.md)、[API 契约](api.md)、[界面规格](ui-spec.md)、[测试矩阵](test-matrix.md)、[PRD](../../docs/prd/2026-07-25-knowledge-base-prd.md)、[CONTEXT.md](../../CONTEXT.md)

本文件描述 Flyway `V1`～`V5` 演进后的当前结构。基础五表来自
`V2__knowledge_base_schema.sql`，后续字段必须以增量 migration 添加，不能回改已执行的 V2。

## 1. 全局约定

| 约定 | 做法 | 理由 |
|---|---|---|
| 主键 | `bigint generated by default as identity` | 单用户项目无需 UUID 防猜测；bigint 作为向量表主键比 uuid 省空间、比较更快 |
| 时间戳 | `timestamptz`，`create_time` / `update_time` 默认 `now()` | 统一带时区，避免后续部署到不同时区时的解释歧义 |
| 枚举 | `varchar` + `check` 约束，**不用 PostgreSQL 原生 enum 类型** | 原生 enum 增删值需要 `ALTER TYPE`、无法在事务中回滚部分操作，演进成本比 check 约束高 |
| 逻辑删除 | 每张业务表带 `deleted boolean not null default false` + `delete_time timestamptz` | [PRD §7.6](../../docs/prd/2026-07-25-knowledge-base-prd.md) 全局约束 |
| 命名 | 表名单数、列名 snake_case | 与 Flyway/JDBC 直连风格一致，无 ORM 命名策略介入 |

**逻辑删除对唯一约束的影响**：普通唯一索引会让"删掉再建同名"失败。凡需要唯一性的列都用**部分唯一索引** `where deleted = false`，这样逻辑删除会释放该名字。

**逻辑删除对查询的影响**：`repository` 层所有查询方法必须带 `deleted = false`。这是一条靠约定维持的纪律，容易漏——测试矩阵里为此专门安排了一组"删除后各查询接口都不再返回该记录"的用例（见 [任务书 Lane 测试](../../docs/exec-plans/active/2026-07-25-knowledge-base-implementation-lanes.md)）。

## 2. 表清单与 CONTEXT.md 术语对应

| 表 | CONTEXT.md 术语 | 说明 |
|---|---|---|
| `knowledge_base` | 知识库（Knowledge Base） | 同时承载「向量配置版本（Embedding Profile）」的声明 |
| `source_document` | 源文档（Source Document）+ 文档版本（Document Revision） | 版本以自增 `revision` 字段承载，不建独立表（[architecture.md §4.2](architecture.md)） |
| `document_chunk` | 文档分块（Document Chunk） | 通过 `revision` 追溯到具体文档版本 |
| `document_chunk_embedding` | 分块的可检索表示 | 派生索引，**唯一一张不做逻辑删除的表** |
| `ingestion_run` | 入库任务（Ingestion Run）+ 链路记录（Trace）的入库侧载体 | 同时是异步任务队列 |

## 3. DDL

### 3.1 `knowledge_base`

```sql
create table knowledge_base (
    id                   bigint generated by default as identity primary key,
    name                 varchar(128)  not null,
    storage_alias        varchar(64)   not null,
    description          varchar(1024),
    embedding_model      varchar(128)  not null,
    embedding_dimensions integer       not null,
    deleted              boolean       not null default false,
    delete_time          timestamptz,
    create_time          timestamptz   not null default now(),
    update_time          timestamptz   not null default now()
);

create unique index uk_knowledge_base_name on knowledge_base (name) where deleted = false;
```

- `embedding_model` / `embedding_dimensions` 是 CONTEXT.md「向量配置版本」的落地。第一版必须与全局配置一致（创建时校验），一经确定不可修改——改模型会让已有向量全部失效，那是一次"重建"操作而非"编辑"。
- `storage_alias` 是创建时由名称生成的不可变存储别名，只服务于 RustFS Key 可读性；知识库改名不搬动对象。
- 归一化方式与相似度口径不入表：全局统一为**余弦距离**（向量表索引用 `vector_cosine_ops`），向量按 Embedding API 返回值原样存储（主流供应商返回的已是单位向量）。将来若要支持多种口径，再把它加成本表的列。

### 3.2 `source_document`

```sql
create table source_document (
    id                  bigint generated by default as identity primary key,
    kb_id               bigint        not null references knowledge_base (id),
    name                varchar(256)  not null,
    source_type         varchar(16)   not null,
    -- FILE 与 URL 共用
    storage_object_id   varchar(36)   not null,
    file_key            varchar(512),
    file_size           bigint,
    content_type        varchar(128),
    content_hash        varchar(64),
    -- 仅 URL
    source_uri          varchar(2048),
    http_etag           varchar(256),
    http_last_modified  varchar(128),
    sync_enabled        boolean       not null default false,
    sync_cron           varchar(64),
    next_sync_time      timestamptz,
    last_sync_time      timestamptz,
    -- 分块配置（每文档可配，V3 补入）
    chunk_strategy      varchar(16)   not null default 'RECURSIVE',
    chunk_size          integer       not null default 1000,
    chunk_overlap       integer       not null default 100,
    -- 处理状态
    status              varchar(16)   not null default 'PENDING',
    revision            integer       not null default 0,
    chunk_count         integer       not null default 0,
    error_message       varchar(2048),
    enabled             boolean       not null default true,
    deleted             boolean       not null default false,
    delete_time         timestamptz,
    create_time         timestamptz   not null default now(),
    update_time         timestamptz   not null default now(),

    constraint ck_source_document_source_type check (source_type in ('FILE', 'URL')),
    constraint ck_source_document_status
        check (status in ('PENDING', 'RUNNING', 'SUCCESS', 'FAILED')),
    constraint ck_source_document_url_fields
        check (source_type <> 'URL' or source_uri is not null),
    constraint ck_source_document_sync_fields
        check (sync_enabled = false or (source_type = 'URL' and sync_cron is not null)),
    constraint ck_source_document_chunk_strategy
        check (chunk_strategy in ('FIXED_SIZE', 'RECURSIVE')),
    constraint ck_source_document_chunk_params
        check (chunk_size > 0 and chunk_overlap >= 0 and chunk_overlap < chunk_size)
);

create index idx_source_document_kb on source_document (kb_id, deleted, id desc);
create index idx_source_document_sync on source_document (next_sync_time)
    where deleted = false and sync_enabled = true and source_type = 'URL';
```

- **文档名不做唯一约束**：同一份文件上传两次是合理场景（比如想用不同分块参数各处理一份对比效果），强制唯一只会碍事。
- `ck_source_document_sync_fields` 用数据库约束保证"只有 URL 来源能开定时同步"，而不是只靠 Service 层校验——这是 PRD §4.3 的硬性边界，值得在最底层兜一道。
- `revision` 从 0 开始，每次成功分块 +1。`revision = 0` 表示"上传后还没成功分块过"。
- `idx_source_document_sync` 是部分索引：定时扫描只关心开了同步的 URL 文档，索引只覆盖这部分记录，比全表索引小得多。注意 `status <> 'RUNNING'` **没有**放进索引条件——`status` 是高频更新列，放进部分索引条件会导致每次状态变更都触发索引项的增删。
- `file_key` 对 URL 来源同样有值：URL 文档抓取后也会存进对象存储（有了本地副本才能在不重新下载的情况下重新分块）。
- `storage_object_id` 是文档级稳定 UUID，用于把同一文档的所有不可变版本聚合到一个对象前缀下；文档改名不改变它。
- `file_key` 始终表示**当前成功版本**的原文。定时同步的新对象在入库成功前只由 `ingestion_run.input_file_key` 引用，失败时不会提前切换本列。
- **分块配置三列是每文档独立的**，不是全局配置：定时同步重新分块时必须沿用该文档原本的策略，否则用户为某份文档特意调小的 `chunkSize` 会在下一次自动同步时被悄悄改回默认值。列名用 `chunk_overlap` 而非 `overlap`，避免与 SQL 的 `overlaps` 谓词形近读错。这三列由 `V3__source_document_chunk_config.sql` 补入——`V2` 建表时漏了，而 `V2` 已实际执行过，改它会破坏 Flyway 的校验和。

**状态机**：

```
PENDING ──触发分块──> RUNNING ──成功──> SUCCESS ──重新触发/定时同步──> RUNNING
   ▲                     │                                              │
   └── 无 ────────────────┴──失败/超时回收──> FAILED ──重新触发──────────┘
```

`RUNNING` 是唯一的排他状态：CAS 条件 `status <> 'RUNNING'` 意味着 `PENDING`/`SUCCESS`/`FAILED` 都可以被抢占触发。**没有任何路径回到 `PENDING`**——`PENDING` 只表示"从未处理过"。

### 3.3 `document_chunk`

```sql
create table document_chunk (
    id           bigint generated by default as identity primary key,
    kb_id        bigint      not null references knowledge_base (id),
    doc_id       bigint      not null references source_document (id),
    revision     integer     not null,
    chunk_index  integer     not null,
    content      text        not null,
    char_count   integer     not null,
    token_count  integer     not null,
    content_hash varchar(64) not null,
    enabled      boolean     not null default true,
    deleted      boolean     not null default false,
    delete_time  timestamptz,
    create_time  timestamptz not null default now(),
    update_time  timestamptz not null default now()
);

create index idx_document_chunk_doc on document_chunk (doc_id, deleted, chunk_index);
create index idx_document_chunk_kb on document_chunk (kb_id, deleted);
```

- `kb_id` 是相对 `doc_id` 的**冗余列**，有意保留：删除知识库时可以一条 SQL 级联标记全部分块，不必先查文档列表；分块归属校验也能一次查完。
- `chunk_index` **不是唯一约束**，允许重复。它只是"按原文顺序展示"的排序字段。手动新增分块时若指定了一个已存在的序号，两条分块相邻展示即可，不需要为此重排整份文档的序号（那会是一次大范围写入，代价与收益不成比例）。
- 自动追加分块时 `chunk_index` 取 **`max(chunk_index) + 1` 而不是 `count(*)`**：分块可以被删除，`count` 会小于实际最大序号，用 `count` 会算出一个和现存分块冲突的序号。
- `content_hash` 当前用于定时同步的变更判断；也为将来"增量分块"（比对新旧分块哈希，跳过未变内容的向量化）预留。
- `token_count` 是启发式估算，仅供展示（[architecture.md §5](architecture.md)）。

### 3.4 `document_chunk_embedding`

```sql
create table document_chunk_embedding (
    chunk_id    bigint      primary key references document_chunk (id),
    kb_id       bigint      not null references knowledge_base (id),
    doc_id      bigint      not null references source_document (id),
    embedding   vector(1024) not null,
    create_time timestamptz not null default now()
);

create index idx_chunk_embedding_kb on document_chunk_embedding (kb_id);
create index idx_chunk_embedding_hnsw on document_chunk_embedding
    using hnsw (embedding vector_cosine_ops);
```

**这张表的三条不变量**（Phase 3 检索侧依赖它们，必须由本模块保证）：

1. **无 `deleted` 列，只做物理删除**（[PRD §7.6](../../docs/prd/2026-07-25-knowledge-base-prd.md) 例外 1）。
2. **表中存在的每一行，都对应一个未删除、已启用、且所属文档也未删除已启用的分块。** 检索方可以直接查这张表而不必关联业务表过滤。
3. `chunk_id` 作主键（而非独立自增 id）：一个分块最多一条向量，主键天然保证；更新分块内容时 `delete + insert` 同一个 `chunk_id`，不会产生重复行。

`vector(1024)` 的维度写死在 migration 里，与 `app.embedding.dimensions` 配置必须一致，应用启动时校验（[architecture.md §6](architecture.md)）。维度需要变更时走新的 migration，属于一次数据重建操作。

`kb_id` / `doc_id` 是为检索过滤和批量删除保留的冗余列——按知识库检索时直接过滤本表，不必关联 `document_chunk`。

### 3.5 `ingestion_run`

```sql
create table ingestion_run (
    id             bigint generated by default as identity primary key,
    kb_id          bigint      not null references knowledge_base (id),
    doc_id         bigint      not null references source_document (id),
    trigger_source varchar(16) not null,
    status         varchar(16) not null default 'QUEUED',
    input_revision           integer,
    input_file_key           varchar(512),
    input_content_hash       varchar(64),
    input_file_size          bigint,
    input_content_type       varchar(128),
    input_http_etag          varchar(256),
    input_http_last_modified varchar(128),
    phase          varchar(32),
    revision       integer,
    chunk_count    integer,
    error_message  varchar(4096),
    started_time   timestamptz,
    finished_time  timestamptz,
    heartbeat_time timestamptz,
    create_time    timestamptz not null default now(),

    constraint ck_ingestion_run_trigger check (trigger_source in ('MANUAL', 'SCHEDULED')),
    constraint ck_ingestion_run_status
        check (status in ('QUEUED', 'RUNNING', 'SUCCESS', 'FAILED', 'SKIPPED'))
);

create index idx_ingestion_run_doc on ingestion_run (doc_id, id desc);
create index idx_ingestion_run_pending on ingestion_run (id)
    where status in ('QUEUED', 'RUNNING');
```

这张表同时扮演三个角色，都是有意合并的：

1. **异步任务队列**——`status='QUEUED'` 的行就是待办任务，`idx_ingestion_run_pending` 部分索引让轮询只扫这几行（表会持续增长，但待办永远只有几条，索引大小与历史总量无关）。
2. **执行历史**——用户在界面上能看到每次同步/分块的结果，包括 `SKIPPED`（检查过但内容没变，PRD §4.3 要求可见）。
3. **失败诊断**——`phase` 记录失败发生在哪一步（`DOWNLOAD` / `EXTRACT` / `CHUNK` / `EMBED` / `PERSIST`），对应 CONTEXT.md 对「入库任务」的要求："应能说明失败发生在哪一步"。
4. **不可变输入快照**——`input_*` 记录任务创建时确定的原文版本。执行器只读这些字段；任务失败时，`source_document.file_key` 和既有分块/向量仍保持上一成功版本。

**为什么不像课程那样拆成"定时任务配置表 + 执行历史表"两张**：课程的配置表是为多种同步源、独立调度配置服务的。在 xrag 里，同步配置与文档是严格一对一（一个文档一套同步配置），拆表只会多一次关联而不产生任何新能力，所以配置内联进 `source_document`，本表只管执行记录。

`heartbeat_time` 服务于心跳超时回收（[architecture.md §3.4](architecture.md)），执行线程每 10s 更新一次。

`status` 的两条终态路径：`QUEUED → RUNNING → SUCCESS|FAILED`，以及定时同步的 `QUEUED → SKIPPED`（判断出内容未变，无需真正执行）。

## 4. 删除保护与级联 SQL

逻辑删除的级联不能依赖数据库外键的 `on delete cascade`（那是物理删除的机制），必须在 Service 层显式写。三个删除操作各自的完整动作：

**删除知识库**先做保护检查：

- 存在 `QUEUED` / `RUNNING` 入库任务 → `409 KB_HAS_ACTIVE_RUNS`
- 存在未删除文档 → `409 KB_NOT_EMPTY`

只有知识库为空且没有活动任务时才逻辑删除。事务中仍保留下面的清理 SQL，用于清理此前
已逻辑删除文档留下的分块与向量：
```sql
delete from document_chunk_embedding where kb_id = ?;                     -- 物理删除
update document_chunk    set deleted = true, delete_time = now(), update_time = now() where kb_id = ? and deleted = false;
update source_document   set deleted = true, delete_time = now(), update_time = now() where kb_id = ? and deleted = false;
update knowledge_base    set deleted = true, delete_time = now(), update_time = now() where id = ? and deleted = false;
```

**删除文档**（一个事务，前置：CAS 确认文档不在 `RUNNING`）：
```sql
delete from document_chunk_embedding where doc_id = ?;
update document_chunk  set deleted = true, delete_time = now(), update_time = now() where doc_id = ? and deleted = false;
update source_document set deleted = true, delete_time = now(), update_time = now(), sync_enabled = false where id = ? and deleted = false;
```
删除时顺手关掉 `sync_enabled`，让定时扫描的部分索引不再覆盖这行——虽然扫描 SQL 本身也带 `deleted = false`，但把它从索引里摘出去更干净。

**删除分块**（一个事务）：
```sql
delete from document_chunk_embedding where chunk_id = ?;
update document_chunk set deleted = true, delete_time = now(), update_time = now() where id = ? and deleted = false;
update source_document
   set chunk_count = case when chunk_count > 0 then chunk_count - 1 else 0 end,
       update_time = now()
 where id = ?;
```
`case when chunk_count > 0` 这层防护成本是几个字符，收益是这个冗余计数字段永远不会出现负数。它正常不该为 0，但冗余计数和实际行数不严格一致这种事，早期 bug、手工改库、并发回滚都可能造成。

对象存储中的原始文件在删除请求里**不删除**（PRD §7.6 例外 2）。后台审计把未删除文档、
`delete_time` 尚未超过宽限期的已删除文档，以及活动任务 `input_file_key` 视为引用。
默认只报告超过 7 天宽限期的孤儿；永久清理由独立配置显式开启。宽限期到期后，数据库的
逻辑删除记录仍在，但原文件可能被清理，因此不能再承诺完整恢复。
