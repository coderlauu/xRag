# ADR 0005：分离模型配置、熔断运行态与诊断历史

- 状态：已接受（2026-08-02）
- 日期：2026-07-28
- 相关：[ADR 0002](0002-knowledge-base-async-and-concurrency.md)、[技术方案](../../tech/model-scheduling/architecture.md)、[数据模型](../../tech/model-scheduling/data-model.md)

## 背景

Provider/模型目录、breaker 滑动窗口和调用复盘记录有不同的一致性与生命周期。如果全部进数据库，就需要运行时 CRUD、热更新和高频健康写入；如果全部留内存，应用重启后无法复盘。xrag 当前明确是单实例、单用户应用，诊断又不能污染模型首包延迟。

## 决策

- Provider、deployment、能力、等级和限制由版本控制内的配置文件持有，密钥由环境变量解析，重启生效。
- 熔断窗口和 HALF_OPEN 许可由当前 JVM 的 Resilience4j registry 持有；重启后回到 CLOSED，多实例不共享窗口。
- 完成态逻辑调用、候选、非 HTTP 调度事件、attempt 和 breaker transition 以最小化快照异步写 PostgreSQL；写入失败不改变主调用结果。熔断许可拒绝、重试等待、故障转移和预算耗尽必须按真实顺序持久化，详情页不得根据 attempt 间隙猜测事件。
- 诊断记录保留 7 天或最近 10,000 次逻辑调用并物理删除。它们是有强制保留期的运维事实，不是用户维护的业务实体，因此是“业务数据逻辑删除”规则的显式例外。

## 后果

- 诊断可跨重启查询，模型调用热路径不等待数据库。
- 进程崩溃时在途调用和尚未 flush 的少量完成记录可能缺失；页面第一版不展示进行中调用。
- 当前 breaker 状态只对本实例成立，诊断页必须公开这一语义。
- 未来多实例化时需要替换 breaker 状态协调或独立调度服务，但配置、能力端口和诊断 Schema 不必随之重写。
