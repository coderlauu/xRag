## 4. 做对了什么

### 4.1 把"不可验证的宣称"逐条改成可证伪的断言

规格里几处措辞如果照字面实现，测试会绿但事实是错的。这一阶段反复出现同一类修正：

- `failovers24h` 的口径是"发生过切换的调用数"而不是"切换次数求和"。最初的 fixture 让窗口内
  只有一次切换，`count` 与 `sum` 得到相同结果——**用例读起来在守这条口径，实际区分不了**。
  改成切换两次后才真正把它钉死。
- 隐私审计如果永远找不到标记串，和一个正确的扫描器测试结果一模一样。补了自检用例：
  人为往两张表种入标记串，断言都被扫出来。
- `verifiedCapabilities` 恒为空数组，写清是"尚未验证"而不是"不支持"——两者在页面上长得像，
  含义完全相反。

### 4.2 变异测试成了默认动作

写完关键 SQL 与不变量后主动做变异：把窗口从 24h 改成 48h、把 `count` 改成 `sum`、
把 `order by ... desc` 改成 `asc`，确认用例确实红。三次里有一次抓到了假阳性用例（见 4.1）。

### 4.3 浏览器实测抓到了读代码抓不到的缺陷

工单 18 的四个缺陷——列表列恒为 `—`、1280px 双栏挤成竖排、375px 页头折成单字列、
可点击元素没有可访问名——没有一个能靠 review 代码发现。原型闸门确认的是**信息架构**，
真实数据 + 真实视口确认的是**它到底能不能用**，两者不能互相替代。

### 4.4 先核对再动手，避免重复造用例

工单 21 进场先核对，发现 DIA-07/08/09/17 早已被工单 04 覆盖——那些证明的是 writer 自身行为。
缺的是另一半（routed client 是否包了 try/catch），只补那一半。如果不核对就照单全做，
会多出四个重复用例，还会让人以为覆盖率提高了。

## 5. 暴露的问题

### 5.1 测试计数虚高了 11，两张工单的记录因此写错

`target/surefire-reports/` 会残留已删除测试类的旧报告，而统计是对 `*.txt` 求和的。
工单 15 删掉的两个 Phase 1 测试类（共 11 例）的报告一直留在那里，于是工单 05 记成 367（实为 356）、
工单 19 记成 372（实为 361）。直到工单 16 改了 `ModelDeployment` 的 record 组件触发
`NoClassDefFound`、被迫 clean 重建才暴露。

**根因不是粗心，是口径没定义。** "测试数"从来没写明以什么构建为准。已在任务书 Decision Log
与各工单记录更正，并写进 test-matrix §14.1：**一律以 clean 构建为准**。

### 5.2 死配置在部署文档里存活了整整一个阶段

`deploy/env/*.env.example` 里的 `EMBEDDING_BASE_URL` / `EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS` /
`EMBEDDING_BATCH_SIZE` 在工单 15 删除对应属性后就失效了，但没人改文档。照着它们配置的人
会以为自己在调模型，其实什么都没发生——**这比没有文档更糟**。

工单 15 的完成定义里没有"检查文档中引用了被删属性的地方"。删除类改动应当把
"grep 全仓库找残留引用"写进完成定义。

### 5.3 包分层在需要时才发现是反的

工单 17 要用 `ApiException` / `PageResponse`，才发现它们在 `com.app.knowledge.web` 下，
而 `knowledge.web` 已经依赖 `com.app.ai.model`——再让 `ai.web` 反向引用就成环。
这三个类本来就是全应用契约（`ApiExceptionHandler` 的注释自己写着"不能限定 basePackages"），
只是当初随手放在了第一个用到它的模块里。

**Phase 1 结束时没有做过一次分层检查。** 迁移本身只花了十分钟，但它是在一张功能工单中途
被迫做的，不是计划中的。

### 5.4 前端测试运行器的缺口被推迟了两次

仓库从来没有前端测试。工单 18 想引入 vitest 时撞上 pnpm store 版本不一致（`node_modules`
由 10.7.1 装出、当前环境 10.12.3），要解决必须整体重装依赖——这会改变所有人的本地环境，
不该在一张前端功能工单里单方面决定，于是推给工单 22；工单 22 判断这属于工具链决策，
又推给了后续独立工单。

推迟本身是对的（两次都给出了理由），但结果是 UI-04/05/08/09/10 与工单 20 的页面 DOM 扫描
至今只有浏览器实测证据。**这类"横跨多张工单的基础设施缺口"应该在 Step C 拆工单时就识别出来
单独立项**，而不是让它在两张工单之间来回弹。

### 5.5 规格承诺了 Schema 装不下的字段

api.md §7 承诺 Embedding `capabilityDetails.validation` 的三个校验标志，但 V6 Schema
没有存它们，失败调用也无法把 `PROTOCOL_CONTRACT + PROVIDER_RESPONSE_VALIDATION` 归因到
具体哪一项。当前实现成功时返回三个 true、其余返回 null，**不猜**。

Step C 的一致性复核核对了"枚举/SQL 闭集、JSON 示例、编号连续性"，但没核对
"API 承诺的每个字段在数据模型里都有来源"。

## 6. 手工验收带来的直接收益

四个前端缺陷（§4.3）全部来自浏览器实测。其中"列表首个有效块列恒为 `—`"还反向暴露了
**后端列表 DTO 缺字段**——顺着修的时候又发现测试 fixture 给同步 Chat 也塞了流式时刻，
是个不真实的 fixture。一次视觉检查连带修掉了三层的问题。

## 7. 给 Phase 3 的建议

1. **删除类改动的完成定义加一条**：grep 全仓库找残留引用（配置示例、部署文档、CI）。
2. **Step C 拆工单时识别横跨性基础设施缺口**并单独立项，不要让它在工单之间弹来弹去。
3. **Step C 一致性复核加一项**：API 承诺的每个字段在数据模型里都要有来源。
4. **测试计数一律以 clean 构建为准**，已写进 test-matrix §14.1。
5. **先解除 P2-02（前端测试运行器）再开始 Phase 3 的前端工作**，否则会继承同一个缺口。
6. Phase 3 不得绕过 `com.app.ai` 直接调用 Provider SDK；Rerank 可能返回 Noop 降级，
   调用方必须区分 `rerankApplied=false` 与普通成功。
