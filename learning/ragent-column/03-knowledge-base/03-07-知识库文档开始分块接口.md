# 《AI大模型Ragent项目》——知识库文档开始分块接口

> 原文链接：https://t.zsxq.com/FtWRt
> 所属分组：03-knowledge-base AI知识库建设

## 一句话概括

`startChunk` 接口把"触发分块"拆成同步（CAS状态更新+RocketMQ事务消息，几毫秒返回）和异步（消费消息→解析→分块→向量化→原子写入）两个阶段；核心亮点是用 **RocketMQ 事务消息**解决"数据库状态更新"和"消息投递"两个独立操作的一致性问题，用 **CAS（而非分布式锁）**防止重复触发，用**手动事务模板 + 先删后插**保证 chunk 表和向量表的原子一致性，且全程贯彻"事务内不做耗时操作"的原则。

## 核心内容提炼

- **为什么拆成 upload / startChunk 两个接口（呼应 03-01/03-06 已有结论，这里给出更完整的论证）**：耗时差异悬殊（upload几秒可等，分块几分钟等不了）+ 职责分离（存文件 vs 处理文件）；拆开后还带来：批量触发的灵活性、失败后直接重试不用重新上传、调整分块参数只需重新触发不用重新上传文件。

- **startChunk 的同步阶段**：`POST /knowledge-base/docs/{doc-id}/chunk` 只需 `docId`。核心逻辑是发送一条 **RocketMQ 事务消息**，本地事务回调里做两件事：① **CAS 原子更新状态**（`UPDATE ... SET status='running' WHERE id=? AND status != 'running'`）——如果当前已经是 running，这条 UPDATE 不会命中任何行，`updated=0`，直接抛异常告知"正在处理中"，天然防止手抖点两次/并发重复触发；② 调用 `scheduleService.upsertSchedule` 同步定时任务配置（呼应 URL 来源的定时刷新机制）。`kbId` 字段是在本地事务回调**查询到文档后才设置**到消息体上的，因为只有在事务内部才能拿到完整文档信息。

- **为什么必须用 RocketMQ 事务消息，而不是"先更新数据库再发消息"这种朴素做法**：朴素做法有两个方向的一致性风险——① 数据库更新成功、消息发送失败 → 状态卡在 running，没人来执行分块，用户既不能重试也等不到结果；② 消息发送成功、数据库更新失败 → 消费者已经在跑，但数据库里还是 pending，数据不一致。事务消息把"本地事务"和"消息投递"绑定成原子操作：先发**半消息**（Broker收到但消费者看不到）→ 执行本地事务（CAS更新等）→ 本地事务成功则通知Broker提交消息（消费者才能看到），失败则通知回滚（消息被丢弃）→ 如果应用在通知Broker之前宕机，**Broker 会主动回查**本地事务状态（本例中回查逻辑就是查一下文档状态是不是 running，是就提交消息，不是就丢弃）。

- **异步处理链路**：MQ Consumer（`@RocketMQMessageListener`）消费到消息后，第一件事是**手动设置 `UserContext`**——因为消费者是异步线程，没有 HTTP 请求上下文，`operator` 字段就是为了在异步线程里恢复"是谁触发的"这个审计信息。然后调用 `executeChunk` → 查文档是否还存在（可能已被删除，不存在则直接跳过）→ `runChunkTask` 执行真正的处理流程。

- **`runChunkTask` 核心步骤**：
  1. **先创建一条分块日志记录**（`t_knowledge_document_chunk_log`，独立于文档表，因为文档可能被多次重新分块，需要保留每次执行的完整历史，而不是只覆盖文档表上的一个状态字段）。
  2. **按处理模式分发**：CHUNK 模式走固定流程（读文件→Tika解析→按配置分块→调Embedding API生成向量→返回`List<VectorChunk>`）；PIPELINE 模式走用户自定义节点序列，**关键细节**是构建 `IngestionContext` 时设置 `skipIndexerWrite=true`——Pipeline 里本来有个 `IndexerNode` 负责写向量库，但如果让它直接写，就没法和 chunk 表的数据库写入保持同一个事务的原子性，所以让它跳过写入、只把 chunks 放进 context，真正的写入延后到统一的原子写入步骤里做。两种模式最终都归一到同一个 `List<VectorChunk>`，后续处理完全一致。
  3. **原子性写入**（`persistChunksAndVectorsAtomically`，全文最关键的一步）：用 `TransactionTemplate` 手动开启事务，在同一个事务里依次做5件事——① DELETE 该文档的所有旧chunk；② INSERT 新chunk；③ DELETE 该文档在向量库里的所有旧向量；④ INSERT 新向量；⑤ UPDATE 文档状态为 success 并写入 `chunkCount`。**为什么先删后插而不是 UPDATE**：如果旧文档100个chunk、新文档只有50个，UPDATE只能覆盖前50个，后50个旧数据没法被UPDATE语句删除，会留下脏数据；先删后插是"数据完全替换"的简单可靠策略，不用管新旧数量是否一致。**为什么chunk表和向量表必须在同一个事务里**：如果chunk插入成功但向量插入失败，前端会看到"有50个chunk但检索不到"；反过来向量插入成功chunk插入失败，则是"检索得到但列表里看不到chunk记录"——两种情况都会让用户觉得系统有bug，所以必须绑在一起，失败了大不了用户重新触发，不会留下不一致状态。
  4. **更新分块日志**：记录 `extractDuration`/`chunkDuration`/`embedDuration`/`persistDuration`/`totalDuration` 等各阶段耗时，为后续性能诊断提供数据（比如某文档 `embedDuration` 特别长，说明瓶颈在Embedding API调用，可以去查API调用日志是不是超时重试了）。
  5. **异常处理**：整个流程 try-catch 包裹，失败时调用 `markChunkFailed`（**在一个新事务里执行**，避免随外层事务一起回滚导致状态卡死在 running 无法重试）+ 更新日志记录失败状态和 `errorMessage`（存下具体异常信息，方便排查——比如"Embedding API timeout"直接指向网络/API问题，"Failed to parse PDF"直接指向文件本身有问题）。

- **向量库的事务支持能力是一个直接影响架构可行性的因素**：项目里 `PgVectorStoreService`（pgvector 就是普通PostgreSQL表）**完全支持事务**，内部用 `JdbcTemplate` 自动参与外层 Spring 事务；而 `MilvusVectorStoreService` **不支持事务**，删除/插入向量是独立操作，无法和 PostgreSQL 事务保持一致，切到 Milvus 就必须靠"先写Milvus成功后再写PG、失败靠补偿机制清理Milvus数据"这类更复杂的方案。**这是"选pgvector而不是Milvus"的又一个理由**（03-01篇讲的是运维/成本，这里补充了事务能力这一条）。

- **事务边界设计原则贯穿全文**：`startChunk` 方法本身不加 `@Transactional`（本地事务由 RocketMQ 事务消息框架内部的 `TransactionTemplate` 管理，只包住CAS更新+定时任务注册这几毫秒的操作）；`runChunkTask` 绝对不能加事务（包含耗时的文件解析/分块/向量化，可能几分钟，事务持有连接几分钟会导致连接池耗尽）；只有 `persistChunksAndVectorsAtomically` 内部手动开事务，**精确圈定只有数据库和向量库写入这一小段**。核心原则就一句话：**事务内不做耗时操作，耗时操作在事务外执行，只有真正需要原子性的数据库写入才进事务**。

- **FAQ：为什么用 CAS 而不是分布式锁（Redisson）来防重复触发**——这个场景本质上"根本不需要锁"：要解决的问题是"状态判断+状态更新"，`WHERE status != 'running'` 一条SQL天然原子性；语义上CAS表达的是"只有状态符合预期才更新"，正好匹配防重复触发的需求，而分布式锁的语义是"独占资源一段时间"，这里根本不需要独占任何资源；架构上CAS只依赖数据库，少一个Redis依赖就少一个故障点，用锁还要多一次网络往返去获取/释放。作者的类比很形象：判断桌子有没有人坐，看一眼就知道了（CAS），不需要先把整个房间锁起来再看（分布式锁）。

## 关键概念/术语

- **RocketMQ 事务消息（半消息/事务回查）**：把本地数据库事务和消息投递绑定成原子操作的机制，解决"两个独立系统间的一致性"问题。
- **CAS（Compare-And-Swap）**：乐观并发控制，"只有当前值符合预期才更新"，不需要加锁。
- **`skipIndexerWrite`**：Pipeline 模式里跳过索引节点直接写向量库的标记，把实际写入延后到统一的原子事务里做。
- **分块日志表（`t_knowledge_document_chunk_log`）**：独立于文档表的执行历史记录，支持多次重新分块的完整追溯和分阶段耗时诊断。
- **先删后插（delete-then-insert）**：处理"新旧数据量不一致"场景的简单可靠数据替换策略，避免 UPDATE 留下脏数据。

## 与 xrag 项目的关系

- **这是目前 03-knowledge-base 分组里对 xrag 技术方案影响最直接的一篇**：`persistChunksAndVectorsAtomically` 的"chunk表+向量表同事务、先删后插"模式，以及"事务边界只圈定数据库写入、耗时操作放事务外"这个原则，应该直接写进 xrag 知识库模块的技术方案，作为分块落库的标准实现模式。
- **xrag 目前还没有引入消息队列**（`docker-compose.yml` 只有 postgres/redis/rustfs），如果要复刻"CAS + 事务消息"这套异步触发机制，需要先在技术方案里明确决策：是引入 RocketMQ（本文用的方案，能保证CAS更新和消息投递的原子性），还是用更轻量的方式（比如 Spring 的 `@Async` + 数据库轮询，或者 Redis Stream）。考虑到 xrag 是单用户个人项目，暂时不需要 RocketMQ 级别的可靠性保证，但"CAS防重复触发"和"chunk+向量原子写入"这两条核心设计原则无论选哪种消息机制都应该保留。
- **`markChunkFailed` 开新事务这个模式，是 xrag 后续所有"异步任务失败标记状态"场景都要遵循的**：如果失败标记逻辑和主流程共用一个事务，主事务回滚会导致失败状态也回滚不掉，最终卡死在中间态无法重试。
- **分块日志表的设计（记录各阶段耗时+错误信息+完整历史）**，值得在 xrag 数据模型设计阶段就纳入，而不是等出了性能问题再补——这是"可观测性从一开始就设计进数据模型"的一个好例子，也呼应 `CONTEXT.md` 里"链路记录（Trace）"这个已有术语的具体落地形态。

## 值得注意的设计取舍/坑

- **"看起来应该加事务保证一致性"的直觉在这里再次被打破**：`startChunk`/`runChunkTask` 两个方法都刻意不加 `@Transactional`，只有真正涉及数据一致性的写入步骤才用手动 `TransactionTemplate` 精确圈定——这和 03-06 篇 upload 接口"不加事务"的教训是同一个原则的第二次印证，说明这是这个项目贯穿始终的架构约定，不是个例。
- **消费阶段的失败处理有边界**：RocketMQ 的重试机制能应对临时故障（网络抖动、API超时），但应对不了永久故障（文件损坏、格式不支持）——多次重试后进死信队列，仍然需要人工介入，不能假设"重试机制"能兜住所有失败场景。
- **向量库能不能参与事务，是选型时必须提前确认的硬约束，不是事后能补的**：如果 xrag 未来真的要换成 Milvus 之类不支持事务的向量库，`persistChunksAndVectorsAtomically` 这套原子写入方案就完全失效，必须重新设计成"先写向量库成功后写数据库+失败补偿清理"这类更复杂的最终一致性方案——这是选 pgvector 时就该想清楚的代价，不要等到真出现向量库和数据库不一致才发现问题。
- **UserContext 在异步线程里必须手动传递和清理**：`finally` 块里的 `UserContext.clear()` 容易被忽略，如果消费者线程被线程池复用且不清理，会导致下一个任务读到错误的操作人信息——这是异步/多线程场景下 ThreadLocal 类工具的通用坑，不限于这个项目。
