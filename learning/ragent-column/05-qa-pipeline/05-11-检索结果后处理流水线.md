# 《三个通道返回 30 条结果，最终只给模型 5 条》

> 原文链接：https://t.zsxq.com/XsbNY
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

多通道的原始结果有三个病——**重复、分数不可比、数量太多**；后处理流水线用职责链把它们逐个治掉：`DeduplicationPostProcessor`（order=1，按通道优先级保序去重、重复取高分）→ `RerankPostProcessor`（order=10，Cross-Encoder 统一打分 + topK 截断），28 → 21 → 5。

## 核心内容提炼

- **三个病对应三个动作**：重复浪费 Token 且占 topK 名额；余弦相似度 0.82 与 BM25 12.5 量纲不同，**放在一起排序毫无意义**；28 条上万 Token 塞进 Prompt 会稀释核心信息。

- **`SearchResultPostProcessor.process()` 同时收三个参数**，各有其用：
  - `chunks` — 上一个处理器的输出，流水线上的半成品；
  - `results` — 原始的**按通道分组**结果，只读；
  - `context` — 全局上下文（`getMainQuestion()` 给 Rerank 当 query、`getTopK()` 给截断用）。

  **去重处理器压根没用 `chunks` 参数**，它直接从 `results` 入手——因为打平后的 `chunks` 已经丢失通道归属，而去重需要按通道优先级处理。**这就是为什么接口要同时传两种数据视图。**

- **去重排在第一位的理由是省钱**：不先去重就精排，同一条 chunk 要被 Rerank 打两次分，浪费 API 调用与算力，还占 topK 名额。

- **去重的通道优先级（INTENT_DIRECTED=1 > KEYWORD_ES=2 > VECTOR_GLOBAL=3）与"重复取高分"是两个独立机制**：优先级只决定谁先占坑（进而决定结果列表的顺序），高分逻辑决定最终保留谁的分数。原文自己承认——**如果下游不关心顺序，排序对去重结果没有影响**，它的价值是控制输出顺序、为后续截断留口子。

- **去重键两级策略**：有 `id` 用 `id`（向量库主键，跨通道稳定），无 `id` 用 `text.hashCode()` 兜底。原文点破了内容哈希的脆弱性——**同一条 chunk 在不同通道返回时文本末尾可能多一个空格**，hashCode 就对不上了。

- **Cross-Encoder 与 Bi-Encoder 的分工是经典的粗排 + 精排**：Bi-Encoder 可预先编码、检索时只算距离（快但不够准，从百万里筛 30 条）；Cross-Encoder 把 query 与 chunk 拼成一个序列走完整注意力交互（准但慢，从 30 条里选 5 条）。

- **`relevance_score` 覆写原始分数，这是"分数不可比"的解法**——不管原来是余弦 0.82 还是 BM25 12.5，过完 Rerank 都变成同一标准下的相关性评分。

- **`RerankPostProcessor` 一步完成精排 + 截断**：`topK` 直接传给 `rerank()`，服务端打分时就截断，输出即最终上下文。

- **三层兜底**：`RoutingRerankService` 按优先级路由 + 失败切换 → `NoopRerankClient` 不精排直接截前 topK → 处理器链的 try-catch（Rerank 抛异常则 `chunks` 保持去重后的 21 条继续往下）。

- **`BaiLianRerankClient` 有两处防御**：入口再去一次重（Rerank API **按文档数计费**，重复文档白花钱），以及"去重后数量已不超过 topN 就不调 API 直接返回"。

- **`getOrder()` 留间隔（1 与 10 之间空出 2~9）**，和 CSS `z-index` 用 10/20/30、数据库自增步长设 10 是同一个工程习惯——将来插新处理器不用改已有的 order。

- **去重与精排拆成两个处理器的三个理由**：单一职责（测去重不用 mock Rerank 模型）、独立开关（单通道场景可以只关精排）、独立替换（换重排算法不影响去重）。

- **每步日志构成漏斗监控**，运维价值很具体：去重从 -7 变成 -0 说明通道之间没有重复（可能某通道没启用）；精排从 -16 变成 -0 很可能是 Rerank 挂了降级到了 Noop。

## 关键概念/术语

- **后处理流水线**：多通道原始结果 → 精炼上下文的职责链。
- **`SearchResultPostProcessor`**：`getName` / `getOrder` / `isEnabled` / `process` 四方法接口。
- **通道优先级去重**：按通道可信度排序后保序去重，重复时取高分。
- **Cross-Encoder 精排**：query 与 chunk 联合编码，输出统一量纲的相关性分数。
- **`relevance_score`**：Rerank 输出的统一相关性评分，覆写原始异构分数。
- **Noop 降级**：Rerank 不可用时按原始顺序截前 topK。

## 与 xrag 项目的关系

- **xrag 的 Rerank 端口在两个关键点上已经比原文做得更严，不能反向照抄。** 对照 [`RerankResult`](../../../backend/src/main/java/com/app/ai/model/RerankResult.java)、[`RankedCandidate`](../../../backend/src/main/java/com/app/ai/model/RankedCandidate.java)、[`RerankCommand`](../../../backend/src/main/java/com/app/ai/model/RerankCommand.java)：
  - **降级是显式的。** `rerankApplied` 与 `degradationReason` 由构造期不变量绑死（前者为真**当且仅当**后者为 null），而且降级结果**不许携带 `relevanceScore`**。原文的 `NoopRerankClient` 则是静默的——它返回的列表在类型上与真实精排的结果完全一样，下游无从分辨。原文自己也承认这一点，只能靠"日志里精排从 -16 变成 -0"来事后猜测。**xrag 的调用方可以直接判断，不需要猜。**
  - **对齐用稳定 ID 而非下标。** `RerankCommand` 的注释写得很直白：Provider 返回的是 index，没有稳定 ID 就只能靠下标对齐，调用方一旦重排或过滤过输入就会静默错位。原文的 `BaiLianRerankClient` 恰恰是 `candidates.get(idx)` 的下标对齐——它当前是对的，但**任何一次"在调 API 前多加一道过滤"的改动都会让它静默错位**。

  Phase 3 用 Rerank 时要**沿用 xrag 的端口语义**，把"降级了"这件事一路传到链路记录甚至界面上，而不是像原文那样让它消失在类型里。

- **"分数不可比"这个病，xrag 现阶段其实没有。** 原文的三个通道分别产出余弦相似度、BM25 分数、余弦相似度；xrag 若只做定向 + 全局两个通道，**两者都是同一张表上的 `embedding <=> ?::vector` 余弦距离，量纲完全一致，直接排序是有意义的**。这有两个推论：
  1. **Rerank 在 xrag 的价值主要是"精度提升"而非"分数归一化"**——这会改变它的优先级排序。没有 Rerank 时，xrag 可以直接按距离排序截断，结果是可用的；原文没有 Rerank 时只能按"原始顺序"截断，那个顺序是拼接出来的，几乎没有意义。
  2. **只有引入关键词/BM25 通道才会真正出现分数不可比。** 所以"要不要做混合检索"与"Rerank 是不是必需"是同一个决策的两面，应当一起提交给所有者（并入待决策项 D-02）。

- **去重在 xrag 的形态更简单，但也更容易被误判为"不需要"。** chunk 的身份是 `document_chunk_embedding.chunk_id`（bigint 主键），跨通道稳定，不存在原文那种"文本多个空格导致哈希不一致"的问题。**但如果定向与全局是同一张表上的两次查询，定向结果基本是全局结果的子集**——去重会大量命中，甚至把定向通道的全部结果都去掉。这正是第 10 篇末尾提的那个问题的延续：**两个通道查同一份数据，去重之后可能等价于只查了一次**。Step C 要么给两个通道找到真正不同的检索面（例如全局走不同的 topK/过滤条件），要么承认单通道就够。

- **`relevanceScore` 只在真实 Rerank 时存在，这个约束对下游有强制影响。** 降级时 `RankedCandidate.relevanceScore` 全为 null，**问答链路不能假设"每条 chunk 都有一个可展示的相关性分数"**。这会传导到 Step B 的 ui-spec：如果引用面板上打算显示每条引用的相关度，就必须设计"降级时显示什么"（隐藏？显示"未精排"？）。**这是原型该覆盖的那种"只在特定状态下才出现的界面规则"。**

- **`isEnabled(context)` 当前两个处理器都恒返回 `true`，xrag 不该照抄这个形状。** 一个永远返回 `true` 的方法就是一个没有被使用的扩展点。原文写它是为了将来；xrag 的纪律是不预留走不到的分支。**要么给它一个真实的条件**（例如"只有一个通道启用时跳过 Rerank"——这在 xrag 里是个真实且有价值的条件，因为单通道的分数本来就可比），**要么不要这个方法**。

- **`getOrder()` 留间隔这个习惯值得保留，但要配一条纪律**：order 值必须在一处集中声明（常量类或枚举），不能散在各个 `@Component` 里。否则新增处理器时没人知道 5 已经被占了。这与 xrag "调度类组件都带 enabled 开关"是同一类"分散配置需要集中登记"的问题。

- **Rerank 的截断数量与生成阶段的 Prompt 预算要一起定。** 原文的 topK=5 是拍的，理由只有"太多会稀释"。xrag 有更硬的约束来源——生成阶段的上下文预算（第 14 篇）与摘要压缩的水位线（第 3 篇）共享同一个 Token 上限。**topK 应当由预算倒推，而不是先定 5 再看塞不塞得下。**

## 值得注意的设计取舍/坑

- **原文自己拆穿了通道优先级排序在去重里的作用有限**，这是本篇最诚实的一段。"如果下游不关心顺序、且同一 chunk 除 score 外无差别，排序确实没有实际意义"。它保留排序是"为后续扩展留了个口子"——**而这个口子的成本是：读代码的人会以为通道优先级参与了去重决策**。xrag 若要保留顺序语义，应当在注释里写清"排序只影响输出顺序，不影响去重结果"。

- **"重复取高分"跨通道比较的是不同量纲的分数——这是一个真实的缺陷。** 同一条 chunk 在定向通道得余弦 0.82、在 ES 通道得 BM25 12.5，代码里 `chunk.getScore() > existing.getScore()` 会判定 12.5 更高从而替换。**这恰恰是本篇开头批判的"分数不可比"问题，在去重环节被原封不动地犯了一次。** 反正下游 Rerank 会覆写分数，所以后果不严重——但**它决定了保留下来的是哪个通道的那份对象**（进而影响 metadata、来源归属）。在 xrag 里，如果引入了 BM25 通道，这个坑会照样存在。

- **"Rerank 结果不足 topN 时用原始候选补齐"是一个可疑的好心。** 补进来的 chunk 是 Rerank **没有选中**的（可能就是它判为不相关的），却被按原始顺序塞进最终上下文。这等于说"数量比质量重要"。xrag 的 `RerankResult` 没有这个行为——返回什么就是什么。**这是一个要显式决策的差异**：宁可给模型 3 条精选，还是凑够 5 条掺 2 条杂质。倾向前者，理由与第 6 篇的"错误的路由比没有路由更糟"同源。

- **处理器链的 try-catch"跳过失败的处理器"在去重上是危险的。** 如果去重失败被跳过，重复的 chunk 会直接进 Rerank——按文档数计费的 API 上是真金白银的浪费，而且 topK 名额被重复内容占掉。**同一个容错策略对"可选的增强"（Rerank）与"必需的清洗"（去重）适用性完全不同**。xrag 应当区分：处理器要么标记为可跳过，要么标记为失败即失败。

- **`text.hashCode()` 作为去重兜底存在碰撞风险，且 `hashCode()` 返回 int。** 对于知识库规模的文本量，碰撞概率虽小但不为零，一次碰撞的后果是**静默丢掉一条不相关的 chunk**——没有任何日志。防御性编程的兜底路径本身埋了一个更隐蔽的 bug。xrag 的 chunk 一定有主键 ID，**不需要这条兜底路径，也就不要写它**。

- **漏斗日志是本篇最实用的产出，但它只在日志里。** "去重 -7、精排 -16" 这两个数字是判断检索链路健康度的核心指标，**放在日志里意味着只能靠人翻**。xrag 已经有 `com.app.ai.diagnostic` 与 `/diagnostics` Trace Console 的先例——**问答链路的漏斗数据应当落成结构化的链路记录**，这样"某天去重量突然归零"是能被查询和告警的，而不是等出了问题再去 grep。
