# 《三个子问题命中了八个意图，该保留哪几个》

> 原文链接：https://t.zsxq.com/vwZle
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

`IntentResolver` 做两件事：把 N 个子问题**扇出到专用线程池并行分类**（延迟从 sum 降到 max），再用 `capTotalIntents` 做**跨子问题的总量封顶**——先给每个子问题保底一个最高分意图（多样性优先），剩余配额才按分数全局竞争，避免"用户问了两件事系统只答了一件"。

## 核心内容提炼

- **并行的收益是确定的**：单次意图分类 LLM 调用约 800ms，三个子问题串行 ~2400ms、并行 ~800ms。这 1.6 秒直接计入用户感知的首字延迟（会话加载 + 改写 + 意图 + 检索 + 生成的累加），不是可以忽略的量级。

- **专用线程池 `intentClassifyThreadPoolExecutor` 而非共用**。隔离理由是 IO 特征不同：意图分类是调外部 LLM，检索是调向量库。共用一个池子时，向量库抖动会把线程占满，**LLM 已经返回了却拿不到线程继续执行**。参数：核心线程数 = CPU 核数，最大 = 2×CPU 核数，队列用 `SynchronousQueue`（直接交接不排队），拒绝策略 `CallerRunsPolicy`（池满就让调用者线程自己跑，宁可降级同步也不丢任务）。

- **`try-catch` 必须包在 lambda 内部，不能放在 `.join()` 外面**。放外面的话单个子问题抛异常会让对应 future 进入 `completeExceptionally`，`.join()` 抛 `CompletionException`，**一个失败可能中断整个流程**；放里面则永远返回 `SubQuestionIntent(q, List.of())`，future 正常完成，其他子问题不受影响。

- **这是第二层兜底**。第 6 篇的 `classifyTargets()` 内部已有全局 try-catch，兜的是 JSON 解析阶段；lambda 里这层兜的是更外层——LLM 服务挂了、HTTP 超时、线程中断，**第一层根本走不到的场景**。

- **`.join()` 的阻塞语义**：三个 future 挨个 join，但它们早已在池里并行跑，总耗时是 max 而非 sum。`resolve()` 本身阻塞主线程，但 LLM 调用不占主线程。

- **意图经过三层筛子，各管一件事**：
  | 层 | 条件 | 管什么 |
  |---|---|---|
  | Prompt | 评分标准 + 数量规则 + 歧义规则 | 约束 LLM 的输出行为 |
  | `classifyIntents()` | `score >= 0.35` 且 `limit(3)` | 兜底 LLM 不听话 |
  | `capTotalIntents()` | 总数 `<= 3` + 多样性 | 跨子问题的全局约束 |

- **为什么阈值不设更严（比如 0.6）**：查询改写后的子问题措辞可能偏离原问题，分数天然比用原句打分时低一些。0.35 是"有点相关"的底线，**保守留着让下游判断，好过误杀**。

- **封顶的必要性来自下游成本**：8 个意图 = 1 次 MCP 工具调用 + 7 次定向检索，检索延迟累加到 3~4 秒、chunks 塞爆 Prompt 稀释核心信息、生成 Token 成本翻倍。

- **三种封顶策略的取舍**：
  | 策略 | 优点 | 缺点 |
  |---|---|---|
  | 全局分数截前 N | 实现简单 | **部分子问题可能全军覆没** |
  | 每子问题均摊 | 保证覆盖 | 低分意图挤掉高分意图 |
  | 多样性 + 分数（采用） | 覆盖与质量兼顾 | 实现稍复杂 |

  反例很有说服力：子问题 A 命中三个高分（0.92/0.90/0.88），子问题 B 最高才 0.70，简单截前 3 会让 A 独占名额，**用户问的退货问题完全没人管**。

- **算法五步**：统计总数（未超限直接放行）→ `collectAllCandidates` 扁平化并全局降序排序 → `selectTopIntentPerSubQuestion` 用 `boolean[] selected` 扫一遍给每个子问题发保底名额 → 算剩余配额 → `selectAdditionalIntents` 按分数补 → `rebuildSubIntents` 按 `subQuestionIndex` 分组塞回原结构。

- **`IntentCandidate(subQuestionIndex, nodeScore)` 是让算法成立的中间结构**。没有它，全局排序之后就不知道 0.88 这个意图属于哪个子问题，多样性保证无从谈起。**"为了同时满足全局排序和分组归属，引入一个携带来源标记的中间类型"是这类算法的通用手法。**

- **重建时保留原始结构而非只返回选中的意图**，因为下游（第 9 篇）要按子问题走定向检索。`getOrDefault(i, List.of())` 保证被全淘汰或本就没命中的子问题**位置不丢，只是意图列表为空**。

- **多样性必须在分数之前做**。反过来（先分数竞争再补救多样性）意味着要踢掉已选的高分意图，逻辑复杂且结果不稳定。

- **封顶后下游还有三个动作**（后续篇章展开）：`mergeIntentGroup` 按 KB/MCP 拆成两条链路；`isSystemOnly`（只命中一个且是 SYSTEM）短路返回预设回复，延迟只有几十毫秒；歧义检测在封顶之后、拆分之前触发（第 8 篇）。

- **原文自己给两个常量留了退路**：0.35 与 3 是电商客服场景下的经验值。法律咨询意图集中，2 甚至 1 就够；医疗分诊可能要 5 才不漏诊。调参方法是"默认值跑起来 → 收集查询日志统计意图数/分数分布 → 挑 bad case → 调参重跑评估"。

## 关键概念/术语

- **总量封顶（`capTotalIntents`）**：跨子问题的意图数量全局约束。
- **多样性保证**：每个有命中的子问题至少保留一个最高分意图。
- **`IntentCandidate`**：`(subQuestionIndex, NodeScore)` 二元组，封顶算法的中间结构。
- **保底名额 / 剩余配额**：算法的两段配额，前者按子问题分配，后者按分数竞争。
- **`IntentGroup`**：按 `IntentKind` 拆分后的 MCP 意图组与 KB 意图组。
- **系统意图短路（`isSystemOnly`）**：单一 SYSTEM 意图时跳过检索与生成。

## 与 xrag 项目的关系

- **`CompletableFuture` + 专用线程池 vs Reactor，Phase 3 必须选一个并写进 ADR。** [ADR 0004](../../../docs/adr/0004-reactive-streaming-runtime.md) 已把流式运行时定为 WebClient + Reactor，而问答链路里这种"扇出 N 个短调用、全部完成后汇总"的形态用 `Flux.merge` / `Mono.zip` 同样自然。**同一个模块里两套异步模型并存是长期维护负担**，尤其是取消语义——`com.app.ai.model` 已有 `CancellationToken`，用户点"停止生成"（第 16 篇）时怎么把取消传导到正在跑的 N 个意图分类调用，两套模型的答案完全不同。这条应当在 Step C 的技术方案里先定，不要边写边定。

- **线程池隔离的理由在 xrag 同样成立，但要重新算池子大小。** 原文按"子问题 2~4 个"配了 `SynchronousQueue` + `CallerRunsPolicy`。xrag 还有第 17~18 篇的**全局并发许可**（同时只允许 N 个人提问），两者叠加后的实际并发上限要一起算——**否则会出现"许可放行了 10 个请求，每个又扇出 3 个分类调用，共 30 个并发 LLM 调用"打爆下游模型配额的情况**。而模型侧的熔断（`ModelBreakerRegistry`）会把这种打爆解读成供应商故障，触发不必要的降级。

- **0.35 / 3 这两个常量在 xrag 应当可配，且配置形态要和已有约定一致。** 知识库的分块策略、意图节点的 `topK` 都是"全局默认 + 单体覆盖"模式（第 5 篇），意图阈值与总量上限同理。**但不要照抄 `ai-models.yml` 的启动时快照方式**——那个模式改配置必须重启，而这两个参数正是最需要按 bad case 反复调的。

- **`guaranteedIntents.contains(candidate)` 这行在 xrag 需要换写法。** 原文的 `NodeScore` 是 Lombok `@Data`，`IntentCandidate` 是 record，`contains` 走的是**值相等的深比较**——一路比到 `IntentNode` 的全部字段（含 `children`）。这有两个问题：一是 O(n²) 的比较里嵌了深比较；二是**字段全同的两个不同候选会被误判为同一个**。xrag 若把意图节点建成不可变记录，同样会继承 record 的值相等语义，所以**应当按 `subQuestionIndex + 节点 ID` 建集合去重，而不是依赖对象相等**。

- **`@RagTraceNode(name = "intent-resolve", type = "INTENT")` 这个注解揭示了原文有一套链路追踪机制。** xrag 有对应的东西但不完全一样：`com.app.ai.diagnostic` 记的是**模型调用维度**的诊断（每次 attempt、路由决策、熔断转移），已有 `/diagnostics` Trace Console。而 [CONTEXT.md](../../../CONTEXT.md) 里定义的「链路记录」是**问答链路维度**的（一次提问经历了哪八个阶段、每阶段耗时与产物）。**这两层是不同粒度，Phase 3 要决定是复用 `com.app.ai` 的诊断表还是另起一套**——倾向另起，因为模型诊断是"这次调用打给了谁、成功没有"，链路记录是"这次提问改写成了什么、命中了哪些意图"，共表会让两边的查询都别扭。

- **`isSystemOnly` 的短路对 xrag 是纯收益。** 它跳过检索与 Reranker，只留一次短 Prompt 的 LLM 调用（第 9 篇给出了实现：仍然走 `streamChat`，只是不带 chunk）。注意它**并不能绕开没有 Chat 凭据这个阻塞**——真正完全不碰 Chat 的路径只有第 8 篇的歧义引导短路（预拼字符串直推 SSE）。Step D 若排期在拿到 Key 之前，能端到端验证的只有那一条。

## 值得注意的设计取舍/坑

- **算法在"子问题数 > `MAX_INTENT_COUNT`"时会突破封顶值，原文没有讨论这个分支。** 按代码推演：4 个子问题时 `selectTopIntentPerSubQuestion` 会一直选到 `topIntents.size() == 4` 才退出，`remaining = 3 - 4 = -1`，`selectAdditionalIntents` 返回空，最终重建出 **4 个意图**——超过了上限 3。文中只讨论了 `==` 的情形（"三个子问题配三个名额，刚好一人一个"）。查询改写侧（第 4 篇）**没有对子问题数量设上限**，所以这不是不可达分支。xrag 实现时要么在改写阶段就给子问题数封顶，要么在保底阶段也受总量约束（按分数只保前 3 个子问题的代表）——**两种选择的语义不同：前者是"不允许问那么多件事"，后者是"问了但只答前三件"，该让用户看到哪一种，是产品决策不是实现细节。**

- **保底阶段的提前退出条件在有空意图子问题时不会触发。** 某个子问题没命中任何意图时，`selected[index]` 永远为 false，`topIntents.size() == subQuestionCount` 这个条件就不成立，循环会扫完整个候选列表。行为是正确的（自然退出），但**"提前退出"这个优化在最需要它的场景下反而失效**。规模小无所谓，值得知道的是这类"看起来有的优化实际条件不成立"的模式。

- **单子问题的 `limit(3)` 和跨子问题的 `<= 3` 复用同一个常量 `MAX_INTENT_COUNT`，但语义完全不同。** 一个防 LLM 返回太多，一个控下游检索压力。**复用常量意味着以后调其中一个必然误伤另一个**——两个数字碰巧相等不等于它们是同一个概念。xrag 应当拆成两个命名清晰的配置项。

- **"多样性优先"的前提是子问题拆分本身是可信的。** 如果改写阶段拆出了一个不该拆的子问题（第 4 篇提到的对比型误拆），保底机制会**强制给这个错误的子问题分配一个名额**，挤掉真正相关的高分意图。也就是说：上游拆错的代价被下游的保底机制放大了。这条链路上，**改写的质量比意图分类的质量更关键**。

- **`log.error` 里把降级记成 error 级别是对的，但要防日志洪水。** 模型服务整体不可用时，每个请求的每个子问题都会打一条 error。xrag 已有诊断表记录模型侧失败，问答侧的降级日志**应当有聚合或降采样**，否则一次供应商故障就能把日志刷满，反而看不到真正的异常。

- **原文最后一节"没有放之四海而皆准的数字"值得当作方法论保留**：先跑起来 → 统计分布 → 挑 bad case → 调参重评估。这正好对应 06 组的评测体系——**参数调优要有评测集才做得下去**，否则就是拍脑袋改数字。这为"评测体系不能拖到最后才做"提供了一个具体理由。
