# 《用户说的话 ≠ 该搜的词》

> 原文链接：https://t.zsxq.com/rCa8F
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

**模型有记忆，检索没有**——用户第二轮问"那它的保修期呢"，模型知道"它"是 iPhone 16 Pro，但检索引擎拿到的就是这句原话；阶段 2 用一次 LLM 调用同时做两件事：改写（消解指代、去噪）解决检索精度，拆分（复合问题拆成子问题）解决意图覆盖。

## 核心内容提炼

- **拆分解决的是"意图被吞掉"**。"iPhone 的退货政策是什么？AirPods Pro 的保修期呢？"如果不拆，整句去做意图分类可能只命中退货政策一个方向，AirPods 保修被弱化；拆成两个子问题后各自命中 `kb-return-policy` 与 `kb-warranty`，两个方向都保住。

- **判据是"子问题能不能独立回答"**，不是"有没有多个关键词"：

  | 问题 | 拆? | 原因 |
  |---|---|---|
  | A 的退货政策？B 的保修期？ | 拆 | 两个独立问题 |
  | A 和 B 的退货政策分别是什么 | 拆 | 话题相同但指向不同产品 |
  | **A 和 B 有什么区别** | **不拆** | 对比型，两者放一起才能答 |
  | A 从哪些方面考虑 | 不拆 | 笼统询问，没有明确列举 |
  | 你好 | 不拆 | 问候语 |

  **对比型问题是最容易误拆的**：拆开后各自检索到一堆独立介绍，用户要的对比反而没了——拆了比不拆更差。

- **`RewriteResult(rewrittenQuestion, subQuestions)` 有一条关键约定**：不拆分时 `subQuestions` 只含一个元素且与 `rewrittenQuestion` 一致。这样下游 `IntentResolver` 不用判断拆没拆，一律遍历 `subQuestions`。

- **LLM 之前先做术语归一化**，纯规则文本替换、零 LLM 开销："苹果手机"→"iPhone"、"降噪豆"→"AirPods Pro"。相当于**先帮 LLM 做好功课**，让它专注于语义层面的改写。两个实现细节：
  - **长词优先替换**：若"苹果→Apple"先生效，"苹果手机"就变成"Apple 手机"，"苹果手机→iPhone"这条规则再也匹配不上。排序是优先级降序 + 源词长度降序。
  - **规则缓存在 Redis 而非本地内存**，走 Cache-Aside（读时加载、写时失效），管理后台改规则后所有实例下次自动加载，不用重启。

- **改写的消息数组只带最近 2 轮历史，且过滤掉 SYSTEM 消息**。指代消解一般 1~2 轮就够；带太多不仅费 Token，还会让 LLM **过度改写**把原问题改得面目全非。摘要是给最终生成用的，对改写没价值。

- **改写的 LLM 参数追求确定性**：`temperature=0.1`、`topP=0.3`、`thinking=false`。同一个问题在同样上下文下应该改写出同样结果。对比摘要压缩的 `0.3/0.9`——**摘要要归纳灵活性，改写要精确一致**。

- **Prompt 明确划三类边界**：保留（专有名词、时间/环境/角色等关键限制）、删除（礼貌用语、"详细说明"这类回答指令、"我是新人"这类无关描述）、**禁止**（不得添加原文没有的条件、维度、假设）。禁止项最容易被忽视——LLM 会把"退货政策"擅自扩写成"包括七天无理由、拆封后退货、运费承担等环节"，多出来的枚举词会把检索引向错误方向。

- **拆分规则的兜底是"不确定时不拆分"**——错误的拆分比不拆分危害更大。

- **JSON 解析要四层容错**：剥 Markdown 代码围栏 → 逐元素校验子问题数组 → `rewrite` 为空则整体失败 → 没有子问题则用 `rewrite` 兜底。原文的经验之谈：**Prompt 里写了"严格返回 JSON、不要额外文字"，LLM 大概率还是会时不时包一层 Markdown**，不能在解析端假设它守规矩。

- **三层兜底且都用归一化后的问题**：开关关闭 → 归一化 + 按标点规则拆分；LLM 调用异常 → 归一化问题作为唯一子问题；JSON 解析失败 → 同上。**兜底用 `normalizedQuestion` 而不是原始输入**，即使 LLM 挂了，术语映射的成果不白费。

- **改写不需要强模型**。输入短、输出短（一个 JSON），7B~14B 足够，把大模型留给最终答案生成。

## 关键概念/术语

- **术语归一化**：LLM 之前的规则预处理，把口语化别名映射为标准术语。
- **子问题拆分**：把复合问题拆成可独立检索、独立分类的多个问题。
- **一致性约定**：不拆分时 `subQuestions` 仍有且仅有一个元素，保证下游统一处理。
- **过度改写**：LLM 擅自补充原文没有的维度、枚举词或假设，是改写最典型的失败模式。
- **渐进式降级接口**：`rewrite` → `rewriteWithSplit(q)` → `rewriteWithSplit(q, history)`，后两者有 default 实现逐级回退。

## 与 xrag 项目的关系

- **对应 Phase 3 阶段 2，是阶段 3 意图识别的直接输入**。子问题列表的质量决定了意图能否被完整覆盖——这一环出错，后面的意图树设计得再好也救不回来。

- **术语归一化的缓存方案要按 xrag 的实际情况重新决定。** 原文用 Redis + Cache-Aside 是为了集群下的一致性；而 [ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 记录 xrag 当前是**单实例假设**。单实例下本地内存缓存 + 写时清空就够了，引入 Redis 需要单独论证。xrag 已经有 Redis（readiness 探测里就有），但"有"不等于"该用"。

- **改写用轻量模型这一点，正好是 Phase 2 能力端口的用武之地。** `ai-models.yml` 支持按 `service-tier`（`ECONOMY`/`BALANCED`/`QUALITY`）路由，改写调用应当显式走 `ECONOMY`——这是 Phase 2 设计的服务等级第一次有真实业务场景。注意 [ADR 0003](../../../docs/adr/0003-separate-model-capability-ports.md) 的约束：**不跨等级故障转移**，所以 ECONOMY 候选必须配够，否则改写会直接失败而不是降级到 BALANCED。

- **`temperature` / `topP` / `thinking` 三个参数要落到 `CallOptions`。** Phase 2 已有这个位置，Phase 3 不需要新增机制；但要确认 `CallOptions` 是否已支持 `topP` 与 `thinking`，缺了就得先补契约（这类"规格承诺了但类型装不下"的问题，Phase 2 复盘 §5.5 刚记过一次）。

- **JSON 容错工具应当做成共享能力。** 原文的 `LLMResponseCleaner.stripMarkdownCodeFence` 在项目里多处复用——凡是要从 LLM 返回里提 JSON 的地方都要过一遍。Phase 3 至少有改写、意图打分、参数抽取三处需要它，**第一次用到时就放在公共位置**，不要等第三处才提取。

- **改写开关（`rag.query-rewrite.enabled`）对应 xrag 的既有惯例**：调度类/增强类组件都带 `enabled` 开关。这条与 ADR 0002 的纪律③一致，直接沿用。

## 值得注意的设计取舍/坑

- **"不确定时不拆分"是把不对称的代价写进了规则。** 漏拆的代价是某个方向召回差一点；错拆的代价是把对比型问题变成两份互不相干的资料，答案质量断崖下跌。两种错误代价不对等时，规则就该向代价小的一侧倾斜——这个思路值得在 Phase 3 的其他决策点上复用。

- **长词优先替换不是性能优化，是正确性要求。** 短词先替换会截断长词规则，症状是"某些别名映射时灵时不灵"，取决于规则表里的顺序——典型的偶发且难归因。

- **过滤 SYSTEM 消息这一步容易漏。** `ctx.history` 里混着摘要（SYSTEM 类型），不过滤就会把摘要塞进改写上下文：既浪费 Token，又可能让 LLM 拿早期话题去"补全"当前问题，改出用户根本没问的东西。

- **不能在解析端假设 LLM 遵守格式。** 这条对 Phase 3 尤其重要——改写、意图打分、工具参数抽取全都依赖结构化输出。**每一处 LLM 返回的解析都必须有兜底路径，且兜底后链路要能继续走**，不能抛异常中断问答。

- **`rewrite` 与无历史版 `rewriteWithSplit` 目前都没有实现，是为将来预留的。** 这与上一篇 `refreshCache` 空实现是同一类东西——xrag 应当谨慎：**default 方法构成的降级链只有在真有第二个实现时才有价值**，否则就是永远走不到的分支。Phase 3 若只打算做一个改写实现，接口就定义一个方法。

- **改写是增强项，失败只降低精度不中断链路。** 这个定位与摘要压缩一致。但要注意二者的差别：摘要失败最坏是"丢上下文"，改写失败最坏是"拿原话去检索"——后者用户能直接感知到答非所问，所以改写的兜底质量（至少保住术语归一化）比摘要更重要。
