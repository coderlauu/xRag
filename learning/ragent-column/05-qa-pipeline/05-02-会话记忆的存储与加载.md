# 《大模型没有记忆，多轮对话怎么做到不失忆？》

> 原文链接：https://t.zsxq.com/WFr43
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

记忆的本质是**让每次独立的 API 调用看起来像一段连贯的对话**：把"摘要 + 最近 N 轮原文"并行拉出来拼进消息数组；难点不在存取，而在几个时序与格式约束——先加载再追加、历史必须以 USER 开头、摘要必须在原文之前。

## 核心内容提炼

- **三层分工**：编排层（Pipeline，只调 `loadMemory`）→ 门面层（`ConversationMemoryService`，暴露 `load` / `append` / `loadAndAppend`）→ 基础能力层（`MemoryStore` 管持久化 + `SummaryService` 管压缩）。分层的收益是换存储不影响压缩、换压缩不影响存储、编排层只拿 `List<ChatMessage>`。

- **`append` 做两件事**：写库 + **异步**触发摘要压缩。两个细节：
  - **只有 ASSISTANT 消息才触发压缩**——一轮完整对话是 user + assistant，assistant 到了才说明这轮结束；用 user 触发会压出缺半轮的摘要。
  - **压缩必须异步**，它内含 LLM 调用，耗时不确定，同步会拖慢当前请求。

- **`load` 并行拉两路**，用 `CompletableFuture.allOf` 把总耗时从"两次 RT 之和"降为"两次 RT 的最大值"。更重要的是**两路各自降级、互不牵连**：

  | 路径 | 异常降级 | 后果 |
  |---|---|---|
  | 摘要 | 返回 `null` | 历史照常返回，只是缺早期对话的浓缩信息 |
  | 历史 | 返回空列表 | 当前请求继续处理，只是没有上下文 |

- **滑动窗口 = 倒序 + LIMIT**：`historyKeepTurns` 默认 8 轮，取 `8 × 2 = 16` 条，`ORDER BY create_time DESC LIMIT 16` 后在内存反转。不用正序是因为正序需要先算总数才知道 OFFSET 从哪起。

- **`normalizeHistory` 剥掉开头的 ASSISTANT 消息**。窗口可能恰好从一条 assistant 回复切开，得到 `[assistant, user, assistant, …]`——大模型 API 要求 user/assistant 交替且以 user 起头，格式乱了模型会困惑于"第一条怎么是我自己的回复"。**宁可少一轮也不能格式乱**。

- **`attachSummary` 的三个边界**：历史为空（新会话）→ 返回空列表，摘要也不要（摘要是对历史的浓缩，没历史就没意义）；摘要为 `null` → 原样返回历史；两者都有 → 摘要作为 SYSTEM 消息插到**头部**。

- **`loadAndAppend` 先 load 再 append**，返回的是追加**之前**的快照。顺序反过来会让当前问题在最终 Prompt 里出现两次——历史里一次、阶段 8 拼入一次。这是**关注点分离**：记忆服务管历史，Pipeline 管当前轮次。

- **最终消息数组的注入顺序**，每个位置都有理由：

  ```text
  SYSTEM    — RAG 角色规则        最高优先级的行为约束
  SYSTEM    — MCP 工具数据（如有）
  USER      — KB 检索结果（如有）
  SYSTEM    — 对话摘要（如有）     先看浓缩背景再读原文，理解更连贯
  USER/ASSISTANT 交替 — 最近 N 轮原文
  USER      — 当前用户问题         紧邻生成位置，模型对最后一条 user 注意力最高
  ```

- **配置项交叉校验：`summaryStartTurns > historyKeepTurns`**，违反则启动直接报错。理由是时序——第 9 轮触发压缩时第 1 轮刚滑出窗口，压缩正好接住它。若阈值 ≤ 窗口，压缩时没有消息滑出，纯属空转。

## 关键概念/术语

- **滑动窗口**：只保留最近 N 轮原文的策略，`historyKeepTurns` 控制轮数（1 轮 = 1 条 user + 1 条 assistant）。
- **摘要水位线**：记录"本次摘要覆盖到哪条消息"的标记；原文用雪花 ID 兼任（ID 按时间递增，比大小即可），省掉额外时间戳字段。
- **两路降级隔离**：摘要与历史各自 fallback，边缘功能异常不拖垮主链路。
- **normalize**：把窗口切片修正为合法的 user/assistant 交替序列。
- **前情提要位**：摘要作为 SYSTEM 消息置于原文历史之前的位置安排。

## 与 xrag 项目的关系

- **对应 Phase 3 的阶段 1**，是八阶段中唯一在"检索"和"生成"之外、却决定二者输入质量的环节：阶段 2 的代词消解、阶段 3 的意图识别都吃这里的输出。

- **持久化技术栈不同，不能照搬**：原文用 MyBatis-Plus + 雪花 ID + `@ConfigurationProperties`；xrag 是 **JdbcTemplate 直连、无 JPA/MyBatis**，主键与逻辑删除要遵循现有 migration 的既定约定（Flyway 已到 V6）。**逻辑删除这一条正好一致**——原文 `t_message.deleted` 与 xrag [知识库 PRD §7.6](../../../docs/prd/2026-07-25-knowledge-base-prd.md) 的全系统约束同向，repository 查询必须带 `deleted = false`。

- **术语要对齐 [CONTEXT.md](../../../CONTEXT.md)**：那里已经定义了「对话」「用户问题」「回答」等词。落库时不要另造 `t_message` 这类与既有命名风格不一致的表名，也不要把「会话」和「对话」混用。

- **异步压缩会撞上两条既有纪律**：
  - **事务内不得有外部 IO**（跨模块纪律②）——摘要压缩含 LLM 调用，必须在事务之外；
  - **调度类组件要带 `enabled` 开关**（[ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 的单实例假设）——异步压缩若做成常驻任务，得能关掉，否则集成测试会与 dev 实例互抢。

- **LLM 调用只能走 `com.app.ai` 的能力端口**（[ADR 0003](../../../docs/adr/0003-separate-model-capability-ports.md)）。摘要压缩用 `ChatClient`，不得自建 HTTP 客户端。

- **并行加载的实现方式可以更简单。** 原文用 `CompletableFuture` + 自定义 `memoryLoadExecutor`；xrag 若两路都是本地 Postgres 查询，先测实际 RT 再决定要不要引入线程池——单实例、同库、两次索引查询的场景下，并行带来的收益可能小于线程池的复杂度。这一点留给 Step C 用数据说话。

## 值得注意的设计取舍/坑

- **`loadAndAppend` 的时序是本篇最容易写错的地方。** 先 append 再 load 在功能上"看起来也对"——历史更完整了——但会导致当前问题在 Prompt 里重复出现。这类 bug 不会报错，只会让模型的回答莫名其妙地强调用户刚说过的话，极难从日志看出来。

- **`normalizeHistory` 是格式正确性问题，不是优化。** 少了它，滑动窗口在偶数/奇数边界上会随机产出以 assistant 开头的历史——**只在特定轮数才复现**，是典型的"偶发且难归因"缺陷。

- **交叉校验放在启动期而不是运行期。** 这与 xrag 既有做法一致（Embedding 维度与 `vector(1024)` 不符时应用直接启动失败）。放行只会把错误推迟到某次真实压缩时才暴露。

- **摘要放头部而不是尾部。** 尾部紧邻生成位置、注意力最高，那个位置要留给当前问题；摘要是背景不是问题，抢了那个位置反而会让模型去回答摘要里的旧话题。

- **`refreshCache` 是空实现的预留接口。** 原文坦白当前版本没有 Redis 缓存。xrag 不应照抄这个空方法——**预留一个永远不被调用的接口方法，比没有它更容易误导人**（Phase 2 的复盘 §5.2 记过同类教训：死配置比没有配置更糟）。要加缓存时再加接口。

- **滑动窗口丢掉的信息，摘要不一定接得住。** 原文自己举的例子——员工在第 2 轮提过"我是外包身份，审批流程不同"——这类**约束型信息**一旦被摘要漏掉，后续所有回答都会基于错误前提。这是下一篇要处理的问题，也是记忆系统真正的难点所在。
