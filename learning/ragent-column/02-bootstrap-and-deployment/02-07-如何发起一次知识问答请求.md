# 《AI大模型Ragent项目》——如何发起一次知识问答请求

> 原文链接：https://t.zsxq.com/zfpgj
> 所属分组：02-bootstrap-and-deployment 本地开发与模型部署环境

## 一句话概括

参考 Ragent 的首次问答不是直接打开聊天框，而是先建立知识库、上传并检查文档分块，再由意图树把用户输入路由到知识检索、闲聊/情感响应或 MCP 实时工具，最后用代表性问题验证每条路径。

## 核心内容提炼

### 1. 首次知识问答需要完整数据准备

参考操作链路为：

1. 创建知识库并选择 Embedding 模型与稳定底层标识。
2. 上传 Markdown、Word 或 PDF 原文件到对象存储。
3. 选择处理模式与分块策略；Markdown 建议优先尝试结构感知分块。
4. 提交分块任务，等待状态由 running 进入终态。
5. 在分块管理页人工抽查并修正被截断或混杂的 Chunk。
6. 发起与文档内容相关的问题，验证检索和回答。

这说明“文件上传成功”只代表原始对象已保存，距离知识可检索还隔着解析、分块、Embedding、索引、状态管理和质量检查。

### 2. 分块质量是可观察、可修正的产品对象

参考控制台允许查看和编辑每个 Chunk。对退货政策、产品说明等语义边界明显的文档，错误切分会直接降低检索与回答质量。

人工编辑适合调试和少量纠错，但修改后必须重新生成向量并记录版本；否则展示文本、向量和来源文档会出现不一致。大规模内容还需要抽样、自动质量规则和回归评测。

### 3. 不是所有输入都应该检索知识库

用户会发送问候、关于助手的问题、表扬、质疑或纠正。把这些输入一律送入向量检索会产生无关结果。

参考系统用意图树区分：

- 知识库精准问答。
- 日常闲聊。
- 情感反馈。
- MCP 工具调用。

模糊表达应澄清，情感反馈只需短回应，实时业务数据则交给工具。意图路由的本质是选择不同能力链路，而不是为每句话都做一次同样的 RAG。

### 4. 意图配置也有运行时状态

文章通过 SQL 导入示例意图节点，并指出直接改数据库不会自动刷新 Redis 中的意图树缓存，需要触发应用侧刷新。这暴露了管理旁路问题：数据源已更新而运行时仍使用旧版本。

配置变更应走单一写入口或带版本/事件的刷新机制，不应依靠“随便编辑一个节点再保存”这种人工技巧。

### 5. MCP 用于实时、不可预先入库的数据

工单、销售统计、天气等数据具有实时性或来自业务系统，不适合定期写成静态知识文档。参考流程先识别工具意图，再从用户问题提取受 Schema 约束的参数，调用对应 MCP 工具并把结果交回模型。

知识检索和工具调用解决不同类型的事实来源：前者从已摄入文档取证，后者读取或操作当前外部状态。两者都必须保留来源、授权和失败语义。

### 6. 首次体验要分路径验证

至少应准备：

- 一个文档中有明确答案的问题。
- 一个文档没有答案的问题。
- 一个普通问候或关于助手的问题。
- 一条正向或负向反馈。
- 一个能触发工具的实时问题。

只有这样才能确认数据摄入、检索、拒答、意图和工具不是“单条 happy path 看起来能跑”。

## 关键概念/术语

- 文档状态：原始文件从已上传、处理中、可检索到失败等生命周期状态。
- 分块任务：将文档解析、切分、向量化并写入索引的一次处理执行。
- Chunk 校对：对分块边界和内容进行人工或自动质量检查。
- 意图树：用层级节点描述输入类别并关联知识库、提示或工具的路由模型。
- 闲聊路径：不需要知识检索、使用通用或受控 Prompt 回复的处理分支。
- 情感反馈路径：针对用户评价进行简短回应并避免重复生成原答案的分支。
- 实时工具路径：通过受控接口查询无法预先固化到知识库的当前数据。
- 运行时缓存版本：应用当前实际使用的配置快照版本。

## 与 xrag 项目的关系

当前 xrag 没有知识库、上传、分块、问答、意图或 MCP 接口；本文描述的是未来验收旅程，不是当前可操作步骤。

- Phase 1 的首条纵向用例可以定义为“创建知识库 → 上传小型 Markdown → 处理完成 → 查询 Chunk/状态”，先不把闲聊和 MCP 并入同一批实现。
- 文档原件、处理任务、Chunk 和向量记录需要独立身份与状态，避免用一个“上传成功”布尔值掩盖多阶段失败。
- xrag 应在实现时决定处理是同步还是异步、客户端如何观察状态，以及失败后能否安全重试；不直接继承参考项目的刷新轮询体验。
- 意图树和 MCP 属于后续问答编排阶段，只有出现真实多路径需求后再引入。

## 值得注意的设计取舍/坑

- **创建知识库跨多个资源系统**：元数据、Bucket 和向量空间可能部分成功，必须有可恢复状态和补偿/重试，不能假设一个按钮对应原子事务。
- **Embedding 模型是数据兼容性属性**：更换模型通常需要重建全部文档向量，必须显式版本化，而非仅锁死下拉框。
- **手工编辑 Chunk 会产生派生数据一致性问题**：编辑后需重新向量化，并保留来源、版本和审计。
- **固定意图树容易过早复杂化**：首期仅有单知识库检索时，树结构未必有收益；先用真实路由需求证明。
- **绕过应用直接执行 SQL 会绕过缓存和校验**：参考文中的刷新技巧是架构缺口，不应成为 xrag 运维流程。
- **工具参数提取 Prompt 不能替代授权和校验**：即使 Prompt 声明用户文本不是指令，执行端仍要限制字段、类型、权限和副作用。
- **外部 Embedding 失败不只因余额**：还可能是限流、认证、模型下线、维度变化或网络问题，错误状态应准确分类。
