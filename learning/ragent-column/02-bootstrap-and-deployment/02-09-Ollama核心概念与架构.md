# 《AI大模型Ragent项目》——Ollama核心概念与架构

> 原文链接：https://t.zsxq.com/d4HI2
> 所属分组：02-bootstrap-and-deployment 本地开发与模型部署环境

## 一句话概括

Ollama 是围绕 llama.cpp 构建的本地模型服务与模型包管理工具：它用常驻服务统一模型下载、加载、卸载和 HTTP 推理，适合本地开发与低并发验证，但其 OpenAI 兼容、资源调度、安全边界和生产运维能力都需要单独验证。

## 核心内容提炼

### 1. Ollama 是客户端—服务端系统

`ollama serve` 启动常驻服务，默认监听 `127.0.0.1:11434`；`ollama run`、`pull`、`list`、`rm`、`show` 等 CLI 命令本质上是该服务的客户端。

退出一次 `ollama run` 交互并不等于关闭 Ollama 服务，也不一定立即卸载模型。模型是否继续驻留由 keep-alive 策略控制，因此排查显存占用时必须区分 CLI 会话、服务进程和已加载模型。

### 2. 模型以带元数据的包管理

`ollama pull` 获取的不只是单个权重文件，还包括：

- GGUF 权重 Blob。
- Manifest 与配置层。
- Chat Template、默认参数和 System Prompt。
- 许可证等模型元信息。

模型标签通常同时表达参数规模和量化版本。省略标签会使用默认标签，但默认标签可能随上游更新；需要可复现时应固定明确版本，并记录实际 digest。

默认模型目录因操作系统和安装方式而异，可通过 `OLLAMA_MODELS` 调整。模型文件体积大，迁移目录前需要同时考虑磁盘空间、权限、备份和重复下载。

### 3. Modelfile 用于派生运行配置

Modelfile 的常用指令包括：

- `FROM`：指定基础模型。
- `PARAMETER`：设置温度、上下文窗口等推理参数。
- `SYSTEM`：定义默认系统提示词。
- `TEMPLATE`：定义模型消息模板。
- `ADAPTER`：加载适配器。

增大 `num_ctx` 会同步增加 KV Cache 的内存/显存成本。模板必须与模型训练时的消息格式匹配，除非确有需要，不应随意覆盖。

### 4. 原生接口与 OpenAI 兼容接口服务于不同目标

Ollama 原生接口如 `/api/chat` 能暴露加载、评估和耗时等更丰富的本地运行信息；OpenAI 兼容接口如 `/v1/chat/completions` 更利于复用现有 SDK 和抽象 Provider。

兼容只降低接入改造成本，不保证工具调用、结构化输出、流式分片、错误码、usage 或参数集合完全等价。

### 5. 资源驻留和并发由多个配置共同决定

常见环境配置包括：

- `OLLAMA_HOST`：监听地址。
- `OLLAMA_MODELS`：模型存储目录。
- `OLLAMA_NUM_PARALLEL`：单模型并行请求数。
- `OLLAMA_MAX_LOADED_MODELS`：可同时驻留的模型数。
- `OLLAMA_KEEP_ALIVE`：模型请求结束后的驻留时间。

实际能否让 Chat 与 Embedding 模型同时驻留，最终取决于权重、KV Cache、上下文、并发和硬件内存。模型被驱逐后重新加载会产生明显冷启动延迟。

Ollama 会探测 GPU，并可能在资源不足时进行 CPU/GPU 混合卸载。多卡策略、Flash Attention 等能力随 Ollama 和底层引擎版本变化，不能把文章中的行为当作稳定接口。

### 6. 易用性不等于生产就绪

Ollama 优势在于安装和开发体验；高并发调度、完整指标、细粒度限流、滚动升级、容量管理和集群容错仍需外部系统补足。将其绑定到 `0.0.0.0` 后，默认服务本身没有适合公网暴露的认证边界，必须增加防火墙、反向代理和访问控制。

## 关键概念/术语

- Ollama Server：常驻的本地模型管理与推理 HTTP 服务。
- Ollama CLI：通过本地 HTTP 服务执行模型管理和交互的命令行客户端。
- Manifest：记录模型层、配置和摘要等信息的模型包清单。
- GGUF：llama.cpp 生态常用的模型权重与元数据格式。
- Modelfile：基于已有模型创建派生运行配置的声明文件。
- Model Tag：模型名称后的变体标识，常用于区分参数量和量化版本。
- Model Digest：模型内容的不可变摘要，比可变标签更适合追踪真实版本。
- Keep-alive：请求结束后模型继续驻留内存/显存的时间策略。
- 冷启动：模型不在内存时重新读取并加载权重所产生的首请求额外延迟。
- OpenAI 兼容接口：复用 OpenAI 风格请求结构的接口层，不代表完整行为等价。

## 与 xrag 项目的关系

xrag 当前 Compose、后端依赖和配置都没有 Ollama，Phase 0 也不需要下载或持有本地模型。

- 若 Phase 1 用 Ollama 做本地验证，应将它作为可选 Provider，通过明确的 Base URL、模型 ID 和超时配置接入。
- Chat 与 Embedding 应分别声明模型和能力，不能假设同一模型或同一驻留策略同时适合两种负载。
- 模型标签、digest、上下文长度和量化版本应进入可追溯配置，避免评测结果无法复现。
- Ollama 不应成为文档检查和常规 CI 的强依赖；需要模型的端到端验证可放到显式的本地集成测试配置中。
- 若未来对外提供 Ollama 服务，xrag 或基础设施层必须承担认证、授权、限流和审计，不能直接暴露默认端口。

## 值得注意的设计取舍/坑

- **标签可能漂移**：使用默认标签便捷，但无法保证下次拉取仍是相同内容；正式评测要记录 digest。
- **OpenAI 兼容存在语义缺口**：SDK 能发出请求不等于 Function Call、流式终止和错误处理可无差别复用。
- **无限驻留可能饿死其他模型**：将 keep-alive 设为永久可减少冷启动，却可能让 Chat 模型长期占满 Embedding 所需显存。
- **公网监听是安全边界变化**：`OLLAMA_HOST=0.0.0.0` 只解决可达性，没有自动提供认证和租户隔离。
- **上下文窗口会放大资源成本**：只改 `num_ctx` 而不测 KV Cache、并发和首 Token 延迟，容易在真实请求下 OOM。
- **实现细节具有版本时效性**：GPU 卸载、多卡、并发和实验特性应以目标 Ollama 版本实测为准。
- **模型存储未必按标签完全重复**：Ollama 的内容寻址层可能复用 Blob，不能据“不同标签”直接推算磁盘翻倍。
- **开发工具不是自动的生产平台**：上线前仍需容量、告警、升级回滚、故障隔离和效果回归方案。
