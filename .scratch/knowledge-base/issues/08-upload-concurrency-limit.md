# 08 — 上传并发限流

**What to build:** 同时上传的请求数超过上限时，多出来的请求快速收到 429 而不是一起把磁盘和 IO 压满。

这张工单的全部技术含量在**拦截位置**：必须在 `Filter` 里，不能在 `HandlerInterceptor` 里。原因是 multipart 请求体由 `DispatcherServlet` 解析，时机在 `Filter` 之后、`Interceptor` 之前——放在 `Interceptor` 里限流时文件已经完整读进来了，保护磁盘和 IO 的目的已经落空。

### 两条手工项都改成了自动化，理由不同

**① "并发 3 个、2 个被拒"改成单元测试。** 集成测试里没有可靠手段把一个上传请求**精确地卡在持有许可的状态**——只能传个大文件让它慢一点、再赌它比超时更慢，那是典型的 flaky。改用一个阻塞在 `CountDownLatch` 上的假 `FilterChain`，那一刻被钉死，时序完全确定。`UploadConcurrencyFilter` 只依赖三个构造参数、不碰数据库和对象存储，正好适合这么测。

**② "被拒请求没有产生临时文件"改成断言"chain 未被调用"。** 这两件事是同一件事的两种说法，而后者更强：multipart 请求体正是由 chain 下游的 `DispatcherServlet` 解析的，**chain 没被调用就意味着请求体没被读、临时文件无从产生**。去 `/tmp` 数文件反而更弱——数不到也可能是刚好被清理了。

### 另加一条集成测试，守的是单元测试守不住的东西

单元测试证明不了这个 Bean **真的被注册进了 servlet 过滤器链**——`@Component` 的 `OncePerRequestFilter` 靠自动注册生效，哪天被 `FilterRegistrationBean` 关掉或改了顺序，单元测试照样全绿。

`UploadLimitIntegrationTests` 把许可数设成 **0**，于是不需要制造任何并发：每个上传请求都必然拿不到许可。同一个类里还有一条"非上传接口照常 200"——**许可数是 0 时，如果路径判断写错，整个应用所有接口都会返回 429**，那是会瞬间瘫痪全站的错误，而它在只测上传路径的用例里完全看不出来。

### 几处实现判断

- **信号量用公平模式**。上传耗时长，非公平信号量下先到的请求可能被后到的反复插队、一直等到超时被拒——对用户表现为"我先点的那个反而失败了"。
- **429 响应体在 Filter 里手写**。Filter 在 `@RestControllerAdvice` 的作用范围之外，不显式写的话前端拿到的是容器默认错误页，只能靠状态码猜。
- **`app.upload.acquire-timeout` 补成了配置项**（工单 03 当时留给本工单决定）。默认 5s。带超时而不是无限期排队：排队的请求同样占着一个容器线程，无限等会把线程池也拖垮。
- **URL 抓取接口不走这个信号量**，有单独一条用例守着。它不接收请求体，限流保护的磁盘与 IO 压力与上传不是一回事。
