## 完成记录

产出 [ui-spec.md](../../../tech/knowledge-base/ui-spec.md)。清单项全部覆盖，额外做了三件工单没要求的事：

1. **发现并解决了一个 API 契约缺陷。** `409 INVALID_STATE` 在 api.md 里对应至少三种情况（给禁用文档触发分块 / 给禁用文档新增分块 / 启用分块但父文档禁用），前端从错误码上无法区分。选择"后端 `message` 必须是可直接展示的完整句子"而不是拆三个错误码——三者的修复动作是同一个（先启用文档），前端不需要按码分支，拆码只会多一层映射表。已同步写进 api.md §1 的错误响应约定，并给出三处成品文案。
2. **分块为空的空态拆成了两条**（`revision=0` vs `revision>0`）。同一个"没有分块"，前者是"还没处理"（正常，需要用户动作），后者是"处理过但切不出内容"（异常，多半是空文件或扫描版 PDF）。合并成一句话会让第二种情况的用户一直点"开始处理"却永远得不到分块。
3. **点明了启用/禁用分块的不对称**：禁用不受父文档状态限制，启用才受（api.md 的既有规则）。所以父文档禁用时"批量禁用"仍可用、只有"批量启用"要灰掉。这个不对称不写清楚，前端很容易图省事把两个按钮一起禁用。

**PENDING 状态被当成重点处理**：上传接口返回后文档并没有被分块，如果界面只显示一个灰标签，用户会以为系统在后台自动处理然后一直等下去。为此规定了上传成功 toast 的具体措辞、`PENDING` 行的主按钮样式，以及知识库级的"有 N 篇文档待处理"提示条。

文案全部写成成品，不用"给出明确提示"这类占位描述——那等于没写规格。
