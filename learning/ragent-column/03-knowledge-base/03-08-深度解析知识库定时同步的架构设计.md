# 《AI大模型Ragent项目》——深度解析知识库定时同步的架构设计

> 原文链接：https://t.zsxq.com/YMhqa
> 所属分组：03-knowledge-base AI知识库建设
> 系列上篇（讲设计），下篇见 03-09（讲运行时）

## 一句话概括

定时同步不是一个简单的 `@Scheduled` 方法，而是一整套调度系统：两张表（任务主表+执行历史表）打底 → 拆成五个各司其职的组件 → 用"数据库租约锁"（而非Redis锁）解决多实例重复执行问题，配合自动心跳续锁 → 用"HTTP Header 快查 + 内容哈希兜底"两级变更检测避免绝大多数无意义的重复下载和重新分块。

## 核心内容提炼

- **业务背景**：企业文档常放在飞书/Notion/钉钉这类会持续更新的在线平台，作者改完不会记得回来重新上传，不做定时同步会导致"知识库回答的是过期内容"。本地文件上传是一次性的（不需要同步机制），只有 URL 来源需要：`scheduleEnabled` + `scheduleCron` 两个配置驱动"定时扫描→抢任务锁→拉远程文件→检测变更→抢文档运行权→重新分块→更新状态"整条链路。

- **两张表的设计分工**（主表管当前状态、历史表管完整流水，这是贯穿全文的核心分层思路）：
  - **`t_knowledge_document_schedule`（任务主表，`doc_id` 唯一约束——一份文档最多一条schedule记录）**：四组字段——① 基础信息（`docId`/`kbId`/`cronExpr`/`enabled`）；② 调度状态（`nextRunTime`/`lastRunTime`/`lastSuccessTime`/`lastStatus`/`lastError`，扫描器靠 `nextRunTime<=now` 找到期任务）；③ 变更检测缓存（`lastEtag`/`lastModified`/`lastContentHash`，留给下次比对用）；④ 分布式锁字段（`lockOwner`/`lockUntil`）。
  - **`t_knowledge_document_schedule_exec`（执行历史表）**：保存每次执行的完整流水（status/message/耗时/文件哈希等）。**为什么需要单独一张历史表**：如果只在主表存最近一次结果，就回答不了"过去一周执行了多少次""成功率多少""哪些时段常失败"这类问题——这和 03-07 篇"分块日志表独立于文档表"是同一个设计哲学的再次应用。

- **五个组件的职责拆分**（不拆会导致"一个方法几百行、改一处影响全局、无法单独测试某环节"）：
  1. **`KnowledgeDocumentScheduleJob`（调度入口）**：① 每10秒扫描一次到期任务（`enabled=1 AND nextRunTime<=now AND lockUntil<now`），找到后先抢锁，抢到才执行；② 每分钟扫描一次，把卡在 RUNNING 超过30分钟的文档重置为 FAILED（进程崩溃后的兜底恢复）。只负责"找到该跑的任务+兜底恢复"，不管具体刷新逻辑。
  2. **`ScheduleLockManager`（锁管理器）**：`tryAcquire`/`renew`/`release`/`startHeartbeat` 四个方法，把锁的续期复杂度封装起来，业务代码不用操心锁的细节。
  3. **`ScheduleRefreshProcessor`（刷新处理器，"总控台"）**：编排完整流程（启动心跳→校验任务→创建执行记录→变更检测→抢占文档运行权→上传新文件→执行分块→应用元数据→更新状态→清理文件→关闭心跳→释放锁），用 `Phase` 枚举（`INIT→DOC_OCCUPIED→CHUNK_STARTED→CHUNK_COMPLETED→FILE_SWITCHED`）追踪执行到了哪一步，据此在关键节点检测锁是否失效、精细化控制文件清理策略。
  4. **`ScheduleStateManager`（状态管理器）**：更新 schedule/exec 表状态，所有方法都是 `xxxIfOwned` 模式（更新前检查 `lockOwner` 是否匹配当前 token）——**状态更新必须是"锁感知"的**，不匹配就不更新主表（但仍会写 exec 记录并附加"调度锁已失效"标记），防止已经丢锁的实例覆盖新持锁者的状态。
  5. **`DocumentStatusHelper`（文档状态助手）**：`tryMarkRunning`（CAS抢占文档运行权）、`markFailedIfRunning`、`applyRefreshedFileMetadata`、`recoverStuckRunning`——这是**第二层并发控制**（第一层是任务级的数据库租约锁，防止同一个schedule被多实例同时执行；第二层是文档级的CAS，防止"定时刷新"和"手动分块"同时跑同一份文档）。

- **为什么选数据库锁而不是 Redis 分布式锁**：作者列了对比表——Redis性能更高、更通用、生态成熟（Redisson），但需要额外维护Redis高可用、锁状态和业务数据分离、排查问题要跨系统查（数据库+Redis）；数据库锁性能相对低但"不新增基础设施"、锁和任务状态在同一张表里、只需查数据库就能排查（哪个实例持锁、什么时候过期）。**关键判断依据**：调度状态本来就在数据库里（加两个字段就能把锁也放进去）、锁粒度是schedule级别（和主键对应）、扫描频率不高（10秒一次、每次最多20个任务，数据库完全扛得住）——"架构上更收敛"是最终选择理由，不是数据库锁天生比Redis锁好。

- **"租约锁"和"分布式锁"不是二选一，是同一个东西的两个描述维度**：分布式锁强调"作用范围"（多实例互斥），租约锁强调"持锁模型"（不是永久占有，带租期，到期失效，可续租）——这里的实现是"一把带租期的分布式锁"，作者类比 Redisson 看门狗机制的简化版本。核心语义：`lockUntil` 为空或已过期时才能抢锁成功；心跳续锁本质就是不断把 `lockUntil` 往后推。

- **锁的获取/续期/释放的具体机制**：
  - **获取**：`UPDATE ... SET lockOwner=?, lockUntil=? WHERE id=? AND (lockUntil IS NULL OR lockUntil<now)`——典型CAS，多实例同时跑这条SQL只有一个能成功。**为什么要生成唯一 `lockToken`**：如果不验证token，会出现"A执行慢锁过期→B抢到锁→A执行完后释放锁→A误释放了B的锁"这种错乱场景，所以续锁/释放锁都要验证token匹配。锁过期时间默认900秒（15分钟）：太短（如1分钟）任务还没跑完就被别人抢走，太长（如1小时）宕机后恢复太慢，15分钟是"正常刷新流程（下载+分块+上传）几分钟内完成"和"故障恢复速度"之间的平衡点。
  - **自动心跳续锁**：传统"手动在每个耗时操作前调用renew"心智负担重、容易遗漏；改成后台心跳线程周期性自动续锁，业务代码只需在关键阶段检测锁是否失效。**心跳间隔 = 锁持有时间/3，限制在5~60秒**（900/3=300秒但有60秒上限，实际是60秒）——这个1/3比例和 Redisson 看门狗机制的默认值一致，经过大量实践验证：太频繁浪费数据库资源，太稀疏容错空间不够。心跳失败时不直接抛异常，而是 `markLost()` 标记，业务逻辑自己决定在安全时机中止（因为可能正在执行某个操作，比如上传文件，不能被粗暴打断）。
  - **锁失效的两重检测**（`shouldAbortForLeaseLoss`）：① 检查心跳是否已标记lost；② 主动尝试续锁一次。**为什么要两重**：只查心跳标记可能心跳线程还没来得及执行；只主动续锁可能心跳线程已经发现失败但业务逻辑还没检测到——两者互补才能及时发现失效。检测点选在"抢占文档运行权之前"和"执行分块之前"这类高成本操作前。
  - **释放**：`UPDATE ... SET lockOwner=NULL, lockUntil=NULL WHERE id=? AND lockOwner=?`——同样要验证 `lockOwner` 匹配，理由和获取锁时一样，防止误释放他人持有的锁。释放动作放在 `finally` 块里，确保成功/失败/跳过都一定会执行。

- **变更检测的成本账**：如果每小时同步一次、24次/天，但文档实际可能一周才更新一次（168次触发只有1次真正需要刷新），无脑重新下载+分块+调Embedding API+写向量库全是浪费。**两级检测策略（先cheap check再expensive check）**：
  1. **第一级 HEAD 请求**：拿 `ETag`/`Last-Modified` 两个HTTP标准头，任意一个和上次存的值相同就直接短路判定"没变"。优点是不用下载、几十毫秒就能返回；局限是有些服务器不支持HEAD、不返回这两个头、或者返回的头不可靠。
  2. **第二级下载+SHA-256哈希**：HEAD失败或没命中短路条件时，下载文件同时（**边下载边计算哈希，只遍历一次数据流**，用 `DigestInputStream` 包装）算出SHA-256，和上次存的 `lastContentHash` 比对。优点是不依赖服务器头的可靠性、完全基于内容判断；成本是要下载完整文件+算哈希（CPU密集），但比重新分块+调Embedding API的成本低得多。
  - **`RemoteFetchResult` 实现 `AutoCloseable`**：配合 try-with-resources 自动管理临时文件生命周期（没变化时自动删除临时文件，不会因为异常导致临时文件泄漏）——这是 03-06 篇"远程抓取统一先落临时文件"这个设计模式的延续和加固。

## 关键概念/术语

- **数据库租约锁（database lease lock）**：用两个字段（`lockOwner`+`lockUntil`）在数据库层面实现的、带自动过期能力的分布式锁。
- **自动心跳续锁**：后台线程周期性自动调用 `renew`，业务代码无需手动管理续期时机，参考自 Redisson 看门狗机制。
- **Phase 追踪**：用枚举记录长流程执行到了哪个阶段，用于精细化的锁失效检测和异常清理策略。
- **`xxxIfOwned` 模式**：所有状态更新方法在写库前都验证锁归属，防止已丢锁的实例覆盖当前持锁者的状态。
- **两级变更检测**：HTTP Header（ETag/Last-Modified）快速判断 + 内容SHA-256哈希兜底，是"先廉价检查再昂贵检查"策略的具体应用。

## 与 xrag 项目的关系

- **这是迄今为止对 xrag 知识库模块技术方案影响最大、也最具"企业级"含量的一篇**，从数据模型（两张表设计）到组件拆分（五个职责单一的类）到并发控制（两层：任务级租约锁+文档级CAS）到成本优化（两级变更检测），几乎是一份可以直接拿来改写成 xrag 技术方案的现成蓝图。
- **给 xrag 的一个明确决策点**：既然是单用户个人项目、不会真的多实例部署，"数据库租约锁防止多实例重复执行"这层机制在功能上暂时用不上（本来就只有一个实例），但作为学习和"企业级全流程展示"的既定目标，仍然值得按本文思路实现——文档级 CAS（防止"手动触发分块"和"定时刷新"撞车）无论单/多实例都有实际意义，应该保留；任务级租约锁可以简化实现但保留设计说明，写清楚"为什么这么设计、单实例场景下的价值退化为什么"。
- **两级变更检测策略应该直接复用**：这是最具性价比的一条——即使 xrag 场景小，"先HEAD再哈希"的成本节省逻辑依然成立，不应该因为规模小就跳过这个设计。
- **数据库锁 vs Redis锁的选型论证过程，可以直接作为 xrag 相应 ADR 的参考模板**："架构上更收敛、排查更简单、不新增基础设施"这套判断标准，本身就是很好的企业级技术选型示范。

## 值得注意的设计取舍/坑

- **心跳失败"只标记不抛异常"是一个容易被忽略但很重要的设计**：业务逻辑正在执行某个不可安全中断的操作时，直接抛异常可能导致更糟的中间状态；标记+业务自行在安全点检测，是处理"异步发现的失效信号"的通用好模式，适用于任何"后台监控+前台业务"配合的场景。
- **两重锁失效检测容易被简化成一重，从而留下检测盲区**：只做心跳标记检查或只做主动续锁检查，都会有各自的时间窗口盲区——这是个容易被"看起来已经够用了"误导而简化掉的细节。
- **锁过期时间（15分钟）和心跳间隔（1/3且封顶60秒）都是经验值，不是理论最优解**，原文明确说这是"平衡点"——xrag 如果场景明显不同（比如文档普遍很大、下载+分块经常超过15分钟），需要重新评估这两个参数，不能直接照抄默认值。
- **"两张表都要设计好再动手写代码"这个顺序本身值得注意**：文章明确说"要理解这套机制，最好先从数据模型入手，因为所有调度逻辑、锁机制、状态管理最终都要落到数据库表上"——这是一个值得在 xrag 技术方案写作时遵循的顺序：先定数据模型，再谈组件拆分和流程编排，而不是反过来。
