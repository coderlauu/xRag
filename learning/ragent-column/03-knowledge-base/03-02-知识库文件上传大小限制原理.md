# 《AI大模型Ragent项目》——知识库文件上传大小限制原理

> 原文链接：https://t.zsxq.com/pFmQ6
> 所属分组：03-knowledge-base AI知识库建设

## 一句话概括

破除"配置了 `max-file-size` 就等于超限文件会先被整个读进内存再拒绝"这个常见误解——Spring Boot + Tomcat 有完善的"早期拒绝"机制（先看请求头 `Content-Length` 再决定收不收），且即便文件没超限也是流式写临时文件而不是整个塞进内存，所以合理配置大小限制不会有 OOM 风险。

## 核心内容提炼

- **常见误解**：直觉认为"上传=整个读到内存→检查大小→保存或拒绝"。这个直觉在小文件下没问题，但放大到 GB 级会导致：如果真是先读后检查，恶意用户并发上传多个 1GB 文件就能把服务器内存瞬间占满，造成 OOM——这是个真实的安全担忧，但实际情况并非如此。

- **早期拒绝机制的基础是 HTTP 的 `Content-Length` 请求头**：客户端发请求前就算好了请求体大小并写进这个头，服务器读请求体之前就已经知道大小。类比：不是"快递员先搬进仓库称重超重再搬出来"，而是"看包裹上的重量标签直接拒收"。

- **两层检查**：
  1. **Tomcat 层**：解析请求头拿到 `Content-Length`，如果超过 `maxSwallowSize`（默认 2MB），直接返回 413/拒绝，根本不读取请求体。
  2. **Spring Boot 层**：解析 multipart 请求时通过 Servlet 3.0 标准的 `getParts()`（Tomcat 边读边解析实现），逐个 Part 检查 `part.getSize()`，一旦某个文件超过 `max-file-size` 就抛出 `MaxUploadSizeExceededException`，不会等整个文件读完。

- **即使文件没超限，也不会整个装进内存**：Spring Boot 采用"流式处理 + 临时文件"——数据先进一个小的内存缓冲区（默认 8KB），根据 `file-size-threshold`（默认 `0`，即所有文件都写临时文件）决定是否落盘，全程内存占用只有缓冲区那么大。临时文件位置由 `java.io.tmpdir`（Linux `/tmp`、macOS `/var/folders/xxx`）决定，可通过 `spring.servlet.multipart.location` 自定义；请求处理完/抛异常后会自动清理。

- **Controller 拿到的 `MultipartFile` 只是磁盘临时文件的一个轻量引用**，本身不占大内存；但怎么用它决定了会不会真的把内容读进内存：`file.getBytes()`（❌ 会整个读进内存）vs `file.getInputStream()`（✅ 流式读取）vs `file.transferTo(...)`（✅ 文件级移动/复制，不经内存）。这是实际编码时最容易踩的坑——配置再对，业务代码里调用 `getBytes()` 照样会把大文件读进内存。

- **异常抛出的两种时机**：① 整个请求超 `max-request-size`——Tomcat 在 `getParts()` 时就抛异常，还没开始读请求体；② 单个文件超 `max-file-size`——Tomcat 读该 Part 过程中发现超限抛出，虽然"看起来像"先读后检查，但由于是流式读取、边读边写临时文件，不会占用大量内存。

- **客户端伪造 `Content-Length` 的情况**：声明 10MB 实际发 100MB，Tomcat 读到声明值后发现还有数据会直接断开连接（客户端收到 connection reset），不会继续读完剩余部分。

- **实战验证**：用 Ragent 项目（`application.yml` 里配了 `max-file-size: 50MB`/`max-request-size: 100MB`）直接调接口上传超过 50MB 甚至 1GB 文件测试，观察到超限请求几毫秒内被拒绝、内存无明显波动，验证了早期拒绝和流式处理都确实生效。

- **文章结尾埋了个伏笔**：即使单请求的文件大小校验做对了，为了避免"大量并发上传都在写临时文件"，还需要控制并发量——下一篇会讲基于全局信号量的并发限流机制。

## 关键概念/术语

- **Content-Length**：HTTP 请求头，客户端发送前算好的请求体总字节数，是"早期拒绝"机制的基础。
- **maxSwallowSize**：Tomcat 层的请求体大小上限配置（默认 2MB），超过则直接拒绝、不读取请求体。
- **`max-file-size` / `max-request-size`**：Spring Boot multipart 配置，分别限制单个文件大小和整个请求（含所有文件+表单字段）总大小。
- **`file-size-threshold`**：控制"多大的文件才写临时文件、多小可以留内存"的阈值，默认 `0` 表示全部写临时文件。
- **`MaxUploadSizeExceededException`**：文件或请求超限时 Spring 抛出的异常，需要在全局异常处理器里捕获转成友好提示，否则会有默认报错页。
- **`MultipartFile`**：Spring MVC 里代表上传文件的抽象，本身只是磁盘临时文件的轻量引用，`getBytes()`/`getInputStream()`/`transferTo()` 三种使用方式对内存占用影响完全不同。

## 与 xrag 项目的关系

- xrag 知识库模块的文档上传接口在设计/实现时应该直接沿用这套"早期拒绝 + 流式落盘"的默认机制（Spring Boot + Tomcat 内置），不需要自己造轮子去手动限流内存；重点是要在 Controller/Service 层的实际代码里避免调用 `MultipartFile.getBytes()` 这种一次性读全量到内存的写法，改用 `transferTo()` 直接落到目标位置（比如先落本地临时目录，再上传到 RustFS）或流式读取。
- 需要在 xrag 的 `application.properties`/`application.yml` 里显式配置 `spring.servlet.multipart.max-file-size`、`max-request-size`，目前 `backend/src/main/resources/application.properties` 里还没有这两项配置，是知识库模块开发时的一个具体待办。
- 这篇讲的是"单个请求内"的安全边界；文章明确指出下一步要解决"并发多个上传请求"的资源保护问题（全局信号量限流），这正好是 03-knowledge-base 分组接下来几篇要学的内容，两者需要放在一起设计（单请求大小限制 + 并发数限制），不能只做一半。

## 值得注意的设计取舍/坑

- **配置对了不代表业务代码安全**：`max-file-size` 只保证 Spring/Tomcat 层面不会读超限文件，但如果业务代码里对本来就没超限的文件调用了 `file.getBytes()`，一样会把整个文件（比如刚好 49MB，卡在限制以内）读进内存——大小限制和"业务代码怎么消费 MultipartFile"是两个独立的风险点，都要注意。
- **`file-size-threshold` 生产环境不建议改大**：文章明确建议保持默认值 `0`（全部走临时文件），因为内存比磁盘贵、临时文件 I/O 通常不是瓶颈，改大阈值让小文件走内存看似"优化"，实际是拿内存风险换一点点性能，得不偿失。
- **客户端伪造 `Content-Length` 只能被动检测，不能完全杜绝**：Tomcat 是"读到声明值后发现还有余量就断连接"，这意味着如果客户端刻意少报大小、真实文件更大，在达到声明值之前的这部分数据已经被处理了——如果对这种攻击场景有更高安全要求，需要额外的应用层校验，不能完全依赖 Content-Length 自证。
