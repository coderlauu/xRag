- `phase`: Phase 3 / 3B 子里程碑（`2026-08-08` ~ `2026-08-12`）
- `status`: [里程碑状态](../status/2026-08-12-phase-3b-retrieval-tools.md)

## 1. main 坏了 21 个提交，没人发现——因为工作区一直帮它兜着

`com.app.ai.config` 下有 `EmbeddingClientConfiguration` 和 `RerankClientConfiguration`，
**独缺 Chat 的那份**。而 `AmbiguityActionService` 构造依赖 `ChatClient`，于是任何加载完整
Spring 上下文的测试都起不来。在 HEAD 上跑全量是 **589 tests / 161 errors**。

它从 `bdec72b`（3A 理解链路后端）就存在，跨越 21 个提交无人察觉。原因是补洞的
`ChatClientConfiguration` 一直躺在**未提交的工作区**里——每次本地跑测试它都在，所以本地永远
是绿的；提交出去的代码从来没绿过。

**教训**：工作区里的未提交文件会系统性地掩盖提交缺陷，而且掩盖得毫无痕迹。这次是靠"在
worktree 里 checkout HEAD 跑一遍"才看见。**判断一批提交是否健康，唯一可靠的办法是在干净的
检出上跑**，本地绿不说明任何事。

## 2. 诊断第一次走错了方向，而且证据看起来很像

入库测试的 `awaitStatus` 随机超时，7 次全量里 5 次命中，落点在不同测试类之间漂移。

第一版判断是"上下文变体 × Hikari 池逼近 `max_connections`"。证据链看起来完整：实测连接峰值
88/100，把测试池压到 6 后降为 62。**然后 flaky 照旧**。

真正的根因一开始就摆在眼前，只是没被当成线索：**三个 flaky 全是"期望失败"的测试，期望成功的
从来不失败**。顺着这条查才发现——问答那批测试不需要假 Embedding 所以没导入
`FakeEmbeddingConfig`，而它们的 `IngestionDispatcher` 默认开着，本机 `.env` 里有真实
`EMBEDDING_API_KEY`，于是那些调度器抢到入库任务后**真的调通了阿里云并成功**。
`SHOULD_FAIL` 这类 static 开关只影响自己上下文里的实例。

**教训**：症状的**不对称性**比症状本身信息量大。"只有 A 类失败、B 类从不失败"直接排除了
一整类原因（资源竞争会无差别地影响两者）。压池的改动保留了，但注释写明它**不是任何已知
flaky 的修复**——免得下次有人误以为这条已经解决了问题。

## 3. 矩阵回写差点拿 Phase 2 的测试冒充 3B 的证据

第一版回写脚本按"矩阵 ID 短形式出现在测试方法名里"批量匹配，扫描范围误含 `com/app/ai/`。
结果 **Phase 2 的 `cfg01_合法配置生成不可变脱敏快照`（`ai-models.yml` 的配置测试）匹配上了
`3B-CFG-01`（检索并行度配置）**。那一版把 61 条标成 passed，其中至少 5 条是伪造的证据。

发现它靠的是一个很小的不一致：同一批 CFG 条目，第一次扫描说"待判断"、第二次却直接标了
passed。**两次结果不一致本身就是信号**，比任何单次结果都值得追。

**教训**：矩阵回写产出的是"证据"，字符串启发式不足以支撑它——**证据错了比没有更糟**，因为
它会让人停止追问。改成按前缀限定文件集合后重做，另有 5 条方法名不含 ID 的逐条人工核对。

## 4. 依赖图缺了一环，而且是最关键的那环

工单 08 建了 `RetrievalOrchestrator`，工单 11 建了响应契约，**没有任何工单负责把两者接起来**。
`RetrievalOrchestrator` 一直没有业务调用方，真实链路上 `retrieval` 恒为 null。

发现于实现工单 11 时 grep 调用方——只有我自己刚加的 controller 注入。补成 08b 之后，接入
**当场暴露了工单 08 的一个真 bug**：`plan()` 为每个 (子问题 × 通道) 建任务，而每个任务遍历该
子问题的全部 action，于是同一条 action 被两个向量通道各记一次 target，撞 `uq_qa_target`。

那个组合**只有真实链路才产生**（3A 得真的产出 `KB_TARGETED` + `GLOBAL_FALLBACK` 那一对），
所以工单 08 的 17 条用例一条都没覆盖到，包括我自己补的 CFG-05。

**教训**：组件建好、契约建好，不等于系统能跑。**"接线"本身要有工单**，而且它往往是第一个
暴露上游设计问题的地方——因为只有它会产生真实的输入组合。

## 5. 隐私测试只有反向断言时永远绿

工单 11 里 `api02` 的隐私断言一开始是**假绿**：白名单没配 → `definition` 为 null → 参数表为空
→"`orderNo` 不出现"自然成立。

同一个陷阱在工单 14 又出现一次，这次是被**正向断言**抓出来的——`priv02` 断言"工具参数值
**应该**出现在响应里"，它红了，才发现白名单没配。

**教训**：隐私测试必须同时有正向与反向断言。只有"不该出现的没出现"那一半，会在功能压根没
生效时自动通过。这条 3A 复盘已经写过一次（§2），3B 又踩了两次——说明它不是"知道就能避免"的
那类问题，得靠**每写一条隐私断言就配一条正向断言**的机械习惯。

## 6. 新增门禁不反证，等于没有

工单 16 给 `check-deploy-contract.mjs` 加了两项检查（配置必须登记、计费测试必须守门）。加完
立刻反证：抹掉 README 里一条登记 → 报错点名该变量；拿掉 `RealRerankApiTests` 的
`@EnabledIfEnvironmentVariable` → 报错点名该类。

同样的做法用在工单 08 的两个 bug 修复（撤回修复后专项用例精确变红、其余不动）和工单 13 的
三条界面规则（临时加 `autoFocus`、改成 `dangerouslySetInnerHTML`，两条用例红）。

**教训**：守"某件事不该发生"的测试与门禁，第一次就绿是**默认可疑**的。反证一次的成本是分钟
级，收益是把"它真的在工作"从推测变成事实。

## 7. `.env` 让本地测试产生真实计费——这次是被接入放大的

3A 复盘已经记过一次（§4）。3B 又出现了新形态：把检索接进 turn 流程后，走到 `ACTIONS_READY` 的
E2E 会执行检索、检索要算查询向量，于是**三个 QA E2E 类每跑一次就打一次真实的阿里云 Embedding
接口**，本机 `.env` 的 Key 让它真的成功了。

证据很直接：补上 `FakeEmbeddingConfig` 后 `QuestionUnderstandingE2ETests` 耗时
**从 6.9 秒降到 1.3 秒**。

**教训**：`@EnabledIfEnvironmentVariable` 看的是 `System.getenv`，而 Spring 的 `Environment`
会加载 `.env`——**两者不是一回事**。前者守住了显式的收费测试，但守不住"某个改动让普通测试
间接调用了真实模型"。耗时突变是这类问题最好的探针。工单 16 把"收费测试必须守门"变成了 CI
检查，但"普通测试不得间接计费"目前仍然只靠人注意。

## 8. 有效的做法（继续保持）

- **规格冲突时先回文档，不在实现里裁决。** ADR 0008 决策 2 与架构 §9.4 自相矛盾（互斥激活 vs
  低置信度补充），修的是 ADR 而不是让代码迁就；契约 §12 把状态机终态搬到 HTTP 层，修的是契约。
- **"没有落点不得关闭"真的挡住了东西。** 6 条 no-coverage 都是"同前缀其余都齐、独缺这一条"的
  形态（`ch01~ch05`、`ch07` 都在就差 `ch06`），靠人扫一眼不可能发现。
- **不为不可达的场景写实现。** 三个"没有抛出点"的错误码，最后证明是契约错了而不是缺实现——
  当初硬造抛出点的话，就会同时留下错误的代码和错误的文档。
- **走查用 seed 而不是真实链路。** 零模型调用、可重复执行、场景齐全，而且资产留在仓库里，
  下次改界面能直接复用。
