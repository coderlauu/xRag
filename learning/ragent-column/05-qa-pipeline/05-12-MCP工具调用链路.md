# 《知识库答不了的问题，交给 MCP 工具去查》

> 原文链接：https://t.zsxq.com/mfPoB
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

实时数据（订单状态、物流轨迹、优惠券余额）不在知识库里而在业务系统里，KB 检索答不了；MCP 路径嵌在阶段 6 内部与 KB **并行**执行：`mcpToolId` → 注册表查执行器 → LLM 提参 → 远程调用 → 格式化成 `<data>` 块，与 KB 上下文一起汇入 `RetrievalContext`。

## 核心内容提炼

- **MCP 不是独立流水线，它嵌在阶段 6 `retrieve` 里**。意图识别阶段就已经判好了谁走知识库、谁走工具，阶段 6 只是各走各的路，最后汇合到同一个 `RetrievalContext`。

- **分流就两行**：`NodeScoreFilters.kb()` 与 `NodeScoreFilters.mcp()`，后者的条件是 `kind == MCP` **且 `mcpToolId` 非空**。

- **MCP 节点携带三个专属字段**：`mcpToolId`（关联注册表）、`paramPromptTemplate`（自定义参数提取提示词，可选）、`promptSnippet`（回答规则片段，可选，如"回答时附上订单编号和物流公司"）。

- **注册表就是一个 `Map<String, McpToolExecutor>`**，`@PostConstruct` 时把 Spring 容器里所有 `McpToolExecutor` Bean 注册进去。**注册表只管存，不管造**——执行器的创建是 `McpClientAutoConfiguration` 的事。

- **远程工具的注册发生在应用启动阶段**：读配置的 Server 列表 → Streamable HTTP 建连 → `client.initialize()` 完成协议握手 → `client.listTools()` 发现工具 → 为每个 `Tool` 建一个 `McpClientToolExecutor` 注册进表。

- **单个 Server 连接失败只打日志跳过，不影响其他 Server，更不影响应用启动**。理由写得很清楚：**MCP 工具是增强能力，不能因为一个工具服务挂了就让整个系统起不来**。`@PreDestroy` 负责关连接防泄漏。

- **执行器不抛异常，统一把失败包成 `isError=true` 的 `CallToolResult`**。上层因此不需要处理异常分支——所有返回都是同一个类型，只需检查 `isError` 标志。

- **两层异常兜底**：执行器内部 catch + `executeMcpTools()` 外层 catch。目的相同——单个工具失败不拖垮整个问答流程。

- **单工具调用四步**：`intentNode.getMcpToolId()` → `registry.getExecutor(toolId)` → `extractParameters(question, tool, customParamPrompt)` → `executor.execute(params)`。**参数提取是本篇有意留的黑盒**（下一篇）。

- **多个 MCP 意图并行执行**（`mcpBatchExecutor` 专用线程池，不与 KB 检索的池争资源），结果按 `toolId` 分组成 `Map<String, List<CallToolResult>>`——分组是为了后续格式化时能把结果关联回意图节点。

- **格式化的产物是带标签的文本块**：`<rules>`（来自 `promptSnippet`，可选）+ `<data>`（工具返回内容）。多子问题时再套一层 `<result index="1"><question>...</question><data>...</data></result>`。

- **成功与失败的结果分开渲染**：成功的直接拼，失败的用 `<errors>` 包起来。**让大模型看得见哪些工具挂了**，从而能给出"物流查询成功，但退货系统暂时无法访问"这类诚实回复，而不是装作没查过。

- **`RetrievalContext` 是两条路径的汇合点**，`mcpContext` 与 `kbContext` 是两个独立 String 字段，另有 `intentChunks` 保留原始 chunk 用于引用溯源。`hasMcp()` 会改变生成阶段的采样参数（0.3/0.8 vs 0/1）。

## 关键概念/术语

- **MCP（Model Context Protocol）**：与外部工具服务通信的协议，本篇只讲它在 Ragent 里的接入链路。
- **`McpToolRegistry`**：`toolId → McpToolExecutor` 的注册表。
- **`McpClientToolExecutor`**：持有 `McpSyncClient` 与 `Tool` 定义的远程调用执行器。
- **`CallToolResult`**：官方 SDK 的结果类型，`content` + `isError` 两个字段。
- **`promptSnippet`**：意图节点上的回答规则片段，渲染成 `<rules>` 注入上下文。
- **`RetrievalContext`**：KB 与 MCP 结果的统一载体。

## 与 xrag 项目的关系

- **本篇是待决策项 D-03 的定价单，读完应当能给出答案了。** 接一套 MCP 至少要做：SDK 依赖、Server 连接配置与启动期握手、工具注册表、执行器抽象、**每次调用多一次 LLM 参数提取**、结果格式化与错误合并、专用线程池、以及意图树上的三个 MCP 专属字段。这是一个完整的子系统，不是"顺手加个功能"。**而 xrag 当前连一个可用的 Chat 凭据都没有**——MCP 路径的参数提取环节要调 LLM，没有 Key 时它一步都跑不了。

- **xrag 已经有原生工具调用能力，这给了 D-03 一个原文没有的选项。** [`ToolDefinition`](../../../backend/src/main/java/com/app/ai/model/ToolDefinition.java) / [`ToolCall`](../../../backend/src/main/java/com/app/ai/model/ToolCall.java) / [`ToolResultMessage`](../../../backend/src/main/java/com/app/ai/model/ToolResultMessage.java) 都已存在，`ChatCommand` 的 `tools` 字段是一等参数，`OpenAiCompatibleChatProvider` 完整实现了 `tools` 请求体、`tool_calls` 响应解析、`ChatFinishReason.TOOL_CALLS`，**连流式的 tool-call 增量都解码了**。于是有两条路：
  - **A（原文路线）**：意图树把问题路由到某个 `mcpToolId`，再单独调一次 LLM 提参。**两次 LLM 调用，工具选择由意图分类决定。**
  - **B（原生 function calling）**：把工具定义直接交给 Chat，让模型在一次调用里同时完成"选哪个工具"与"参数是什么"。**一次 LLM 调用，工具选择由模型决定。**

  两者不是简单的优劣关系：A 的工具选择走的是意图树，可控、可审计、可用管理界面维护；B 更省一次调用且天然支持多轮工具编排，但工具选择变成黑盒。**原文选 A 是因为它把意图树当作全链路路由表（第 5 篇）；xrag 是否也要这样，是 Step C 的架构决策，应当写成 ADR。**

- **"MCP 工具是增强能力，不能因为它挂了就让系统起不来"与 xrag 的既有启动哲学完全一致**。`FlywayConfig` 迁移失败只记警告、`StorageConfig.ensureStorageBucket` 同理——**都是"启动不因依赖未就绪而崩溃"**。但 xrag 也已经记下了这个模式的代价：**依赖恢复后不会自动补跑，必须重启应用**。MCP 的工具注册若照抄，同样会有"Server 后来起来了但工具永远不在注册表里"的问题。**xrag 若做 MCP，应当把工具发现做成可重试或可手动触发的，而不是只在 `@PostConstruct` 跑一次。**

- **`RetrievalContext.intentChunks` 这个字段名指向了引用溯源，而第 9 篇的实现里它是坏的。** 第 9 篇 `retrieveAndRerank` 把同一份 chunks 塞给了每个意图，溯源信息实际已经丢失。[CONTEXT.md](../../../CONTEXT.md) 里「引用」是正式术语，xrag 要做引用就必须**从检索通道开始保留召回来源**——这条在第 9 篇笔记里已经记过，本篇是它的第二个证据点。

- **`<data>` / `<rules>` / `<errors>` 这套标签化上下文，xrag 可以直接借鉴且成本很低。** 它解决的是"模型怎么知道这段文本是什么"的问题，比用自然语言前缀（"以下是工具返回的数据："）更稳。**但要注意标签名与内容的注入风险**——如果工具返回的文本里本身含有 `</data>`，就能篡改上下文结构。原文没有做任何转义。xrag 若采用，**必须对工具返回内容做标签转义**，这属于第 14 篇 Prompt 组装该覆盖的安全边界。

- **`promptSnippet` 注入的是"回答规则"，它与检索到的"事实"混在同一个上下文里。** 第 5 篇解释过它存在的理由（多意图命中时没法用某一个节点的完整模板）。但把规则和数据放在同一个上下文块里，意味着**运营人员在意图树里写的一句话会直接成为 LLM 的指令**。这是一个真实的权限面：**能编辑意图节点的人就能改变系统的回答行为**。xrag 若做意图树管理界面（已确认本期要做），这条要写进 ui-spec 的权限与提示——至少让编辑者知道自己写的是指令而不是备注。

- **专用线程池的隔离理由在 xrag 依然成立，但池子数量要收敛。** 到本篇为止，原文已经出现了六个线程池：`intentClassifyExecutor`、`ragContextExecutor`、`ragRetrievalExecutor`、`ragInnerRetrievalExecutor`、`mcpBatchExecutor`，加上 Web 容器自己的。**每一个都有合理的隔离理由，但六个池子在单实例上共享同一批 CPU 与同一个数据库连接池**——隔离的是线程，不是真正的资源。xrag 应当**先算清楚真实的资源瓶颈（连接池 10 条、模型侧配额、并发许可）再决定要几个池**，而不是按调用点数量开池。

## 值得注意的设计取舍/坑

- **`DefaultMcpToolRegistry` 用的是普通 `HashMap` 且 `register()` 没有同步。** 启动期 `@PostConstruct` 单线程写入没问题，但接口上明明有 `register()` / `unregister()` 两个运行期可调用的方法——**只要有任何一处在运行时注册工具（比如管理界面动态接入一个新 Server），就是并发读写 HashMap**，可能死循环或读到脏数据。要么把 Map 换成 `ConcurrentHashMap`，要么把接口收窄到只允许启动期写入。**"接口暴露了运行期变更能力，实现却按启动期一次性写入来做"是最容易漏的那类不一致。**

- **`register()` 遇到重复 `toolId` 只打 warn 就覆盖。** 两个 MCP Server 各自暴露了同名工具时，后注册的静默胜出——**而注册顺序取决于配置文件里 Server 的排列顺序**。一次配置文件的顺序调整就能悄悄改变系统调用的是哪个后端。这类"顺序决定行为但没人知道"的耦合在第 8 篇也出现过（`toMap` 合并函数的 `>=`）。**xrag 应当把重复 toolId 视为配置错误直接启动失败**，理由与"Embedding 维度不一致时直接启动失败"完全同源——放行只会把问题推迟到运行时。

- **`executeSingleMcpTool` 在工具不存在时 `return null`，然后调用方用 `result == null ? null : ...` 过滤掉。** 结果是：**意图命中了某个工具，但工具没注册，用户什么都看不到**——上下文里既没有数据也没有错误说明，LLM 只会基于 KB 结果作答，仿佛这个意图从未存在。这与 `isError=true` 的显式失败处理形成了刺眼的对比：**远程调用失败会告诉模型，工具压根不存在反而静默**。而"工具不存在"恰恰是配置漂移的典型症状，最需要被看见。

- **参数提取要多调一次 LLM，这笔账在延迟预算里容易被漏掉。** 一次 MCP 调用 = 参数提取 LLM（~500ms）+ 远程调用（100~500ms）。而它与 KB 检索并行，**所以整个阶段 6 的耗时会从"检索的 165ms"跳到"MCP 的 1s"**。也就是说：**只要问题命中了任何一个 MCP 意图，检索侧那些并行优化的收益就全部被淹没了**。这为选原生 function calling（B 路线）提供了一个实打实的性能理由。

- **`mergeResultsToText` 里失败结果的文本直接来自异常 message**（`"远程调用失败: " + reason`）。异常 message 可能包含内部主机名、端口、堆栈片段、甚至连接串——**这些会原样进入发给大模型的 Prompt，也可能出现在最终答案里**。xrag 的 `ApiExceptionHandler` 已经有"只翻译显式抛出的 ApiException，未预期异常照常走 500"的纪律，同样的思路要延伸到这里：**给模型看的错误必须是脱敏的固定措辞，不是原始异常文本**。

- **本篇的例子在电商订单查询与 `sales_query` 之间来回切换**，原文自己说明了这是因为示例场景与代码实现不一致。这提醒一件事：**读这类教程时要区分"讲解用的场景"与"代码里真实存在的东西"**——第 8 篇的 `maxOptions=6` 死配置就是在示例与实现的缝隙里产生的。xrag 的规格文档要避免同样的问题，`ui-spec` 与原型里的示例数据应当来自同一套。
