# 《AI大模型Ragent项目》——如何在简历中呈现RAG项目？

> 原文链接：https://t.zsxq.com/h2E2h
> 所属分组：00-overview 项目概览与学习指南

## 一句话概括

这篇文章不讲技术原理，而是给学完 Ragent 项目的学员提供一份"简历/面试话术模板"：告诉你项目该起什么名字、简介怎么写、技术栈怎么列、以及每一项技术亮点该用什么句式描述成"个人职责"，目的是校招/社招面试时能把项目讲清楚、讲出深度。

## 核心内容提炼

- **项目改名建议**：作者给出多个可替换的项目名候选（如 RagentHub、Sage RAG 知识问答、AskFlow 智能问答引擎、RetriBot 检索机器人等），核心用意是让不同学员写出的简历项目名不完全一样，降低"简历撞衫"的概率，同时也提示项目定位可以是"智能检索与问答平台"这个大类。

- **项目简介给了两个版本**，对应两种简历表达策略：
  - 偏技术深度的版本：突出多路检索引擎、意图识别、查询重写、会话记忆、MCP 工具调用等能力点的堆叠，强调"多模型路由 + 熔断降级"支撑高并发稳定性，"分布式队列限流 + 全链路追踪"支撑可观测性。
  - 偏业务价值的版本：把同样的技术能力包装成"解决企业知识库检索效率低、信息孤岛问题"，突出双路召回（意图定向检索 + 全局向量检索）带来的高准确率问答体验。
  - 两版本的差异本质是"讲技术栈"还是"讲业务收益"，供应聘者根据面试官偏好（技术面 vs 业务面）二选一或组合使用。

- **技术栈清单（面试可背诵的关键词）**：SpringBoot、MyBatis Plus、Milvus（向量库）、Redis、Redisson（分布式锁/限流基础设施）、Apache Tika（文档解析）、Sa-Token（权限/鉴权框架）。这一串关键词本身就是简历"技术栈"栏的现成素材。

- **个人职责模板，逐条对应一个系统能力点**（这是全文信息量最大的部分，本质是把 Ragent 系统里已实现的技术方案，压缩成一句"问题—方案—效果"式的简历话术）：
  1. 检索层：意图定向检索 + 全局向量检索的双路召回，用 CompletableFuture 并行跑多个检索通道，后接去重、重排序的后处理流水线，解决单一检索方式召回覆盖率不足的问题。
  2. 限流层：用 Redis 信号量 + ZSET + Pub/Sub 实现分布式排队限流，靠 Lua 脚本保证"排队声明"这个操作的原子性，支持公平排队和超时拒绝，配合 SSE 把排队状态实时推给前端。
  3. 高可用层：三态熔断器做模型健康监控，配合优先级降级链和"流式首包探测"机制——某个模型连续失败到阈值就自动熔断切到下一候选模型，且对用户无感知。
  4. 链路上下文层：用 TransmittableThreadLocal（TTL）在异步线程池间透传用户上下文和 Trace 上下文，配置了 8 个专用线程池并用 TtlExecutors 包装，避免线程池资源竞争导致上下文丢失。
  5. 查询理解层：基于 LLM 做问题重写与拆分，支持多轮对话的上下文补全，把复杂问题拆成多个子问题并行检索，再配合术语归一化和规则兜底，解决用户口语化表达跟知识库标准术语对不上的问题。
  6. 会话记忆层：滑动窗口保留最近 N 轮对话，超过阈值后用 LLM 生成摘要持久化到 PostgreSQL，摘要压缩 + 窗口裁剪双重手段控制 Token 成本，避免长对话把上下文窗口撑爆。
  7. 文档处理层：基于"节点编排"的入库流水线——数据获取、文档解析、分块、内容增强、向量索引各是一个节点，节点间可视化连线配置，每个节点独立执行并记日志，支持条件跳转和环检测。
  8. 可观测性层：用 AOP 打点做全链路追踪，注解标记关键节点，维护调用层级栈并落库，记录 traceId、耗时、输入输出、异常信息，并靠上面提到的 TTL 机制解决异步场景下追踪链断裂的问题。
  9. 工具调用层：集成 MCP 协议，意图识别的结果关联到具体的 MCP 工具 ID，再用 LLM 自动提取工具调用所需的参数，支持并行调用多个 MCP 工具，把知识检索和外部系统调用打通。
  10. 意图识别层：基于 LLM 的树形意图分类器，意图树从 Redis 缓存加载，区分 KB（知识库）/MCP（工具）/SYSTEM 三类意图，识别置信度不够时主动反问用户澄清，而不是硬答。
  11. 幂等层：在 framework 层做"双维度"幂等——用注解防止表单重复提交，用 SpEL 表达式生成幂等 Key，底层靠 Redis 实现分布式幂等控制。
  12. 文档解析层：基于 Apache Tika 支持多格式文档（PDF/Word/Excel/Markdown）解析，分块策略上同时支持"固定大小分块"和"结构感知分块"两种，兼顾切分速度和语义完整性。
  13. 架构可扩展性：项目里落地了策略模式、工厂模式、责任链模式、装饰器模式等经典设计模式，让检索通道、后处理器、MCP 工具都可插拔替换，新组件靠 Spring 的自动发现机制零配置接入。

- **写简历的两条实操建议**：一是根据目标岗位所在行业调整项目场景包装（比如包装成银行客服系统、旅游助手等），因为 Ragent 本身能力是通用的，换个业务壁纸就能降低"简历重复率"；二是不要照抄模板原句，建议用 ChatGPT/Claude 等工具把模板改写成贴合自己实际做过的部分的个性化表达，避免面试官一看就知道是同款模板简历。

- 文中评论区提到的一个真实讨论点：把 Ragent 包装成"客服系统"是否合适——这说明"选一个具体、可信的业务场景来包装通用 RAG 能力"是学员普遍关心、也容易踩坑的环节（后续 00-05《简历上写AI项目，业务场景怎么选》一文会专门展开）。

## 关键概念/术语

- 双路召回：同时用"意图定向检索"（先判断该查哪个知识库/范围再检索）和"全局向量检索"（不限定范围的向量相似度检索）两条路径找结果，再合并去重，兼顾精准度和覆盖率。
- 三态熔断器：熔断器不止"开/关"两态，还有一个"半开"探测态，用于判断故障模型是否已恢复，是本文里高可用设计的关键词。
- 流式首包探测：在流式（SSE）调用大模型时，通过是否很快收到第一个数据包来判断该模型是否健康，作为熔断决策的信号之一。
- TransmittableThreadLocal（TTL）：阿里开源的 ThreadLocal 增强方案，解决线程池场景下 ThreadLocal 值无法跨线程（尤其是线程池复用线程）传递的问题，这里用于跨异步线程传递 Trace/用户上下文。
- 节点编排式入库流水线：把文档处理拆成可视化连线的多个独立节点（解析、分块、增强、索引等），强调流程的可配置和可观测，而不是写成一段固定代码。
- 双维度幂等：同时从"接口调用防重复提交"和"业务 Key 唯一性"两个维度做幂等控制，前者靠注解拦截，后者靠 SpEL 生成的 Key + Redis 实现。

## 与 xrag 项目的关系

这篇文章本身是"简历话术"向导，不是系统设计文档，但它把 Ragent 全系统的技术亮点做了一次高度压缩的清单式罗列，等于提前给出了 xrag 项目后续要覆盖的模块地图，可以作为设计阶段的"检查清单"使用：

- 检索模块要考虑双路召回（意图定向 + 全局向量）+ 并行执行 + 去重重排序，而不是单一检索通道。
- 限流/高并发控制模块要考虑分布式排队（Redis 信号量/ZSET/Pub-Sub + Lua 原子性）而不是简单的令牌桶，且要支持把排队状态实时推给前端（SSE）。
- 模型调度模块要设计三态熔断 + 优先级降级链 + 流式首包探测，这是"多模型路由网关"模块（对应 INDEX 里的 04-model-scheduling 分组）的核心设计点。
- 异步链路要提前规划好上下文传递方案（TTL + 专用线程池），并配套 AOP 埋点做全链路追踪，这两点在实现检索问答核心链路（05-qa-pipeline）时是绕不开的基础设施。
- 会话记忆、查询重写、意图识别（树形分类器）、MCP 工具调用、文档解析与分块、幂等控制——每一项都对应 xrag 后续要单独设计的子模块，具体落地时可以回来对照本文的职责描述反推设计要点。

整体上，这篇属于"目录级"参考：暂不直接指导某一模块的具体实现，但值得在做模块划分和技术选型时对照检查是否覆盖了这些点。

## 值得注意的设计取舍/坑

- 文章反复强调"改名 + 换业务场景包装"，反映一个现实问题：Ragent 是知识星球公开教学项目，学完的人很多，简历上如果原样照抄项目名和职责描述，容易被面试官识别为"模板简历"，可信度打折。这提示我们在整理 xrag 的对外呈现（如果未来也要用于简历/作品展示）时，同样需要有自己的业务包装和差异化叙述，而不是复述通用能力清单。
- 简介给出"技术深度版"和"业务价值版"两种写法，暗含一个取舍：纯堆技术名词的描述在技术面容易被追问细节（需要真的理解才能扛住），纯讲业务价值的描述则可能被质疑"实际技术含量"，如何组合取决于面试对象和自己对项目的掌握深度，没有标准答案。
- 评论区"包装成客服系统是否合适"的疑问没有在本文里得到解答，说明业务场景选择本身是个需要额外指导的独立问题（专栏后面有专文讨论），不能简单套用。
