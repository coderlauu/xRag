# 《AI大模型Ragent项目》——SSE协议与流式响应

> 原文链接：https://t.zsxq.com/IKMx1
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章把"能跑通"的大模型流式调用 demo（stream=true + BufferedReader 逐行读 data:）升级为"懂原理、扛得住生产"的水平：讲清 SSE 协议的完整规范、大模型 SSE 响应的数据结构细节，以及一个考虑了超时、容错、断线处理的生产级 Java SSE 客户端实现。

## 核心内容提炼

### 1. SSE 协议本质
- SSE（Server-Sent Events）是 WHATWG HTML 标准的一部分，定义了 `text/event-stream` 格式和浏览器 `EventSource` API，本质是**基于 HTTP 的单向服务端推送**：客户端发一次普通 HTTP 请求，服务端不关闭连接、持续推送事件，直到推送完毕或客户端断开。
- 与普通 HTTP（一问一答，返回即关连接）的区别是"一问多答"；标志性响应头是 `Content-Type: text/event-stream`。

### 2. SSE 完整字段格式（不只是 data:）
SSE 规范定义了 4 个字段 + 1 种注释，一个事件以**连续两个换行（空行）**结束，这是事件边界标志：
- `data:`：事件数据，核心字段。同一事件可以有多行 `data:`，会按 `\n` 拼接成一段内容。大模型 API 唯一常用的字段，每个 chunk 都有。
- `event:`：自定义事件类型，不写则默认是 `message`。大模型 API（OpenAI、SiliconFlow 等）基本不用，全靠 data 里的 JSON 内容区分；自建 SSE 服务端时才有用（用于区分 token/error/done 等事件）。
- `id:`：事件 ID，用于支持**断线重连**——客户端记住最后收到的 id，重连时在请求头带上 `Last-Event-ID`，服务端据此从下一个 id 继续推送。大模型 API 基本不用这个字段，原因是流式生成是一次性、有状态的过程（依赖服务端的 KV Cache），断了无法真正续传，只能重新发起整个请求。
- `retry:`：告知客户端断线后等多久重连（毫秒）。浏览器 `EventSource` 会自动按这个值重连（默认约 3 秒），但 Java/OkHttp 客户端不会自动处理，需要自己实现重连逻辑。
- 注释行（以 `:` 开头）：客户端直接忽略，主要用途是**心跳保活**——大模型思考时可能十几秒没有输出，中间的 Nginx/负载均衡/CDN 可能因为长时间无数据而主动断连，服务端定期发 `: keepalive\n\n` 之类的空注释可以防止这种误判超时。

四个字段里，大模型 API 几乎只用 `data:`，其余三个字段主要在自建 SSE 服务端（下一篇 Spring Boot 实战）时才用得上；理解全貌是为了排查问题（比如看到 `:` 开头的行知道那是心跳不是数据）。

### 3. SSE vs WebSocket vs 长轮询
三者的本质差异：长轮询仍是"一问一答"，只是服务端 hold 住请求直到有新数据才返回，不是真推送；SSE 是一次 HTTP 请求上的服务端单向持续推送；WebSocket 是 HTTP 握手升级后的独立全双工协议。

大模型 API 选 SSE 而非 WebSocket 的四点理由：
1. **方向匹配**：流式输出是纯粹的服务端→客户端单向推送，用户的问题已经在第一次 HTTP 请求里发完了，不需要 WebSocket 的双向能力。
2. **HTTP 原生兼容**：SSE 就是普通 HTTP 响应换了个 Content-Type，Nginx/CDN/负载均衡/API 网关都天然支持；WebSocket 需要单独配置 Upgrade 代理（如 `proxy_set_header Upgrade $http_upgrade`），在部分企业网络里还可能被防火墙拦截。
3. **自动重连内置**：SSE 规范自带 `Last-Event-ID` + `retry:` 重连机制，浏览器自动处理；WebSocket 断线重连要自己写。
4. **实现更简单**：SSE 只是按行输出文本；WebSocket 有自己的帧协议，要处理帧编解码、ping/pong、关闭帧，复杂度高出一档。

判断准则：只要是服务端向客户端持续推送，优先 SSE；只有客户端也需要主动、实时地向服务端发消息的场景（协作编辑、实时游戏、"对方正在输入"），才需要上 WebSocket。

### 4. 大模型流式响应的数据结构细节
- 非流式响应：`Content-Type: application/json`，一个完整 JSON，答案在 `choices[0].message.content`，`usage` 直接在响应体里。
- 流式响应：`Content-Type: text/event-stream`，多条 `data:` 行、每行一个 JSON，答案在 `choices[0].delta.content`（**增量**）；`role` 字段只出现在第一个 chunk 的 delta 里；`finish_reason` 只在最后一个 chunk 里有值（正常结束前全是 `null`）；连接持续推送直到收到 `data: [DONE]`（注意 `[DONE]` 不是 JSON，不能直接丢给 JSON 解析器，要单独判断）。
- 逐 chunk 拆解的关键细节：第一个 chunk 的 content 可能是空字符串甚至完全没有 content 字段（不同平台不一致，需要做兼容判断）；中间可能出现空 delta `{}`；`finish_reason` 除了 `"stop"`（正常结束）外，还可能是 `"length"`（触发 max_tokens 截断）、`"content_filter"`（被安全过滤截断）、`"tool_calls"`（转入工具调用），业务代码要按不同取值分别处理，不能只判断 stop。
- Token 用量统计在流式模式下没有统一方式，三种典型情况：①（如 SiliconFlow）附着在 `finish_reason: "stop"` 那个 chunk 里；②（如 OpenAI）需要请求里显式加 `stream_options: {"include_usage": true}`，之后会在流末尾多发一个 `choices` 为空数组、只带 `usage` 的 chunk；③部分平台流式模式下压根不返回 usage，`completion_tokens` 只能客户端按收到的内容自行估算，`prompt_tokens` 拿不到就是拿不到。接入新模型平台时必须先实测这三种情况里是哪一种，不能假设。

### 5. 生产级 Java SSE 客户端要补的短板
入门 demo（`BufferedReader.readLine()` 逐行判断 `data:` 前缀）缺的五类东西：超时控制、错误处理、回调机制（不能只 `System.out.print`）、Token 统计、边界情况容错（空 delta、缺字段、JSON 解析失败）。文章给出的实现要点：
- **回调接口设计**：`StreamCallback` 定义 `onToken`（每个增量）、`onComplete(fullContent, usage)`（正常结束）、`onError(exception, partialContent)`（出错但带上已收到的部分内容，不能让调用方两手空空）。
- **OkHttp 的 readTimeout 在流式场景下语义变了**：不再是"拿到完整响应的总耗时上限"，而是"两次数据读取之间的最大等待间隔"。建议设 30~60 秒——太短（如 5 秒）容易把模型深度思考的停顿误判为超时，太长（如 300 秒）会导致真正卡死的请求要等很久才被发现。`connectTimeout`/`writeTimeout` 不受流式影响，正常设 10~15 秒即可。
- **解析细节**：跳过空行和 `:` 开头的注释行；`data:` 前缀之后按规范最多去掉一个可选空格再取内容；命中 `[DONE]` 单独判断退出循环，不当 JSON 解析；单个 chunk JSON 解析失败时只跳过该 chunk 继续处理后续数据，不能让整条流因为一个坏包而崩掉。
- **粘包问题不用自己处理**：SSE 走 HTTP chunked transfer encoding，一次 TCP 传输可能包含多个 `data:` 行，也可能把一行截断成两次传输；只要用 `BufferedReader.readLine()`，它会自动按换行符分割保证读到完整行，没必要为了"性能"改用原始 `InputStream.read(byte[])` 自己处理行边界。
- **连接中断的处理策略**：大模型流式生成依赖服务端的 KV Cache 状态，断线后无法真正续传，只能整个请求重新发；代码上要区分"正常结束"（收到 `[DONE]`）和"异常 EOF"（`readLine()` 返回 null 但没收到 `[DONE]`，判定为异常），异常时把已收到的部分内容通过 `onError` 回调传回，交给调用方决定是重试还是直接展示部分结果。重试本身是安全的（对话类请求语义上无副作用，可视为幂等），但如果请求链路里带有 Function Call 触发的外部系统操作，重试前要额外小心副作用。

## 关键概念/术语

- SSE（Server-Sent Events）：基于 HTTP 的单向服务端推送协议，规范属于 WHATWG HTML Living Standard。
- `text/event-stream`：SSE 响应的标志性 Content-Type，客户端据此按 SSE 规则解析响应体。
- `delta`：流式 chat completion 响应里表示"本次增量内容"的字段（与非流式的完整 `message` 字段相对）。
- `finish_reason`：标识一次生成为何结束的字段，取值包括 stop/length/content_filter/tool_calls，仅出现在流的最后一个 chunk。
- `Last-Event-ID`：SSE 断线重连时客户端在请求头里带上的、记录已收到的最后一个事件 id 的字段，用于让服务端从断点继续推送。
- `stream_options.include_usage`：OpenAI 流式接口里用来要求在流末尾额外返回 Token 用量统计 chunk 的请求参数。
- 心跳保活（keepalive comment）：SSE 里以 `:` 开头、客户端会忽略的注释行，用于防止中间代理因连接空闲太久而主动断开。

## 与 xrag 项目的关系

当前 xrag 后端（`backend/`，Java）只有健康检查接口，尚未实现问答 API，也没有 SSE/`EventSource`/`SseEmitter` 相关代码；Git 历史里的轮询问答属于重置前已删除的 TypeScript 系统，不能当作当前实现。这篇笔记为未来从零设计流式问答接口（打字机效果）提供了直接的技术基础：

- 如果要接大模型的流式 API（OpenAI 兼容接口），本文里关于 `delta`/`finish_reason`/`[DONE]`/usage 三种获取方式的细节，是编写解析代码时必须处理的边界情况清单，可以直接对照检查现有或将来的调用代码是否漏了空 delta、`[DONE]` 特殊判断、usage 兼容等。
- 如果未来要让后端自己对前端暴露 SSE 接口（Java 后端同时是大模型 API 的 SSE 客户端 + 前端浏览器的 SSE 服务端），下一篇 Spring Boot `SseEmitter` 实战会更直接相关；但本文已经预警了一个关键的部署坑：项目 `deploy/nginx/web.conf` 和 `deploy/caddy/Caddyfile` 是现有的反向代理配置，如果启用流式接口，需要检查这两处是否开启了响应缓冲（Nginx 对应 `proxy_buffering`/`X-Accel-Buffering` 之类的配置项）——否则即使后端逐 token 推送正确，前端也可能看到"卡顿一下、一坨输出"而不是真正的打字机效果。
- 文中"Java 客户端 readTimeout 在流式场景下是两次读取之间的最大间隔，建议 30~60 秒"的结论，以及断线后不能续传只能整请求重试的结论，可以直接作为 xrag 后端调用上游大模型 API 时的超时/重试参数设定依据。

## 值得注意的设计取舍/坑

- **大模型 API 是 SSE 规范的"最小子集用户"**：只用 `data:` 字段，`event:`/`id:`/`retry:` 几乎不用。容易被误导为"SSE 就是 data: 格式"，但如果要自建 SSE 服务端（给自己的前端推送），这几个字段的价值（自定义事件类型、断线续传、指定重连间隔）才会体现出来。
- **`id:`/断线重连机制对大模型场景基本失效**：因为生成过程有状态（KV Cache 在服务端），断线不能真正续传，只能整个重新请求——这是一个反直觉点，SSE 规范本身设计了断点续传能力，但在 LLM 流式生成这个具体场景下用不上。
- **OkHttp 不会像浏览器 `EventSource` 一样自动按 `retry:` 重连**，容易被新手忽略，需要在 Java 客户端里自己实现重连/重试逻辑。
- **readTimeout 语义陷阱**：非流式场景下 readTimeout 是"总响应时间上限"，流式场景下变成"两次读取之间的最大间隔"，如果照搬非流式的超时设置容易在长文本生成场景下过早超时，或者设置过大导致故障发现延迟。
- **反向代理响应缓冲是最容易踩、也最容易被忽视的坑**：客户端和服务端代码都完全正确，中间只要 Nginx/负载均衡开了响应缓冲，前端体验上依然会变成"憋一下再一坨输出"而不是逐字流式，这个问题往往要等到线上环境才会暴露。
- **重试的幂等性边界**：大模型对话类请求可以放心重试（无副作用），但一旦请求链路涉及 Function Call 触发的外部系统操作，重试前需要额外确认是否会产生重复副作用。
