# 15 — 分块批量启用/禁用

**What to build:** 用户勾选一批分块，一次性启用或禁用。

这是本模块设计含量最高的一个接口：批量 Embedding 调用的耗时随数量线性增长，因此**必须用编程式事务**把它挪到事务外，用 `@Transactional` 注解会让数据库连接在等待 API 响应期间被长时间占用。

**Blocked by:** 14（分块新增与单条启禁用）

**Status:** done `2026-07-25`

- [x] 后端 `PATCH /api/v1/documents/{docId}/chunks/enabled`，返回 `{requested, changed, alreadyInTargetState}`
- [x] **`chunkIds` 必填**，不支持"全部启用/禁用"（那个需求应该用文档级接口，语义更准确）
- [x] 单次上限 500 条，超限返回 `400`
- [x] **任一 id 无效或不属于该文档 → 整批失败返回 `400`**，不静默跳过。放宽成"跳过无效的继续处理"会让调用方以为 500 个都处理了、实际只处理了 498 个
- [x] 只处理 `enabled <> 目标值` 的分块，已是目标状态的计入 `alreadyInTargetState`；**全部已是目标状态时正常返回 `changed: 0` 而不报错**
- [x] 启用/禁用两条路径都是"精准写入/精准删除"，只处理本次变更的分块，**不做全量重建**（必须与单条接口的策略一致：如果全量重建对批量是必要的，单条也该做；如果不必要，批量也没必要）
- [x] **用 `TransactionOperations` 编程式事务**，批量 Embedding 在事务外算完，事务内只有数据库写入 + 向量操作
- [x] **方法本身不能加 `@Transactional`**——否则内部的 `executeWithoutResult` 会加入外层事务，精确控制事务范围的意图就落空了。这一点在代码注释中说明
- [x] 前端：分块列表多选 + 批量操作按钮，操作前展示"已选中 N 个，其中 M 个将发生状态变化"，操作后用响应的 `changed` 二次确认
- [x] 集成测试：501 条返回 `400`；含一个不存在的 id 时整批失败且**数据库无任何变更**；含一个属于其他文档的 id 时同样整批失败
- [x] 集成测试：3 个分块中 1 个已是目标状态，返回 `{requested:3, changed:2, alreadyInTargetState:1}`
- [x] 集成测试：全部已是目标状态时返回 `changed: 0` 且 HTTP `200`（不是错误）
- [x] `./mvnw -q -B verify` 与 `pnpm build && pnpm lint` 通过

### 把 CHK-36 从手工项变成了自动化断言

工单和测试矩阵都把"Embedding 在事务外"列为手工验证：跑一个 200+ 分块的任务，同时反复执行 `psql` 盯 `pg_stat_activity` 里有没有 `xact_age` 持续增长的连接。那个办法能覆盖异步入库链路，但对同步接口既贵又容易漏。

改成在假 Embedding 实现里记录**调用时刻 `TransactionSynchronizationManager.isActualTransactionActive()`**，一条测试同时守住三条同步路径（编辑分块 / 新增分块 / 批量启用）。

**这条断言的价值验证过**：临时给 `setEnabledBatch` 加上 `@Transactional` 重跑，测试立刻红在"批量启用"那条上（`Expecting value to be false but was true`），随后还原。这正是这条纪律最典型的破坏方式——加了注解之后内部的编程式事务会静默地加入外层事务，边界一路扩张到整个方法把网络调用圈进去，**没有任何报错**。

### 整批失败的三种触发方式合成了一条测试

不存在的 id、属于其他文档的 id、已逻辑删除的 id（CHK-33 / CHK-34 / DEL-09），三者走同一条判定：`findAllByDocIdAndIds` 返回的行数少于请求的去重数就整批拒。测试里最关键的不是三次 400，而是最后那两行断言——**合法的那个分块 `enabled` 未变、向量行仍在**。只断言 400 的话，"先改一部分再报错"的实现也能过。

### 归属校验与查询合并成一步

`findAllByDocIdAndIds` 的 SQL 里同时带 `doc_id = ?` 和 `id in (...)`，不先查再比对归属。少一次查询是次要的，主要是**没有"查到了但归属不对"这个中间状态**要处理。

### 重复 id 的处理

同一个 id 传两次不是错误，但它只对应一个分块。用去重后的集合做校验与计数，`requested` 报去重后的数量——这样 `requested === changed + alreadyInTargetState` 恒成立。若用原始条数，传 `[1,1,2]` 会得到 `requested:3` 而 `changed+already` 只有 2，三个数字自相矛盾。已单独一条测试守住。

### 前端

确认框的数字用**已加载列表本地算出**，toast 用后端返回的**实际**数字（ui-spec §6 的要求）。两者通常一致；不一致就说明在用户确认的这几秒里数据被别处改动了，此时用户看到的是真实结果而不是自己以为的结果。

500 上限在界面上先拦（超限时批量按钮禁用 + 提示），不等后端报 400。实际上单页 20 条，靠界面选不出 500 个——保留这个守卫是因为 ui-spec §6 明确要求，且它与后端上限是同一个常量语义。
