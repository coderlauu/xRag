# 《AI大模型Ragent项目》——多轮对话记忆设计

> 原文链接：https://t.zsxq.com/mBDLI
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章解释了"大模型没有记忆，多轮对话的记忆感完全是应用层把历史消息重新塞进 messages 数组实现的"这一根本事实，并在此基础上系统梳理了五种会话记忆策略（完整历史、滑动窗口、Token 截断、摘要压缩、混合策略）、RAG 场景下 System Prompt / 历史 / 检索上下文 / 生成空间四者的 Token 预算分配方法，以及会话存储的选型方案（内存/Redis/MySQL），并给出对应 Java 实现示例，为下一篇《Query 改写》埋下伏笔。

## 核心内容提炼

- **大模型 API 本质是无状态的**：每次请求都是独立的，模型不保存任何对话状态，不知道"上一轮说了什么""这个用户是谁"。ChatGPT 等产品呈现出的"记忆"，实质是把此前所有的 user/assistant 消息重新打包进 `messages` 数组一起发给 API，模型每次都是"从头看一遍全部历史"，记忆的管理责任完全在应用代码侧，不在模型侧。文中用 iPhone 16 Pro 退货政策→保修期的追问案例说明：一旦第二轮请求漏发第一轮的历史消息，模型看到"那它的保修期呢"这种带指代的问题会直接反问用户"请问您想了解哪款产品"。

- **Token 膨胀是会话记忆要解决的核心矛盾**：如果无脑把所有历史都塞进去，随着轮次增加历史消息的累计 Token 会持续增长（文中示例：第 10 轮累计约 2,500 Token，第 20 轮约 5,000 Token）。而 RAG 系统每次请求除了历史，还要额外挤入 System Prompt（约 500~1,000 Token）、检索到的 Top-K chunk 内容（约 2,000~5,000 Token）、以及模型生成答案要预留的空间（约 500~2,000 Token）。几者叠加，第 10 轮总 Token 就可能到 7,500，第 20 轮到 10,000，用户聊满 50 轮时总 Token 很容易冲到 15,000~20,000，直接导致两个后果：小上下文窗口模型（4K/8K）直接报错超限；大窗口模型则是每轮都在为"重复发送旧消息"付费，成本随轮次线性甚至更快增长。

- **五种会话记忆策略**（按信息保留与实现复杂度递增排列）：
  1. **完整历史**：所有消息一条不丢，信息零丢失但 Token 无限膨胀，只适合能确定对话轮数不超过 5 轮的简单场景（如一问一答 FAQ）。
  2. **滑动窗口**：只保留最近 N 轮，超出的历史直接丢弃，实现简单、Token 上限固定，但早期关键信息（如用户在第 1 轮提过的订单号）到窗口滑出后永久丢失。N 的取值没有标准答案，文中给出经验参考：简单 FAQ 3~5 轮，电商客服 5~8 轮，技术支持 8~10 轮，法律/金融等复杂咨询 10~15 轮（且建议配合摘要压缩），起步经验法则是"从 N=5 开始，按实际反馈调整"。
  3. **Token 截断**：滑动窗口按"轮数"截断的问题是各轮长度差异很大（一句"好的"两个 Token，一次商品描述贴图可能 500 Token），按轮数无法精确控制总 Token。Token 截断改为设一个 Token 上限（如 4,000），从最新消息往前累加，一旦超出上限立即停止纳入更早的消息。关键约束：必须**成对丢弃**——同一轮的 user 和 assistant 消息要一起保留或一起丢弃，否则模型会看到"没有对应问题的回答"而产生混乱。Token 估算给出的简化公式是中文字符数 × 1.5 + 非空白字符数 / 4（不依赖 tokenizer，因为多数国产模型没有公开、通用的 tokenizer 可用，Java 生态也缺少现成库）。
  4. **摘要压缩**：不丢弃早期对话，而是调用大模型把它压缩成一段简短摘要（类比"同事工单交接说明"），原本 20 轮、约 5,000 Token 的对话可能压缩到 200~500 Token，但关键实体（产品名、订单号、日期、金额）、已确认结论、未解决问题都保留下来。摘要 Prompt 明确要求："保留核心意图和关键实体、保留已确认结论、保留未解决问题、省略寒暄和重复确认、第三人称、控制在 200 字以内"。压缩后的摘要以一条独立的 system 消息插入 messages 靠前位置。触发时机三种方式：按轮数（简单但不灵活）、按 Token 阈值（如超过 3,000 Token 触发，文中推荐）、按话题切换（效果最好但检测本身有难度）。摘要压缩会引入额外的一次 API 调用（有延迟和费用成本），文中建议用小模型（如 Qwen2.5-7B-Instruct）来做压缩以降低成本。
  5. **混合策略（推荐，Ragent AI 项目实际采用）**：早期对话压缩为摘要 + 最近 N 轮保留完整原文，摘要负责"长期记忆"（不完全丢失早期信息），最近几轮完整对话负责"短期精度"（保证模型理解当前话题的具体细节）。文中给出的 messages 结构示例是：一条 system 角色定义 + 一条 system 摘要（前缀"【对话背景摘要】"）+ 最近 1~2 轮的完整 user/assistant 消息 + 当前问题。

- **五种策略的定性对比**：完整历史（Token 无控制、信息完整、复杂度极低、无额外调用，适合≤5轮）；滑动窗口（按轮数控制、丢失早期、复杂度低、无额外调用，适合大多数客服场景）；Token 截断（按 Token 精确控制、丢失早期、复杂度中、无额外调用，适合消息长度差异大的场景）；摘要压缩（大幅压缩、保留关键信息、复杂度高、每次压缩需 1 次额外调用，适合长对话/需要长期记忆）；混合策略（精确可控、长期摘要+短期完整、复杂度高、触发时 1 次额外调用，适合生产级系统）。

- **RAG 场景下的 Token 预算分配**：上下文窗口必须同时装下 System Prompt、对话历史/摘要、检索上下文（chunks）、当前用户问题、预留生成空间这五部分。文中以 32K 窗口给出一个具体分配示例：System Prompt 1,000、对话历史/摘要 4,000（摘要+最近 3~5 轮）、检索上下文 5,000（Top-3~5 chunk）、当前问题 100、生成预留 2,000，合计约 12,100，只用了窗口的 30%~50%——刻意留有余量，因为 Token 越多延迟越高、费用越贵。文章特别提醒一个容易被忽视的点：**上下文窗口 = 输入 Token + 输出 Token**，生成预留空间也要占用总窗口预算，不能只算输入侧。

- **预算紧张时的取用优先级（从高到低）**：System Prompt（不能省，否则模型可能编造答案或超出知识库范围乱答）＞ 预留生成空间（不够会导致回答被截断）＞ 最近 2~3 轮完整对话（理解当前指代的关键，如"那它呢"）＞ 检索上下文（RAG 的核心价值所在，缺失等于 RAG 失效）＞ 更早的历史对话（优先级最低，可摘要压缩或直接丢弃）。

- **动态调整思路**：根据当前对话历史已占用的 Token 数，动态反算留给检索 chunk 的 Token 预算（`可用chunk预算 = 总预算 - System - 生成预留 - 当前问题 - 历史Token`，并设一个最小保底如 500 Token 保证至少能放 1 个 chunk）。效果是对话刚开始时可以多召回几个 chunk（信息更丰富），对话后期历史 Token 变多时自动减少召回数量或触发摘要压缩腾出空间。

- **会话存储方案选型**：
  - 内存（HashMap/ConcurrentHashMap）：读写最快，但服务重启数据全丢、只能单机用，适合开发调试。
  - Redis：序列化后存 JSON，天然支持 TTL 过期清理，支持多实例共享（分布式），生产环境常用方案。
  - MySQL：按消息逐条建表存储（`session_id`/`role`/`content`/`token_count`/`created_at`），持久化、可审计、可做数据分析（如统计平均对话轮数），但读写性能相对较低。
  - 生产推荐组合：**Redis 做主存储（对话进行中，快速读写）+ MySQL 做归档（对话结束后异步持久化）**；即使 Redis 缓存过期或被清理，只要用户没有主动删除会话，仍可以从 MySQL 里取回历史继续对话。

- **Java 实战示例的工程要点**（用 OkHttp + Gson 调用 SiliconFlow 的 Qwen3-8B）：
  - 无记忆 demo 每轮独立发送、不带历史，直观展示第二轮模型答非所问；有记忆 demo 用一个不断 append 的 `List<JsonObject> history` 承载全部消息并逐轮追加，能正确理解"它"指代之前提到的产品。
  - `SlidingWindowMemory` 类：按 `sessionId` 存消息列表，`getRecentMessages` 只取最后 `maxRounds * 2` 条消息（一轮=user+assistant两条），`buildMessages` 组装 system + 最近历史 + 当前问题。
  - `SummaryMemory` 类：每次 `addMessage` 后估算当前会话总 Token，超过 `tokenThreshold` 就触发 `compress`——把超出 `keepRecentRounds` 轮之外的早期消息拼成文本，连同"已有摘要"一起发给模型生成新摘要，再用新摘要替换旧摘要、并把 `store` 里的消息裁剪为只保留最近的完整轮次。

- **效果对比实验**（同一场景：用户围绕 iPhone 16 Pro 连续问 6 个问题）：无记忆模式在第 2 轮就答非所问；滑动窗口（N=3）能记住窗口内的近期信息（如第 5 轮问"它多少钱"能答对第 3 轮提到的价格），但第 6 轮问"第一次说的起售价"时因为第 1 轮已滑出窗口而答不出来；摘要压缩模式把早期 4 条消息压缩成摘要后，第 6 轮仍能通过摘要正确答出最初的起售价——直观证明了"摘要压缩能保留滑动窗口会丢的关键信息"。

- **生产环境的三个注意事项**：
  1. 会话超时清理——内存可用 Caffeine/Guava Cache 的过期机制或定时扫描；Redis 直接设 TTL（如 30 分钟）；数据库场景可以用定时任务清理或标记会话为"已关闭"，否则内存/Redis 会无限增长直至 OOM 或内存不足。
  2. 敏感信息处理——对话历史可能含身份证号、手机号、银行卡号等，需要脱敏存储（如手机号打码显示）、加密存储、并做访问控制与日志审计，金融/医疗等合规场景尤其要重视。
  3. 可观测性——需要监控每轮 Token 消耗构成（历史/检索各占多少）、是否触发过摘要压缩及压缩前后 Token 变化、响应时间在压缩/检索/生成各环节的耗时占比、以及"记忆命中率"（用户追问是否被正确理解，需人工抽检或用户反馈统计），这些指标用来发现摘要丢关键信息、或窗口/阈值设置不合理等问题。

- **结尾埋下的下一篇钩子（Query 改写）**：文章明确指出会话记忆只解决了"模型记住了什么"，但没解决"检索系统看到的还是原始的模糊追问"这个问题——比如"那它的保修期呢"这句话本身几乎没有语义信息，直接拿去做向量检索召回效果会很差。下一篇要讲的 Query 改写，就是结合对话历史把这种指代不明的追问自动改写成语义完整的检索 query（如改写成"iPhone 16 Pro 的保修期"）后再送去检索，是让多轮对话下的 RAG 检索不掉链子的必要补充步骤。

## 关键概念/术语

会话记忆（Conversation Memory）：应用层通过维护并在每次请求时重新发送历史消息，让本身无状态的大模型 API 呈现出"记得之前聊过什么"效果的机制。
Token 膨胀：随对话轮次增加，历史消息累计占用的 Token 持续增长，挤压检索上下文和生成空间预算的问题。
完整历史（Full History）：把全部对话历史原样塞进 messages 数组，不做任何裁剪的记忆策略。
滑动窗口（Sliding Window）：只保留最近 N 轮完整对话、更早轮次直接丢弃的记忆策略。
Token 截断（Token Truncation）：按精确 Token 预算而非轮数、从最新消息往前保留历史，且要求同一轮的 user/assistant 消息成对保留或丢弃的策略。
摘要压缩（Summary Compression）：调用大模型把早期对话压缩为一段保留关键实体和结论的简短摘要，用于替代原始历史消息的策略。
混合策略：早期对话摘要化 + 最近 N 轮保留完整原文，兼顾长期信息保留与短期上下文精度的记忆方案（Ragent AI 项目实际采用）。
Query 改写：下一篇文章的主题，指结合对话历史把含糊指代的追问改写为语义完整、可直接用于检索的查询。

## 与 xrag 项目的关系

- 这篇文章是 xrag 多轮对话/会话记忆模块的直接设计依据：应在构建发给模型的 `messages` 时显式实现历史裁剪或压缩逻辑，不能假设模型或框架会自动处理记忆——记忆管理必须落在 xrag 自己的应用代码（或 Spring AI 提供的对应抽象）里。
- 落地建议优先级：可以先实现滑动窗口作为 MVP（实现成本低、效果对大多数场景够用），再按需要叠加摘要压缩形成混合策略；需要提前设计好 Token 预算的四段式分配（System Prompt / 历史或摘要 / 检索 chunk / 生成预留），并实现一个简单的 Token 估算工具（哪怕只是文中的字符数估算公式）用于动态裁剪和动态调整检索 chunk 数量。
- 存储层选型可直接参考文中"Redis 主存储 + MySQL 归档"的生产方案：开发阶段可先用内存或简单 Redis 起步，上线前补齐 TTL 过期清理和归档持久化，避免会话数据无限增长。
- 文章结尾提到的 Query 改写是本篇记忆模块的强下游依赖：设计当前会话记忆接口时应预留"改写后的检索 query"这一输出字段/环节，为后续接入 Query 改写模块做好接口准备，避免记忆做好了但检索侧仍在用原始模糊问题去召回。
- 敏感信息脱敏、访问控制、可观测性指标（Token 消耗构成、摘要压缩命中率、记忆命中率）这几点应作为 xrag 会话记忆模块从"能跑通"到"生产可用"的验收清单，在设计阶段就预留埋点位置。

## 值得注意的设计取舍/坑

- 完整历史策略只适合能确定对话不超过 5 轮的简单场景，否则 Token 会失控，轻则成本飙升，重则直接超出上下文窗口报错。
- 滑动窗口按"轮数"而非"Token 数"截断，无法应对单轮消息长度差异悬殊的场景（比如某一轮用户贴了一大段商品描述），这种情况应换成更精确的 Token 截断策略。
- Token 截断必须成对丢弃 user/assistant 消息，只丢弃一半会让模型看到"没有对应问题的回答"，导致理解混乱——这是实现时容易忽略的硬约束。
- 摘要压缩本身会引入额外的大模型调用开销（延迟+费用），触发时机选"按 Token 阈值"比"按轮数"更精确，"按话题切换"理论效果最好但话题切换检测本身就是一个有难度的独立问题，工程上不一定值得优先做。
- 容易被忽视的一点：上下文窗口 = 输入 Token + 输出 Token，规划预算时必须把生成预留空间也计入总窗口上限，不能只按输入侧的历史+检索来算。
- 评论区的两点讨论值得留意：一是历史会话存储选 MySQL 还是 Elasticsearch，多数意见认为 ES 是搜索引擎，适合有全文检索/召回需求的场景，单纯存储历史对话用 MySQL 性价比更高，追求性能可考虑 Redis，"没有最好的技术，只有最好的场景"；二是本文实现的是以单次会话为单元的"短期记忆"，并未涉及跨会话的长期记忆，评论普遍认为当前多数产品都是"以一个会话作为一个记忆单元"，跨会话长期记忆容易让上下文过于混乱，是更复杂的独立课题，文章本身也未展开。
- 文章结尾指出的关键陷阱：会话记忆只解决了模型"记住了"的问题，检索系统依然是拿用户原始的、指代不明的追问去做向量检索，语义信息不足会导致召回效果变差——记忆设计和检索 Query 改写是两个必须配套解决的问题，只做记忆而不做改写，多轮对话下的 RAG 检索仍然会掉链子。
