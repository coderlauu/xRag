# 《AI大模型Ragent项目》第6小节：数据分块Chunk策略与实践

> 原文链接：https://t.zsxq.com/baxAh
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章回答"为什么要把长文本切块、怎么切才对"：先说明直接把整份文档塞给大模型会同时撞上上下文窗口限制和检索精度（大海捞针）两堵墙，因此需要先把文本切成可检索的小块（Chunk），再系统梳理了固定大小、重叠、递归、语义、混合五种主流分块策略的原理、优缺点和适用场景，并给出 chunkSize/overlap 的经验取值和企业级实践中容易踩的坑。

## 核心内容提炼

- **为什么不能整篇文档直接丢给大模型——两堵墙**：
  1. **上下文窗口限制**：当前主流模型上下文窗口大约在 128K～1M token 之间，但一份 200 页文档的纯文本量轻松超过 30 万字，远超窗口上限，直接后果是塞不进去、被截断，或成本显著上升。文章特别提醒：上下文窗口从 128K 涨到 1M 用了不到一年，但窗口是否应该无限做大仍待观察——从成本、延迟、实际效果看，token 并不是越多越好。
  2. **检索精度问题（大海捞针）**：即便窗口足够大能装下整份文档，模型也要从几十万字里自己找出与问题相关的那几段，信息噪音太大，容易抓不住重点或把无关内容混进回答。而且即使上下文做到 1M token，很多在线客服类场景仍会倾向用 RAG，原因是全量长 Prompt 会明显拉高成本、延迟，且降低吞吐。
  - 结论：RAG 的思路是"先检索出最相关的几段、只把这几段喂给模型"，但要检索就必须先有"可检索的单元"——整份文档粒度太粗，必须先切成聚焦单一知识点的小块，这正是分块（Chunking）要解决的问题。

- **分块在 RAG 数据处理流程中的位置**：上一篇用 Apache Tika 从 PDF/Word 等格式中抽取出的纯文本只是"原材料"，分块是紧接在文本抽取之后、向量化之前的一步。文章强调一个关键判断：分块质量是检索质量的天花板——块切得好，检索才可能准；块切烂了，后续任何检索或生成层面的优化都补不回来。

- **两个必须搞清楚的参数：chunkSize 与 overlap**：
  - **chunkSize（块大小）**：每个块的长度上限（字符或 token）。核心权衡是"块太大→信息多但检索易混入不相关内容、精度下降；块太小→精准但容易把一个完整意思切断、丢失上下文"。文章给出的常见范围是 200～1000 字符，具体取决于文档类型和检索需求。
  - **overlap（重叠）**：相邻两个块之间共享的文本长度，用来缓解"关键信息恰好落在切割边界、被拆成两半、两个块都检索不到完整答案"的问题。文章用一段电商退货政策文本举例：chunkSize=40 且不加 overlap 时，"七天无理由退货"这个关键短语被硬生生切进两个块，任一块都不完整；加上 overlap=15 后，块与块之间产生重叠区域，该短语能在至少一个块里保持完整。overlap 也不是越大越好，太大会导致大量重复文本、显著增加存储和计算成本；经验值是 overlap 设为 chunkSize 的 10%～25%。
  - **字符 vs token 的单位区分**：字符是肉眼可见的每个符号；token 是大模型实际处理文本的最小单位，英文常见单词多为 1 个 token，中文一个汉字通常对应 1～2 个 token。因为大模型的上下文窗口是按 token 计的，如果用字符数设定 chunkSize，中文场景下实际消耗的 token 可能比预期更多；入门阶段用字符数设 chunkSize 已经够用，后续可再切换到基于 token 的分块。

- **五种主流分块策略（以一段约 600 字符、包含退货/换货/会员/物流/售后 5 个章节的电商知识库示例文本贯穿讲解）**：
  1. **固定大小分块（Fixed Size Chunking）**：不管内容，每隔固定字符数切一刀，实现是从头开始按 chunkSize 依次截断、互不重叠。优点是实现极简、性能好、无需任何 NLP 处理；缺点是完全无视文本结构，容易把句子/段落从中间切断。适合日志等结构不重要的纯数据文本，或作为其他策略的兜底方案；不适合有明确段落结构的知识库、手册、政策文件。
  2. **重叠分块（Overlapping Chunking）**：在固定大小分块基础上引入 overlap，本质是把"每次前进 chunkSize"改成"每次前进 chunkSize-overlap"，让相邻块产生重叠区域。优点是能有效缓解边界处的语义断裂；缺点是依然不理解文本内容，只靠重叠弥补，且会增加存储量。适合还没确定用什么策略时的通用入门方案；不适合法律条款、合同这类对语义完整性要求很高的场景。
  3. **递归分块（Recursive Chunking）**：目前实践中最常用的策略。维护一份按优先级从高到低排列的分隔符列表（如"先按段落空行，再按句号，再按逗号，最后才按字符硬切"），先用最大的分隔符切，若某块仍超过 chunkSize 才换更细的分隔符继续切，逐层细化、尽最大努力保留原文结构。优点是兼顾语义完整性与块大小控制，是目前最通用的默认策略；缺点是分隔符列表需要按语言调整（中英文标点不同），且依赖文本本身存在合理的分隔符。适合绝大多数不确定该用什么策略的场景；不适合代码文件（应按函数/类切）、表格数据（应按行切）这类有特殊结构诉求的内容。
  4. **语义分块（Semantic Chunking）**：前三种策略都是基于规则（字数或标点），不理解文本语义。语义分块改用 Embedding 模型逐句计算相邻句子的向量相似度，当相似度低于某个阈值（意味着话题发生转换）时切一刀；另一条路是直接用大模型（LLM）通读文本、判断主题切换的位置，比 Embedding 相似度方式更准确、能处理更复杂语境，但速度是秒级而非毫秒级、成本也更高，因此 Embedding 方式更适合大批量文档处理，LLM 方式更适合高价值、需要精细分块的文档。语义分块整体优点是切割点基于语义、每块主题高度内聚，分块质量最高；缺点是需要额外调用 Embedding/Chat 模型，有计算成本和延迟，阈值需要调参，效果依赖所用模型质量。适合法律问答、医疗知识库、金融合规这类对检索精度要求很高的场景；不适合文档量巨大且对延迟敏感、或文本结构本身已经很清晰（递归分块就够用）的场景。
  5. **混合分块（Hybrid Chunking）**：单一策略往往不够用，混合分块是把多种策略组合，常见三种组合方式——① 先用递归分块粗切成段落/章节大块，再对每个大块用语义分块细切；② 按文档类型路由到不同分块器（如政策正文用递归、FAQ 按问答对切、合同用语义分块）；③ 分块后再做后处理（合并太短的块、拆分太长的块、给每个块补充章节标题/文档来源等元数据）。优点是能针对不同内容选最合适策略、整体效果最好；缺点是实现复杂度高，需要维护多套分块逻辑和路由规则。适合文档类型多样、检索质量要求高的企业级 RAG 系统；不适合简单 demo 或 POC 阶段（属于过度设计）。

- **用 ChunkViz 做可视化对比**：文章推荐一个在线工具 https://chunkviz.up.railway.app/，可以把示例文本粘贴进去，分别用 CharacterTextSplitter（对应固定大小分块）和 RecursiveCharacterTextSplitter（对应递归分块），拖动 Chunk Size / Chunk Overlap 滑块，页面用不同颜色高亮每个块的边界范围。文章给出了 4 组对照实验的设计思路（同一分割器改 overlap、同一分割器改 chunkSize、两种分割器互相对照），观察结论是：递归分块在保持语义完整性方面明显优于固定大小分块，但当内容结构更复杂、语义跨度更大时（比如问答结构复杂的场景），递归分块的边界判定依然可能不够准，容易把本应属于同一语义单元的内容切散——文章据此把递归分块定位为"偏基础的方法，更适合轻量、结构明确的场景"，而不是万能解。

- **分块策略怎么选：按文档类型对照表**（原文给出的推荐，可作为设计分块路由逻辑时的参考起点）：产品手册/知识库→递归分块（有清晰章节段落结构）；FAQ/问答对→递归分块（每个 Q&A 是自然单元不应被拆开，注意原文在"混合分块"举例部分又提到 FAQ 更适合按问答对单独切割，两处表述略有出入，实际设计时应以"每个 QA 保持完整"为目标而非拘泥于策略名称）；合同/法律文档→语义分块（条款边界需要精确识别）；日志文件→固定大小或按行切割（结构简单）；代码文件→专用代码分块器（按函数/类切）；HTML 页面→先清洗标签再递归分块；格式混乱文本（如 OCR 输出）→重叠分块（缺乏可靠分隔符，靠重叠缓解边界断裂）；多类型混合的企业知识库→混合分块。

- **chunkSize/overlap 的经验参考值**：chunkSize 常见范围 200～1000 字符，问答场景建议偏小（200～500），摘要场景可以偏大（500～1000）；overlap 建议取 chunkSize 的 10%～25%（如 chunkSize=500 时 overlap 取 50～125）。实用调参思路是从 chunkSize=500、overlap=50 起步，跑几个真实测试 query 观察检索效果——检索不够精准就调小 chunkSize，上下文经常被切断就调大 overlap。

- **企业级实践中的现实问题**：
  - 分块效果不好，很多时候根源不是 chunkSize/overlap 没调对，而是上游文本抽取阶段就已经"脏"了——尤其 PDF：页眉页脚/目录/页码混进正文稀释语义、断行或连字把一句话拆成多段导致按段落/句子的递归分割失效、表格被打散成碎词或错位字段（检索能命中但拼不出可读上下文）。因此正确流程不是"抽完就切"，而是"文本抽取 → 清洗与结构修复去噪 → 才进入分块与向量化"三段式。
  - 像 Dify、RAGFlow 这类标准 RAG 工具很多时候依赖单一分块策略，调参容易"顾此失彼"：chunkSize 调大有利于一类问题召回完整上下文，却可能拖累另一类问题的检索精度；调小则反过来。
  - 针对中小规模文档，文章给出的实用折中方案是：先用基础策略生成分块初稿，再做一轮人工二次编排——根据相邻块的语义关系进行合并、拆分或重新分配，使最终 chunk 更贴合真实问题类型；具体形式是在管理界面里可以点开某个分块进入编辑，保存后底层 chunk 同步更新生效。

## 关键概念/术语

chunkSize：单个分块的长度上限（字符或 token），是分块最核心的可调参数，常见范围 200～1000 字符。
overlap：相邻两个分块之间共享的重叠文本长度，用于缓解关键信息被切割边界拆断的问题，经验值为 chunkSize 的 10%～25%。
Token：大模型处理文本的最小单位，与"字符"不是一一对应关系（中文一字约 1～2 token），上下文窗口按 token 计而非按字符计。
固定大小分块（Fixed Size Chunking）：按固定字符数硬切、不考虑内容结构的最基础分块方式。
重叠分块（Overlapping Chunking）：在固定大小分块基础上引入 overlap 参数，通过重叠区域缓解边界语义断裂。
递归分块（Recursive Chunking）：按优先级从高到低的分隔符列表逐层细化切割（段落→句子→逗号→字符），目前最常用的默认分块策略。
语义分块（Semantic Chunking）：基于 Embedding 相似度或 LLM 语义理解，在话题发生转换的位置切割，分块质量最高但成本也最高。
混合分块（Hybrid Chunking）：组合多种分块策略（粗切+细切、按文档类型路由、分块后人工/规则后处理），适合企业级多类型文档场景。
ChunkViz：一个开源在线可视化工具（chunkviz.up.railway.app），用于对比不同分块策略、chunkSize、overlap 组合下的实际切割效果。

## 与 xrag 项目的关系

- 分块模块在 xrag 数据管道中应紧接在 Tika 解析与文本清洗之后（承接上一篇 01-05 笔记里"解析 → 清洗 → 分块 → 向量化"的顺序结论），设计上要明确约束"不能抽完就切"，即分块器的输入必须是已完成清洗（去页眉页脚、修复断行、处理乱码）的干净文本，否则再好的 chunkSize/overlap 调参都无法弥补上游脏数据带来的语义损失。
- 建议以递归分块作为 xrag 默认/兜底分块策略，分隔符列表按中文语境定制（优先段落空行，再句号、逗号），并把 chunkSize、overlap 做成按文档类型可配置的参数而非全局硬编码常量——为后续接入"按文档类型路由到不同分块器"的混合分块能力预留扩展点（比如政策类正文走递归、FAQ 按问答对整体保留、代码片段走专用分块器）。
- chunkSize/overlap 的起始参考值（500/50，问答场景可降到 200～500）可以直接作为 xrag 分块服务的默认配置，并在设计里保留"按检索效果反馈迭代调整"的接口，而不是一次性定死。
- 每个 chunk 除文本内容外，应携带来源文档、章节标题、原始位置等元数据（与 01-05 笔记中 Tika 元数据保留的结论呼应），为后续检索排序、答案溯源、按文档类型/时间过滤提供数据基础；这一元数据传递链路需要在分块阶段就设计好字段，而不是等检索或生成阶段发现缺失再补采。
- 可以考虑在 xrag 管理后台预留"分块结果可编辑/可重新编排"的能力（合并过短块、拆分过长块、跨块调整边界），作为中小规模知识库低成本提升分块质量的手段，避免完全依赖单一自动化策略；同时把 ChunkViz 类似的可视化对比方式，作为 xrag 分块参数调优阶段的验证工具，而不是凭感觉设定参数。
- 是否引入语义分块（Embedding 或 LLM 辅助）应作为分阶段决策：初期可用递归分块快速验证 RAG 全链路，等确认哪些文档类型（如合同、高价值知识条目）对分块精度有明显更高要求后，再针对性引入语义分块，避免一开始就为所有文档承担语义分块的额外计算成本和延迟。

## 值得注意的设计取舍/坑

- chunkSize 没有放之四海而皆准的最优值：块太大混入噪音、块太小切断语义，且这个权衡会随文档类型变化；连 Dify、RAGFlow 这类成熟 RAG 工具依赖单一策略调参时也会出现"顾此其彼"（调大有利这类问题、有损那类问题）的现象，说明单一全局 chunkSize 很难适配所有文档类型，需要按类型分场景配置。
- overlap 不是越大越好：能缓解边界断裂，但会成倍增加重复存储的文本量和计算成本，需要按 10%～25% 的经验区间控制，而不是盲目加大。
- 字符数与 token 数不对齐是中文场景容易忽略的坑：按字符数设定的 chunkSize，在中文文本里实际消耗的 token 数可能明显高于预期（一字约 1～2 token），如果上下文窗口预算是按 token 算的，用字符数直接类比会低估真实占用。
- 递归分块的分隔符列表依赖语言特性（中英文标点体系不同），需要针对语言单独调整；即便是递归分块，遇到语义跨度大、结构复杂的内容（如条款嵌套多个条件的政策文本）时边界判定仍可能不准，不能把递归分块当成万能默认解。
- 语义分块的两条路径（Embedding 相似度 vs LLM 辅助）在速度和成本上差距明显（毫秒级低成本 vs 秒级高成本），选型时要先明确文档价值密度和延迟容忍度，而不是默认认为"LLM 分块更准就该全用 LLM"。
- 最容易被忽视的坑是把分块问题和上游文本质量问题混为一谈：如果 PDF 抽取阶段本身混进页眉页脚、断行、表格错位等噪声，无论怎么调 chunkSize/overlap 都是在"脏文本"上做局部优化，正确的修复点是在分块之前补一道清洗与结构修复的工序，而不是指望分块参数兜底。
- 混合分块效果最好，但代价是要同时维护多套分块逻辑和路由规则，实现和运维复杂度显著上升；在 demo 或 POC 阶段引入混合分块属于过度设计，应该等确认单一策略确实不够用之后再升级。
