# 《流式路由的首包探测机制》

> 原文链接：https://t.zsxq.com/gYKNI
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

流式故障转移的安全边界是“下游提交点”：提交前可以短暂缓冲并探测候选，失败后丢弃缓冲切换模型；一旦内容已交给下游，就不能把另一模型的回答拼进同一条流。

## 核心内容提炼

- 流式调用不能直接复用同步故障转移：启动流的方法返回时，上游还没有产生内容，真正的错误可能在异步回调里出现。
- 原文使用 probe-and-commit：
  1. 为当前候选创建探测桥接回调；
  2. 上游事件先进入缓冲；
  3. 等待首个内容/思考事件、错误、超时或无内容完成；
  4. 成功则提交缓冲并转为直通；
  5. 失败则取消当前上游，丢弃缓冲，尝试下一候选。
- 探测结果分为 `SUCCESS`、`ERROR`、`TIMEOUT`、`NO_CONTENT`。在首个内容到达前完成，也被视为不可交付结果。
- `ProbeStreamBridge` 用一个只能完成一次的 Future 协调首结果，用同一把锁保护“事件入缓冲”和“提交排空”，防止提交过程中丢事件、重复事件或打乱顺序。
- 候选成功后熔断器复位；探测错误、超时或无内容则记录失败。所有候选失败后才向下游发送最终错误。
- 该机制对本地 Ollama/vLLM 很有价值：进程可能先返回 HTTP 200，随后因显存不足在首 token 前失败；只看响应头会误判成功。

## 关键概念/术语

- **首个上游事件**：解析出的第一条合法 SSE 事件，可能只是元数据或注释。
- **首个有效业务块**：第一条可交付的文本、工具参数、拒答等业务增量。
- **下游提交点**：第一条业务事件真正交给调用方，此后不能透明切换模型。
- **探测缓冲**：提交前暂存事件的有界区域，失败时可整体丢弃。
- **流中失败**：下游已经收到内容后，上游中断或返回错误。

## 与 xrag 项目的关系

- xrag 应明确记录三个时刻：

  | 时刻 | 用途 |
  |---|---|
  | `firstUpstreamEventAt` | 网络和协议健康 |
  | `firstMeaningfulChunkAt` | 模型开始产生业务结果 |
  | `downstreamCommittedAt` | 故障转移安全边界与用户感知延迟 |

- “有意义事件”不能只定义为非空文本。Phase 3 可能需要工具参数增量、结构化输出或拒答事件，成功事件集合应由调用契约决定。
- 探测缓冲必须同时限制事件数、字节数和时间；探测与后续候选共享逻辑调用总截止时间，不能让每个候选都独占完整的 60 秒。
- 取消句柄必须在启动路由后立即返回。调用方要能在仍处于首包探测时取消当前候选和整个候选链，不能等首包成功后才拿到句柄。
- 提交后的流中错误应向下游发送明确终止/错误并结束，保留已产生的部分结果还是在 UI 上标记无效，留到 Step B 产品契约决定；不能无感切换并混流。

## 值得注意的设计取舍/坑

- **原文每个候选最多等 60 秒，会形成 `候选数 × 60 秒` 的最坏延迟。** xrag 必须使用共享总截止时间和尝试预算。
- **在锁内调用下游回调有阻塞和重入风险。** 可以用单写者/串行 drain 保证顺序，让锁只保护状态和缓冲切换。
- **首个思考片段是否算成功需要产品定义。** 如果前端不展示思考内容，因思考事件提交后最终没有正文，用户仍可能看到空回答。
- **探测成功不等于整条流成功。** 熔断/健康统计要区分首包成功、完整完成和提交后中断。
- **缓冲越大，透明切换机会越多，但首屏延迟和内存占用也越高。** 第一版应只缓冲到首个有效事件，不做长时间答案级缓冲。
