# 《三态熔断器与故障转移》

> 原文链接：https://t.zsxq.com/C0btU
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

熔断器用 `CLOSED → OPEN → HALF_OPEN` 阻止持续打向故障模型，故障转移则按候选链切换目标；两者必须由错误分类、原子半开许可和共享总预算约束，不能把“捕获所有异常后换一家”当成完整容错。

## 核心内容提炼

- 原文的 `ModelHealthStore` 为每个模型维护连续失败次数、打开截止时间、半开探测占用和状态：
  - `CLOSED`：正常放行，连续失败达到阈值后进入 `OPEN`。
  - `OPEN`：冷却时间内拒绝调用，时间到后允许竞争半开许可。
  - `HALF_OPEN`：只放行一个真实请求探测；成功关闭熔断并清零，失败重新打开并重置冷却时间。
- 使用 `ConcurrentHashMap.compute()` 对单个 key 的状态转换做原子更新。同一模型的许可竞争串行化，不同模型仍可并行。
- `markSuccess` 会打断连续失败序列，符合“连续失败阈值”的语义；如果改用失败率窗口，成功和失败的统计规则也要一并改变。
- `ModelRoutingExecutor<C,T>` 接收能力、候选、客户端解析器和真正调用函数，依次执行：解析客户端、申请熔断许可、调用、成功复位；失败则记录健康状态并尝试下一个候选。
- 泛型执行器可供同步 Chat、Embedding 和 Rerank 复用，但流式 Chat 的成功与失败发生在异步回调中，不能直接套同步返回值模板。
- 一手资料表明成熟熔断器除了主干三态，还需要统计窗口、最小样本数、失败率/慢调用率、有限半开许可和异常记录规则；运维还可能需要 `DISABLED`、`FORCED_OPEN` 等特殊状态。

## 关键概念/术语

- **熔断器**：根据近期调用结果暂时阻止访问不健康目标，保护调用方和上游。
- **半开许可**：冷却后放行的有限探测名额，用于判断服务是否恢复。
- **故障转移**：放弃当前候选并切换到候选链中的下一个合格目标。
- **同候选重试**：仍调用同一 Provider/模型，和故障转移不是一回事。
- **共享尝试预算**：重试和换候选共同消耗的最大次数与总截止时间。

## 与 xrag 项目的关系

- xrag 第一版熔断键至少应是 `provider + model + capability/endpoint`。同一 Provider 的 Chat 故障不应顺带熔断可用的 Embedding，不同模型也可能有独立配额和健康状态。
- 当前部署假设是单实例，因此进程内熔断状态可以作为第一版候选；技术方案必须注明升级为多实例后各实例状态独立，不等于全局熔断。
- Phase 1 Embedding 目前只对 429 做同候选指数退避。Phase 2 应把重试、故障转移和熔断拆开，并共享 `overallDeadline` 与 `maxAttempts`，避免“每个候选各重试 N 次”造成请求量和延迟成倍增长。
- 建议第一版错误策略至少区分：

  | 错误 | 同候选重试 | 换候选 | 计入熔断 |
  |---|---|---|---|
  | 网络错误、上游 reset、5xx | 按预算 | 通常可以 | 是 |
  | 429 | 尊重 `Retry-After` 或按预算退避 | 可切独立配额候选 | 单独记录受限状态 |
  | 401/403 | 否 | 仅当其他候选凭据独立 | 通常否 |
  | 400、模型名/维度/参数错误 | 否 | 默认否 | 否 |
  | 调用方取消 | 否 | 否 | 否 |
  | 流提交后的中断 | 否 | 同一响应内不切换 | 是 |

- 诊断需要同时记录逻辑调用和每次 attempt。最终回退成功不能覆盖首选模型已经连续失败的事实。

## 值得注意的设计取舍/坑

- **原文执行器捕获所有异常并统一记失败，策略过粗。** 调用参数错误、鉴权配置错误和用户取消不是模型健康故障，若全部计入会误熔断。
- **只用连续两次失败打开 30 秒适合教学，不是可直接冻结的生产参数。** Step C 要结合供应商特性决定窗口、最小样本、阈值和半开许可数。
- **429 不等于服务宕机。** 它通常表示当前配额受限；应读取 `Retry-After`，并考虑候选之间是否共享同一配额。
- **半开探测应使用真实请求，但不能让所有并发请求一起探测。** 许可获取、成功复位和失败重开必须是原子的。
- **熔断不替代超时。** 连接、首个业务事件、流空闲和总截止时间各自解决不同问题；没有总截止时间，长候选链仍会拖垮体验。
