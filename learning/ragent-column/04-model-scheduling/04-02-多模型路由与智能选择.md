# 《多模型路由与智能选择》

> 原文链接：https://t.zsxq.com/yJRRN
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

第一版模型路由最重要的不是“用 AI 决定用哪个 AI”，而是先按能力和健康状态做硬过滤，再用明确、稳定、可解释的规则生成候选顺序。

## 核心内容提炼

- 原文的 `ModelSelector` 先找到能力对应的候选配置，再确定首选模型：普通 Chat 使用默认模型，需要深度思考时使用思考模型。
- 候选先过滤空项、禁用项和能力不匹配项；思考请求还会排除不支持思考模式的模型。过滤之后才排序，避免“优先级最高但根本不能完成请求”的候选进入尝试链。
- 排序是确定性的：首选模型最前，其余按显式优先级排列，优先级缺失的靠后，最后用稳定 ID 打破平局。这样相同输入和相同配置能复现相同结果。
- “默认模型”和“优先级”表达不同语义：默认模型是当前明确首选，可以随运营决策调整；优先级是普通回退顺序。二者不要压缩成一个字段。
- 模型 ID 可显式配置，也可由 `provider::model` 组合生成。生产系统更适合显式稳定 ID，避免供应商模型名或命名规则变化后让历史诊断、熔断状态失去关联。
- `ModelUrlResolver` 先使用候选级 URL 覆盖，否则由 Provider 基地址和能力端点安全拼接。URL 解析属于基础设施，不应让业务层反复拼字符串。
- 原文有两层健康检查：选择阶段用只读状态提前排除明显不可用候选；真正调用前再由执行器原子申请熔断许可。前者减少无效候选，后者才保证并发正确性。
- Rerank 可以登记一个低优先级 Noop 候选作为显式降级，但这种“可选质量增强”不应推广到 Chat 或 Embedding。

## 关键概念/术语

- **硬约束过滤**：能力、协议、流式、维度、上下文、地域、启用和健康等不满足就不能调用的条件。
- **软策略排序**：优先级、成本、延迟、质量或负载等可以权衡的排序信号。
- **确定性路由**：相同请求上下文和配置快照产生相同候选链。
- **首选提升**：把当前明确指定的默认候选提升到普通优先级之前。
- **稳定模型 ID**：不随显示名称和 URL 变化的内部标识，用于配置、诊断和熔断键。

## 与 xrag 项目的关系

- xrag Phase 2 第一版应采用“两阶段路由”：

  ```text
  能力与配置硬过滤
        ↓
  确定性候选排序
        ↓
  调用前熔断许可
        ↓
  按共享预算执行
  ```

- Phase 4 之前没有真实评测数据、偏好标签和成本质量闭环，因此“智能选择”不应实现为额外调用一个 LLM 来判路由。先做可解释规则，未来再把学习型策略作为可替换的 `RoutePolicy`。
- 每次逻辑调用应冻结候选快照并记录：初始候选、过滤原因、最终顺序、实际 Provider/模型、重试和故障转移。调用过程中不应重新读取变化后的配置并生成另一条不可复盘的候选链。
- Embedding 的路由约束比“支持 EMBEDDING、维度相同”更严格：知识库创建和入库时已经固化向量模型，同维度的不同模型也不在同一语义空间，不能自动互为故障转移候选。
- 轻量诊断页应直接展示路由解释，而不只展示最后成功的模型；否则首选 Provider 持续失败但被回退掩盖的问题仍然不可见。

## 值得注意的设计取舍/坑

- **过滤顺序与排序顺序不能颠倒。** 先对所有候选做成本或优先级评分，再在执行时才发现能力不匹配，会让路由解释和实际尝试不一致。
- **候选生成与尝试执行是两个模块。** `ModelSelector` 不应该发网络请求，执行器也不应该偷偷改变策略顺序。
- **健康预筛只是优化，不是并发保障。** 从选择到调用之间状态可能变化，半开状态的唯一探测许可必须在执行前原子获取。
- **动态指标容易引入抖动。** 第一版如使用近期延迟或错误率，需要定义窗口、冷启动和稳定排序；没有这些定义时，显式优先级更可靠。
- **Noop 必须是可见降级。** Rerank Noop 的结果应携带“未重排”诊断事实，不能伪装成真实模型成功。
