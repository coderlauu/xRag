# ADR 0008：三通道混合检索与 RRF 融合

- `status`: accepted（2026-08-08）
- `date`: 2026-08-08
- `decision_owner`: liuqiang
- `scope`: Phase 3B 的检索通道构成、中文关键词实现、候选融合、去重截断与精排边界
- `related`: [PRD §12](../prd/2026-08-07-qa-pipeline-prd.md)、[Phase 3 计划 §5.5](../exec-plans/completed/2026-08-07-qa-pipeline-phase-plan.md)、[架构](../../tech/qa-pipeline/architecture.md)、[数据模型](../../tech/qa-pipeline/data-model.md)、[ADR 0007](0007-versioned-intent-tree.md)

## Context

3A 已产出不可变的检索动作（`KB_TARGETED` / `GLOBAL_FALLBACK` / `SYSTEM` / `NO_MATCH`）。3B 要把这些
动作变成真实的召回结果，并把"依据了什么"如实呈现给用户。

约束来自三处，且互相牵制：

1. **存储形态**：xrag 是一张 `document_chunk_embedding` 表加一个 HNSW 索引，不是 Milvus 的物理集合
   隔离。课程里"每个知识库一次独立检索再合并"的三层并行架构在这里塌缩掉一半——全局检索就是一条不带
   `where kb_id` 的 SQL，而且结果比"N 路各取 TopK 再合并"更正确（后者是近似的分组 TopK）。
2. **产品语义已冻结**（PRD §12）：同一片段只展示一次、不展示任何原始分数、未精排必须可见、
   部分知识库失败必须点名、Rerank 返回不足 topN 时不得用原始候选补齐。
3. **项目所有者已裁决**（计划 §8，2026-08-08）：检索通道 = 定向向量 + 全局向量 + 关键词，三路混合。

起草本 ADR 时对 PRD §12.8 的两处技术前提做了核查，结论与原文不同，必须先纠正：

- **PostgreSQL 内置全文检索没有 BM25。** 排序函数是 `ts_rank` / `ts_rank_cd`，按词频与覆盖密度加权，
  与 BM25 的文档长度归一化不是一回事。要真 BM25 需要 ParadeDB/`pg_search` 一类方案，等于换数据库镜像。
- **`pgvector/pgvector:pg16` 不含 `zhparser` / `pg_jieba`。** 用它们必须自建 Postgres 镜像。

## Decision drivers

- 不引入需要自建数据库镜像的依赖；部署基线保持现成镜像。
- 跨通道分数不可比是 PRD §12.2「不展示分数」的成因，融合方案不能反过来假设它们可比。
- 真正的并发上限是数据库连接数，不是线程池大小。
- 去重必须有稳定身份，不能有可能静默丢证据的兜底路径。
- 不预留走不到的分支：枚举、接口方法和线程池都要有第二个真实用例才建立。
- 降级必须显式且可传到界面，不能消失在类型里。

## Considered options

### 通道构成

**A. 只做定向 + 全局两个向量通道。** 零新依赖，两个通道分数同量纲可直接排序。但专有名词、
型号、单据号这类"字面命中才准"的查询会明显变差——向量检索对精确串不敏感。**未选**（所有者已裁决做三路）。

**B. 定向向量 + 全局向量 + 关键词（选中）。** 覆盖语义相似与字面命中两类查询。代价是引入
分数不可比问题，由融合方案承接。

### 中文分词

**甲. 应用侧分词 + `tsvector('simple')`（选中）。** Java 侧切词，把切好的词以空格连接后
`to_tsvector('simple', ...)` 存入派生表；查询用同一套切词生成 `tsquery`。数据库镜像与部署基线不动。
代价：切词逻辑必须索引期与查询期严格一致；更换词典要重建整列。

**乙. 自建 Postgres 镜像装 `zhparser`。** 分词在库内，SQL 更正统，换词典不用改应用。代价是数据库镜像
变成定制件——Dockerfile、CI build、deploy 基线全部要改，并再引入一个可能自己出问题的基础件。
仓库已经在 RustFS 上吃过一次这种亏（alpha 镜像偶发 `CreateBucket` 503）。**未选**。

**丙. 不做关键词通道。** 推翻已裁决的通道构成。**未选**。

### 融合策略

**RRF（选中）**：`score = Σ 1/(k + rank_i)`，`k=60`。只消费**排名**，不消费分数。

**加权分数融合（未选）**：需要先把余弦距离与 `ts_rank_cd` 归一到同一量纲。两者分布形状不同，
归一化参数没有原则性取法，只能靠拍——而拍出来的参数会直接决定用户看到的来源顺序，却没有任何证据支撑。

选 RRF 还有一个连带好处：**"Postgres 给的不是 BM25"这件事随之失去影响**。RRF 不关心通道内部用什么
打分函数，只要同一通道内的排序是自洽的。PRD §12.2 又已冻结"不展示任何原始分数"，绝对分值对用户
同样不可见。于是"没有真 BM25"从一个质量缺陷降级为一个实现细节。

### 定向与全局的关系

**无条件同时激活（未选）**：在 pgvector 单表下，定向结果是全局结果的子集（只要 topK 足够大）。
不看动作就两个都跑，等于查两遍同一份数据。

**按动作激活（选中）**：3A 的动作模型已经把条件定好了——`KB_TARGETED` 与 `GLOBAL_FALLBACK`
是两种不同动作，后者只在"无候选 / 最高分 `<0.6` / 单候选 `<0.8`"时产生。3B 按动作激活通道，
不自己重新解释分数，也不额外加"互斥"守卫：3A 说要补全局，就补。

## Decision

1. **三个检索通道，一个接口，只有一套优先级。**
   `INTENT_TARGETED`（定向向量）、`GLOBAL_VECTOR`（全局向量）、`KEYWORD`（关键词）。
   通道有唯一的 `priority`，同时用于稳定排序与去重取舍；**不设第二套 `type` 优先级**——课程实现里
   `getPriority()` 与 `getType()` 语义重叠且无机制保证一致，新增通道时必然出现矛盾。

2. **激活条件由 3A 动作决定，不由 3B 重算分数。**
   - 该子问题存在 `KB_TARGETED` → 激活 `INTENT_TARGETED`，限定在这些 `knowledge_base_id` 上。
   - 该子问题存在 `GLOBAL_FALLBACK` → 激活 `GLOBAL_VECTOR`（不带 `kb_id` 过滤）。
   - `KEYWORD` 始终激活，作用域与同轮向量通道一致（定向则同 `kb_id` 集合，否则全局）。

   **修正（2026-08-09，实现工单 08 时发现）**：本条起初还有一句"两个向量通道不同时激活"，
   已删除。它与 3A 的动作模型冲突——[架构 §9.4](../../tech/qa-pipeline/architecture.md) 规定
   "只有一个 KB 候选且分数 <0.8"时**同时**产出 `KB_TARGETED` 与 `GLOBAL_FALLBACK`，那正是意图层
   在说"这个定向匹配不够有把握，再全局找一遍"。压掉全局通道会让这个补充从不发生，
   还会把一个从未执行的目标记成成功。而"别重复查"由动作模型自己保证：只有定向动作时
   3A 根本不产出 `GLOBAL_FALLBACK`。本条前两句（按动作激活）与被删的那句本来就自相矛盾。

3. **关键词通道用应用侧分词 + 派生表。**
   新建 `document_chunk_keyword`，形态与 `document_chunk_embedding` 完全对齐：`chunk_id` 主键、
   物理删除、每行都对应一个未删除且启用的分块。写入点与向量写入同一处，排序用 `ts_rank_cd`。

4. **融合用 RRF，`k=60`，按 `chunk_id` 去重。**
   同一 `chunk_id` 在多通道命中时合并为一条，RRF 分数累加，来源归属取 `priority` 最小的通道。
   **不写 `text.hashCode()` 兜底**：chunk 一定有主键，兜底路径只会带来一个静默丢证据的可能。

5. **检索并行度必须小于数据库连接池，并在启动时校验。**
   `application.properties` 当前未配 Hikari 池大小，默认为 10；而 `ChunkVectorRepository.search`
   带 `@Transactional(readOnly = true)`（需要 `set local hnsw.iterative_scan`），每个并行任务独占
   一条连接。因此显式配置池大小，并令 `检索并行度 < 池大小`，不满足直接启动失败。

   **池大小取 10（= 原隐式默认值），不取更大。** 起草时定的 20 在实现工单 01 时被实测推翻：
   一次 `verify` 会起十几个 Spring 测试上下文，每个各建一个池，而 Postgres 默认
   `max_connections=100`，20×N 直接打穿，症状是成片的 `FATAL: sorry, too many clients already`
   ——看起来像数据库坏了，实际是池大小乘上了上下文数量。显式化的价值在于校验与可见性，
   不在于数字变大；要调大必须与 Postgres 的 `max_connections` 一起改。
   理由与"Embedding 维度与 `vector(1024)` 不一致时启动失败"同源：放行只会把问题推迟成运行期的
   "检索变慢了"，而那个症状会把排查带到完全错误的方向。

6. **精排调用 `RerankClient`，三态显式且不补齐。**
   `rerankApplied=true` / Noop 降级 / 配置故障三条路径在结果对象上可区分，一路传到 API 与界面。
   **Rerank 返回不足 topN 时不用原始候选补齐**（PRD §12.5）——补进来的正是它判定为不相关的片段，
   却会被摆在"已精排"的位置上。

7. **去重是必需清洗，精排是可选增强，容错策略不同。**
   去重失败即本轮检索失败；精排失败降级为"未精排"并继续。课程实现用同一个 try-catch 跳过所有
   处理器，对这两者适用性完全不同。

8. **部分失败是显式状态，不由结果条数倒推。**
   每个知识库目标的检索结果各自带成功/失败状态与归一化原因，汇总成 `partial` 标记（PRD §12.4）。

## Consequences

### 正面

- 部署基线不变：仍是 `pgvector/pgvector:pg16`，没有自建镜像，CI 不需要 build 数据库。
- 融合不依赖任何拍出来的归一化参数，来源顺序可解释为"两个通道都把它排在前面"。
- 去重身份稳定，不存在碰撞丢证据的路径。
- 并发上限有一条可校验的硬约束，而不是散在各处的线程池大小。

### 负面与代价

- **切词一致性成为长期纪律**：索引期与查询期必须用同一套词典和同一份切词代码。换词典要重建
  `document_chunk_keyword` 全表，这一点必须写进运维文档，不能只活在注释里。
- **`ts_rank_cd` 不是 BM25**，关键词通道的排序质量弱于成熟检索引擎。RRF 消化了跨通道可比性问题，
  但消化不了"通道内部排序本身不够好"。Phase 4 评测若显示关键词通道贡献为负，应当直接关掉它，
  而不是去调 RRF 的 `k`。
- **存量分块需要回填**：应用侧分词决定了回填不能是纯 SQL，要跑一次 Java 批处理。
- **新增一张派生表**，知识库入库写入点因此多一处职责；`document_chunk_embedding` 与
  `document_chunk_keyword` 的不变量必须同时维护，任何一处漏写都会让关键词通道静默少召回。

### 明确不做

- 不引入 `zhparser` / `pg_jieba` / ParadeDB / Elasticsearch。
- 不做 `AbstractParallelRetriever` 那层模板方法与内层 Collection 线程池：xrag 一条 SQL 就够，
  抄过来是纯负担。
- 不做通道级 `isEnabled(context)` 恒返回 `true` 的扩展点；激活条件由动作决定（决策 2），
  这是一个真实条件，不是占位。

## Compliance

- 启动校验：并行度 < 连接池大小；关键词派生表存在且分词器可加载。
- 契约测试：RRF 在给定排名下输出确定顺序；同 `chunk_id` 跨通道只出现一次；
  Rerank 三态在 API 上可区分；部分失败不由条数推断。
- 数据不变量测试：`document_chunk_keyword` 与 `document_chunk_embedding` 的行集合在同一批
  分块上一致（同增同删）。
- 详见[测试矩阵](../../tech/qa-pipeline/test-matrix.md) `3B-*` 分区。
