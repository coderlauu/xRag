# 《意图分数出来了，该查哪个库、查多少条》

> 原文链接：https://t.zsxq.com/Qokj8
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

意图识别子系列的收尾篇：把打完分的意图翻译成动作——SYSTEM 短路直接回复、MCP 走工具调用、KB 走检索；KB 侧再由**两个通道按置信度动态激活**（定向检索 ≥0.4、全局兜底 <0.6 或单意图 <0.8），低置信度时两条通道**同时跑**，让 Reranker 做最后裁判。

## 核心内容提炼

- **三条路径一张表**：
  | 类型 | 处理 | 走向量检索 | 生成时的 Temperature |
  |---|---|---|---|
  | SYSTEM | `handleSystemOnly` 短路直接回复 | 否 | 0.7（闲聊要自然，不能每次回一样的话） |
  | MCP | LLM 提参 + 工具执行 | 否 | 0.3（结构化数据要组织成自然语言） |
  | KB | 定向 / 全局检索 | 是 | 0.0（必须严格忠实于 chunk，不许编造） |

- **`isSystemOnly` 的判定极严：恰好一个意图且 kind 是 SYSTEM**，且 `handleSystemOnly` 要求**所有子问题都满足**（`allMatch`）。反例："你好，顺便帮我查一下退货政策"拆成两个子问题，第二个是 KB，不短路——**否则退货问题会被静默吞掉**。

- **SYSTEM 短路不走检索但照常带会话历史**。用户连问"你好""你是谁""你能做什么"，每次都短路，但历史在，LLM 不会每次从头自我介绍。**不走检索 ≠ 没有上下文**。

- **SYSTEM 节点可配 `promptTemplate` 覆盖全局 System Prompt**（`findFirst` 取第一个非空的），比通用提示词更贴合场景。

- **`handleGuidance` 排在 `handleSystemOnly` 之前是防御性设计**。SYSTEM 意图当前不参与歧义引导（引导只看 KB 意图），顺序上没有实际差别；这么排是为了万一将来 SYSTEM 也可能产生歧义时，引导仍有机会先拦截。

- **KB 与 MCP 是并行的两条路而非二选一**。一个子问题的意图列表里可以同时有两种，`buildSubQuestionContext` 里各走各的最后合并。`NodeScoreFilters.mcp()` 的过滤条件是 `kind==MCP` **且 `mcpToolId` 非空**——第二个是防御性检查。

- **MCP 链路要多调一次 LLM 做参数提取**（`McpParameterExtractor`），节点上的 `paramPromptTemplate` 可以给特定工具定制提取规则。延迟预期：参数提取 ~500ms + 工具调用 100~500ms，多个 MCP 意图并行（`mcpBatchExecutor`，与 KB 检索的线程池分离），总延迟取最慢那个。

- **定向检索的激活门槛（0.4）高于意图保留门槛（0.35）**。0.35 只是"分数够低但不至于丢掉"的保留线，0.4 才是"值得花一次向量库 IO"的门槛。

- **全局兜底的三个触发条件**：
  | 条件 | 触发场景 | 定向是否同时激活 |
  |---|---|---|
  | 无意图 | LLM 返回空数组 | 否（没有 KB 意图） |
  | 最高分 < 0.6 | 意图不太确定 | 可能（≥0.4 就走） |
  | 单意图 且 < 0.8 | 中等置信度孤军 | 是 |

  第三条的理由最值得记：**只有一个意图意味着没有备选方案**，判错了下游就只能拿到错误知识库的 chunk，补充全局检索相当于买保险。

- **四个阈值递增，对应四级决策**：`0.35` 保留 < `0.4` 定向检索 < `0.6` 全局兜底 < `0.8` 单意图补充。这四个数字散落在两个阶段的不同配置里，**它们之间的偏序关系是隐式的**。

- **两个通道同时激活时并行跑，结果合并后统一进后置处理器链**（去重 → Rerank → 截断）。设计价值在于：**定向赌对了它的结果会在 Rerank 中得高分，定向赌错了全局能从别的库补回正确 chunk**——两条路都不白跑。

- **TopK 分两级算**：子问题级取该子问题所有 KB 意图节点上 `topK` 配置的**最大值**（都没配则用全局默认 10）；意图级再乘以通道倍率（定向 ×2、全局 ×3）。

- **乘倍率是因为检索阶段的 TopK 不是最终塞进 Prompt 的数量**——先多召回给 Reranker 挑，最终由 Reranker 控制。全局倍率更大是因为全库搜噪声更多，需要更大的候选池。

- **节点级 `topK` 存在的理由是内容密度差异**：退货政策库几十条 chunk，5 条就覆盖；跨境物流涉及多国法规，15 条以上才够。统一 10 条对前者太多、对后者太少。

## 关键概念/术语

- **`SearchChannel`**：检索通道抽象，带 `isEnabled(context)` 与 `getPriority()`，由引擎按优先级筛选并并行执行。
- **意图定向检索**：只在命中意图绑定的知识库里检索，优先级 1。
- **全局兜底检索**：在所有知识库里检索的安全网，优先级 10。
- **置信度阈值 / 补充阈值**：`confidenceThreshold=0.6` 与 `singleIntentSupplementThreshold=0.8`。
- **`topKMultiplier`**：检索阶段的召回放大倍率，为 Reranker 准备候选池。
- **两级 TopK**：子问题级取节点配置最大值，意图级再乘倍率。
- **`NodeScoreFilters`**：按 `IntentKind` 与分数下限过滤意图的工具类。

## 与 xrag 项目的关系

- **xrag 的 pgvector 形态让"多通道"这件事比原文简单一个量级，但也撞上了一处刻意的既有设计。** [`ChunkVectorRepository`](../../../backend/src/main/java/com/app/knowledge/vector/ChunkVectorRepository.java) 已经有 `search(long kbId, float[] queryVector, int limit)`，方法注释明确写着"知识库 ID 是必填参数，调用方不存在'不小心忘记过滤'的接口"——**这是一个有意为之的约束**。映射到本篇：
  - **定向检索**几乎零成本：现成的 `search(kbId, ...)` 就是它，多个意图就是多个 `kbId`。
  - **全局检索则要求打开这个约束**——同一条 SQL 去掉 `where kb_id = ?` 即可，`idx_chunk_embedding_hnsw` 直接给出全局最近邻，**不需要像原文那样"并行查 N 个 Collection 再合并"**。一条查询、一次索引扫描，比原文的实现简单得多。

  但这意味着 Phase 3 必须显式修改一个带着"防误用"注释的接口。**正确做法是新增一个命名清晰的 `searchGlobal(...)` 方法并在注释里写明它为什么可以不带 kb 过滤，而不是把 `kbId` 改成可空**——后者会让原来的防误用设计整个失效。

- **全局检索不需要 join `knowledge_base` 过滤逻辑删除，这是级联删除设计的直接红利。** 知识库被逻辑删除时，`KnowledgeBaseRepository.deleteEmbeddingsByKbId` 会**物理删掉**它的全部向量（PRD §7.6 例外 1），`ChunkVectorRepository` 的类注释也把"表中每一行都对应一个未删除且已启用的分块"写成了 Phase 3 检索侧可依赖的不变量。**所以全局检索直接扫全表是安全的**——这条不变量正是为了今天这个场景准备的，Step C 的技术方案里应当明确引用它，而不是重新加一层过滤。

- **多意图定向检索在 pgvector 下有一个原文没有的选择题：`kb_id IN (...)` 一次查，还是每个意图各查一次。** 原文因为是物理隔离的 Collection，只能并行 N 次。xrag 两种都行，但语义不同：
  - `IN (...)` 一次查 = 全局排序后取 TopK，**某个知识库可能一条都没被选中**；
  - 每意图各查一次 = 每个知识库保证有自己的 TopK 条，**再合并**。

  原文的行为等价于后者（每个意图按自己的 `topK × 倍率` 各取一批）。这个差别会直接影响召回的品类覆盖，**Step C 要显式选一个并写清理由**，不能因为 `IN` 写起来更短就顺手用了。

- **`search()` 里 `limit > 100` 会抛异常，这个上限在两级 TopK 下要重新核对。** 全局检索的 `10 × 3 = 30` 没问题，但节点级 `topK` 若配到 40、倍率 3，就是 120——**直接抛 `IllegalArgumentException`，而且是在检索链路的深处**。要么在配置侧就限制 `topK` 上限，要么把这个校验换成截断 + 告警。**当前的写法在 Phase 1 是合理的（调用方只有入库链路），Phase 3 引入用户可配的 `topK` 之后就不合理了。**

- **意图节点的 `description` 不能复用知识库自己的 `description`。** `knowledge_base` 表已有 `description varchar(1024)`，看起来正好能当意图节点的描述用。但两者用途不同：知识库的 description 是给**人**看的"这个库装了什么"，意图节点的 description 是给 **LLM** 做路由判断的"什么样的问题该来这里、以及它和兄弟节点的区别"（第 5 篇明确指出它直接决定匹配准确率）。**合成一个字段会让两边都写不好**，而且知识库改描述会静默改变路由行为。

- **本篇给出了第三组不同的 Temperature（0 / 0.3 / 0.7），采样参数缺口的证据又厚了一层。** 加上第 6 篇的意图分类（0.1/0.3）与第 8 篇的歧义确认（0.1/0.3），Phase 3 至少要用到**五种不同的采样参数组合**。`com.app.ai` 当前一个都不支持（`ChatCommand` / `CallOptions` / `ProviderChatRequest` 里没有任何采样字段）。**这已经不是"补个字段"，而是需要在 Step C 里给出一个完整的参数传递设计**，且要回答"业务代码传采样参数算不算触碰模型内部"这个 [ADR 0003](../../../docs/adr/0003-separate-model-capability-ports.md) 的边界问题。

- **`rag.search.channels.*` 这套配置的形态可以借鉴，但要连同第 6~8 篇的阈值一起管。** 现在已经攒了至少 8 个参数（0.35 / 0.4 / 0.6 / 0.8 / 两个倍率 / 默认 topK / maxOptions），且**它们之间有偏序约束**（保留 ≤ 定向 ≤ 兜底 ≤ 补充）。散着配一定会配出矛盾组合（比如把定向门槛调到 0.7 却把兜底阈值留在 0.6，结果是 0.65 分的意图既不定向也不兜底——什么都不查）。**xrag 应当把这组阈值收在一个配置类里并在启动时校验偏序关系**，这与知识库的"启动时校验 Embedding 维度一致性"是同一种做法。

- **MCP 相关内容对应待决策项 D-03。** 本篇明确了 MCP 的成本：**每个 MCP 意图要多一次 LLM 参数提取调用**，加上工具注册表、参数 Schema、执行器抽象。若 Phase 3 本期不做 MCP，本篇的 SYSTEM / KB 两条路径完全独立可用，**意图树里保留 `IntentKind.MCP` 这个枚举值但没有任何执行路径**——按 xrag 的纪律（不预留永远走不到的分支）这是不允许的。**所以 D-03 的答案会直接决定意图树的领域模型形态**，不能推迟到 Step D。

## 值得注意的设计取舍/坑

- **`retrieveAndRerank` 里的按意图分组是假的。** 代码把**同一份 `chunks`** 塞给了每一个 KB 意图：`for (NodeScore ns : kbIntents) { intentChunks.put(ns.getNode().getId(), chunks); }`。也就是说三个意图各自的 `intentChunks` 值是同一个列表引用，**"这条 chunk 是哪个意图召回的"这个信息在这里已经丢了**。下游 `formatKbContext` 按意图分组渲染上下文时，看到的是三份一模一样的内容。这大概率是多通道引擎重构后遗留的——通道化之后结果是合并的，无法再追溯归属。**xrag 若要在回答里做引用溯源（[CONTEXT.md](../../../CONTEXT.md) 定义了「引用」这个术语），必须从检索通道开始就保留召回来源**，事后补不回来。

- **子问题级 TopK 取"所有意图节点中的最大值"，是一个偏向浪费的选择。** 一个子问题命中了"退货政策"（`topK=5`）和"跨境物流"（`topK=15`），结果两个都按 15 检索。理由说得通（宁多勿少，反正有 Reranker），但代价是**内容密度高的小知识库被强行多召回了 10 条噪声**，而这些噪声要占 Reranker 的算力和候选位。取 `max` 简单，但**按各自节点的配置分别检索**才是这个字段设计的本意（`resolveIntentTopK` 里其实已经又读了一次节点自己的 `topK`——两级逻辑存在重叠，同一个字段被读了两遍且语义不同）。

- **三个全局兜底条件里，第二条会让第一条永远走不到吗？** 不会，但要看清楚：条件 1（无意图）与条件 2（最高分 < 0.6）在"意图列表为空"时都成立，代码里条件 1 先返回。真正的区别在日志文案与可观测性上——**两种情况的运营含义完全不同**（意图树覆盖不到 vs 意图树描述写得不够好），分开记是对的。xrag 的链路记录也应当区分这两种兜底原因。

- **全局兜底跑了，但没人保证它跑出来的东西更好。** 两个通道的结果合并后交给 Reranker 裁判，**这条链路的正确性完全押在 Reranker 上**。而 xrag 当前 `aliyun-qwen3-rerank-cn` 是 `enabled: false`（[检查点 §4](../PHASE-3-STEP-A-CHECKPOINT.md)），没有可用的 Rerank 能力。**没有 Reranker 的情况下开全局兜底会直接劣化答案质量**——把一堆跨库的弱相关 chunk 原样塞进 Prompt。所以 xrag 的实现顺序应当是：先定向检索，Rerank 可用之后再开全局兜底，**而不是照着原文一次做全**。

- **`temperature=0` 用于 KB 回答，理由是"不能编造细节"，但这是个常见的误解。** temperature=0 保证的是**输出稳定**（同样输入给同样输出），不保证**忠实于上下文**——模型照样会在低温下自信地编造。真正防幻觉的是 Prompt 约束（第 14 篇）与引用校验，不是采样参数。这条取舍抄可以抄，**但不要连同"温度 0 就不会编"这个理由一起抄**。

- **SYSTEM 短路仍然要调一次 LLM。** 表格里"LLM 生成 ~0.5s"这一行容易被略过——它跳过的是检索与 Reranker，不是生成。**真正完全不调模型的路径只有第 8 篇的歧义引导短路**（预拼字符串直推 SSE）。这个区别在没有 Chat 凭据时是决定性的。

- **原文这一篇里 `IntentNode` 上挂了 `collectionName` / `topK` / `promptTemplate` / `paramPromptTemplate` / `mcpToolId` 五个执行相关字段。** 第 5 篇说过"意图树不只是分类结构，它是整个 RAG 链路的路由表"——本篇是这句话的兑现。代价是**意图树节点成了一个高度耦合的胖对象**，改检索策略要动它、改工具接入要动它、改 Prompt 也要动它。xrag 设计意图树的数据模型时要意识到：**这些字段的变更频率与变更人完全不同**（运营改 description、开发改 promptTemplate、管理员改 topK），塞在一张表里意味着它们共享同一套权限与审计。
