## 完成记录

`RemoteFetcher` + `SyncCronValidator` + `DocumentService.addUrl`，9 条集成测试。

### 源站用 JDK 内置的 HttpServer 起在本地，不打真实外网

外网会让这组用例依赖网络连通性和对方站点的可用性，而这里要验的是抓取逻辑、大小限制、失败不落库，**与对端是谁无关**。本地源站还能精确构造 404、空响应、带 ETag、HTML 这些情形——真实站点上碰运气才遇得到。

工单里"URL 来源能正常触发分块"原本是手工项，这里顺手自动化了：抓取时就把文件存进了对象存储，所以分块阶段读的是同一个 `file_key`，**与 FILE 来源共用完全同一条执行链路、没有任何分支**。测试断言分块数 = 向量数。

### 一处与工单原文不同的判断：HTML 走白名单拒绝，而不是放行

工单第 6 条写的是"抓到 HTML 时**不报错**（Tika 能提取正文，噪声多是用户输入质量问题）"。实现选择了**按文件名走与本地上传相同的白名单**（`.txt/.md/.pdf/.docx`），于是 `page.html` 返回 `415`。

理由是同一条工单的下一句要求"大小限制与格式白名单与文件上传保持一致"——两句话是矛盾的。取了后者，因为：① 白名单不一致会造成"同样一个 .html 文件，本地传被拒、贴链接却能进"的怪异行为；② 从 HTML 提取出的正文夹着导航和页脚，进了向量库就是持续污染检索结果的噪声，而用户往往要到问答阶段才发现；③ 这个功能的定位本来就是**文件直链**。

**如果你更倾向工单原文（放行 HTML，靠前端提示），告诉我，改动只在 `addUrl` 的白名单那一行加一个例外。**

### 其他实现判断

- **`RemoteFetcher.head()` 失败返回 `Optional.empty()` 而不是抛异常**：很多服务器不支持 HEAD 或返回 405，那不是错误，只是第一级检测用不上——调用方应退到第二级（比内容哈希），而不是把整次同步判成失败。
- **边下边计数，超限立刻中止**。等下完再看大小，等于允许对方用一个无限流把磁盘写满。
- **`ContentHash.sha256OfFile` 分块读**，不把 50MB 文件整个读进堆——那正是学习笔记 03-03 记的那类内存放大。
- **cron 最短间隔校验在本工单实现**（工单原文把它列在 17）。这个接口在创建时就接受 `syncCron`，不校验就能存进一个 `* * * * * ?`。它是本模块**唯一一处直接与钱挂钩的输入校验**。判据是实际算出的相邻两次执行间隔，不是解析表达式字段——后者要自造一套语义，对 `0/30 * * * * ?` 这类写法很容易判错。**第一段间隔有意跳过**：它是"此刻到下次触发"，长度取决于现在几点，与表达式疏密无关。
