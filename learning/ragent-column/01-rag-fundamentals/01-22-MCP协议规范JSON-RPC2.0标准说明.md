# 《AI大模型Ragent项目》——MCP协议规范：JSON-RPC 2.0标准说明

## 一句话概括

这篇文章是 MCP 系列（01-13/01-14/01-15）的协议底层加餐：它不讲 MCP 的三层架构或 Spring AI 用法，而是专门把 MCP 借用的消息格式——JSON-RPC 2.0——拆到字段级讲清楚（Request/Notification/Response/Error/Batch 各自的必需字段、互斥规则、边界情况），并额外补了一份规范本身不管、但工程落地必须自己做的清单（入参校验、超时重试、幂等去重、日志链路、鉴权签名、版本灰度、错误码分层）。

## 核心内容提炼

- **为什么 MCP 选 JSON-RPC 2.0，而不是自己发明协议**：文章先做了一次分层澄清——REST/Feign/Dubbo/gRPC 解决的是"业务接口用什么框架调用"的问题；JSON-RPC 2.0 解决的是"请求/响应/通知这几种消息该长什么样"的协议层封装问题；MCP 是在 JSON-RPC 2.0 之上，再定义 tools/resources/prompts 这套能力模型。三者不是替代关系，是分层叠加关系。选 JSON-RPC 2.0 的直接动机是：如果没有统一的消息结构标准，不同语言、不同框架实现的 MCP Client 和 Server 之间就无法互操作，大模型也没法用统一方式调用外部工具。JSON-RPC 2.0 本身不绑定传输层，可以跑在 HTTP、WebSocket、stdio 之上，但它明确不管鉴权、服务发现这些工程能力，这些必须在网关/框架/系统规范里另外补。

- **JSON-RPC 2.0 的定位与版本边界**：一句话定义是"用 JSON 描述一次远程方法调用的轻量 RPC 协议"，设计哲学是简单优先。规范发布于 2010 年 3 月 26 日，且 2.0 与 1.0 不兼容——区分方式是 2.0 的请求/响应对象都必须带 `"jsonrpc": "2.0"` 字段，1.0 没有这个字段。文章反复强调这一点是因为 MCP 生态里所有实现默认都是 2.0，混入 1.0 语义的代码会直接不兼容。

- **四种消息结构 + 两个角色**：核心对象是 Request（发起调用）、Notification（无需回包的请求）、Response（服务端响应）、Batch（批量打包多个请求）。角色只有 Client（发请求方）和 Server（收请求并返回结果方），但文章特别指出角色是相对的——同一个程序在调用链里可以先是 Server（被上游调）再是 Client（调下游），例如服务 A 调 B 时 A 是 Client，B 转头调 C 时 B 又变成 Client。

- **Request Object 字段级规则**：
  - `jsonrpc`（必需）：必须精确等于字符串 `"2.0"`。
  - `method`（必需）：字符串类型，且以 `rpc.` 开头的方法名是协议保留的，不能用作业务方法名（例如 `getUserInfo`、`order.create` 是合法命名，但 `rpc.xxx` 不行）。
  - `params`（可选）：只能是 Object（按名称传参，如 `{"userId":"12345"}`）或 Array（按位置传参，如 `[42,23]`）二选一；省略表示无参调用。命名参数的字段名必须与服务端约定完全一致，**包括大小写**——这是一个隐蔽的跨语言/跨团队互操作陷阱。
  - `id`（条件必需）：类型是 String/Number/Null。**没有 id 字段本身就是 Notification 的判定依据**（不是靠某个显式的 type 字段）；服务端必须在响应里原样带回相同的 id；规范建议不要用 Null 做 id，Number 类型不要带小数。

- **Notification 的强约束**：Notification 就是没有 id 字段的 Request，规范要求服务端**永远不能**为它返回 JSON-RPC Response 对象——哪怕执行报错，客户端也感知不到（因为规范不允许把错误包成响应发回去）。如果底层传输是 HTTP，服务端仍然要给一个 HTTP 层的响应（比如 204 No Content），但那不是 JSON-RPC 语义上的 Response。适用场景是调用方根本不关心结果、也不想为等响应/重试/去重付出成本的场合，比如日志埋点、旁路异步触发。

- **Response Object 的互斥规则**：服务端处理非 Notification 的请求时必须返回 Response，字段包括 `jsonrpc`（同样必须是 "2.0"）、`result`（成功必须有、失败必须没有）、`error`（失败必须有、失败必须没有的反面，值必须是 Error Object）、`id`（正常情况下与请求 id 一致；如果服务端连请求都解析不了，id 必须设为 null）。**核心约束是 result 和 error 必须"有且只有一个"存在**，两者都出现或两者都不出现都是违规实现。

- **Error Object 与规范预留错误码区间**：Error 对象三个字段——`code`（必须是整数）、`message`（人类可读的简短描述）、`data`（可选，任意 JSON 值，放调试上下文）。规范把 **-32768 到 -32000** 整段保留给协议层，其中定义了 5 个标准码：-32700 Parse error（JSON 解析失败）、-32600 Invalid Request（请求对象本身不合法）、-32601 Method not found（方法不存在）、-32602 Invalid params（参数不对）、-32603 Internal error（JSON-RPC 内部错误），另外 -32000~-32099 保留给具体实现自定义使用（比如给基础设施类错误）。这个区间之外的错误码空间才是留给业务自定义的。

- **Batch 的完整规则和 5 类边界情况**（文章明确说这是 JSON-RPC 2.0 里最容易被实现错误的部分）：
  - 基本规则：请求侧发一个 Array，里面可以混合普通 Request 和 Notification；响应侧服务端返回一个 Array，但**只有带 id 的请求才对应一条 Response，Notification 不产生 Response**；响应顺序不保证和请求顺序一致，客户端必须靠 id 匹配；服务端可以并发处理 Batch 内的请求。
  - 边界情况 1——4 个请求里有 1 个 Notification：只返回 3 条响应，顺序不保证。
  - 边界情况 2——Batch 全是 Notification：不返回任何 JSON-RPC Response，HTTP 场景下通常是 204 或 200+空 body。
  - 边界情况 3——Batch 是空数组 `[]`：这本身是无效请求，返回**单个**（不是数组）`{"error":{"code":-32600,...},"id":null}`。
  - 边界情况 4——Batch 数组里的元素不是合法 Request 对象（如 `[1,2,3]`）：给数组里每个非法元素分别返回一条 `id:null` 的 Invalid Request 错误，凑成一个错误数组。
  - 边界情况 5——整个 Batch 都不是合法 JSON：返回单个 Parse error（-32700），因为连数组结构都解析不出来，无法按元素处理。

- **8 类最容易踩的实现错误**（文章逐条给了错误示例和修正示例）：①漏写 `jsonrpc:"2.0"`；②给 Notification 返回了 Response（哪怕内容是 `{"result":"OK","id":null}` 也不行）；③`result` 和 `error` 同时出现在一个 Response 里；④`method` 传成了非字符串（如数字）；⑤`params` 传成字符串等非 Object/Array 类型；⑥命名参数大小写不匹配（如约定 `userId`，实际传了 `userid`）；⑦Batch 全是 Notification 时错误地返回了空数组 `[]`（正确做法是完全不返回 JSON-RPC 响应体）；⑧业务错误滥用协议保留码（如用 -32603 表示"用户不存在"，正确做法是用户不存在这类业务语义应该用 1000+ 的自定义正数错误码，把 -32768~-32000 严格留给协议/基础设施层）。

- **规范之外必须自己补的 7 块工程能力**（这是文章篇幅最长、实操价值最高的部分，逐块给了 Java 风格伪代码）：
  1. **输入校验分三层**：协议层（jsonrpc 字段值、method 类型、params 类型、id 类型、result/error 互斥性）、业务层（参数类型/范围/必填/参数间逻辑关系，如开始时间早于结束时间）、安全层（参数长度限制防大 JSON 攻击、内容过滤防注入/XSS、方法名白名单防调内部方法、频率限制防暴力调用）。
  2. **超时与重试**：客户端要设合理超时（5~10 秒级）、区分读超时与写超时；重试只对幂等方法（查询/删除）做，非幂等方法（创建/支付）要谨慎；重试用指数退避（1s→2s→4s）、次数有上限（如 3 次）、且重试时保持同一个 id 以便服务端识别去重；服务端要设方法执行超时（如 30 秒）防止慢查询拖垮整个服务，超时后返回 -32000 或自定义码并记日志。
  3. **幂等去重**：用 Redis 或内存缓存按 id 记录最近处理过的请求（如最近 5 分钟），收到重复 id 直接返回缓存的响应而不重新执行；只对带 id 的请求做去重，Notification 天生不需要（没有响应可去重）；去重 key 建议加上客户端标识（`clientId:requestId`）避免不同客户端的 id 撞车；缓存窗口不宜过长以免内存膨胀。
  4. **日志与链路追踪**：每条调用要记请求 id、方法名、参数（敏感信息脱敏）、结果、耗时、客户端 IP/User-Agent、Trace ID；Trace ID 通过 HTTP Header（如 `X-Trace-Id`）或协议扩展字段在服务间传递，配合 ELK/Jaeger/Zipkin 做链路可视化，因为调用链可能很长（客户端→网关→服务A→服务B）。
  5. **鉴权与签名**：优先做传输层鉴权——HTTPS+API Key（Header 带 Bearer Token）、HTTPS+JWT（验签+验过期）、mTLS（双向证书验证）；应用层鉴权（在 JSON-RPC 请求里加 `auth` 字段）文章明确**不推荐**，理由是会把鉴权逻辑和业务逻辑耦合在一起，破坏分层设计，只在没有其他选择时才用；另外可以做签名防篡改，客户端用私钥签名（内容含请求体+时间戳+nonce 防重放），服务端用公钥验签。
  6. **兼容性与灰度**：版本号可以放在方法名（`getUserInfo_v1/v2`）、HTTP 路径（`/api/v1/jsonrpc`）或协议扩展字段里三种方式之一；灰度策略是按客户端标识（User-Agent/IP/用户 ID）路由到不同版本，配合 Feature Flag 控制开关，并监控新版本错误率/响应时间以便快速回滚。
  7. **错误码分层与文档化**：明确三层——协议层错误（-32768~-32000，直接用规范定义的码）、基础设施错误（复用规范保留的 -32000~-32099 Server error 区间，比如数据库连接失败、Redis 超时）、业务错误（正数自定义，如 1001 用户不存在、2001 余额不足）；建议维护一份包含"错误码/message/含义/解决方案"四列的错误码表格，写进 API 文档，并用枚举/常量定义避免硬编码散落在代码各处。

- **一次调用的完整流程图（文字描述）**：文章用时序图描述了 5 种典型场景——①普通 Request 成功：带 id 请求→服务端校验格式→执行业务逻辑→返回带 result 的响应；②普通 Request 失败：业务逻辑抛异常→返回带 error 的响应，id 保持不变；③Notification：无 id 请求→服务端执行但不返回任何响应；④协议错误：JSON 解析失败→返回 Parse error，id 为 null（因为连请求 id 都读不出来）；⑤Batch：发一个 Array→服务端可并发处理→只给带 id 的请求生成响应→响应顺序可以和请求顺序不同。

- **文末小结重申的核心心智模型**：一次标准调用 = Request + Response；Notification 本质也是 Request，只是没有 id 所以不需要响应；Response 里 result 和 error 二选一；Batch 只是把多条 Request/Notification 打包发送，是否返回响应仍然取决于每条内部有没有 id；协议内置错误码解决的是协议层问题，和业务异常码是两套体系不能混用。进一步阅读指向了 JSON-RPC 2.0 官方规范（jsonrpc.org/specification）、JSON 规范 RFC 4627、规范关键词定义 RFC 2119。

## 关键概念/术语

JSON-RPC 2.0：用 JSON 描述一次远程方法调用的轻量协议，2010 年 3 月发布，与 1.0 不兼容，MCP 采用它作为消息层格式。
Request Object：一次 RPC 调用的请求消息，必需字段 jsonrpc/method，可选 params，条件必需 id。
Notification：没有 id 字段的 Request，服务端永远不为其返回 Response，即使出错也不例外。
Response Object：服务端对非 Notification 请求的响应，result 与 error 必须二选一，id 需与请求匹配或在无法识别请求时为 null。
Error Object：响应失败时的错误结构，字段为 code（整数）/message（字符串）/data（可选），-32768~-32000 为协议保留区间。
Batch：把多个 Request/Notification 打包成一个 JSON Array 一次发送，响应也是 Array 但只包含有 id 的请求对应的结果，顺序不保证、靠 id 匹配。
rpc. 前缀保留方法名：JSON-RPC 规范保留给协议内部/扩展使用的方法名命名空间，业务方法不能用这个前缀。
幂等去重（Idempotency Dedup）：按请求 id 缓存已处理过的响应，重试时直接命中缓存返回而不重复执行副作用操作。
Trace ID：贯穿一次调用链路（客户端→网关→多个下游服务）的唯一标识，用于日志聚合和问题定位。
mTLS：双向 TLS，客户端和服务端互相验证证书，是 JSON-RPC 传输层鉴权的一种推荐方式。

- 这篇是 01-13《MCP协议入门与实践》、01-15《MCP之官方Java-SDK深度解析》两篇里"JSON-RPC 是 MCP 的底层消息格式"这句话的字段级展开——01-15 提到 `McpSchema` 里的 `CallToolRequest`/`CallToolResult` 最终会被包进标准 JSON-RPC 结构（如 `{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{...}}`），本篇把这个"包法"背后的强制规则（result/error 互斥、id 匹配规则、Notification 不回包）讲清楚了。xrag 走的是 Spring AI + 官方 Java SDK 路径，SDK 的 Schema 层和 Session 层已经把这些规则实现好了，日常开发基本不需要手写 JSON-RPC 校验代码，但**排查协议层异常时**（比如工具调用没收到响应、或者响应结构看起来不对）需要对照本篇的字段规则去判断是 SDK 用法错了还是对端（尤其是自建/第三方 MCP Server）实现不合规。
- 本篇"规范之外必须自己补的 7 块工程能力"里，**幂等去重**和**超时重试**两块直接对应 01-13 提到的 `MCPToolExecutor`（工具执行器）在真实生产场景下需要补的逻辑：工具调用失败重试时要按请求 id 去重、非幂等工具（比如触发下单、发送通知类的 MCP 工具）不能无脑重试，这是 xrag 设计工具调用重试策略时必须提前想清楚的边界，而不是简单包一层 retry 装饰器就完事。
- **错误码分层**（协议层 -32768~-32000 / 基础设施层 -32000~-32099 / 业务层自定义正数）这条规则应该直接作为 xrag 定义自己 MCP 工具错误码规范的依据——工具执行失败时的错误应该用业务正数码（比如"知识库不存在""检索超时"各给一个固定编号），不能像文章里的反例那样偷懒复用 -32603 之类的协议保留码，否则客户端没法区分"是协议出问题"还是"是业务逻辑判定失败"。
- **鉴权部分**明确指出 JSON-RPC/MCP 协议本身不管鉴权，且不推荐把鉴权字段塞进业务请求体里——这直接呼应 01-13 提出的"MCP 远程 Server 认证方式还没有统一标准，需要自己定"这个局限性，本篇给出的具体落地选项（HTTPS+API Key、HTTPS+JWT、mTLS）可以作为 xrag 给 Streamable HTTP 方式暴露的 MCP Server 选鉴权方案时的候选清单，优先在传输层（网关/Header）解决，不要往 JSON-RPC 请求体里加自定义鉴权字段。
- 日志与链路追踪那部分要求的字段清单（请求 id、method、脱敏后的 params、耗时、Trace ID）可以直接对照 xrag 现有的可观测性设计（Trace ID 贯穿多服务调用）来补齐 MCP 工具调用这一段的埋点，避免出现"业务链路有 Trace，工具调用这一跳单独丢失可观测性"的断层。

## 值得注意的设计取舍/坑

- **Notification 出错也不告诉你，是设计选择不是 bug**：规范明确要求 Notification 即使执行失败也不能返回错误对象，这意味着一旦某个调用被设计成 Notification（没带 id），调用方就彻底放弃了感知失败的能力。如果业务上其实关心"日志到底写成功没有"，就不该用 Notification，这是一个容易被"看起来省事"诱导而做错的选择。
- **Batch 全是 Notification 时必须不返回响应体，而不是返回空数组**：这是文章明确点名的高频错误——很多实现会想"没有内容就返回 `[]`"，但规范要求的是完全不产生 JSON-RPC 响应（HTTP 层面对应 204 或空 body），返回 `[]` 本身就是不合规的响应。
- **命名参数大小写不匹配是隐蔽的跨团队/跨语言坑**：JSON 字段名大小写敏感，客户端传 `userid`、服务端期望 `userId` 会被当成参数缺失处理（Invalid params），且报错信息往往不会直接提示"是不是大小写错了"，排查成本较高，尤其是 Client 和 Server 分别由不同团队或不同语言实现时更容易踩。
- **业务错误码不能偷懒复用协议保留码**：把"用户不存在"这类业务语义塞进 -32603（Internal error）会让客户端无法区分"协议/基础设施出问题需要重试或告警"和"业务逻辑判定失败需要提示用户"，这是协议层错误码和业务异常体系混用的典型反模式。
- **应用层鉴权字段是一个明确被文章判了"不推荐"的取舍**：把 `auth` 字段塞进 JSON-RPC 请求体technically可行，但会让鉴权逻辑和业务方法处理逻辑耦合在同一段代码里，违反分层设计；文章的态度是"有时必须用，但不是推荐做法"，优先级应该始终是先考虑传输层方案。
