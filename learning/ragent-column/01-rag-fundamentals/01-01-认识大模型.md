# 《AI大模型Ragent项目》第1小节：认识大模型

> 原文链接：https://t.zsxq.com/qlL8D
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇是整个 Ragent 系列的开篇铺垫，回答的是"在写代码调用大模型 API 之前，Java 开发者需要先搞懂哪些大模型基础概念"——即大模型是什么、怎么分类、Token/上下文窗口/Temperature/MoE 等核心参数含义，以及为什么必须通过 API 而不是网页来把大模型接入自己的系统。

## 核心内容提炼

**1. 大模型和传统方案的本质差异**
- 传统 if-else 客服逻辑靠硬编码规则匹配关键词，用户表达方式一变就失效（"退货""东西不想要了""买错了能退吗"是同一意图，但字面完全不同）。
- 传统 NLP（关键词匹配、TF-IDF、朴素贝叶斯）比 if-else 聪明一点，本质仍是统计词频/概率，不理解语义。
- LLM 的路径是"喂海量文本数据（书籍、网页、代码等），让模型自己从中归纳出语言规律"，而不是人工写规则——这是它能理解同义改述表达的根本原因。

**2. 参数量（模型的"大"）**
- 参数 = 模型内部的数字权重，数量级用 B（十亿）表示，如 7B=70亿、72B=720亿。类比人脑突触连接数（约100万亿）。
- 参数越多，知识容量和语言处理能力越强，但计算资源需求（显存/算力）也越高。
- 原文给出的参数量级—代表模型—能力—硬件需求对照（本地部署视角）：
  - 1.7B（如 Qwen3-1.7B）：简单对话/分类，消费级显卡 4GB 显存
  - 8B（Qwen3-8B、Llama3-8B）：日常问答、基础代码生成，8~16GB 显存
  - 14B（Qwen3-14B）：中等复杂度任务，16~24GB 显存
  - 32B（Qwen3-32B）：接近大参数模型能力，24~48GB 显存
  - 72B（Qwen3-72B）：接近顶级闭源模型，多卡服务器 80GB+ 显存
  - 671B（DeepSeek-V3）：对标 GPT-4 级别，需大规模集群
- 关键结论：**参数越大越好是误区**。通过 API 调用时硬件问题由平台方解决；即便本地部署，RAG 问答场景 14B/32B 通常已够用，选型要看场景不是一味堆参数。

**3. 四个反复出现的核心概念**
- **Token**：模型处理文本的最小单元，不等于字/词。英文约 1 词≈1~1.5 token；中文约 1 字≈1~2 token。重要性：(a) API 按 token 计费；(b) 上下文窗口按 token 计算而非字数。
- **上下文窗口（Context Window）**：一次对话中模型能看到的 token 总量上限（涵盖 system prompt + 历史对话 + 当前问题 + 回答），超出会截断早期内容。常见档位：4K/8K/32K/128K/1M token，分别对应约 2000~3000 字到 50万~75万字中文。这个概念直接解释了 RAG 为什么必要——整本产品手册几十万字远超窗口，且信息太多模型也会"迷失",所以要先检索最相关片段再喂给模型。
- **Temperature**：控制输出随机性/创造力的参数。0=每次选最高概率词，稳定但死板；0.7=自然有变化；1.0+=更随机更有创意但也更容易"胡说"。场景推荐值：RAG 问答 0~0.3、代码生成 0~0.2、日常对话 0.5~0.7、创意写作 0.7~1.0。RAG 场景通常压到 0~0.1，因为答案已在检索片段里，模型只需忠实转述，不需要发挥。
- **MoE（Mixture of Experts，混合专家）**：与传统 Dense（稠密）模型（每次推理所有参数都参与计算）不同，MoE 把模型拆成多个专家子网络，每次推理只激活一部分。例如 DeepSeek-V3 总参数 671B，但每次推理只激活 37B，即"671B 的知识容量，37B 的推理成本"。看到"671B（37B 激活，MoE）"这种标注时，实际推理资源消耗对应激活参数（37B），不是总参数。

**4. 当前主流大模型地图**
- 国际闭源：GPT 系列（OpenAI，综合能力/Agent 生态最成熟）、Claude 系列（Anthropic，代码与长上下文突出、computer-use/Agent 能力强）、Gemini 系列（Google，原生多模态+超长上下文最高 1M）；Llama 系列（Meta）是开放权重但国内用中文效果和门槛都不占优。国内访问 GPT/Claude/Gemini 有网络门槛。
- 国内开源主线：**DeepSeek**（V3 通用对话 + R1 推理增强，MIT 开源、性价比高、API 定价行业低位）和 **Qwen 通义千问**（阿里，尺寸覆盖最全、agentic 方向强、Apache-2.0 开源生态完善）是文章反复强调后续系列会重点使用的两个系列。此外还提及智谱 GLM、MiniMax、Kimi 等国内厂商各自定位（长上下文、Agent、编码等方向）。
- 文章给了一张详细的模型对比表（厂商/参数量/上下文窗口/开源与否/特点），核心结论是"选型要匹配场景"，而非追新追大。

**5. 基座模型（Base Model）vs Chat 模型**
- 训练分两阶段：预训练（Pre-training，学语言规律，得到 Base 模型）→ 对齐训练（Alignment，通过指令微调 Instruction Tuning + RLHF，教会模型服从指令，得到 Chat/Instruct 模型）。
- Base 模型只会"续写"，不会"服从指令"——给它一句情绪分析指令，它可能不输出"负面"而是继续编造更多用户反馈文本，因为它只是在预测下一个最可能出现的词，不理解"指令"这个概念。
- 命名规律：`-Instruct`/`-Chat` 后缀（如 Qwen2.5-7B-Instruct）明确标注是对话模型；到 Qwen3 之后新模型默认发布即为 Chat 版，不再需要后缀；DeepSeek 用 V3（通用对话）/R1（推理增强，R=Reasoning）区分；同一模型在不同平台（HuggingFace/Ollama/SiliconFlow）命名可能有差异（是否带 Instruct 后缀、是否加命名空间前缀）。
- **RAG 系统只需要 Chat 模型**：因为最后一步"根据检索片段回答问题"需要模型理解指令、按要求组织语言，这正是 Chat 模型的能力；Base 模型只会顺着文本往下续写，做不到这一点。

**6. 模型量化（本地部署相关，API 调用不用管）**
- 参数本质是一堆浮点数权重。浮点数格式在"数值范围（指数位）"与"精度（尾数位）"之间做权衡：
  - FP32（4字节/参数）：全精度，占用大，现在很少直接存权重。
  - BF16（2字节）：指数位同 FP32（范围大，不易溢出），尾数位少（精度稍低）——当前训练和推理的主流默认精度。
  - FP16（2字节）：尾数位多于 BF16（精度更高），但指数位少，数值范围小（±65504），训练时容易溢出。
  - TF32：NVIDIA GPU 内部使用，开发者一般无需关心。
- 量化：把权重从 BF16/FP16 进一步压缩到 INT8（1字节/参数）、INT4（0.5字节/参数），以精度换体积/显存。7B 模型显存粗估：FP32≈28GB、BF16/FP16≈14GB、INT8≈7GB、INT4≈3.5GB（实际还要加 KV Cache 等开销，建议预留 1.2~1.5 倍）。
- 常见量化格式：GPTQ/AWQ 需 GPU 推理（AWQ 更快、精度相当）；GGUF 支持 CPU 推理，是 llama.cpp 生态标准格式，适合无独显场景。
- 量化等级（GGUF 命名如 Q4_K_M/Q5_K_M/Q8_0）：数字越大精度越高体积越大；Q4_K_M（INT4）性价比最高，多数本地部署场景够用。
- **重要边界**：这一整块量化知识只在"本地部署模型"时才需要关心；通过 API 调用（本系列的技术路线）时平台方已处理好，开发者不用管。

**7. 深度思考模式 / 思维链（Chain of Thought, CoT）**
- 深度思考（如 DeepSeek-R1）在给出最终答案前，先生成一段可见的 thinking 内容（一步步的推理过程），再输出结论——类似考试先打草稿再誊抄答案。
- 原理：把推理过程显式展开、逐步推导，比直接"蹦出"答案准确率更高（类比心算 17×24 直接算容易错，分步算 17×20+17×4 更准）。
- 代价：响应变慢、Token 消耗增加（thinking 内容也计入 token）。
- 适用边界：数学计算/逻辑推理/复杂代码生成/多方案对比等需要推理的场景适合开启；简单问答、日常闲聊、以及**RAG 场景下的知识检索回答通常不需要**——因为答案已经在检索到的文本片段里，模型只需理解、提取、组织语言，不需要推理计算，开深度思考只是多花 token、拖慢响应。这是文章给 RAG 系统的一条明确工程建议。

**8. 为什么必须用 API 而不是网页**
- 网页端本质上也是在背后调用 API，只是把调用细节和一个前端 UI 包装好了给个人用户用。
- 网页端对开发者的六个局限：无法集成进已有系统（如 Java 客服系统）、无法批量处理、无法自定义 system prompt 模板、无法控制 temperature/max_tokens 等参数、无法实现 RAG 检索+拼接流程、业务数据要经浏览器发到第三方服务器存在数据安全风险。
- API 调用本质是把大模型当"远程函数"：输入一段文本（含 system prompt + user message + 参数如 temperature），返回一段文本。文章给了 Java 伪代码和真实的 SiliconFlow curl 示例作为直观感受。

**9. 本系列的技术选型（对后续文章的定位说明）**
- API 平台：**SiliconFlow（硅基流动）**——国内可直连、注册简单（手机号）、新用户有免费额度、支持多种开源模型、且 **API 兼容 OpenAI 协议**（这点被强调为重要，意味着切换到 OpenAI/DeepSeek 官方 API 或其他兼容平台时代码几乎不用改）。
- 模型选择：**Qwen 系列**——中文效果好、开源社区活跃、SiliconFlow 上部分 Qwen 模型可免费调用、尺寸覆盖全（7B~72B）可按场景灵活选。
- 不直接用 GPT 系列的三个原因：国内网络访问门槛、API 成本较高、国内开源模型中文效果已经足够好，没必要"舍近求远"。

## 关键概念/术语

Token：大模型处理文本的最小单元，中英文切分粒度不同，决定计费和上下文占用量。
上下文窗口（Context Window）：模型单次对话能处理的 token 总量上限，超出部分会被截断丢弃。
Temperature：控制输出随机性/创造力的采样参数，值越低越确定，越高越有创意也越容易出错。
MoE（Mixture of Experts）：模型架构，把参数拆成多个专家子网络，每次推理只激活部分专家，用低于总参数量的推理成本获得大参数量的知识容量。
基座模型（Base Model）：只经过预训练、只会"续写文本"、不理解指令的原始模型。
Chat/Instruct 模型：经过指令微调和 RLHF 对齐训练、能理解并服从人类指令的模型，是开发者实际调用的对象。
量化（Quantization）：把模型权重从高精度（如 BF16）压缩到低精度（如 INT8/INT4），用精度损失换取显存/存储体积下降，仅本地部署时需要关心。
BF16/FP16/FP32：浮点数存储精度格式，区别在于"数值范围（指数位）"与"精度（尾数位）"的分配方式；BF16 是当前主流的模型权重默认精度。
思维链（Chain of Thought, CoT）/深度思考：模型在给出最终答案前先显式生成分步推理过程（thinking），以提升复杂推理类任务的准确率，代价是延迟和 token 消耗增加。

## 与 xrag 项目的关系

这篇文章明确给出了 xrag 项目在模型调用层面的技术选型基线，可以直接指导后续设计：
- API 层应设计为兼容 OpenAI Chat Completions 协议的调用方式，优先对接 SiliconFlow 平台，同时保留切换到其他 OpenAI 协议兼容平台（DeepSeek 官方、其他厂商）的可替换性。
- 模型选择上默认使用 Qwen 系列 Chat/Instruct 模型（而非 Base 模型），具体尺寸（7B~32B 等）按后续 RAG 问答场景的复杂度决定，不必一开始就选最大参数版本。
- 生成阶段的调用参数应遵循：Temperature 设低（0~0.3）以保证 RAG 答案忠实于检索片段；除非涉及复杂多步推理的场景，默认不开启深度思考（CoT）模式以节省 token 和延迟。
- 上下文窗口的概念直接关联到 xrag 的检索策略：必须先做片段检索、控制拼给模型的上下文长度，而不能指望把整份文档直接喂给模型，这是 RAG pipeline 存在的根本原因之一，后续设计 chunk 策略和 top-k 检索数量时要以模型的上下文窗口大小和"信息过多会分散注意力"这一点作为约束。
- Token 计量将直接影响 xrag 的成本估算和限流/截断逻辑设计（输入输出都计费，需要在系统里预留 token 用量监控）。

## 值得注意的设计取舍/坑

- "参数越大越好"是常见误区：更大参数模型意味着更高延迟和成本，RAG 问答场景 14B/32B 通常已经够用，选型要按场景而不是一味追求旗舰模型。
- MoE 模型标注的总参数量（如 671B）不代表实际推理开销，真正对应的是激活参数量（如 37B），评估硬件/成本需求时不能被总参数的数字唬到。
- 深度思考（CoT）不是普适增强：会显著增加延迟和 token 消耗，RAG 问答场景因为答案已经在检索片段里，开深度思考反而是浪费，需要按场景显式关闭。
- FP16 与 BF16 都是 16 位，但取舍方向相反：FP16 精度更高但数值范围小、训练容易溢出；BF16 范围大更稳定但精度略低，这是当前大模型训练/推理选择 BF16 而非 FP16 作为默认精度的直接原因。
- 量化格式选择要匹配硬件：有 NVIDIA 显卡优先 AWQ/GPTQ（需要 GPU），显存不够或想用 CPU 跑则选 GGUF——但这整块知识只跟本地部署相关，通过 API 调用时不需要关心，容易在学习时把精力错放在不相关的本地部署细节上。
- 同一模型在不同平台（HuggingFace/Ollama/SiliconFlow）上的命名可能不一致（是否带 `-Instruct` 后缀、是否加命名空间前缀），对接多平台 API 时需要注意模型名字符串本身不是可移植的标识，要按平台文档核对。
