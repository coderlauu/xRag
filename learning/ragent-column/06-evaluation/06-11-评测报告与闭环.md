# 《测评报告》

> 原文链接：https://t.zsxq.com/PrCzD
> 所属分组：06-evaluation RAG 评测体系

## 一句话概括

评测产物应让机器能守门、研发能下钻、负责人能决策，并把失败样本回流成新的回归用例；展示层不能替代可审计的原始记录和指标定义。

## 核心内容提炼

- 课程为 CI 输出 `_scores.json`，为研发输出 `report.md`、`per_sample.csv`、`failures.jsonl`，为汇报输出 `slides.html`。
- 数据流继续遵循“录制一次，评分 N 次，报告 M 次”：runs、scores 和 reports 分层缓存，各层可独立重算。
- 报告按 overall → 二级意图 → per sample 三层下钻，防止总体均值掩盖局部高风险退化。
- 一条样本可同时有多个失败原因，保留“检索 miss + 答案错误”等故障链，比只选一个根因更诚实。
- A/B diff 展示 before、after、delta；发现的真实 bad case 经脱敏和复标后回流评估集，形成持续回归闭环。

## 关键概念/术语

- **机器可读报告**：包含指标定义、值、样本数和资格状态，可由门禁程序消费。
- **失败归因**：根据多项事实缩小排查范围，不等同于自动证明根因。
- **A/B diff**：在可比评测配置和样本上比较两个系统版本。
- **Bad-case 回流**：把线上或评测发现的问题转成长期回归样本。

## 与 xrag 项目的关系

- 第一版不一定需要新评测页面。版本化 JSON/JSONL + Markdown/CSV 已可满足机器守门和研发复核；是否做 UI 留给 Step B 项目所有者裁决。
- 每份报告头部必须显示可比性身份：数据集、知识库/意图 revision、代码、Prompt、被评模型、judge、指标实现版本和运行时间。
- 指标值旁必须显示有效样本数、失败/跳过数和置信信息；只给百分比无法发现分母变化。
- failures 只存必要预览或引用，敏感正文通过受控查看路径读取；报告不应成为用户问题和知识库正文的第二份永久副本。

## 值得注意的设计取舍/坑

- 漂亮 slides 是可选展示，不是 Phase 4 首版质量体系的前置；先保证 JSONL、指标定义、失败下钻和可复现。
- 固定绝对阈值和任意 delta 门禁都可能误伤。发布门禁应区分确定性回归、judge 噪声、高风险样本和人工裁决。
- Bad case 回流若直接围绕当前实现修题，会造成评估集过拟合；新增样本要保留独立验证集或定期轮换盲测集。
