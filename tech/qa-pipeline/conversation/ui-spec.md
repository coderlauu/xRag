## 1. 设计问题

问答页最终要成为用户发问和阅读答案的主入口，但 3A 只交付“理解层”。界面必须同时解决：

1. 用户能自然地创建、切换和继续对话。
2. 歧义时系统以一条正常对话消息请用户选择，不让用户理解内部评分。
3. 3A 验收者能看见规范化问题、子问题、意图和降级事实，但这些信息不能伪装成助手答案或思维链。
4. 页面结构能自然接入 3B 来源/工具和 3C 流式/停止，而不需要推倒重来。

原型用三个结构明显不同的方案回答这个问题：

- **A — Conversation + Inspector**：左侧对话列表、中央消息、右侧可收起的本轮处理面板。
  2026-08-07 选中，2026-08-08 改判为落选。
- **B — Pipeline Workbench**：处理阶段是页面主骨架，消息与对话历史退居下方/侧边，更适合开发验收。
- **C — Focused Chat（已选择，2026-08-08）**：中央单列沉浸对话，对话列表与本轮处理都是按需打开的抽屉，
  更接近最终用户产品。

## 2. 与现有应用的关系

### 2.1 顶部导航

建议顺序：

```text
xrag | 问答 | 知识库 | 意图树 | 诊断
```

- `问答` 与 `意图树` 是 Phase 3 新增顶级入口。
- 3A 期间根路径仍可保持跳转知识库；Phase 3 完整关闭时再把根路径切到 `/chat`。
- 原型展示完整导航，但所有非本页链接都不执行真实跳转。

### 2.2 页面宽度（2026-08-08 按 C 改写）

- 消息主列固定为居中单列，正文测量宽度 760px 上限；窗口再宽也不拉伸正文行长。
- **对话列表与本轮处理在所有断点上都是抽屉**，包括 1440px。桌面不再有常驻侧栏，
  因此不受 `.app-main` 1100px 限制影响。
- 720px 以下抽屉转为全高覆盖层；消息输入始终可达。

## 3. 信息架构

C 方案下，`对话列表` 与 `本轮处理` 两支都是按需打开的抽屉，不是常驻栏；下面的层级是逻辑归属，不是屏幕分栏。

```text
/chat
  ├─ 顶部应用导航
  ├─ 对话列表（抽屉）
  │    ├─ 新对话
  │    ├─ 搜索/筛选（3A 只做标题过滤）
  │    └─ 最近对话
  ├─ 当前对话
  │    ├─ 标题与对话操作
  │    ├─ 消息时间线
  │    ├─ 歧义引导卡
  │    └─ 消息输入区
  └─ 本轮处理（抽屉）
       ├─ 本轮结果（3B 起，§13.2）
       │    ├─ 来源
       │    └─ 工具
       └─ 处理详情（3A 验收信息）
            ├─ 阶段与稳定终态
            ├─ 原问题 / 规范化问题
            ├─ 子问题
            ├─ 意图路径与分数区间
            ├─ 检索动作描述
            └─ 降级事实
```

## 4. 页面共同区域

### 4.1 对话列表

每项只展示：

- 标题，最多两行；
- 最近活动相对时间；
- 最近一条用户可见消息的单行摘要；
- 当前是否有待处理的歧义选择。

行为：

- `新对话`立即打开空白对话，不提前落库；首条消息保存时才创建真实记录。
- 点击对话切换；当前输入未发送可保留在当前对话的页面内存，切回后恢复。
- 标题重命名使用轻量弹层；删除必须二次确认并说明“消息将从列表隐藏”。
- 3A 不提供文件夹、置顶、分享、批量删除或全文搜索。

状态：

| 状态 | 表现 |
|---|---|
| 初次加载 | 6 个中性骨架项，不显示假标题 |
| 空列表 | `还没有对话` + `发出第一个问题后会自动保存` |
| 加载失败 | 列表区错误 + 重试；不清空已打开的当前对话 |
| 当前对话被删除 | 返回空白新对话并给出成功提示 |

### 4.2 对话头部

包含：

- 当前标题；新对话显示 `新对话`；
- `本轮处理`开关（桌面 A 方案可控制右栏，其他方案打开抽屉/区域）；
- 更多菜单：重命名、删除。

不得包含：模型选择、Provider 选择、Temperature、服务等级或“深度思考”开关。

### 4.3 消息时间线

消息类型：

| 类型 | 视觉与内容 |
|---|---|
| 用户消息 | 右对齐或有明确用户标识；保留原文，不展示规范化后的替换文本 |
| 助手消息 | 3A 仅用于歧义引导、超限提示和无法确定方向等真实系统回复；不生成假答案 |
| 系统提示 | 轻量居中状态，如“已根据你的选择明确为 3C 数码” |
| 失败提示 | 靠近对应消息，说明可重试动作；不把整页变红 |

- 历史按时间顺序加载；加载更早消息的入口在顶部。
- 时间戳默认弱化，悬停/聚焦或消息间隔较大时显示。
- 原问题始终保留在消息中，规范化问题只出现在验收信息。

### 4.4 输入区

必须包含：

- 多行文本框，提示 `输入你的问题…`；
- 发送按钮；
- 辅助提示 `Enter 发送 · Shift+Enter 换行`；
- 当前有活动本轮时输入与发送禁用，并说明正在处理。

第一版限制：

- 不支持附件、图片、语音、联网搜索开关或模型选择。
- 空白不可发；字数上限与错误文案由 Step C API 契约确定，界面预留计数位置但不预填虚假上限。
- 歧义等待期间允许输入自然语言补充，也可直接点击选项。

## 5. 三种布局方向

### 5.1 A — Conversation + Inspector（2026-08-07 选中，2026-08-08 改判落选）

```text
┌────────────┬──────────────────────────┬──────────────────┐
│ 对话列表   │ 消息时间线 + 输入        │ 本轮处理         │
│ 280px      │ minmax(480px, 1fr)       │ 340px / 可收起   │
└────────────┴──────────────────────────┴──────────────────┘
```

优点：

- 用户任务与 3A 验收信息同时可见，最适合当前阶段。
- 3B 可在右栏增加来源/工具，3C 可继续展示队列/模型终态。
- 对话列表符合用户已有聊天产品心智。

代价：

- 低宽度下三栏不能常驻，必须认真设计抽屉降级。
- 右栏若默认信息过多会抢走答案阅读注意力，因此默认可收起，Phase 3 完整交付后可默认关闭。

### 5.2 B — Pipeline Workbench

结构：顶部是“保存 → 历史 → 改写 → 意图 → 动作”的宽阶段条，中部并列原问题/规范化问题/意图结果，
下方才是消息时间线，最近对话作为窄侧栏。

优点：最容易核对 3A 每一步和降级；复合问题并列比较清楚。

代价：像内部调试台而不是问答产品；3C 最终答案会和流水线争主视觉。

### 5.3 C — Focused Chat（已选择，2026-08-08）

结构：中央 760px 单列对话，左上按钮打开对话列表抽屉，右上按钮打开本轮处理抽屉。

优点：阅读和输入最专注；桌面与手机是同一套结构，不需要维护"常驻栏 / 抽屉"两条渲染路径；
最接近最终产品形态，Phase 3 收尾时不需要再做一次默认布局切换。

代价（已知并接受）：

- **验收要频繁开关抽屉**，且 3B 往本轮处理里又加了来源与工具两个区，开关频率只会更高。
  这条代价压在验收流程上，不压在最终用户身上——普通用户本来就不看那个面板。
- 无法把消息、改写结果和意图并排比较。需要并排时用 B 的思路另开验收视图，不改这一页。
- **本轮处理默认关闭，所以它绝不能承担关键失败的传达**。§6.1 原本就有这条约束，
  在 C 下它从"最好遵守"升级为"唯一保险"；§13.1 第 2 条是它在 3B 的具体兑现。

## 6. 本轮处理面板

### 6.1 定位

- 面板标题固定为 `本轮处理`，副标签 `3A 验收信息`。**3B 起副标签下移到「处理详情」分组，见 §13.2。**
- 明示：`这里展示规范化问题与路由结果，不是模型思维链。`
- **C 方案下它始终是抽屉、默认关闭**，因此绝不能依赖它向普通用户传达关键失败；
  关键失败必须进入消息区。这条约束在 3B 直接决定了来源摘要、无结果、部分失败与工具确认的落点，
  见 §13.1。
- 抽屉打开时焦点进入面板，`Esc` 关闭并把焦点还给触发按钮（§10）。

### 6.2 阶段

| 阶段 | 进行中 | 成功 | 降级/失败 |
|---|---|---|---|
| 保存消息 | `正在保存…` | `消息已保存` | `消息未保存`，本轮停止 |
| 加载历史 | `正在加载历史…` | `摘要 + 6 条近期消息` | `仅使用摘要` / `仅使用近期消息` |
| 查询改写 | `正在理解问题…` | 展示规范化问题 | `使用原问题` |
| 意图匹配 | `正在匹配方向…` | 展示意图路径 | `无法确定方向` |
| 歧义检测 | `正在判断是否需要澄清…` | `无需澄清` | `等待用户选择` |
| 动作映射 | `正在形成后续动作…` | 展示知识库名称/ID 和兜底标志 | 不进入 3B |

不显示逐 token 推理、Prompt 内容或供应商返回的 `reason` 原文。可展示代码侧归一后的简短匹配理由，
例如“问题明确提到海外仓”。

### 6.3 复合问题

- 子问题用 1~3 个编号区块展示，保持用户表达顺序。
- 每个子问题展示规范化文本、最高意图路径和动作。
- 超过三个时不展示被截断的假结果，直接进入用户可见超限提示。

## 7. 歧义引导交互

助手消息示例：

> 这个问题可能涉及以下几个方向。请选择最接近的一项，或补充具体产品/业务范围。

选项：

1. `商品服务 > 3C 数码 > 退货政策`
2. `商品服务 > 家电 > 退换货规则`
3. `商品服务 > 服装 > 退货政策`
4. `都不是这些`

规则：

- 方向是单选按钮，不用让用户记编号；用户仍可输入“手机退货”作为自然语言补充。
- 点击后立即形成一条用户消息，例如 `我指的是：3C 数码`，保证刷新和摘要后指代仍完整。
- 提交中选项禁用；失败时保留选中项并允许重试。
- 不显示意图分数；分数只在 3A 验收面板用“强/中/低”区间表示。
- `都不是这些` 后助手请用户补充，不自动选择全局检索。

## 8. 关键页面状态

| 状态 | 主区域 | 输入区 | 本轮处理 |
|---|---|---|---|
| 新对话 | 欢迎语 + 3 个问题示例 | 可输入 | 空态 |
| 处理中 | 已发送用户消息 + `正在理解问题…` | 禁用 | 当前阶段高亮 |
| 已形成动作 | 不生成助手答案；显示克制系统提示 | 可继续提问 | 完整结果 |
| 等待澄清 | 助手方向单选卡 | 可补充文本 | 标记短路点 |
| 子问题超限 | 助手提示拆分问题 | 可重新输入 | 显示 4+ 主题，不显示截断结果 |
| 无匹配 | 助手请补充产品/业务范围 | 可输入 | 标记低置信度 |
| 改写降级 | 正常继续，不弹全局错误 | 依最终结果 | 显示“使用原问题” |
| 消息保存失败 | 原消息旁失败提示 | 可重试 | 停在保存阶段 |
| 历史部分失败 | 顶部非阻塞提示一次 | 可输入 | 显示实际加载来源 |

3B 新增的十一种状态见 §13.8，与本表同列同口径。

## 12A. 布局改判：A → C（2026-08-08）

项目所有者在 3B Step B 审阅原型后把问答页方向改为 **C — Focused Chat**。这不是 3B 增量的一部分，
但发生在 3B Step B 的闸门上，因此记在这里而不是新开一份文档。

- **改的是什么**：桌面不再有常驻对话列表与常驻本轮处理面板；中央单列 760px，两侧都是抽屉。
- **不改的是什么**：§4 的区域职责、§6 的面板字段、§7 的歧义交互、§8 的状态口径、§13 的全部 3B 语义。
  它们都是"哪些信息、什么文案、什么时候出现"，与分栏方式无关。
- **为什么现在改代价最小**：3B 前端代码还不存在。3A 前端虽已按 A 实现，但 `ChatPage` 本就按断点分支渲染，
  `ConversationListPane` / `TurnInspectorPane` 在常驻栏与抽屉里是同一份组件，`Drawer` 已具备
  Esc 与焦点返回。切 C 约等于"让宽屏也走窄屏那条分支 + 主列居中"。
- **代价**：`3A-UI-07` 那条手工走查是对着三栏走的，随本次改判作废，需要在 3B Step E 重走；
  其余 3A-UI 行与布局无关，继续有效。见 §14。

### 13.1 增量前提与四条不变量

1. **3B 仍不生成答案。** 生成属 3C。来源展示的是"将来交给生成阶段的依据"，
   界面**不得把来源拼成一段读起来像答案的文字**——那正是 3A P-03 否决过的假答案，
   换了个位置一样是假的。3A 那条带 `3A 验收` 标签的完成提示在 3B 改为对应的 3B 措辞（§13.5）。
2. **本轮处理默认是关着的抽屉**（§5.3 / §6.1）。因此凡是**影响结果可信度**或**需要用户决定**的
   事实——无结果、部分知识库失败、未精排、工具确认——都必须在消息区有落点，不能只活在抽屉里。
   这条是本节大量布局决定的唯一来源，不是审美偏好。选 C 之后它不再是保守设计，而是硬性前提。
3. **全页不展示任何原始分数**，验收区也不例外（PRD §12.2）。跨通道分数不可比，
   3A 的"强/中/低"区间惯例延续到这里。
4. **3B 没有停止能力**（属 3C）。执行中的工具不提供中止入口，也不摆一个点了没用的按钮。

### 13.2 本轮处理抽屉的结构调整

抽屉内容拆成两组，顺序固定：

```text
本轮处理
├─ 本轮结果            ← 3B 新增，面向最终用户的长期产品内容
│   ├─ 来源            §13.3
│   └─ 工具            §13.7
└─ 处理详情  [3A 验收信息]  ← 原 §6 全部内容，位置不变、字段不变
```

对 §6.1 的修订：**`3A 验收信息` 副标签从面板标题移到「处理详情」分组标题上。**
理由是这个标签带着一条删除承诺（§9.2：正式交付后删除）。如果它继续挂在整个面板上，
3B 的来源与工具就会被读成验收脚手架，Phase 3 收尾时被连带删掉——而它们恰恰是要长期留下的东西。

「本轮结果」在上、「处理详情」在下：用户关心前者，验收者才关心后者。
在 C 下这个顺序更要紧——抽屉一打开先看到的必须是来源和工具，而不是阶段条。

### 13.3 来源区

每条来源展示三项，缺一不可（PRD §12.2）：

| 项 | 取值 | 缺失时 |
|---|---|---|
| 知识库名称 | 知识库名，不显示 ID | 不可能缺失；缺失即数据错误，显示 `未知知识库` 并进失败提示 |
| 文档名 | 源文档名 | 源文档已逻辑删除时显示 `文档已删除`，条目**保留**且禁用跳转 |
| 片段位置 | `#{chunkIndex}`，沿用知识库页序号语义（不是行号、不重编号） | 显示 `位置未知`，不隐藏该条 |

**不展示**：原始分数、相关度百分比、名次序号、命中通道、命中次数。
同一片段被多条通道命中时只出现一次，且不因命中两次显得更可信。
列表顺序即系统认定的相关性顺序——顺序本身就是排名，不需要再标数字。

其他规则：

- 每条可展开一段原文片段预览，默认折叠；预览按**纯文本**渲染（§13.7 同一条安全规则）。
- 每条有一个打开对应文档分块页的入口。定位到具体分块所需的参数由 Step C 与 `api.md` 冻结，
  界面此刻不预设 query 名，也不预填未经确认的路径。
- 区标题右侧最多挂两个状态标记：`未精排`（§13.4）与 `结果不完整`（§13.6）。两者可同时出现。
- 空态区分两种：`本轮没有召回任何来源`（§13.5 无结果）与 `本轮未执行检索`（歧义短路、超限等 3A 短路态）。
  用"暂无数据"把这两件事合并是错的——一个该改问法，一个该先回答澄清。

**消息区落点**：助手消息下方一行摘要 `依据 5 条来源 ›`，点击打开本轮处理抽屉并定位到来源区。
摘要行同时承载 `未精排` 与 `结果不完整` 标记。

在 C 下这一行不是"辅助入口"而是**来源的主入口**——抽屉默认关着，绝大多数用户只会看到这一行。
因此它必须自己说清三件事：有几条依据、精排了没有、结果全不全。

### 13.4 未精排

- 标记文字固定为 `未精排`，并附一句解释：`本轮重排不可用，结果按检索相关度排序。`
- 出现在两处：来源区标题、消息区来源摘要行。
- **不区分成因**。无 Key、供应商故障、Noop 降级对用户是同一件事；成因只进「处理详情」
  与链路记录，不进面向用户的标记。
- **不因未精排而少展示或补齐来源。** Rerank 返回不足 topN 时展示的就是那几条，
  界面不显示"结果被截断"，也不允许出现用原始候选补位的条目（PRD §12.5）。
  界面表现即 `未精排 · 3 条` 是完全正常的一屏。
- `已精排` 不需要标记。默认状态不加标签，避免把常态渲染成成就。

### 13.5 无结果

- 助手消息：`没有在你的知识库里找到相关内容。`，跟三条可操作下一步：
  换个说法再问一次 / 指定要查的知识库 / 检查这份资料是否已入库。
- **必须与 3A 的 `NO_MATCH` 可区分**，两句文案摆在一起要能看出说的是两件事：
  - 3A：`我还不能确定应该从哪个方向查找，请补充产品或业务范围。`（方向不明）
  - 3B：`没有在你的知识库里找到相关内容。`（方向明确，库里没有）
- **不提供任何"用通用知识回答"的入口**（PRD §12.3）。没有这个按钮，也没有这个开关。
- 3B 验收提示相应改为：`已完成知识库检索。当前里程碑尚未生成答案。`
  仍带阶段标签（`3B 验收`），正式交付后与 3A 那条一起删除。

### 13.6 部分知识库失败

- 判断依据必须是**显式状态**；界面不得用"条数少"倒推（PRD §12.4）。原型和实现都不许
  出现 `results.length < expected` 这类推断。
- **消息区**：一条非阻塞提示（不是错误弹窗、不把整页变红，沿用 §4.3），点名失败的知识库：
  > 「海外仓运营手册」这个知识库本轮没有查成，下面的结果不完整。

  两个动作：`重试失败的知识库`（主）、`就现有结果继续`（次）。
- **右栏**：来源区标题挂 `结果不完整`；来源列表下方单列失败项，每项为
  知识库名 + 归一化原因 + 状态，不透传异常文本。
- **重试只重跑失败的那部分检索**，不重走改写与意图——否则用户会以为整轮从头再来，
  而且已确认过的歧义选择会被重问。这是界面对 Step C 提出的要求，请在技术方案里正面接住。
- **全部知识库都失败 ≠ 无结果**，两者文案必须不同：一个是"没查成"（可重试），
  一个是"查了但没有"（该改问法）。合并这两句会让用户做错下一步。

### 13.7 工具区与工具状态

主路径是四态：**请求（含参数）→ 用户确认 → 执行中 → 结果或失败**。
另有三个不进主路径的终态（取消、不可用、中止），它们各自对应一条 PRD §12 明确要求"必须让用户看见"的情况。

#### 13.7.1 状态闭集

| 状态 | 何时出现 | 输入区 | 用户可做 |
|---|---|---|---|
| `待确认` | 有副作用的工具，参数已抽取，等待用户裁决 | **可用**（等待用户，沿用歧义等待惯例） | 确认 / 取消 / 用自然语言补充 |
| `执行中` | 已确认，或只读工具直接执行 | 禁用（活动本轮） | 无（3B 无中止，见 §13.1） |
| `已完成` | 工具返回成功 | 可用 | 展开结果 |
| `失败` | 工具返回错误或超时 | 可用 | 重试 |
| `已取消` | 用户在确认卡上取消 | 可用 | 重新提问 |
| `不可用` | 工具未注册或不在白名单 | 可用 | 无（配置问题，用户无法自助） |
| `已中止` | 参数抽取失败或参数非法，未执行 | 可用 | 按提示补充信息后重问 |

只读工具没有 `待确认`，从 `执行中` 起步；**但它的参数同样全程可见**（PRD §12.6）。

#### 13.7.2 工具确认卡（消息区，仅有副作用的工具）

确认需要用户动作，因此卡片必须在消息区，与 3A 的歧义引导卡同一位置、同一心智。内容：

- 标题：`需要你确认：{工具显示名}`，并挂一个 `有副作用` 标记。
- 一句话说明这个工具会做什么。**这句话来自工具白名单配置，不能由模型生成**——
  否则模型既决定调什么工具，又决定怎么向用户描述它，确认就成了走过场。
- 参数表：参数名（Schema 声明的名称）+ 抽取到的值 + 必填标记。
  表头注明 `由模型从对话中抽取`，这是用户确认前唯一能核对的东西。
  不展示 Schema 原文、不展示 `argumentsJson`。
- 按钮：`取消`（次要）+ `确认执行`（主要，危险样式）。
- **参数在 3B 不可就地编辑。** 要改就取消，用自然语言重说。理由是可编辑参数会引出
  "编辑后还要不要按 Schema 校验、校验失败怎么回卡片"一整条分支，而它并不在 PRD §12 冻结的语义里。
  代价是改一个字要重说一遍——这条列入 §13.12 请所有者裁决。
- **没有"记住我的选择""本轮不再询问"。** 每次调用都要确认，包括失败后的重试（§13.7.4）。
- 确认或取消后，卡片就地转为静态记录：按钮消失，留下结果文字，不从时间线里抹掉。

#### 13.7.3 结果与失败

- `已完成`：结果默认折叠，展开显示前若干行预览。
  **工具返回是不可信内容**，一律按纯文本渲染：不解析 HTML、不渲染 Markdown 链接与图片、
  不产生可点击目标。（3C 的 D-08 隔离在 Prompt 侧，这里是同一件事的界面侧。）
- `失败`：只展示归一化后的稳定文案 + `重试`。**绝不透传异常 message**——
  它可能带内部主机名、端口和堆栈片段（PRD §12.6）。超时显示 `执行超时`。
- `不可用`：消息区给一条克制的系统提示，不能静默跳过：
  > 系统判断需要调用「退款申请」，但它不在当前可用工具清单中，本轮未执行。

  右栏工具区记 `不可用`。静默会让用户以为系统不支持这件事，而真相是配置缺失。

#### 13.7.4 参数抽取失败与非法值

- **禁止用默认值继续**（PRD §12.7）。抽取失败即 `已中止`，助手点名缺了什么：
  > 我还需要「起止日期」才能提交这张工单，请补充后再说一次。
- 值非法（枚举外、类型不符）与缺失同等处理，提示里给出允许值而不是 Schema 原文：
  > 「区域」只能填 华东 / 华南 / 华北，"火星"不在范围内。
- **必填参数缺失时不得调用工具**，界面上不存在"跳过这个参数继续"的路径。
- 失败后重试：只读工具直接重跑；**有副作用的工具重新出确认卡**，
  上一次的确认不能被复用——"确认前一律不执行"对每一次执行都成立。

#### 13.7.5 抽屉里的工具区

本轮所有工具调用按发起顺序列出，每项：工具显示名 + 状态标签 + `有副作用` 标记（若有）
+ 参数摘要（可展开）+ 耗时（成功和失败都显示）+ 归一化失败原因（若有）。
没有工具调用时为空态 `本轮没有调用工具`，与"工具不可用"不是同一句。

### 13.8 状态表增量（补 §8）

| 状态 | 主区域 | 输入区 | 本轮处理 |
|---|---|---|---|
| 检索中 | 已发送用户消息 + `正在检索知识库…` | 禁用 | 阶段高亮，来源区骨架 |
| 有来源 | 3B 验收提示 + `依据 N 条来源 ›` | 可输入 | 来源区完整列表 |

### 13.9 意图树管理页在 3B 不变（裁决）

[意图树规格](../intent-tree/ui-spec.md) §5 与 §14 把「MCP 类型及工具绑定」推迟到了 3B Step B。
现在给出结论：**3B 不新增 MCP 叶子类型，意图树不承担工具绑定，其规格与原型在 3B 无增量。**

依据是计划 D-03——3B 采用原生 Function Calling，工具选择由模型在一次 Chat 调用内完成，
可用工具来自白名单配置，不来自意图树。若仍在意图树上加 MCP 叶子，就会出现一个
"配了但从不参与路由"的节点类型，正是 xrag 反复要拦的那种走不到的分支。

代价（D-03 已接受）：工具选择不可通过意图树审计。界面侧的补偿是工具区把
"模型请求了哪个工具、带了什么参数、结果如何"完整摊开，用可见性换掉一部分可审计性。

### 13.10 响应式与无障碍增量

- **1440px / 1024px**：中央单列 760px；本轮处理是默认关闭的抽屉。来源摘要行、无结果、部分失败提示、
  工具确认卡全部在消息区，抽屉一次不开也不丢任何关键信息——这是 §13.1 第 2 条的验收点，
  在 C 下每一档都要验，不只是窄屏。
- **720px**：抽屉转全高覆盖层；工具确认卡全宽；参数表由两列改为纵向键值堆叠；
  来源条目文档名最多两行截断。
- **375px**：确认卡按钮纵向堆叠，`取消` 在上、`确认执行` 在下，间距不小于 12px，防误触；
  来源列表不横向滚动。
- **状态不只靠颜色**：`未精排` / `结果不完整` / `失败` / `不可用` / `已中止` 各自有文字标签，
  且图标形状互不相同；去掉颜色后仍可区分。
- **危险确认默认焦点不在危险按钮**（沿用 3A 惯例）：确认卡出现时**不抢焦点**，
  以 `role="status"` 播报；用户 Tab 进入卡片时第一个可聚焦元素是 `取消`，`确认执行` 排在其后。
- `Esc` 只关抽屉，**不等于取消工具确认**——误触 Esc 不应丢掉一份已抽取好的参数。
- 工具从 `执行中` 变为 `已完成`/`失败` 时用 `aria-live="polite"` 播报状态变化。
- 来源列表与工具卡可完整键盘操作；展开/折叠按钮有明确可访问名称。

### 13.11 原型演示场景增量（补 §11）

3B 新增九个场景，与 §11 的六个 3A 场景并存，在场景控制里分两行标注 `3A` / `3B`：

1. 正常来源展示（多知识库、已精排）；
2. 未精排；
3. 部分知识库失败 → 重试 / 就现有结果继续；
4. 无结果；
5. 工具确认卡（有副作用）→ 确认 → 执行中 → 已完成；
6. 工具确认卡 → 取消；
7. 工具执行失败 → 重试**重新出确认卡**；
8. 工具不可用（未注册/不在白名单）；
9. 参数抽取失败中止（缺必填 + 枚举外取值）。

3B 场景只在已选定的 **C 方案**上演示——A/B 只作为 3A 决策留档，为它们补 3B 状态没有评审价值。
点击 3B 场景时原型自动切到 C 并说明原因。
