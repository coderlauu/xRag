# 《AI基础设施层宏观设计》

> 原文链接：https://t.zsxq.com/xmGYm
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

在业务模块和各家模型 API 之间增加独立的 AI 基础设施层，用“能力端口 + 共享调度骨架 + Provider 适配器”隔离供应商差异；真正应该统一的是选路、容错和诊断，不是把 Chat、Embedding、Rerank 压进一个万能请求对象。

## 核心内容提炼

- 原文把 `infra-ai` 划分为配置、枚举、模型、HTTP、Chat、Embedding、Rerank、Token 和工具九类职责，并形成三层调用关系：

  ```text
  业务能力接口
    LLMService / EmbeddingService / RerankService
             ↓
  路由服务
    选择候选、执行调用、熔断与故障转移
             ↓
  Provider 客户端
    ChatClient / EmbeddingClient / RerankClient
  ```

- 配置分成两类：Provider 配置负责基地址、凭据和能力端点；模型候选配置负责 Provider、真实模型名、优先级、启用状态、向量维度、是否支持思考模式以及可选 URL 覆盖。两者分开后，同一 Provider 可以登记多个模型，同一模型策略也不必携带密钥。
- `ModelTarget` 是一次路由后的调用快照，携带最终 Provider、模型、URL 等上下文。业务层不再拼 URL，也不读取供应商配置。
- 调度核心被拆成三件事：`ModelSelector` 回答“选谁”，`ModelHealthStore` 回答“现在能不能调用”，`ModelRoutingExecutor` 回答“按什么顺序尝试以及失败后怎么办”。
- 原文综合使用策略、模板方法、注册表、熔断、回退链和装饰器等模式。价值不在模式数量，而在于新增 Provider 时主要增加适配器和配置，不把分支判断散落到业务代码。
- Chat、Embedding、Rerank 的上层体验可以一致，但协议不变量并不相同：Chat 关心消息、完成原因和流式事件；Embedding 关心输入顺序、返回 `index` 和维度；Rerank 关心候选身份、排序位置和分数。共享调度骨架、保留独立能力端口更稳妥。

## 关键概念/术语

- **能力端口**：按 Chat、流式 Chat、Embedding、Rerank 分开的稳定业务接口。
- **Provider 适配器**：把内部请求翻译为供应商协议，并把响应、错误和请求 ID 归一化。
- **模型候选**：参与某项能力路由的 Provider/模型组合及其策略元数据。
- **调用快照**：逻辑调用开始时冻结的候选与配置视图，用来保证一次调用可复盘。
- **共享调度骨架**：能力过滤、排序、尝试预算、熔断、故障转移和诊断等横切逻辑。

## 与 xrag 项目的关系

- xrag 当前只有 `knowledge.embedding.EmbeddingClient`，还没有 Chat、流式 Chat、Rerank 或模型路由模块。Phase 2 是新增共享基础设施并迁移已有能力，不是重构一套已经存在的调度系统。
- Phase 1 已经证明 `EmbeddingClient` 是合理的稳定端口：知识库只依赖批量向量化和维度，不应在 Phase 2 改为依赖 Provider SDK。推荐迁移方向是：

  ```text
  knowledge 模块
    └─ EmbeddingClient
         └─ RoutedEmbeddingClient
              └─ 调度骨架 + Provider 适配器
  ```

- xrag 第一版应保持独立的 `ChatClient`、`StreamingChatClient`、`EmbeddingClient`、`RerankClient`；可共享调用上下文、错误分类、路由记录和尝试执行器，但不设计 `invoke(Object)` 一类万能接口。
- 用户已确认建设轻量“模型调度诊断页”。页面只展示 Provider/模型能力、候选与过滤原因、熔断状态、最近调用和故障转移，不扩张成聊天产品页或模型管理后台。

## 值得注意的设计取舍/坑

- **“OpenAI 兼容”只表示一部分协议形状相似，不代表能力和行为完全相同。** 不同 Provider 对端点、字段、流式事件、错误体和限制的支持不同，必须声明“实际验证过的能力”。
- **配置驱动不等于配置无约束。** 候选的模型 ID 必须稳定；凭据、端点、能力和维度要在启动或注册时校验，不能把所有错误推迟到第一次真实调用。
- **共享骨架不能抹掉能力不变量。** 如果为了复用而让 Embedding、Rerank 也走 Chat DTO，得到的是浅接口和大量运行时分支。
- **模型路由不是业务 RAG 路由。** 本阶段解决 Provider/模型选择；知识库选择、意图识别和问答编排仍属于 Phase 3。
- **诊断默认不保存 Prompt 和输出正文。** 第一版只记录调度事实、低基数错误类型、请求 ID、耗时和 token/条目数量，避免把运维页面变成敏感内容仓库。
