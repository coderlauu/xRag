# 《答案一个字一个字蹦出来流式生成的完整链路》

> 原文链接：https://t.zsxq.com/Dl6F2
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

token 从模型到浏览器要过五层接力（入口 / 流水线 / 调度 / 客户端 / 推送），五层靠 `StreamCallback` 这一个四方法接口串起来；关键设计是**首包探测**（提交前可切模型，提交后没有回头路）与**谁读流谁推送**（模型流线程直接调 `SseEmitter.send()`，不引入队列）。

## 核心内容提炼

- **五层与各自的输入输出**：

  | 层 | 关键类 | 输入 → 输出 |
  |---|---|---|
  | 入口 | `RAGChatController` / `RAGChatServiceImpl` | HTTP → `SseEmitter` + `StreamChatContext` |
  | 流水线 | `StreamChatPipeline` | `StreamChatContext` → `ChatRequest` |
  | 调度 | `RoutingLLMService` / `ProbeStreamBridge` / `ModelHealthStore` | `ChatRequest` → 选定模型并启流 |
  | 客户端 | `AbstractOpenAIStyleChatClient` / `OpenAIStyleSseParser` | HTTP SSE 流 → `StreamCallback` 回调 |
  | 推送 | `StreamChatEventHandler` / `SseEmitterSender` | 回调 → 浏览器 SSE 事件 |

- **`StreamCallback` 只有四个方法**：`onContent` / `onThinking`（默认空实现）/ `onComplete` / `onError`。层与层的衔接就是一次普通方法调用——**不需要队列、不需要消息总线**。

- **Controller 立即返回，Tomcat 线程当场释放**。`produces = "text/event-stream;charset=UTF-8"`，`SseEmitter` 超时从配置读，`@IdempotentSubmit` 保证同一用户不能并发发起多个对话。长时间占用的是 NIO 连接而不是线程，所以 SSE 不会耗尽 Tomcat 线程池。

- **回调实例是贯穿全链路的同一个对象**。`StreamCallbackFactory` 在 Service 层就造好 `StreamChatEventHandler`，从调度层一路传到客户端层，谁都往它上面回调。

- **首包探测是调度层最关键的设计，理由说得很直白**：流式请求不能像同步请求那样简单重试——**一旦开始往前端推 token 就没有回头路**，主模型吐了三个字才挂，那三个字已经在用户屏幕上了，撤不回来。`ProbeStreamBridge` 因此站在模型与真回调之间走三阶段：
  1. **缓冲**——首包到达前事件全存 buffer 不下发，同时用 `CompletableFuture` 通知路由主线程探测结果；
  2. **提交**——路由线程收到 `SUCCESS` 后 `commit()`，缓冲事件一次性回放；
  3. **直通**——`committed = true` 之后新事件直接转发。

  探测四种结果：`SUCCESS` / `ERROR` / `TIMEOUT`（60 秒无响应）/ `NO_CONTENT`（正常结束但没吐内容）。后三种都取消连接、标记模型不健康、`continue` 下一个候选；全部候选耗尽才 `onError`。

- **取消句柄分两步绑定，因为时序上没法一步到位**。回调实例在 Service 层就创建了（那时 Prompt 都还没拼），而取消句柄是 `llmService.streamChat()` 的返回值。所以 `register()` 在回调创建时执行，`bindHandle()` 在 LLM 调用返回后执行。`bindHandle` 里有防御：**绑定前若已收到取消信号（用户手速快），立即 `handle.cancel()`**。

- **`sendChunked` 用 `codePointAt()` + `Character.charCount()` 而不是 `charAt()`**。Java 的 `char` 是 16 位，一个 emoji 需要代理对表示，按 `char` 切分会把 emoji 劈成两半。默认 5 个码点推一次，末尾不足一块也立即推出去。

- **`SseEmitterSender` 的三重线程安全保障**：`AtomicBoolean closed` + CAS 保证 `complete()` / `closeWithError()` 幂等；`onCompletion` / `onTimeout` / `onError` 三个回调统一置 `closed`；`sendEvent()` 先查 `closed` 再写。

- **SSE 事件协议五种**：`meta`（conversationId + taskId）→ `message`（`MessageDelta(type, delta)`，`type` 区分 `response`/`think`）→ `finish`（messageId + title）→ `done`（`[DONE]` 纯信号）→ `cancel`。**`finish` 与 `done` 分开是有意的**：前者带业务数据要更新 UI，后者是断连信号，分开发送确保业务数据先到达。

- **线程模型三个角色**：Tomcat 线程（创建 emitter 后立即释放）、Pipeline/路由线程（跑前七阶段 + 等首包）、模型流线程（读流 + 解析 + 回调 + 推 SSE）。**"谁读流，谁推送"**——整条回调链在同一个线程上，没有线程切换。

## 关键概念/术语

- **首包探测（Probe）**：在第一个业务 token 下发给前端之前确认模型可用，是流式故障转移的前提。
- **提交点（Commit）**：缓冲事件回放给下游的那一刻；此后不可再切换模型。
- **取消句柄（`StreamCancellationHandle`）**：包装 OkHttp `Call` + `AtomicBoolean`，取消时双管齐下。
- **分块推送（`sendChunked`）**：把粒度不定的模型回调重新切成固定大小，保证视觉上的流式感。
- **谁读流谁推送**：读取上游与写出下游在同一线程完成，不引入中间队列。

## 与 xrag 项目的关系

- **这五层里，xrag 已经把第三、四层建完了，而且是 Phase 2 的成果——本篇真正对 xrag 有增量的是第一、二、五层。** [`StreamingChatClient`](../../../backend/src/main/java/com/app/ai/model/StreamingChatClient.java) 的 `Flux<ChatStreamEvent> stream(ChatCommand)` 就是原文调度层加客户端层的合并出口。**并且 xrag 的实现路线与原文完全不同**：[ADR 0004](../../../docs/adr/0004-reactive-streaming-runtime.md) 选的是 `WebClient` + Reactor Netty + `Flux`，而不是 OkHttp + 专用线程池 + 回调接口。ADR 里那句"**SSE 解析优先复用 Spring 的事件解码器，不维护按行读取的自研解析器**"，直接把原文第四层的 `OpenAIStyleSseParser` 整个删掉了——`OpenAiCompatibleChatProvider` 用的是 Spring 的 `ServerSentEvent<String>` 解码器。**读这一篇不需要考虑"要不要照着做第四层"，那个决策一年前就下了。**

- **首包探测这个概念 xrag 有等价物，且语义定义得更硬。** ADR 0004 写的是"在首个有效业务块已缓冲后发出 `STREAM_STARTED` 并形成下游提交点；提交前可以取消当前上游并切换候选……提交后中断只能发 `STREAM_FAILED`"。这与 `ProbeStreamBridge` 的缓冲→提交→直通是同一个设计。**差别在于 xrag 把"提交后中断"的语义钉进了类型系统**：[`ChatStreamEvent.StreamFailed`](../../../backend/src/main/java/com/app/ai/model/ChatStreamEvent.java) 的构造器里有 `if (!incomplete) throw new IllegalArgumentException("stream failure must be incomplete")`——**`incomplete=false` 的失败事件根本构造不出来**。原文的 `onError(Throwable)` 完全没有这个区分，前端无从判断"我收到的半截答案算不算数"。

- **"谁读流谁推送"这条 xrag 不能照抄，照抄会出事。** 原文的模型流线程是自家线程池里的普通线程，阻塞它只影响这一条流。xrag 的 `ChatStreamEvent` 到达时**在 Reactor Netty 的 event loop 线程上**，而 `SseEmitter.send()` 是阻塞式 Servlet IO——**在 event loop 上做阻塞写，会连带拖住跑在同一个 loop 上的其他所有流式调用**。这是 ADR 0004 那句"后端同时包含 Servlet 与 WebClient 的 reactive client 依赖"埋下的必然结果：**两套 IO 模型在推送层交汇，必须有一次显式的线程切换**（`publishOn` 到专门的调度器，或把事件投递给一个由 servlet 侧消费的有界队列）。原文说"不需要队列"的理由在 xrag 这里恰好反过来。**这是 Step C 必须明确写下的一条，不能留给实现者临场发挥。**

- **深度思考（thinking）在 xrag 没有任何落点，且补它要改 sealed interface。** [`ChatStreamEvent`](../../../backend/src/main/java/com/app/ai/model/ChatStreamEvent.java) 是 sealed，permits 的六种是 `StreamStarted` / `TextDelta` / `ToolCallDelta` / `RefusalDelta` / `Completed` / `StreamFailed`——**没有 `ThinkingDelta`**；`ChatCommand` 也没有 `thinking` 开关（见第 14 篇笔记，整个 `com.app.ai` 包里 `temperature|topP|thinking` 零命中）。要支持深度思考就得同时改端口的入参与出参，属于 ADR 0003 管辖范围的端口变更。**先决问题是"本期要不要做深度思考"**——它是产品需求不是技术细节，应当在 Step B 的 PRD 里就定，不要等到 Step D 才发现端口装不下。

- **`ChatStreamEvent.StreamStarted` 携带的 `ExecutionInfo` 绝不能原样透给前端。** 它的字段是 `logicalCallId` / `requestId` / `actualExecution` / `attemptCount` / `retryCount` / `failoverCount`——**里面写着这次请求重试了几次、故障转移到了哪个部署**。原文的 `meta` 事件只带 `conversationId` 和 `taskId`，是干净的。xrag 的推送层必须做一次显式映射而不是把内部事件序列化了事，**否则调度的内部决策会直接暴露在浏览器 Network 面板里**。这与 ADR 0003"业务代码不得触碰调度内部态"是同一条纪律的延伸——**不触碰，也不转发**。

- **`@IdempotentSubmit`（同一用户不能并发发起多个对话）在 xrag 有现成的思路可循，但不能照抄注解。** 原文靠注解 + Redis。xrag 的 [ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 明确不引入分布式锁，用**状态字段 CAS** 替代——同一套思路可以搬到会话上（用会话的状态字段做 CAS，而不是加锁）。**但先要回答检查点 D-04：对话与并发许可到底存哪。** 这一篇和下两篇会反复撞上这个问题。

- **xrag 目前一条 SSE 出口都没有，前端也没有对话页。** `backend/src/main/java` 里 `SseEmitter` 零匹配，唯一的 `ServerSentEvent` 出现在 `OpenAiCompatibleChatProvider` 里且是**入站方向**（解析供应商响应）。前端路由表只有知识库三页加 `/diagnostics`。**也就是说原文的第一层与第五层在 xrag 是彻头彻尾的新建**，而且第五层还带着上面那个线程切换的硬约束。这两层的工作量在 Step C 拆工单时不要按"接个 SSE 而已"来估。

- **SSE 事件协议要设计成前后端契约，而不是 `ChatStreamEvent` 的序列化结果。** 原文的五种事件（`meta`/`message`/`finish`/`done`/`cancel`）与 xrag 的六种 `ChatStreamEvent` **不是一一对应的两套东西**：前者是产品层协议（含 messageId、会话标题这类与模型无关的业务数据），后者是模型调度层事件。**中间必须有一层显式映射**，这一层同时承担上一条说的字段裁剪。它属于 `tech/qa-pipeline/api.md` 的内容，应当像知识库的 API 文档一样写成权威规格。

## 值得注意的设计取舍/坑

- **`taskManager.isCancelled(taskId)` 在 `onThinking` / `onContent` / `onComplete` / `onError` 四个方法开头各查了一次 Redis，而这是在逐 token 的热路径上。** 一个 2000 字的回答按 5 码点一块就是 400 次推送，每次推送前都查一次分布式缓存。**取消是一个低频事件，却用了高频轮询的实现方式。** 更合理的做法是让取消信号主动置一个本地 `volatile` 标志（Pub/Sub 收到时置位），热路径只读本地变量。原文下一篇会讲 Redis Pub/Sub 广播——**广播机制已经有了，却仍然在每个回调里查一次**，这两件事本可以合成一件。

- **`sendChunked` 的分块是"重新切分"，它把上游的语义边界抹掉了。** 模型吐出的 delta 边界本身携带信息（有些供应商按词、按句返回），重切成固定 5 码点之后，**前端拿到的边界与模型的生成节奏完全无关**。这对纯文本渲染无害，但一旦要做流式 Markdown 渲染或流式引用标注，固定切分反而制造了麻烦——一个 `**` 会被劈到两个事件里。xrag 若做，**分块大小应当是可关闭的呈现层参数，且默认值要考虑前端的渲染方式**，不要当成一条不可调的常量。

- **`onComplete()` 里持久化失败只记日志，然后照样发 `FINISH`——而 `FINISH` 携带的 `messageId` 此时是 `null`。** 用户看到一个完整的回答，前端拿到 `messageId = null`，后续点赞、复制、引用全部失效，**而界面上没有任何异常提示**。这是一个静默的半失败：答案在屏幕上，但它在系统里不存在。**要么在 `FINISH` 里显式带上"未保存"状态让前端提示，要么把持久化失败当作错误处理**，现在这样是最糟的中间态。第 13 篇"降级到全默认值"是同一类问题的另一个版本——**用户无从察觉的降级。**

- **`onError` 直接 `sender.fail(t)`，把 `Throwable` 交给了 `completeWithError`。** 异常信息会不会渗到前端取决于 Spring 的错误处理配置，这条链路上**没有任何一处做过消息脱敏**。模型调用的异常里可能带 base-url、上游错误体、甚至请求头片段。xrag 有 `ApiExceptionHandler` 统一错误响应体的既有纪律（只翻译显式抛出的 `ApiException`），**流式错误也应当走同一套翻译，而不是把原始 `Throwable` 丢给容器**。

- **首包探测的 60 秒超时是一个纯等待，期间用户看到的是完全空白。** 主模型无响应时，用户要盯着空屏幕 60 秒，才轮到第二个候选开始尝试——**最坏情况下的首字延迟是候选数 × 60 秒**。原文没有讨论这个上界。xrag 有共享 Deadline 与 attempt 预算（Phase 2 工单 08），**整条逻辑调用有统一的截止时间**，不会出现"每个候选各等 60 秒"的累加——这是 xrag 已经比原文强的地方，但也意味着 Step C 要为流式问答**单独设一个合理的 deadline**，而不是沿用同步 Chat 的值。

- **`ProbeStreamBridge` 的缓冲是无界的。** 三阶段描述里，缓冲阶段"所有回调事件存入 buffer"，直到收到首个内容才提交。若某个模型持续吐 `reasoning_content` 却迟迟不吐正式内容，**buffer 会一直涨**，而 `NO_CONTENT` 只在流正常结束时才判定。ADR 0004 在这一点上是明确的——它要求"**有界缓冲**"和"限制慢下游缓冲"。**这是 xrag 已经写进决策而原文留白的地方**，实现时不要因为参考原文而把边界丢了。

- **五层用一个回调接口串起来的代价是：异常语义在层间是隐式的。** `onError` 由谁调、调几次、调完之后上游还会不会继续回调 `onContent`——**接口本身没有任何约定**，全靠各层自觉。`SseEmitterSender` 那个 CAS 幂等保护，本质上就是在为这份不确定性兜底（原文自己也说"`onComplete()` 和 `onError()` 可能在极端情况下被连续调用"）。xrag 的 `Flux<ChatStreamEvent>` 天然有 Reactive Streams 的终态契约（`onComplete`/`onError` 二选一且仅一次），**这是选 Reactor 换来的实打实的好处**，推送层不必再自己发明幂等保护——**但前提是推送层要老实按 Flux 的语义写，而不是先把它转成回调再手工兜底。**

- **`thinkingDurationSeconds` 用 `Math.max(1, ...)` 保证至少显示 1 秒。** 这是个善意的 UI 处理，但它写在了服务端的领域对象上并被持久化——**数据库里存的是一个被 UI 规则污染过的值**。将来若要统计真实思考耗时，这个字段是不可用的（所有 0.2 秒都变成了 1 秒）。**展示层的取整应当发生在展示层**，存储要存真值。这类"为了好看改数据"的坑很隐蔽，因为它当下不会出任何错。
