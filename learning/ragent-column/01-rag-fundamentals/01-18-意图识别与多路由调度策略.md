# 《AI大模型Ragent项目》——意图识别与多路由调度策略

> 原文链接：https://t.zsxq.com/vYbpo
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章解决的问题是："一根筋"的 RAG 系统不管用户说什么都往知识库里检索，导致闲聊、查个人数据这类消息被错误处理；解法是在检索之前加一层意图识别与路由，先判断消息该走知识检索、工具调用、闲聊还是澄清，再分发到对应处理流程。

## 核心内容提炼

- **问题的两个具体案例**：用户说"你好，我想咨询一下"，系统直接拿这句话去检索，召回了退货政策等无关 chunk，模型被迫基于无关内容强行回答；用户问"我还剩几天年假"，系统去知识库检索到的是"公司年假制度"（正式员工每年 10 天带薪年假）这种通用规则文档，而不是这个用户本人的实际余额——这个问题的答案不在知识库里，应该调 HR 系统的 API。核心结论：**闲聊消息走检索反而比不检索还差**（模型要么硬答无关内容，要么触发"找不到相关信息"的兜底，两种表现对一句寒暄都很尴尬）；工具类问题走检索则是"查了但查不到"。

- **医院分诊台类比**：意图识别相当于给 RAG 系统装一个分诊台——患者（用户消息）先经过分诊（意图识别）判断该去哪个科室（处理路径），而不是不管什么病都送去内科。

- **四种意图类型**（以电商客服场景为例，不是固定分类体系，可按业务扩展）：
  1. **知识检索（knowledge）**：问的是知识库里的静态通用知识（退货政策、保修条款、配送范围）。处理方式是走完整 RAG 流程：Query 改写 → 向量检索 → 重排序 → 生成答案。
  2. **工具调用（tool）**：查个人数据、实时信息，或要执行操作（查某个订单状态、查自己的年假余额、申请退货）。处理方式是走 Function Call / MCP：识别要调哪个工具、传参、执行、把结果交给模型生成最终回答。
  3. **闲聊对话（chitchat）**：打招呼、感谢、开玩笑，不涉及具体业务。处理方式是模型直接回答，不检索也不调工具，靠 System Prompt 定义闲聊风格即可。
  4. **引导澄清（clarification）**：问题太模糊无法判断走哪条路（"有什么推荐的吗""怎么办"）。处理方式是反问用户补充信息，但文章强调**这一步要谨慎使用**——如果消息虽短但结合上下文意图明确（比如正在聊 iPhone 16 Pro 时问"价格呢"），就不该反问，只有真正无法判断时才用。
  - **区分知识检索和工具调用的关键标准**：看答案的来源——答案在知识库文档里就是知识检索；答案需要查数据库/调 API/访问外部系统（某个具体订单、某个人的余额、实时库存）就是工具调用。这个标准也说明同一类问题在不同系统能力下分类可能不同（比如"有货吗"，有没有实时库存 API 会决定它该分到哪一类）。

- **三种意图识别实现方案及权衡**：
  1. **规则匹配**（关键词/正则）：速度极快（微秒级）、零调用成本，但准确率低（60%~70%），且无法理解语义——"帮我看看剩几天假"没命中"年假"关键词就会被错分为知识检索；"能退吗"到底是问政策还是要退货，规则完全无法区分。维护成本随 bad case 增多而不断攀升（越补规则越乱）。**适合做第一层快速过滤**，把最明确的场景（"你好"、"查订单 #12345"）直接拦截。
  2. **大模型分类**：给模型一份写清楚四类意图定义+示例（few-shot）的分类 Prompt，结合对话历史输出 JSON（`{"intent": ..., "confidence": ...}`）。准确率通常 90%+，但延迟 500~3000ms，且每次调用都有 token 成本。Prompt 设计要点：每类意图要有清晰边界定义，明确要求"结合对话历史判断"，明确要求"只有真的无法判断时才分类为 clarification"（防止模型动辄要求澄清）。
  3. **混合方案（推荐）**：规则层先拦截高置信度的明确场景（短消息完全匹配闲聊关键词、包含明确工具触发词+具体参数），其余交给大模型分类。实际场景中闲聊+明确工具调用大约占 30%~40% 的消息量，这部分可以被规则层直接拦掉，省下对应比例的模型调用，同时复杂/模糊场景仍有大模型兜底保证准确率。三种方案在速度、准确率、Token 成本、维护成本四个维度上呈现清晰的递进关系，混合方案是文章给出的生产环境推荐选择。

- **意图边界情况**（不追求 100% 准确率，而是设计好兜底）：
  - 上下文相关：单看"能退吗"可能是问政策，但如果前面在聊某个具体订单，就该判断为工具调用（发起退货）。
  - 知识/工具边界随系统能力变化：同样的问题（"有货吗"）取决于你是否接了实时库存 API。
  - 确认回复：助手上一轮问"要不要发起退货"，用户回"好的"——要结合上下文判断这是对操作的确认（工具调用），不是单纯闲聊。
  - 多意图：一句话同时包含知识检索和工具调用需求（"查一下退货政策，顺便看看订单到哪了"），可以取主要意图或拆分处理（可参考上一篇 Query 改写里讲的多意图拆分思路）。
  - 文章特别指出误分类的**风险不对称**：闲聊被误分为知识检索，最多是检索不到内容给个兜底回复，影响有限；但工具调用被误分为闲聊，用户想退货结果系统回"好的呢"，这是实质性的服务失败。这个不对称性直接决定了后面路由层的兜底策略设计。

- **路由器（Router）架构**：拿到意图分类结果后用 switch/dispatch 分发到各自独立的处理函数（`handleKnowledgeRetrieval` / `handleToolInvocation` / `handleChitchat` / `handleClarification`），各处理器互不干扰。**default 分支（未知意图、分类失败）统一兜底走知识检索**，理由是知识检索路径自带"找不到相关信息"的兜底话术，比误走工具调用（可能执行错误操作）或误走澄清（让用户觉得系统很笨）都更安全。

- **意图识别在 RAG 链路中的位置——一个"理论 vs 实际落地"的取舍**：理论上应该放在"会话记忆之后、Query 改写之前"：放在记忆之后是因为意图判断需要对话历史（比如"好的，帮我退了吧"离开上下文完全无法判断）；放在改写之前是因为改写只有知识检索路径才需要，闲聊/工具调用根本用不上改写后的 query。但文章明确说明：**Ragent 项目实际落地时选择了把 Query 改写放在意图识别之前**，理由是生产环境里绝大多数流量本来就是知识库问答，让改写先跑不会造成明显浪费，工程实现上更简单。这是一个值得记录的真实取舍——"架构图上最优雅的顺序"未必是"生产代码里最终采用的顺序"。

- **Java 实战实现要点**（基于 OkHttp 调用 SiliconFlow API，模型用 `Qwen/Qwen2.5-7B-Instruct` 这种小模型做分类以控制成本）：
  - `IntentClassifier.classify()` 是混合方案的入口：先查规则层（短消息完全匹配闲聊关键词集合），命中直接返回高置信度结果（0.99），未命中才调 `classifyByLLM`。
  - LLM 分类结果做两层兜底：`parseIntentResult` 里 JSON 解析失败时默认返回 `("knowledge", 0.5)`；解析出的 intent 不在合法集合（`knowledge/tool/chitchat/clarification`）里同样兜底为 knowledge。
  - `IntentRouter.route()` 用 Java `switch` 表达式按 intent 分发到四个独立 handler，未匹配（default）分支同样走知识检索。
  - 演示的 5 个场景里最有代表性的是场景 5：孤立看"好的，帮我退了吧"这句话语义很弱，但结合前几轮对话（用户在聊 iPhone 16 Pro 屏幕亮点问题、助手刚问是否要发起退货），模型正确判断为工具调用——直观展示了对话历史对意图判断的必要性。

- **生产环境注意事项**：
  - 意图分类错误通常不会被用户直接感知（用户只会觉得"这系统答得不对"），所以必须主动记录日志（query、intent、confidence、method、history_length、latency_ms 等字段）用于监控，而不能指望用户主动反馈。
  - 关键监控指标：分类准确率（人工抽检，目标 90%+）、各意图分布比例（clarification 占比异常升高说明 Prompt 过于保守，动辄要求澄清）、误分类典型案例复盘、规则层命中率（经验区间：低于 10% 说明规则太少，高于 60% 要检查是否规则过于激进导致误判）。
  - 分类失败（JSON 格式不规范、意图不在合法集合、API 超时/报错、置信度低于 0.5）统一兜底走知识检索，不走澄清——因为知识检索自带兜底话术，而澄清会让用户觉得系统"什么都要问"，体验更差。
  - 建议把意图分类体系做成**配置化**（意图定义、示例、关键词都存到数据库/配置文件里），新增意图类别（比如后期加"投诉""催单"）只需改配置，不需要改代码、不需要重新部署。

- **文章结尾串联的完整多轮对话 RAG 链路**：用户提问 → 会话记忆（读取/保存历史）→ 意图识别（判断走哪条路）→ 路由分发（知识检索路径走 Query 改写→检索+重排→生成；工具调用路径走 Function Call/MCP；闲聊路径模型直接回复；澄清路径返回引导问题）→ 保存 assistant 回复到会话记忆。下一篇预告主题是 RAG 系统的评估与优化。

## 关键概念/术语

意图识别（Intent Recognition）：判断一条用户消息应该被归入哪种处理类别的分类过程，是问题路由的前置步骤。
问题路由（Router）：根据意图分类结果，把请求分发到对应独立处理流程（知识检索/工具调用/闲聊/澄清）的调度组件。
知识检索意图（knowledge）：答案存在于知识库文档中的静态通用知识类问题。
工具调用意图（tool）：答案需要调用外部系统 API 才能获取的个人数据/实时信息/操作类问题。
闲聊意图（chitchat）：打招呼、感谢等不涉及具体业务的对话。
引导澄清意图（clarification）：信息不足以判断意图、需要反问用户补充的情况；文章强调要谨慎使用，避免滥用。
混合方案：规则层做第一层高置信度快速过滤，大模型层做第二层精确分类，兼顾速度与准确率的意图识别实现方式。
置信度（confidence）：大模型分类结果附带的可信程度数值，用于在过低时触发兜底策略。
兜底策略：分类失败或结果不合法时统一采取的安全默认处理方式（本文中默认走知识检索）。

## 与 xrag 项目的关系

- xrag 后端目前是 Java/Spring Boot 技术栈（`backend/` 下为 Spring Boot 骨架），本文的 Java + OkHttp + 小模型（Qwen2.5-7B-Instruct 量级）意图分类实现思路可以直接作为未来问答核心链路（对应 `learning/ragent-column/INDEX.md` 里的 05-qa-pipeline 分组/检索增强问答模块）中意图识别子模块的实现参照，技术栈完全对齐，不需要额外做语言/框架转换。
- 当前 xrag 仓库处于纯脚手架阶段（后端仅有基础 Spring Boot 骨架，前端仅有 Vite 默认页面，尚无检索、会话记忆、意图识别等业务代码），本文属于知识储备，具体落地要等到 05-qa-pipeline 阶段的模块设计与开发时才会真正编码实现。
- 落地时建议直接采用文中的混合方案架构：规则层（关键词/正则，可配置化存储）+ 小模型分类兜底，并把 `IntentClassifier` 和 `IntentRouter` 按文中的职责边界拆成两个独立组件（分类 vs 分发），便于后续单独替换或扩展意图类别。
- 需要在设计阶段就显式决定"意图识别 vs Query 改写"在链路中的先后顺序，并把决策理由记录下来（本文给出的先例是：理论上意图识别该在改写之前，但生产落地时 Ragent 选择了改写在前，理由是多数流量走知识库问答）——xrag 团队应结合自己的实际流量分布做出并记录同样的取舍，不要默认照抄"教科书顺序"。
- 生产可观测性清单（分类准确率、意图分布比例、规则命中率、误分类复盘）应作为意图识别模块从"能跑通"到"生产可用"的验收项，在模块设计阶段就预留好日志字段（query/intent/confidence/method/history_length/latency_ms）。
- 评论区关于"是否还需要显式意图路由，还是直接把知识库检索和工具调用都封装成 MCP 服务、让大模型自己从 MCP 服务列表里选"的争论，与 xrag 后续 04-model-scheduling（模型路由网关模块）如何与问答链路对接直接相关，值得在设计该模块时明确表态并写清楚选择的理由，而不是隐含假设某一种做法。

## 值得注意的设计取舍/坑

- 规则匹配的根本缺陷是无法理解语义，"帮我看看剩几天假"这种没有命中预设关键词的自然表达会被规则错分——规则方案只能作为第一层过滤器，不能单独作为生产方案使用。
- 知识检索 vs 工具调用的边界不是由问题文本本身唯一决定的，同一个问题（"有货吗"）该归哪一类取决于系统是否具备对应的实时数据能力（有没有接库存 API）——这意味着意图分类体系的设计必须和系统实际具备的工具/数据能力同步维护，不能脱离系统能力单独定义。
- 误分类的风险是不对称的：工具调用被误判为闲聊（该退货的说了句"好的呢"）比闲聊被误判为知识检索（多余检索一次但有兜底话术）后果严重得多。这个不对称性是路由层"默认兜底走知识检索、而不是澄清或其他路径"这一设计决策的直接依据，抄这个方案时要理解背后的理由，而不是只抄结论。
- 引导澄清容易被滥用：Prompt 里必须明确"只有真的无法判断时才分类为 clarification"，否则模型会动辄反问用户，体验类似"什么都要问"的笨系统；生产监控里 clarification 占比异常升高是这个问题的直接信号。
- 意图识别在 RAG 链路中的"理论最优位置"（会话记忆之后、Query 改写之前）和 Ragent 项目"实际采用的位置"（Query 改写在意图识别之前）不一致——文章坦诚说明了这一出于生产流量分布考量的取舍，提醒读者架构图上的分层逻辑和最终落地代码可以合理地不完全一致，关键是取舍理由要想清楚并记录下来。
- 评论区两处值得留意的讨论：① 读者谢庆提出一种替代思路——把知识库检索和工具调用都作为 MCP 服务暴露给大模型，让大模型直接从 MCP 服务列表里自主选择，这样似乎就不需要做显式的意图路由了；读者石尘溪对此提出反驳：这样做会导致多次调用 MCP，而且无法保证大模型能正确理解每个 MCP 服务本身的意图边界——也就是说，把路由决策隐式地交给大模型的工具选择能力，并不能免除本文想解决的"意图判断不准确"这个根本问题，只是把决策点从"显式分类器"转移到了"模型的工具选择"，可靠性问题并未消失。② 读者马忽悠提出一个本文未直接回答的开放问题：如果一个问题需要同时调用多个不同的工具和知识库，除了用 ReAct 之外还有没有别的处理方式——这是一个留待后续模块设计时需要明确回答的问题，不能假设 ReAct 是唯一或默认答案。
- 文章早期版本据读者反馈（张恒的评论）曾出现过代码复制错误（缺少 IntentRouter 类），后经作者确认修复；提醒即便是专栏配套代码，也应该在实际引用/复用前自行跑通验证，不能完全信任示例代码"一定能直接用"。
