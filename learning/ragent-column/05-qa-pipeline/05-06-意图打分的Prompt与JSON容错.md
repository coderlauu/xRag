# 《怎么让大模型同时给 30 个意图节点打分》

> 原文链接：https://t.zsxq.com/VnGnQ
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

把全部叶子节点序列化成 `key=value` 文本塞进一条 System Prompt，**一次 LLM 调用给所有节点打分**，返回 `[{id, score, reason}]`；Prompt 负责"怎么判"（实体导向 vs 主题导向两套匹配策略 + 数量控制 + 评分区间），代码负责"接得住"（五层 JSON 容错 + 分数阈值兜底）。

## 核心内容提炼

- **序列化五字段：`id` / `path` / `description` / `type` / `examples`**。`id` 是 LLM 必须原样回传的关联键；`path`（全路径）给 LLM 层级与领域上下文；`description` 是匹配的核心依据；`type`（KB/MCP/SYSTEM）给一个额外判断维度——MCP 匹配的是操作语义、SYSTEM 匹配的是社交性问候、KB 匹配的是知识性问题；`examples` 相当于 Few-shot。

- **用 `key=value` 而不是 JSON，是为省 Token**。JSON 的引号/花括号/冒号/逗号全是额外开销，11 个节点差别不大，30 个节点就可观了。`examples` 用 ` / ` 拼成一行而不是每行一条，同样是控制 Prompt 长度。

- **Prompt 的承重设计是"两步判断流程"**：
  1. 先识别问题类型——**实体导向**（含具体系统/产品/模块/客户名）走**强匹配**，关键实体必须出现在 `id`/`path`/`description`/`examples` 里，实体不一致时即使领域相似也不匹配；**主题导向**（只有主题词）走**弱匹配**，`path`/`description` 含相同或高度同义的主题词即可。
  2. 再按相关度三档优先级选：精确匹配（最高）> 场景/主题词匹配（中）> **行业领域相似性（最低，仅弱信号，不能单独作为选择理由）**。

  不区分的后果是双向的：实体问题用弱匹配会跨类目误命中；主题问题用强匹配会因找不到精确实体而漏掉本该命中的分类。

- **数量控制默认返回 1 个**。理由是上游查询改写（第 4 篇）已经把复合问题拆成了子问题，一个子问题通常只有一个核心意图。两个例外：拆分不干净时最多 2 个；同名主题跨类目出现（如"运费"）时最多 3 个候选用于歧义引导（第 8 篇展开）。

- **类目限定规则是专门用来压制 LLM 过度联想的**：问题明确提到某类目时只在该类目下选，除非问题本身就在比较多个类目。

- **评分三档 + 一条整体规则**：`>0.8` 强匹配 / `0.4~0.8` 中等 / `<0.4` 弱相关建议返回 `[]`；**所有候选都低于 0.6 时优先返回空数组**。设计意图很明确——**错误的路由比没有路由更糟糕**：路由错了会从错误的知识库检索到不相关 chunk，基于它生成的答案大概率是错的，而且用户看不出来答案来自错误方向。空数组则会走兜底（全局搜索或澄清），是可见的降级。

- **`reason` 字段代码端不参与任何逻辑判断，纯为可观测性存在**——日志里能看到 LLM 为什么选了这个节点，用来判断 Prompt 规则有没有起作用。

- **调用参数 `Temperature=0.1` + `TopP=0.3` + `thinking=false`**。意图分类是分析性任务要的是确定性：0.7 的温度会让同一个问题今天命中"清关流程"、明天命中"运费计算"，路由不稳定则整个系统不可预测。不用 0 是因为部分模型在 0 时存在数值精度导致的不稳定，0.1 是工程安全值。`thinking=false` 因为模式匹配任务上 CoT 对准确率提升微乎其微，却实打实增加 Token 与延迟。

- **消息结构只有两条**：System（角色 + 规则 + 评分标准 + 输出规范 + 分类列表）+ User（用户问题）。意图分类是单轮任务，不需要对话历史。

- **五层 JSON 容错，逐层递进**：
  | 层 | 处理的问题 | 手段 |
  |---|---|---|
  | 1 | 模型自动加 ` ```json ` 围栏 | 两个正则去头去尾 |
  | 2 | 模型外面包了 `{"results": [...]}` | 是数组直接用，是对象取 `results`，都不是则 warn + 空列表 |
  | 3 | 单个元素缺 `id`/`score` | `continue` 跳过该元素，**不丢掉整批** |
  | 4 | LLM 编造了不存在的 ID | 查 `id2Node` 找不到就跳过并 warn（日志里留下编造的 ID 便于调 Prompt） |
  | 5 | 输出压根不是 JSON | 全局 try-catch 兜底返回空列表，下游走全局搜索 |

  一句话概括：**能解析多少就解析多少，解析不了就优雅降级**。

- **Prompt 里写 `<0.4` 建议返回空，代码端阈值却是 0.35**。这个不一致是故意的——Prompt 里的数字是给 LLM 的建议，LLM 不会严格遵守，边界上可能给出 0.38，代码端留一点容差空间。

- **模板加载：文件后缀是 `.st` 但没有用 StringTemplate 引擎**，`fillSlots()` 就是 `String.replace("{key}", value)`。模板内容用 `ConcurrentHashMap` 缓存避免每次读 classpath，`cleanupPrompt()` 把连续 3 个以上空行压成 2 个。

- **多子问题通过 `CompletableFuture` 并行分类**，提交到专用线程池 `intentClassifyExecutor`，耗时只取最慢的那个；**单个子问题失败降级为空意图列表，不阻断其他子问题**——这是隔离性设计。全部完成后 `capTotalIntents()` 做全局封顶（第 7 篇）。

## 关键概念/术语

- **实体导向 / 主题导向**：Prompt 中给 LLM 的两种问题类型判定，分别对应强匹配与弱匹配策略。
- **`NodeScore`**：`IntentNode` + `score` 的二元组，意图分类的输出单元。
- **`SubQuestionIntent`**：子问题 + 其命中意图列表，是 `IntentResolver` 的输出单元。
- **`INTENT_MIN_SCORE` / `MAX_INTENT_COUNT`**：代码端的分数下限（0.35）与单子问题意图数上限（3）。
- **歧义引导式问答**：同名主题跨多类目命中时返回多个候选，交给下游反问用户（第 8 篇）。
- **五层容错**：代码块清除 → 格式兼容 → 缺失字段跳过 → 未知 ID 校验 → 全局兜底。

## 与 xrag 项目的关系

- **最硬的一条缺口：`com.app.ai` 目前不支持任何采样参数。** `ChatCommand` 只有 `messages` / `tools` / `tier` / `options`，`CallOptions` 只有 `requestId` / `timeout` / `cancellation` / `allowedDataRegions`，`ProviderChatRequest` 只有 `messages` / `tools`——全仓库对 `temperature` / `topP` / `thinking` 的引用**数量为零**（已实测 grep）。而意图分类对确定性的要求不是可选项，`Temperature=0.1 + TopP=0.3` 是这套设计能稳定工作的前提。**Phase 3 Step C 必须先决定怎么补这个能力**，且它跨越 ADR 0003 划出的端口边界，不是加个字段那么随意：
  - 选项 A：`CallOptions` 加采样字段，业务侧逐次传；
  - 选项 B：把"分析型/生成型"做成 `ServiceTier` 之外的第二个维度，由调度层按用途注入固定参数；
  - 选项 C：在 deployment 配置里给不同用途预置参数集。

  这三种对"业务代码不得触碰 Provider SDK"这条纪律的服从程度不同，取舍要写进 Step C。

- **`ServiceTier` 的三档正好能承接原文的成本意图**。意图分类是典型的 `ECONOMY` 场景（高频、短输出、要快要便宜），答案生成才用 `QUALITY`。但**目前 catalog 里 Chat 只有 `aliyun-qwen-plus-cn` 一个 deployment 且处于 `CONFIG_INCOMPLETE`**（见 [检查点 §4](../PHASE-3-STEP-A-CHECKPOINT.md)），三档 tier 现在落不到不同的模型上。这加强了"必须先拿到一把可用 Chat Key"的结论。

- **五层容错在 xrag 应当收敛到一处，而不是每个调用点各写一遍。** Phase 3 里需要 LLM 返回结构化 JSON 的环节至少有四个：查询改写（第 4 篇）、意图打分（本篇）、工具参数抽取（第 13 篇）、评测打分（06 组）。`com.app.ai.model` 里已经有一个包私有的 `JsonTextValidator`（做的是"入参必须是合法 JSON"的校验，方向相反——它校验的是**发出去**的 `ToolDefinition` 参数 schema），**不能拿来做响应清洗**。响应侧的清洗工具该放在问答链路包里还是 `com.app.ai` 里，取决于它算不算"模型能力"的一部分——倾向于放在问答侧，因为它是对 Prompt 约定的补救，属于业务契约而非模型能力。

- **`CompletableFuture` + 专用线程池的并行模式与 xrag 现状有冲突需要留意。** ADR 0004 已经把流式运行时定为 **WebClient + Reactor**，而知识库侧的异步用的是数据库任务表。意图分类这种"扇出 N 个短调用、全部完成后汇总"的形态，用 `CompletableFuture` 还是 Reactor 的 `Flux.merge`，Step C 要给个统一说法——**同一个模块里两套异步模型并存是维护负担**。

- **`log.info` 里 `peek(node -> node.setChildren(null))` 这个副作用在 xrag 不会自然发生，但要主动防**：xrag 用 JdbcTemplate + 显式 RowMapper，且意图树若按不可变领域类型建模（与 `com.app.ai.model` 一致的风格），`setChildren` 这种写法根本不存在。**把意图树节点设计成不可变记录，这类坑就从"要小心"变成"写不出来"。**

- **Prompt 模板的存放与加载方式 xrag 还没有先例。** Phase 1/2 都没有需要 Prompt 模板的场景。原文的做法（`resources/prompt/*.st` + `ConcurrentHashMap` 缓存 + 简单 `{key}` 替换）足够朴素，可以直接借鉴；**但要和 Phase 2 的一处教训对齐**——模型 catalog 是启动时快照、改配置必须重启。Prompt 模板如果也走 classpath + 进程内缓存，就同样是"改了要重启"，这对需要频繁调 Prompt 的意图分类是不是可接受，Step C 要明确表态，不要默认继承。

## 值得注意的设计取舍/坑

- **"宁可返回空数组也不勉强匹配"是整篇最值得带走的判断。** 它的前提是**下游必须真的有兜底路径**（全局搜索或澄清反问）。如果兜底路径不存在或者体验很差，这条规则就会把"路由错误"换成"直接答不了"，未必更好。所以这条规则不能孤立地抄，要和第 8 篇（歧义引导）、第 9 篇（检索策略）一起看。

- **Prompt 阈值 0.4 与代码阈值 0.35 的错位是有意为之，但它是一处"隐式知识"。** 两个数字分散在 Prompt 文件和 Java 常量两个地方，谁也不知道对方存在。如果有人后来把 Prompt 改成 `<0.5 返回空`，代码端的 0.35 就彻底失去意义了。**这种成对出现的阈值应当在规格里写成一条约束（代码阈值必须低于 Prompt 阈值一档），而不是各自躺着。**

- **`reason` 字段不参与逻辑却必须要求 LLM 输出，是拿 Token 换可观测性。** 值得注意的是这笔账在意图分类这种高频短调用上并不便宜——每个子问题一次、每次 1~3 条 reason。如果后期要压成本，这是第一个该被评估的开关，但**关掉之后 Prompt 调优就只能靠猜**。取舍要显式记录，不要某天悄悄删掉。

- **要求 LLM 原样回传 `id` 是整条链路的关联键，也是最脆的一环。** 第 4 层容错（未知 ID 跳过）说明这事真的会发生。这里有个隐含的设计约束：**`id` 越像自然语言、越有语义，LLM 越容易"改写"它**（比如把 `logistics-overseas-customs` 写成 `logistics-oversea-customs`）；但 `id` 太像随机串又会削弱 LLM 的判断依据。原文的 kebab-case 语义 ID 是个折中，代价就是必须配一层校验。

- **序列化格式的 Token 优化在小规模下是伪优化。** 原文自己也承认"11 个节点下来差距不大"。真正的意义是**它在节点数增长时不会失控**——这是一个"现在没收益、将来不会后悔"的选择。区分这类决策与"现在就有收益"的优化很重要，前者不该拿来当作现在就要做的理由。

- **每个子问题独立调一次 LLM，成本是线性叠加的。** 三个子问题 = 三次全量 Prompt（每次都带完整的 30 个节点列表）。节点列表在三次调用里完全相同，这是 Prompt 缓存（prompt caching）最典型的适用场景，但原文没有提。**xrag 若采用同样的扇出结构，应当把这一层的成本量级先算清楚再决定要不要优化。**
