# 《Chat同步调用与模板方法》

> 原文链接：https://t.zsxq.com/3bUOG
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

同步 Chat 适合用模板方法复用 OpenAI 风格请求的固定步骤，并把是否需要 Key、请求体扩展和思考字段等差异留给 Provider 子类；错误分类必须继续参与重试、故障转移和熔断策略，而不能只改善报错文案。

## 核心内容提炼

- 原文区分业务接口 `LLMService` 和供应商接口 `ChatClient`，由 `RoutingLLMService` 根据候选链解析具体客户端并调用。上层不感知供应商类型。
- `ChatRequest` 承载消息、temperature、top-p、top-k、max tokens、思考模式和工具等通用字段，`ChatMessage` 统一 system/user/assistant 角色。
- `AbstractOpenAIStyleChatClient` 固定同步调用流程：
  1. 校验 Provider 配置和凭据；
  2. 构造 OpenAI 风格 JSON；
  3. 解析最终 URL 和鉴权头；
  4. 发送 HTTP 请求并确保响应资源关闭；
  5. 非 2xx 转为结构化异常；
  6. 解析 `choices[0].message.content`；
  7. 响应形状不合法时抛出明确错误。
- 模板通过小钩子表达差异：`requiresApiKey` 控制本地模型是否需要凭据，`customizeRequestBody` 增加 Provider 特有字段，`isReasoningEnabledForStream` 处理思考内容。
- Ollama、百炼、硅基流动等 OpenAI 风格 Provider 只需薄子类；协议差异明显的供应商应直接实现 `ChatClient`，不要为了继承而扭曲请求。
- 原文把错误归一成未授权、限流、服务端错误、客户端错误、网络错误、非法响应和 Provider 错误，并通过 `ModelClientException` 携带类型和上下文。

## 关键概念/术语

- **模板方法**：基类固定调用骨架，子类只覆盖少量供应商差异。
- **薄适配器**：不承载调度逻辑，只负责协议翻译和错误归一。
- **结构化错误**：包含稳定错误类型、HTTP 状态、Provider 和请求标识的异常。
- **请求模型 / 响应模型**：请求时指定的模型和 Provider 实际返回的模型，诊断中应分别保留。
- **完成原因**：正常结束、长度截断、工具调用、内容过滤等完成状态。

## 与 xrag 项目的关系

- xrag 当前同步 Embedding 使用 Spring `RestClient`，已有非 2xx 错误体保留、响应校验和清晰异常的经验，可复用于同步 Chat 的 HTTP 基础设施；Chat DTO 和响应解析仍应独立。
- Phase 2 的公共执行模板应统一“候选快照 → 许可 → Provider 调用 → 归一化结果/错误 → 决定重试或故障转移 → 诊断”，而不是强迫所有能力继承同一个 HTTP 基类。
- 内部 Chat 响应至少应保留实际 Provider/模型、完成原因、usage 和 Provider 请求 ID；只返回 `String` 会让诊断和后续 Phase 3 编排丢失必要上下文。
- Provider 适配器负责把供应商错误转换为稳定类型，调度层负责根据类型执行策略。两层职责必须分开，避免适配器自行重试后调度层再次重试。
- 真实 Provider 能力测试继续沿用 Phase 1 的方式：CI 使用可编程假 Provider，收费或带凭据的真实调用由显式环境变量守门。

## 值得注意的设计取舍/坑

- **错误分类如果不参与策略，就只是更漂亮的异常枚举。** 原文的通用执行器仍捕获所有异常并统一回退，xrag 需要真正建立“错误类型 → 重试/切换/熔断”矩阵。
- **不要把原始错误体无条件写入诊断库。** 它可能包含请求内容或敏感信息；日志和页面默认只存脱敏摘要、稳定类型和请求 ID。
- **OpenAI 风格请求字段不是所有 Provider 都支持。** 未验证字段应由能力元数据和适配器控制，不能因为 JSON 能发送就声称功能可用。
- **同步模板不能复用于流式生命周期。** 同步调用在方法返回时已经知道结果；流式调用在返回后才可能失败、取消或完成，需要不同状态机。
- **模板基类不要无限增长钩子。** 当 Provider 需要大量覆盖时，直接实现接口比继续增加布尔钩子更清晰。
