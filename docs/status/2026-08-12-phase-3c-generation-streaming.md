## 1. 交付范围

Phase 3 首次形成可回答的完整知识问答链路：

> 对话记忆与问题改写 → 意图匹配 → 混合检索与受控工具 → 不可信内容隔离与 Prompt 预算 →
> 流式模型调用 → 排队、停止、断连恢复与唯一终态 → 助手消息持久化。

| 组成 | 落点 |
|---|---|
| Prompt 安全与预算 | `com.app.qa.prompt`：固定两消息结构、JSON 数据编码、完整条目淘汰与超预算短路 |
| 生成深模块 | `com.app.qa.generation`：`GenerationTasks.submit/stop`、FIFO 许可、订阅、恢复与关停 |
| 唯一结算 | `TaskSettlement.trySettle` + V11 数据库约束：任务、turn、助手消息与 SSE 终态只结算一次 |
| HTTP/SSE | `POST /api/qa/turns:stream`、停止接口与 GET 恢复；accepted 前后使用不同错误载体 |
| 前端 | `/chat` 的排队、生成、停止、失败、等待超时、未保存与断连恢复状态 |
| 部署 | 8 个 `QA_GENERATION_*` 配置成组登记、启动校验与 30 秒优雅关停窗口 |

明确不在本里程碑：WebSocket、SSE 重放、多实例分布式队列、再生成/继续生成、流式 Markdown、
第二家 Chat 供应商、生成中的二次工具循环，以及 RAG 质量评测。

## 3. 证据边界

- 7 条浏览器验收由 AI 代理驱动，不是项目所有者人工目视签字。夹具只控制网络时序与终态，页面、
  状态机、样式和可访问性使用生产代码；它证明界面行为，不证明真实模型质量。
- 3C E2E 使用真实 HTTP、PostgreSQL 和假流式模型，验证的是系统接线与协议。真实 DashScope
  `STREAM_CHAT` 已由 Phase 2 的显式计费守门测试验证，但本轮未执行新的真实供应商 3C 端到端调用。
- SSE 不重放 delta。断连后通过 GET 轮询任务，终态时一次性恢复已持久化的完整或部分回答。

## 4. 期间做出的关键裁决

| 裁决 | 内容 |
|---|---|
| 单一结算 | 完成、停止、超时、失败、断连与关停按 CAS 首胜，不用枚举优先级事后改写事实 |
| 不可信输入 | 用户问题、历史、证据、工具结果、意图提示和摘要全部编码为数据，不能进入 System 指令层 |
| 排队与失败 | 队列满发生在 accepted 前，返回 429；accepted 后的失败、停止和超时通过 SSE 终态表达 |
| 断连 | 客户端断开只解绑 observer，后台继续；前端轮询恢复，不伪造打字动画 |
| 部分回答 | 停止或流失败已有正文时只保存一次 incomplete 消息；零字符终止不创建空消息 |
| 无障碍 | 流式区用 `aria-busy`，不逐 token `aria-live`；提交后不把焦点强制跳到停止按钮 |
