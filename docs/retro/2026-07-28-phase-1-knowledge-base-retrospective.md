## 4. 做对了什么

### 4.1 用纵向切片保持每一步可演示

工单按用户路径而不是纯技术层拆分。知识库 CRUD、上传、异步入库、分块管理分别形成独立闭环，使中途状态始终可验证，也让后端、前端和测试对同一行为负责。

### 4.2 把高风险假设变成尖锐的验收项

- 上传内存验证从 30MB 加码到 48MB，并用 `-Xmx256m` 把“是否整体进堆”变成近似二元判定。
- Embedding 是否位于事务外，由观察数据库活动升级为可重复的自动化断言。
- 定时同步的“内容未变/已变”用成对自动化用例固定下来。

### 4.3 保留了真正需要人工参与的浏览器验收

手工走查发现了 `Modal` 在 React StrictMode 下静默失效的问题。163 条接口测试当时全部为绿，但无法证明弹层真的显示在屏幕上。这证明浏览器验收不是接口测试的重复。

### 4.4 发现问题后修正系统边界，而非只补局部症状

存储复核发现 URL 同步会提前覆盖当前原文后，没有只修一条同步语句，而是引入不可变版本 Key、任务输入快照和成功后切换 active 文件的完整生命周期；测试对象泄漏也通过独立测试命名空间与套件清理解决。

## 5. 暴露的问题

### 5.1 产出物闸门最初没有落实到执行清单

可点击原型虽然出现在总计划中，却没有进入 Lane 的写入范围和完成定义，导致所有下游清单彼此一致地漏掉它。修复方式是把每个 Step 的必出产物和用户确认要求写入总计划，并把原型确认设为前端开工前置条件。

### 5.2 界面规格缺少状态组合检查

工单 13 和 14 分别暴露“禁用分块保存后错误提示向量已更新”和“新增分块可指定位置但原型无控件”。单份文档各自自洽仍可能遗漏状态组合；只逐条阅读规格不足以发现这类问题。

### 5.3 外部服务合规与真实限流检查得太晚

- Coding Plan Key 的使用条款在实现并实测后才被查证，当前直接 API 调用路径不适合共享或生产环境。
- 大文档真实调用时才发现供应商 `429` 频率限制；假 Embedding 无法暴露这类供应商行为。

以后接入外部 API，供应商条款、协议形状、额度、单批上限和频率限制都应在设计阶段成为明确检查项。

### 5.4 单实例假设多次污染本地测试

IDE 中遗留的后端实例会和测试上下文争抢同一张任务表，表现为大量业务测试随机失败。问题最终通过执行前端口检查降低了复发概率，但架构本身仍只承诺单实例，边界见 ADR 0002。

### 5.5 状态文档没有随最后一轮实施同步更新

分角色任务书仍记录“152 条测试、剩余 3 项手工验证”，而当前事实是 176 条测试且手工项全部完成。阶段状态不应依赖从提交记录和测试矩阵重新拼装。

### 5.6 远端 CI 与本地基线出现分歧

当前本地完整门禁为绿，但 GitHub Actions 的 `validate` 为红；`infra` 已通过。Step F 未跑绿之前不能把“本地通过”等价成“交付链路完成”。

## 6. 手工验收带来的直接收益

本阶段执行的手工项中有三条抓到真实缺陷，并已修复回归：

1. M-05：`max-request-size=60MB` 让 50～60MB 请求绕过头部预判，改为 51MB 后快速拒绝。
2. M-06：真实 Embedding 大文档触发出站限流，补上批次间隔与 `429` 指数退避。
3. M-09：StrictMode 下弹层一帧内关闭，修正 `dialog` 生命周期。

这三类问题分别位于容器行为、第三方服务和浏览器运行时，单靠后端集成测试无法覆盖。

## 7. 带入 Phase 2 的永久改进

1. **外部 API 先做准入检查**：条款、鉴权方式、模型能力、限额、频率、超时和费用全部确认后，才能冻结方案。
2. **界面规格做状态叉乘**：把状态、来源类型、启禁用、处理中和错误类型列成组合矩阵，再评审每个控件和反馈。
3. **保留浏览器验收**：有界面的模块必须在 Step E 走真实用户路径；Phase 2 设计时单独决定是否引入前端自动化测试。
4. **跨系统写入使用不可变输入**：外部对象先版本化，任务绑定快照，成功后再切换 active 指针。
5. **远端 CI 是交付证据**：功能模块不能只凭本地绿灯关闭；特性分支必须在合并前触发并跑绿质量门禁。
6. **每个 Step 结束即更新状态**：测试数量、手工项和阻塞项只维护一个当前状态入口，避免在多个 Decision Log 中漂移。

## 8. 保留的技术债与边界

- 前端目前没有自动化测试脚本，依赖类型检查、lint 和浏览器验收。
- 入库调度只支持单实例；进入多实例部署前必须重新设计任务所有权和启动回收。
- 对象存储永久清理默认关闭，历史对象未在本阶段批量迁移或删除。
- 当前 Coding Plan Key 仅限项目所有者知情的个人学习场景；任何共享或生产部署前必须替换为合规的纯文本 Embedding 模型和 Key。
- 检索与问答属于 Phase 3；Phase 1 只保证向量正确存在、隔离且生命周期一致。
