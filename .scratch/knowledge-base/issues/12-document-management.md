# 12 — 文档配置更新、启用/禁用、删除

**What to build:** 用户能改文档名和分块参数、临时下线一份有问题的文档（禁用）、删除不需要的文档。

「禁用」这个功能的正确性有一个不直观的要求：**必须物理删除向量库里的数据，而不是只打个标记位**。检索是直接查向量表的，只改数据库标记的话文档内容照样会被检索到，"禁用"就完全没有效果。

## 进行记录

### 为什么这张工单一度停在闸门上（`2026-07-26` 已确认并落地）

工单清单里"前端：文档列表的编辑/启禁用/删除操作"这一行，**三个操作的规格状态并不一样**：

- 启禁用、删除：ui-spec §3 有 `RUNNING` 规则、§9 有两条二次确认文案，原型也早就实现了 → 直接做。
- **编辑文档：规格是空白的。** §3 的禁用表里出现过"编辑文档（名称、分块参数、同步配置）"，但字段、校验、保存后的行为一概没写；原型里这个按钮一直挂着 `notSpecced('编辑文档')`，演示控制台的说明还专门写了"ui-spec.md 目前没有规定它们的字段与校验，**原型不替规格做决定**"。

按 [CLAUDE.md 产出物闸门](../../../CLAUDE.md)与[主计划 §6.1](../../../docs/exec-plans/active/2026-07-24-ragent-column-learning-and-system-build.md)，有界面的部分必须**原型经用户确认后才能写前端代码**。所以补了 [ui-spec §11](../../../tech/knowledge-base/ui-spec.md) 与原型实现，**停在这里等确认**，没有直接写 React 表单。

### ui-spec §11 里需要用户拍板的三处

1. **改了分块参数之后用后续确认弹层，而不是 toast**。它需要用户做一个决定（要不要立刻花钱重算向量），toast 会自动消失、错过就没了。文案：「现有的 N 个分块仍然是按旧参数切出来的。要立即用新参数重新处理吗？」＋［稍后再说］［立即重新处理］。
2. **不做"参数已改但未生效"的持久标记**。后端没存"上次分块用的是哪套参数"，`needsRechunk` 是按请求算出来的，刷新后就无从得知。要做持久标记得在 `source_document` 上再存一份参数快照（一次 migration + 每次分块维护它），代价大于收益。**这是有意接受的取舍**，写进了规格。
3. **FILE 来源不显示来源地址与定时同步两组字段，而不是显示成灰色禁用态**。它们对 `FILE` 根本不存在，灰着摆在那里只会让用户以为"有个开关我打不开"。

### 后端几处实现判断

- **校验的是合并之后的取值**。只传 `overlap` 时也要和库里现有的 `chunkSize` 比——否则能存进一个 `overlap >= chunkSize` 的组合，等到下次分块才在算法里炸开（那时步进 ≤ 0，固定长度切分原地打转停不下来）。有单独一条测试守它。
- **`needsRechunk` 在 `revision = 0` 时恒为 false**。从没处理过的文档没有"旧分块"，提示"需要重新分块"会让用户以为漏做了什么，其实他只要照常点「开始处理」。
- **删除顺手关掉 `sync_enabled`**（data-model §4）：定时扫描的部分索引不再覆盖这行。扫描 SQL 本身也带 `deleted = false`，但把它从索引里摘出去更干净。
- `DocumentService` 因此新增了 `TransactionOperations` 与 `EmbeddingClient` 依赖——启用文档要重算全部已启用分块的向量，必须事务外算完再开事务，`setEnabled` 也就不能加 `@Transactional`。

### 一次踩坑：IntelliJ 起的后端进程在抢测试任务

集成测试首跑 12 条里 10 条失败，症状是 setUp 里等 `SUCCESS` 等到 `FAILED`。根因不是代码：**IntelliJ 启动的另一个后端实例连着同一个库**，两个 `IngestionDispatcher` 都在轮询 `ingestion_run`，它抢走测试建的任务后失败在 `S3 404`。停掉它之后全绿。这是 ADR 0002「单实例假设」在开发机上第二次以不同形态出现（第一次是工单 10 的双 Spring 上下文）。
