# ADR 0002：知识库入库的异步机制与并发控制

- 状态：已接受
- 日期：2026-07-25
- 相关：[ADR 0001](0001-build-xrag-independently.md)、[知识库 PRD](../prd/2026-07-25-knowledge-base-prd.md)、[技术方案](../../tech/knowledge-base/architecture.md)

## 背景

知识库入库（解析 → 分块 → 向量化 → 写库）是一个耗时几十秒到几分钟的操作，必须异步执行；同时它必须保证同一份文档不会被并发处理两次（手动触发和定时同步会撞车），且进程崩溃后不能让文档永久卡在"处理中"。

学习材料给出的方案是：**RocketMQ 事务消息**保证"数据库状态更新"与"异步任务投递"的原子性，**数据库租约锁 + 心跳续期**（`lockOwner` + `lockUntil`，续期间隔 = 租约时长/3，对齐 Redisson watchdog 的做法）保证定时任务在多实例下的互斥与故障恢复，**Redisson `RPermitExpirableSemaphore`** 做上传并发限流。

这套方案针对的是多实例部署的生产环境。xrag 的实际情况不同（[PRD §2](../prd/2026-07-25-knowledge-base-prd.md)：单用户个人项目，单实例部署），按 [ADR 0001](0001-build-xrag-independently.md) 的要求，不能因为"课程这么做"就直接采纳，需要独立判断。

## 决策

### 1. 用数据库任务表替代消息队列，不引入 RocketMQ

异步任务载体是数据库表 `ingestion_run`：接口在事务内插入一行 `status='QUEUED'`，一个 `@Scheduled` 轮询（2s 间隔）取出待办任务、CAS 抢占后提交给线程池执行。

**关键论证**：事务消息解决的是"本地数据库事务"与"远程消息投递"两个异构系统之间的原子性问题——数据库提交了但消息没发出去，任务就丢了；消息发出去了但数据库回滚了，任务就成了幽灵。而当任务本身就是同一个数据库里的一行时，"状态更新"和"任务入队"落在**同一个本地事务**里，两者要么都成功要么都不生效。**这个问题被消除了，而不是用更简单的方案解决了。**

因此不引入 RocketMQ，也就不需要事务消息、半消息回查、消费幂等这一整套机制。

### 2. 用状态字段 CAS 替代分布式锁

并发互斥靠一条 SQL：

```sql
update source_document set status = 'RUNNING', ...
 where id = ? and deleted = false and status <> 'RUNNING'
```

影响行数为 0 即表示已有任务在处理，直接拒绝。

**关键论证**：一条 `UPDATE ... WHERE` 语句在数据库层面是原子的，它把"检查状态"和"占用状态"合并成了一个不可分割的操作，检查与占用之间不存在时间窗口。锁的作用正是消除这个窗口——窗口本来就不存在时，锁没有任何事情可做。这不是"用弱一致换简单"，而是 CAS 在此场景下与锁**能力等价**。

手动触发和定时同步竞争的是同一行的同一个字段，先到先得，无需额外协调。

### 3. 用启动回收 + 心跳超时替代租约锁续期

不做 `lockOwner`/`lockUntil` 租约锁。卡死任务的回收分两层：

- **启动时回收**：应用启动后把所有 `RUNNING` 状态的任务与文档标记为 `FAILED`。
- **心跳超时回收**：执行线程每 10s 更新 `heartbeat_time`；`@Scheduled` 把超过 5 分钟未更新的 `RUNNING` 任务判为卡死。

**关键论证**：租约锁的复杂度（锁归属标识、过期时间、按 1/3 周期自动续期、续期失败的处理）全部来自一个需求——**在多个实例之间区分"这个任务是谁在跑"**。单实例下这个区分不存在：进程刚启动时，任何 `RUNNING` 记录都必然是上次进程留下的僵尸，判断是**完全准确**的，不需要靠时间推测。

心跳超时那一层保留了，因为它覆盖的是另一类问题——进程活着但任务卡住（下载 hang 死、Embedding API 不返回）。这类问题跟实例数量无关，单实例同样存在。

### 4. 用本地信号量替代 Redisson 分布式信号量

上传并发限流用 `java.util.concurrent.Semaphore`，`tryAcquire` 带 5s 超时，拿不到返回 429。拦截位置在 `Filter`（不是 `HandlerInterceptor`）。

**关键论证**：单 JVM 内本地信号量与分布式信号量能力等价，且省掉了网络往返和租约过期处理（`RPermitExpirableSemaphore` 存在的意义就是防止持有者崩溃导致许可永久泄漏——本地信号量在 `finally` 里释放即可，进程崩溃时整个信号量随进程一起消失，泄漏问题不存在）。

拦截位置不是简化，而是正确性要求：multipart 请求体由 `DispatcherServlet` 解析，时机在 `Filter` 之后、`Interceptor` 之前。放在 `Interceptor` 里限流时文件已经完整读入，限流保护磁盘和 IO 的目的已经落空。

## 后果

正面影响：

- 不引入 RocketMQ 和 Redisson 两个中间件依赖。本模块甚至完全用不到已有的 Redis，基础设施保持在 Postgres + 对象存储两项。
- 任务状态天然持久化在数据库里，进程重启后可恢复；执行历史、失败阶段、跳过记录用同一张表承载，无需额外设计。
- 定时同步与手动触发共用同一套互斥与恢复机制，不是两套并行实现。
- 每项简化都有明确的等价性论证，而不是"个人项目就凑合一下"——这个论证过程本身是可展示的产出物。

代价与已知限制：

- **派发延迟最多 2s**（轮询间隔）。对分钟级的入库任务无影响。
- **轮询有恒定的数据库开销**：每 2s 一次索引扫描。部分索引 `where status in ('QUEUED','RUNNING')` 让扫描成本与历史任务总量无关。
- **本决策的正确性依赖"单实例部署"**。多实例下会具体失效在：
  1. 启动回收会把其他实例正在运行的任务误判为僵尸（**这一条会造成实际错误**）；
  2. 本地信号量退化为"每实例各限 N 个"，全局并发上限失控。

  CAS（第 2 条）在多实例下**依然正确**，无需改动。届时的升级路径明确：把启动回收改成带实例标识的租约锁 + 续期（也就是回到课程方案），把本地信号量换成 Redisson。真要走到那一步时，本 ADR 记录的论证过程正好说明了每一处为什么必须改。
- `ingestion_run` 表只增不减，会持续增长。个人项目量级下可接受；需要时增加一个历史归档任务，不影响本决策。
