# 《AI大模型Ragent项目》第2小节：调用大模型API

> 原文链接：https://t.zsxq.com/ykBXs
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章讲清楚了大模型 API 的通用请求/响应协议（OpenAI Chat Completions 格式），并用 Java（OkHttp + Gson）分别实现了非流式和流式两种调用方式，让读者第一次真正"调通"一个大模型接口。

## 核心内容提炼

- **OpenAI 协议是事实标准**：OpenAI 的 Chat Completions API 已经成为大模型接口的通用规范，国内 DeepSeek、通义千问、智谱 GLM、SiliconFlow，国外 Anthropic、Google 几乎都兼容它或提供兼容层（文章写作时 Anthropic/Google 已有各自原生协议，但仍保留 OpenAI 兼容层）。实际后果：学一套协议就能调用市面上几乎所有模型，换模型只需改 `baseURL` 和 `apiKey`，业务代码不用动。这也是本系列 Chat/Embedding/Reranker 三类 API 调用的共同基础。

- **请求体核心字段**：本质是一次 HTTP POST，JSON body 包含：
  - `model`：模型标识，各平台格式不同（SiliconFlow 用"厂商/模型名"如 `Qwen/Qwen3-32B`，OpenAI/DeepSeek 直接用模型名）。
  - `messages`：对话数组，是请求的核心，模型看到的是整个数组而不是最后一句话。
  - `temperature`（0~2，RAG 场景建议 0~0.3）/`top_p`（0~1，建议 0.7~0.9，二者通常只调一个）/`max_tokens`（建议 512~2048，视回答长度需求）/`stream`（是否走流式）。

- **messages 的三种角色机制**（这是本节的核心知识点）：
  - `system`：定义模型的行为边界/人设，模型会始终遵守。例如限定客服只回答退换货相关问题，问天气就会拒答。这是 RAG 里注入"请根据以下参考资料回答，资料中没有就如实告知，不要编造"这类指令的载体。
  - `user`：用户当前的问题输入。
  - `assistant`：模型历史回复，用于拼出多轮对话上下文。
  - 关键推论：大模型本身**无状态、无记忆**，每次调用都是独立的；所谓多轮对话，是客户端每次把完整历史（system+user+assistant交替）重新打包发送，模型才能"看懂"上下文。直接后果：对话越长，重复发送的历史越多，Token 消耗和成本随对话轮数近似线性增长。
  - OpenAI 新版 API 引入 `developer` 角色替代 `system`，但目前 SiliconFlow、DeepSeek 等主流兼容层仍用 `system`，故本系列统一用 `system`。

- **响应体核心字段**：`choices[0].message.content` 是模型回答正文；`choices[0].finish_reason` 说明生成为何停止：`stop` 表示模型主动认为已完整作答，`length` 表示被 `max_tokens` 截断（回答可能不完整，需要调大该参数）；`usage.{prompt_tokens, completion_tokens, total_tokens}` 是计费依据，三者关系为总数=输入+输出。

- **非流式调用（stream=false）**：一次性等模型生成完再拿完整 JSON。技术实现是标准 HTTP 同步请求：OkHttp 构建 POST，`Authorization: Bearer <API_KEY>` 头做鉴权，`client.newCall(request).execute()` 阻塞等待，拿到 body 后用 Gson 解析出 `choices[0].message.content`、`finish_reason`、`usage`。优点是实现简单、直接拿到完整 JSON 方便调试；缺点是长回答场景下用户要空等数秒到数十秒。

- **流式调用（stream=true）基于 SSE（Server-Sent Events）**：与"一问一答后断开连接"的普通 HTTP 不同，SSE 是服务端保持连接、持续推送数据块，每块是一行以 `data: ` 开头的文本，全部推送完后发送特殊标记 `data: [DONE]` 并断开。关键区别：流式响应的增量内容在 `choices[0].delta.content` 里，不是非流式的 `message.content`；第一个数据块的 delta 会带 `role: "assistant"` 标识开始，最后一个数据块 delta 为空且 `finish_reason` 变为 `stop`。客户端实现要点：不能用 `response.body().string()` 一次性读取，必须用 `BufferedReader` 逐行读取；逐行判断是否以 `data: ` 开头，去掉前缀后判断是否为 `[DONE]`；解析每块 JSON 取出 `delta.content` 并拼接成完整回答；`System.out.print`（不换行）模拟打字机效果；读超时要设得比非流式更长（示例中非流式 60s、流式 120s），因为连接保持时间更久。

- **非流式 vs 流式的选择原则**：两者总耗时相同（模型生成速度不变），差异在首字延迟和体感。非流式适合后台批处理、不需要实时展示的场景（如 Embedding、Reranker 调用），且响应中直接带 `usage`；流式适合面向用户的实时对话场景，首字延迟低、体验是打字机效果，但**部分平台的流式响应不返回 usage 字段**，即精确的 Token 统计在流式场景可能拿不到。文章给出一个实用经验：开发阶段先用非流式调试（好拿完整 JSON），功能跑通后再把面向用户的部分切换成流式。

- **技术栈选型**：统一用 OkHttp（纯 HTTP 客户端，不依赖 Spring，可移植到任意 Java 项目）+ Gson（手动拼装/解析 JSON），而非 Spring 的 RestTemplate/WebClient，理由是更轻量、更聚焦。这套组合会贯穿后续所有 API 调用（Chat/Embedding/Reranker）。

- **SiliconFlow 平台落地**：手机号注册、控制台生成 `sk-` 开头的 API Key（需要像密码一样保管，不能提交到代码仓库或群聊）。本系列约定使用的三个模型：`Qwen/Qwen3-32B`（Chat，用于本节调用实战及后续 RAG 生成环节）、`BAAI/bge-m3`（Embedding，用于后续向量化环节）、`BAAI/bge-reranker-v2-m3`（Reranker，用于后续检索重排序环节）。

## 关键概念/术语

OpenAI Chat Completions API：大模型接口事实标准协议，几乎所有主流厂商都兼容或提供兼容层，是本系列所有模型调用的共同基础。
messages 角色机制：system（定义行为边界/RAG中注入检索指令）、user（用户输入）、assistant（历史回复，撑起多轮上下文），大模型本身无记忆，靠每次重发历史实现多轮对话。
SSE（Server-Sent Events）：流式响应所用协议，服务端保持连接持续推送 `data: ` 数据块，以 `data: [DONE]` 结尾。
delta：流式响应里表示"本次新增内容"的字段（区别于非流式的完整 message）。
finish_reason：模型停止生成的原因，`stop` 为正常结束，`length` 为被 max_tokens 截断。
usage（Token 用量）：`prompt_tokens`/`completion_tokens`/`total_tokens`，API 按 Token 计费的核算依据。
Bearer Token 鉴权：通过 `Authorization: Bearer <API_KEY>` 头传递密钥，OAuth 2.0 的标准做法。

## 与 xrag 项目的关系

这一节是 xrag 里"调用底层大模型"这层基础设施的直接技术依据：无论是最终生成答案的 Chat 调用，还是后续 Embedding 向量化、Reranker 重排序调用，都会复用同一套"构建 JSON 请求体 → HTTP POST（Bearer 鉴权）→ 解析响应"的骨架，因此 xrag 中对接大模型的客户端可以做成一个统一的、只需替换 baseURL/apiKey/model 的薄封装，而不必按厂商各写一套逻辑。system 消息机制直接对应 xrag 未来 RAG 生成环节的 Prompt 设计——把检索到的知识片段通过 system 消息注入模型，并约束"资料中没有相关信息就如实告知，不要编造"，这是需要在 Prompt 模板层面落地的关键约束。流式/非流式的选择原则也可直接指导 xrag 的接口设计：面向用户的问答接口应支持流式/SSE 输出以降低感知延迟，而 Embedding、Reranker 等后台处理调用可以统一走非流式，便于同步解析和批处理；同时要注意流式场景下 usage 字段可能缺失，xrag 若要做精确的 Token/成本统计，需要在设计上考虑用非流式调用或额外估算来补齐这块数据。

## 值得注意的设计取舍/坑

- 流式响应体必须逐行读取（`BufferedReader`），不能像非流式那样用 `response.body().string()` 一次性读取，否则拿不到数据或行为不符合预期。
- 流式调用要单独设置更长的读超时（文中示例 120s vs 非流式 60s），因为连接会保持更久；网络环境不稳定时容易触发超时——原文读者评论中也反馈过"写 demo 调 API 时经常连接超时，流式调用有时首包要等 15 秒左右才打印结果"，说明这不只是理论风险，实践中要为超时和重试留出余量。
- 部分平台的流式响应不会返回 `usage` 字段，如果业务需要精确的 Token 计费/统计，流式场景可能拿不到，需要额外设计（例如统计场景用非流式，或自行做 Token 估算）。
- `finish_reason: "length"` 是一个容易被忽略的信号，代表回答被 `max_tokens` 截断而非正常结束，出现频率高时应优先调大 `max_tokens`，而不是误以为模型能力不足。
- system 角色未来存在被 OpenAI 新版 API 的 developer 角色替代的趋势，但目前主流兼容层（SiliconFlow、DeepSeek 等）仍用 system，选型上继续用 system 更保险、兼容面更广。
- 多轮对话本质是每次把全部历史消息重新发送一遍，随对话轮数增加，Token 消耗和调用成本会持续上升，这是长会话场景下需要预留的成本控制点（例如后续可能需要历史消息裁剪/摘要策略，本节未展开）。
