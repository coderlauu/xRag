# 03 — 中文切词器与关键词索引写入点

**What to build:** 应用侧切词器与 `document_chunk_keyword` 的写入/删除接入；不做存量回填。

**Blocked by:** 02
**Status:** complete

## Slice

- 引入切词依赖，封装成单一 Bean；索引期与查询期共用同一实例。
- 知识库入库写向量的同一处同时写关键词行；分块更新走 delete + insert 同 `chunk_id`。
- 分块/文档逻辑删除或停用时物理删除关键词行，与向量表同口径。
- 切词器版本与词典摘要进启动日志与配置指纹。

## Acceptance

- [x] 3B-KW-01~06、3B-KW-09 自动化通过。
- [x] 两张派生表在同一批分块上行集合一致（正面断言，不是抽样）。
- [x] 中文长句、中英混排、型号串、全角标点切词结果稳定可复现。
- [x] 同一文本两次切词逐 token 相等。
- [x] 本工单不改检索查询路径（查询路径属工单 05）。

**Evidence:** `ChineseTokenizerTests`（7 项）、`ChunkKeywordIndexIntegrationTests`（6 项）。

**接法上做了一个结构性选择，与工单原描述不同**：关键词写入没有加在十来个调用点上，而是
放进 `ChunkVectorRepository` 自己的插入/删除方法里。原因是"在每个调用点各补一次"必然会漏，
而漏写零报错、症状只是召回悄悄变少。绑在一起之后，行集合一致成了结构性事实而不是纪律。
代价是类名 `ChunkVectorRepository` 略窄于它现在的职责（javadoc 已改为"派生索引的唯一入口"），
没有改名——那会波及整个知识库模块，收益不抵风险。

**tsv 从 `document_chunk.content` 现读而不是由调用方传文本**：派生表应当派生于实际落库的正文。
测试 `kw03` 正面覆盖了这一点（改完正文重建索引后，查得到新词、查不到旧词）。

**切词一致性做成了结构性保证**：查询也走知识库侧的 `ChunkSearchPort`，用同一个
`ChineseTokenizer` Bean。问答模块传原始查询串，自己不分词——于是"索引期与查询期同一套切词"
不再依赖调用方记得。
