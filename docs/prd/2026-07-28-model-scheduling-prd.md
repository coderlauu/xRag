## 1. 背景与动机

Phase 1 已提供可工作的知识库和单一 OpenAI 兼容 Embedding 客户端，但 xrag 尚无同步 Chat、流式 Chat、Rerank、多模型路由、熔断或故障转移能力。若 Phase 3 直接在问答链路里接各家模型 API，供应商协议、重试、切换和诊断会散落在业务代码中，后续很难解释一次请求究竟“选了谁、为什么切换、哪里失败”。

Phase 2 建设独立 AI 基础设施层。Chat、流式 Chat、Embedding 和 Rerank 保留各自稳定能力端口，共享 Provider/模型注册、候选路由、尝试预算、错误分类、熔断、故障转移和诊断。

本 PRD 定义产品行为，不冻结 Java 接口、数据库 Schema、HTTP 客户端、熔断库或线程模型；这些属于 Step C。

## 2. 产品定位

### 2.1 服务对象

1. **Phase 3 问答编排**：调用 Chat、流式 Chat 和 Rerank，不直接依赖具体 Provider。
2. **Phase 1 知识库**：继续通过既有 `EmbeddingClient` 计算向量，由 Phase 2 在其后提供可路由实现。
3. **单用户运维者**：通过轻量诊断页查看模型能力、熔断状态、最近调用和故障转移。
4. **真实 Provider 验证与评测**：在受控的管理/调试路径中指定具体 Provider/模型，以便复现和比较。

### 2.2 产品承诺

一次逻辑调用应做到：

> 调用方声明能力和服务等级 → 系统生成合格且稳定的候选链 → 在总预算内调用、重试或故障转移 → 返回实际 Provider/模型和结果状态 → 诊断页能解释完整决策过程。

“自动切换”只发生在调用方事先接受的候选范围内，不允许为了成功而越过能力、服务等级、数据边界或 Embedding 模型身份。

## 3. 目标与非目标

### 3.1 目标

1. 为 `CHAT`、`STREAM_CHAT`、`EMBEDDING`、`RERANK` 提供独立、稳定的业务能力入口。
2. 调用方默认不指定具体模型，而是声明能力和服务等级；调度器负责选择。
3. 路由结果确定、可解释，相同输入和配置快照产生相同候选顺序。
4. 对符合策略的瞬时故障自动重试或切换，并严格限制在共享总预算内。
5. 流式响应只在下游提交前允许透明切换，提交后中断必须明确终止。
6. 保持 Phase 1 Embedding 的顺序、维度、向量空间和事务边界不变量。
7. 提供只读诊断页，不查看正文也能复盘路由、熔断和故障转移。

### 3.2 非目标

- 完整聊天产品、多轮对话、Prompt 组装、意图识别、知识库检索和工具调用；这些属于 Phase 3。
- 学习型/LLM 驱动路由。Phase 4 形成质量评测数据前，只做确定性规则路由。
- Provider、模型和密钥的运行时 CRUD。
- 多租户、RBAC、计费、配额售卖或成本结算后台。
- Prompt、文档正文、模型输出或工具参数的诊断采样。
- 跨服务等级降级，或在不同 Embedding 模型空间之间自动切换。
- 在 Step B 指定 Resilience4j、Reactor、WebClient 等实现依赖。

## 4. 统一语言

| 术语 | 定义 |
|---|---|
| 能力（Capability） | `CHAT`、`STREAM_CHAT`、`EMBEDDING`、`RERANK` 四种业务能力 |
| 服务等级（Service Tier） | 调用方对成本、延迟和质量取舍的路由意图，不是经过评测的质量 SLA |
| Provider | 实际提供模型 API 的供应商或本地部署 |
| 模型身份 | 能稳定区分模型制品、版本和关键输出配置的内部标识 |
| 候选（Candidate） | 满足能力、等级、配置、数据边界和模型身份约束的 Provider/模型部署 |
| 逻辑调用（Logical Call） | 调用方看到的一次完整调用，可能包含多个上游 attempt |
| Attempt | 一次真实的 Provider 请求；同候选重试和换候选都会产生新 attempt |
| 故障转移（Failover） | 放弃当前候选，改用同一候选链中的下一个目标 |
| 下游提交点（Commit Point） | 第一条业务内容真正交给调用方；此后不能透明换模型 |
| 显式降级 | 系统继续返回可用但质量能力降低的结果，并明确标注，例如 Rerank Noop |

## 5. 服务等级

第一版定义三个等级：

| 等级 | 路由意图 | 典型场景 |
|---|---|---|
| `ECONOMY` | 优先较低成本和较短等待，候选必须仍满足能力要求 | 意图判断、查询改写、低风险辅助任务 |
| `BALANCED` | 成本、延迟和质量折中；默认等级 | 普通知识问答和未指定等级的调用 |
| `QUALITY` | 优先配置中质量定位更高的候选，允许更高成本和延迟 | 最终答案、复杂推理、高价值生成 |

产品规则：

- 等级是配置驱动的候选组，不表示 Phase 4 已经证明某模型一定更好。
- `BALANCED` 是 Chat、流式 Chat 和 Rerank 的默认等级。
- 同一次逻辑调用不得跨等级故障转移。当前等级没有候选时直接返回“无合格模型”。
- Embedding 不依赖服务等级自由选模型；它必须携带知识库已经绑定的精确模型身份。

## 6. 功能需求

### FR-01 能力调用声明

- 普通业务调用方声明能力和服务等级，不直接选择 Provider。
- 管理、调试和评测路径可以增加精确 Provider/模型约束；该能力不作为普通问答请求参数开放。
- 每次调用携带逻辑请求 ID、总截止时间和取消信号。具体字段和默认值由 Step C 决定。
- 最终结果必须返回实际贡献结果的 Provider/模型、是否发生重试/故障转移及最终状态；若一次 Embedding 调用的不同批次由多个等价 deployment 完成，则返回全部贡献者，不能伪造一个调用级单值。

### FR-02 候选生成与确定性路由

候选按以下顺序处理：

1. 读取本次调用开始时的配置快照；
2. 过滤禁用、配置不完整和不支持所需能力的候选；
3. 应用服务等级、数据边界、模型身份和调用方约束；
4. 排除当前熔断状态不允许调用的候选；
5. 按默认候选、显式优先级和稳定 ID 生成确定顺序；
6. 调用前再次原子申请熔断许可。

诊断记录必须保存候选快照、过滤原因和最终顺序。调用过程中配置变化不改变本次已经生成的候选链。

### FR-03 自动重试与故障转移

- 符合策略的瞬时故障默认自动处理，普通调用方不能逐请求关闭。
- 同候选重试和换候选共同消耗逻辑调用的最大 attempt 数与总截止时间。
- 自动切换对调用流程透明，但不能隐藏诊断事实；最终结果仍应标注实际模型和切换情况。

第一版产品策略：

| 结果/错误 | 同候选重试 | 换候选 | 影响熔断 | 对调用方结果 |
|---|---|---|---|---|
| 连接、DNS、TLS、上游 reset | 按剩余预算 | 是 | 是 | 预算耗尽后失败 |
| 5xx | 按剩余预算 | 是 | 是 | 预算耗尽后失败 |
| 429 | 尊重上游等待建议且预算允许时可重试 | 仅切到配额独立候选 | 记录为受限状态 | 预算耗尽后失败 |
| 首个有效业务块超时 | 同候选不反复等待 | 提交前可切换 | 是或记慢调用 | 切换或最终失败 |
| 400、非法参数、模型/维度配置错误 | 否 | 否 | 否 | 直接失败 |
| 401/403 | 否 | 否 | 否 | 直接失败并提示配置问题 |
| 能力不支持或无合格候选 | 否 | 否 | 否 | 直接失败 |
| 调用方取消 | 否 | 否 | 否 | 返回取消状态 |
| 流提交后的中断 | 否 | 否 | 是 | 保留部分内容并明确终止 |

具体 HTTP 状态映射和 Provider 特有错误解析由 Step C 定义，但不得改变本表的产品语义。

### FR-04 流式调用

内部必须区分：

1. 第一个合法上游事件；
2. 第一个有效业务块；
3. 第一次下游提交。

产品行为：

- 下游提交前，上游错误、首个有效业务块超时或无内容完成时，可丢弃探测缓冲并尝试下一候选。
- 第一个有效业务块提交后，系统不得在同一响应中拼接另一模型的输出。
- 提交后上游中断时，保留已输出内容，发送明确的 `STREAM_FAILED` 终止语义，并标记“回答可能不完整”。
- 正常完成、失败和取消是互斥终态，只能发生一次。
- 调用方取消应尽快停止上游请求，不再重试或故障转移，也不计入 Provider 健康失败。
- 传输层事件名称和编码格式留给 Step C；前端产品文案以“生成中断，已显示的内容可能不完整”为准。

### FR-05 Embedding 保护线

- Phase 1 的 `EmbeddingClient` 继续作为知识库稳定端口。
- 知识库创建后绑定精确 Embedding 模型身份；查询、入库、补向量和重建都必须使用该身份。
- 自动切换只允许发生在同一模型制品、版本、预处理和输出维度的等价部署之间。
- 同维度的不同模型不得互为候选。
- 返回向量必须保持输入条数和顺序，校验响应 index、维度和非法数值。
- 外部 Embedding 调用不得进入数据库长事务。

### FR-06 Rerank 显式降级

- Rerank 是召回后的可选质量增强，不能用 Embedding 相似度伪装成同一种能力。
- 当没有可用 Rerank 候选或所有候选失败时，系统可以使用 Noop，保持原候选顺序并截取 top-N。
- Noop 结果必须返回 `rerankApplied=false`（概念字段，具体 API 命名留给 Step C）以及降级原因。
- Noop 不得被记录成真实 Rerank 模型成功，也不得复位真实候选的熔断状态。

### FR-07 Provider 与模型配置

- 第一版使用版本控制中的非敏感配置文件登记 Provider、模型、能力、服务等级、优先级、端点和限制。
- API Key 等秘密仅通过环境变量注入，不写入仓库、数据库、日志或诊断页面。
- 配置变更在应用重启后生效；第一版不承诺运行时热更新。
- 诊断页只读展示已脱敏配置和实际验证过的能力，不提供新增、编辑、删除或密钥操作。

### FR-08 调度诊断

诊断采用两层结构：

```text
logical_call
  ├─ route_decision
  ├─ attempt #1
  ├─ attempt #2 / retry / failover
  └─ final_outcome
```

诊断页必须回答：

- 请求的能力和服务等级是什么；
- 初始候选有哪些，哪些被过滤以及为什么；
- 实际 attempt 顺序是什么；
- 是否重试、故障转移、降级或被熔断；
- 最终由哪个 Provider/模型贡献结果；mixed Embedding 必须列出全部贡献 deployment；
- 首事件、首有效业务块、下游提交和总耗时；
- 最终是成功、失败、取消还是部分流中断。

记录保留规则：

- 持久化最近 7 天或最多 10,000 次逻辑调用，先达到者触发清理；
- 记录跨应用重启保留；
- 清理是后台维护行为，不要求用户手动操作；
- 诊断写入失败不得让原本成功的模型调用失败，但必须留下可观测告警。

访问规则：

- 沿用 xrag 当前单用户应用边界，不新增独立登录或 RBAC；
- 任何能够访问当前 xrag 应用的人都能查看诊断页；
- 页面只读。

内容安全规则：

- 可以保存能力、等级、候选、过滤原因、Provider/模型、attempt、状态、耗时、计数、错误类型、HTTP 状态和脱敏请求 ID；
- 不保存 Prompt、系统指令、文档正文、模型输出、工具参数、API Key、Authorization 或原始 Provider 错误体；
- Provider 请求 ID 默认在列表中缩略展示，详情中也只能展示脱敏值。

### FR-09 熔断状态展示

诊断页展示每个 Provider/模型/能力故障域的：

- 当前主状态：`CLOSED`、`OPEN`、`HALF_OPEN`；
- 最近一次状态变化时间和原因；
- 当前是否允许调用；
- 近期成功、失败、限流和慢调用摘要；
- 半开探测是否占用。

`DISABLED`、`FORCED_OPEN` 等运维状态是否进入第一版由 Step C 根据熔断方案决定；页面不得把“未配置/禁用”和“故障打开”混为一谈。

## 7. 诊断页信息架构

现有 `/diagnostics` 入口继续保留，并从单一健康探测扩展为模型调度诊断入口。

第一版包含：

1. **调度总览**：应用健康摘要、Provider/模型能力和熔断状态。
2. **最近调用**：按时间倒序查看逻辑调用，支持能力、结果、等级和 Provider 筛选。
3. **调用详情**：展示候选过滤、attempt 时间线、提交点、最终结果和脱敏标识。

详情使用同页分栏或抽屉，不要求增加稳定的详情 URL；是否需要可分享深链由界面评审决定。

## 8. 非功能需求

### 8.1 可解释性

- 路由决策必须可确定复现；动态配置版本或策略版本需要随调用记录。
- 错误文案应区分“请求有问题”“Provider 当前不可用”“所有候选耗尽”和“流已中断”。
- 最终成功不能覆盖中间失败；attempt 历史始终可查看。

### 8.2 隐私与安全

- 诊断内容默认最小化，正文采样不是隐藏开关，而是明确不在第一版。
- 页面和日志均不得显示秘密配置。
- 原始错误体只能在调用期间用于解析，持久化前转换成稳定错误类型和脱敏摘要。

### 8.3 性能与可用性

- 诊断记录不能显著增加首包和总耗时。
- 诊断存储不可用时，主调用继续按原策略完成。
- 最近调用列表必须分页，不能一次加载全部 10,000 条。
- 慢下游不能导致无限流式缓冲。

### 8.4 可测试性

- CI 使用可编程假 Provider，能够模拟 200、400、401、429、5xx、超时、断流和取消。
- 真实 Provider 测试由显式环境变量守门，不作为普通 CI 前置条件。
- 系统时间、熔断状态和路由配置应可替换，以便确定性验证。

## 9. 验收标准

| ID | 场景 | 验收结果 |
|---|---|---|
| AC-01 | `BALANCED` Chat 首选模型成功 | 返回首选实际模型，只有一个 attempt |
| AC-02 | 候选不支持所需能力 | 调用前被过滤，诊断展示过滤原因 |
| AC-03 | 首选同步调用返回 5xx | 在总预算内切换同等级候选并成功，结果标记发生过 failover |
| AC-04 | 首选返回 400/401 | 直接失败，不尝试下一候选，不计入熔断 |
| AC-05 | 429 且存在独立配额候选 | 按剩余预算决定等待或切换，并记录决定原因 |
| AC-06 | 熔断从 CLOSED 打开 | 后续调用不进入该候选；页面展示 OPEN 和变化原因 |
| AC-07 | 半开并发竞争 | 只允许配置数量的真实探测，其余调用选择其他候选或失败 |
| AC-08 | 流首个有效业务块前失败 | 缓冲不下发，透明切换候选，最终只出现一个模型的内容 |
| AC-09 | 流提交后中断 | 保留部分内容，发送 STREAM_FAILED，不切换模型 |
| AC-10 | 用户取消流 | 上游最终停止，不重试、不切换、不计入熔断 |
| AC-11 | Embedding 主端点失败 | 只可切换同一模型身份的等价部署，不得使用同维其他模型 |
| AC-12 | Rerank 不可用 | 返回原顺序 top-N，明确 `rerankApplied=false` |
| AC-13 | 所有候选耗尽 | 返回稳定的最终失败类别，诊断保留全部 attempts |
| AC-14 | 诊断页查看调用详情 | 能解释候选、过滤、attempt、提交点和最终结果 |
| AC-15 | 检查诊断持久化内容 | 不含 Prompt、正文、输出、工具参数、密钥或原始错误体 |
| AC-16 | 超过 7 天或 10,000 次调用 | 旧记录自动清理，页面无需人工维护 |
| AC-17 | 诊断存储失败 | 模型调用结果不受影响，同时产生可观测告警 |
