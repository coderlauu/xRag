# 《用户问退货政策，3C、家电和服装都举手了》

> 原文链接：https://t.zsxq.com/Q19YN
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

封顶算法只看分数与子问题归属，管不了"三个品类的退货政策分数都在 0.6 附近"这种场景；歧义引导的做法是**按 CATEGORY 分组取各品类最强代表 → 用分数比值做三区间判定（明确歧义 / 灰色地带调 LLM / 明确无歧义）→ 命中则生成引导文案，复用 SSE 通道短路输出**，跳过检索与生成。

## 核心内容提炼

- **歧义的判据是三个条件同时成立**：分数接近 **且** 跨品类 **且** 用户没指定品类。三个反例分别打掉一个条件：0.88 vs 0.35（差距大）、"3C 数码的退货政策"（已明示）、同品类下的线上/线下退货政策（不跨品类，检索走同一个库结果本就相关）。

- **只在单子问题场景做歧义判断**（`subIntents.size() != 1` 直接返回 null）。复合问题已被拆开，子问题 A 命中退货、B 命中物流**不是歧义，是用户确实问了两件事**，跨子问题比分数没有业务意义。

- **候选只保留 KB 类且分数 ≥ 0.35**。MCP 是外部接口调用不存在跨品类概念，SYSTEM 是打招呼，**歧义引导是知识库场景专属的事**。

- **按品类分组而不是按节点名称分组**，这是一次方案迭代。按名称分组的刚性限制是：管理员 A 写"退货政策"、管理员 B 写"退换货规则"，语义相同名字不同就检测不出歧义。换成"先按 CATEGORY 分组，每组取最高分 topic 当代表，再比代表之间的分数"，**不再要求名称相同——反正最终让用户选的是品类，不是具体 topic**。

- **`resolveSystemNodeId` 沿 `parentId` 向上回溯，在 CATEGORY 级停下**。三级各自的粒度决定了这个选择：DOMAIN 太粗（所有品类都在"商品服务"下），TOPIC 太细（就是触发歧义的节点本身），CATEGORY 刚好是品类维度。回溯走的是内存注册表（`intentNodeRegistry`），不涉及数据库 IO。

- **用分数比值而不是差值**，因为高低分段的含义不同：0.88 vs 0.78 差 0.1 但前者明显更好；0.45 vs 0.35 同样差 0.1 却是"两个都不太行"。比值天然带上了量级信息。

- **三区间判定（默认 `threshold=0.8`、`margin=0.15`）**：
  | 区间 | 比值 | 判定 |
  |---|---|---|
  | 明确歧义 | `>= 0.8` | 直接触发引导，零延迟 |
  | 灰色地带 | `[0.65, 0.8)` | 调一次 LLM 二次确认 |
  | 明确无歧义 | `< 0.65` | 不触发（`shouldSkipGuidance` 已拦） |

  灰色地带是为了解决纯规则方案的两难——阈值定 0.8 则 0.79 的真歧义漏掉，定 0.7 则 0.72 的假歧义误触发。`margin` 设为 0 就退化成纯规则。

- **`shouldSkipGuidance` 的第二条快速通道匹配的是 DOMAIN 级名称（系统级），不是 CATEGORY 级（品类级）**。面向的是"企业同时接入 OA / 保险 / 电商多个系统"的架构。**单域名多品类的电商场景下这条通道基本不会命中**——品类级的语义消歧（"手机"属于 3C 数码）交给 LLM 确认环节。

- **`normalizeName` 用 `Locale.ROOT` 而不是 `Locale.getDefault()`**，理由具体：土耳其 Locale 下 `"I".toLowerCase()` 得到的是无点的 `ı` 而非 `i`，会导致匹配不上。归一化三步：trim → 小写 → 去掉所有 Unicode 标点与空白。

- **LLM 确认器的 Prompt 精确覆盖了规则方案的两处盲区**：领域线索识别（"我买了个手机想退货" → 手机属于 3C，判不歧义）与同义词识别（"退货政策" vs "退换货规则" → 判歧义）。参数同样是 `Temperature=0.1 + TopP=0.3 + thinking=false`。

- **LLM 失败时降级为"触发引导"（返回 `true`）**。取舍很明确：**引导的代价是多一轮交互，不引导的代价可能是答非所问**——宁可多问不可答错。

- **`GuidanceDecision` 是二态结构（`NONE` / `PROMPT`）+ 私有构造 + 两个工厂方法**，下游只调 `isPrompt()`，决策与执行解耦。

- **短路复用 SSE 通道，前端零适配**：引导文案走和普通回复完全一样的 `onContent` + `onComplete`，事件流也一样（`meta` → `message` → `finish` → `done`），**没有专门的 guidance 事件类型**。前端只管接 `message` 拼文本。唯一差别是速度——预拼好的字符串一次推完，几乎瞬时。

- **短路省掉的是真正贵的部分**：向量检索的数据库 IO、Reranker 的 Cross-Encoder 推理、LLM 的 token 生成。歧义检测本身多数是纯内存计算，只有灰色地带才多 200~500ms 的轻量 LLM 调用。

- **用户选择后的闭环靠两道防线避免重复引导**：会话记忆把引导文案与用户回复"1"载入历史 → 查询改写把"1"改写成"3C 数码的退货政策" → 改写后分数拉开（通道一拦截）或字符串命中品类名（通道二拦截）。**歧义引导只负责问，记忆与改写负责把选择拼回上下文。**

## 关键概念/术语

- **歧义引导（引导式问答）**：系统对无法确定品类归属的问题反问用户，而不是猜或全查。
- **`AmbiguityGroup`**：`(topicName, ranked)`，触发歧义的主题名 + 按分数降序的品类代表列表。
- **品类代表**：同一 CATEGORY 下分数最高的那个 topic 叶子。
- **分数比值（`ratio`）**：次高分 / 最高分，歧义判定的唯一数值依据。
- **灰色地带**：`[threshold - margin, threshold)` 的比值区间，规则判不了、交给 LLM。
- **`GuidanceDecision`**：`NONE` / `PROMPT` 二态决策对象。
- **Pipeline 短路**：在检索之前结束本轮请求，直接向 SSE 推送内容并关闭。

## 与 xrag 项目的关系

- **这一篇直接决定 Step B 问答页 `ui-spec.md` 与原型里最难评审的那一块。** "复用 SSE 通道、前端零适配"是原文的选择，但它把选项渲染成了**纯文本编号列表，要求用户手打"1"或"1,2"或"全部"**。xrag 的问答页要不要做成**可点击的选项按钮**，是一个真实的产品决策：
  - 纯文本零适配：后端改动小，但用户要打字，且"1,2"这种输入还要靠下一轮的查询改写正确解析——**链路长且脆**。
  - 结构化事件 + 可点击选项：前端要认一种新的 SSE 事件类型，但用户一点即选，下一轮送回后端的是明确的意图 ID 而不是"1"，**改写环节可以完全绕开**。

  按 [CLAUDE.md 的产出物闸门](../../../CLAUDE.md)，**这正是"看一眼页面秒判、读 400 行文档评审成本极高"的典型**——要在原型里把两种形态都做出来给所有者选，不要在文档里替他决定。

- **`maxOptions = 6` 在原文的链路里是一个永远走不到的配置。** 推演：`detectAmbiguity` 收到的是 `capTotalIntents` **之后**的 `subIntents`，单子问题场景下 `classifyIntents` 已 `limit(3)`、封顶又限制总数 ≤ 3，所以 `ranked.size()` 最多是 3，**永远不会超过 6，`trimRankedOptions` 永远原样返回**。这正好撞上 xrag 已经记过的一条纪律——[Phase 2 复盘](../../../docs/retro/2026-08-07-phase-2-model-scheduling-retrospective.md) §5.2 的"不预留永远走不到的分支"。xrag 若做歧义引导，要么把候选来源改成封顶**之前**的完整列表（那样 6 才有意义），要么就别配这个参数。**两者不能都要。**

- **引导文案的措辞有事实错误，xrag 不能照抄。** 模板写的是"关于{topic_name}，在**知识库中检索到了**以下内容"，但 `handleGuidance` 在 `retrieve` **之前**执行——**系统根本没有检索过**，列出的是意图节点而不是检索结果。用户读到"检索到了"会以为系统已经搜过并找到了内容，而实际上一条 chunk 都没取。这类"界面状态与实际行为不一致"正是知识库模块反复踩过的坑（`SKIPPED` 的措辞会不会被误读成失败）。xrag 的文案应当如实说"这个问题可能涉及以下几个方向"。

- **`rag.guidance.*` 的配置形态可以直接借鉴，但开关语义要对齐 xrag 约定。** `enabled` 总开关这一点与 xrag 的跨模块纪律③（调度类组件都带 `enabled` 开关）同源。不同的是 xrag 的 `enabled` 是为了 [ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 的单实例假设服务的，而这里的 `enabled` 是功能开关。**同名不同义的配置项混在一份 `application.yml` 里会误导人**，命名上要能区分。

- **`resolveSystemNodeId` 停在 CATEGORY 的写法与第 5 篇的"深度不固定"存在张力，xrag 要显式处理。** 第 5 篇明确说过 `isLeaf()` 只看 `children` 是否为空、不看 `level`，"商品信息"在 CATEGORY 层就是叶子。这种叶子进到 `resolveSystemNodeId` 时，`current.getLevel() == CATEGORY && parent.getLevel() == DOMAIN` 立即成立，**返回的是它自己的 ID**——它自成一个品类组。行为上说得通，但意味着**两层分支的叶子与三层分支的叶子在歧义判定里的语义不同**（前者"品类 = 自己"，后者"品类 = 父节点"）。xrag 的意图树规格里要把这条写清楚，否则实现者会各写各的。

- **LLM 失败降级为"触发引导"这个方向，与 xrag 现有的降级哲学一致但要注意一处差别。** `com.app.ai` 的熔断降级是"换一个候选或抛错"，而这里是"降级到一个更保守的用户可见行为"。后者更接近产品决策而非技术决策。**xrag 的问答链路里每一处 LLM 调用失败时的降级方向都应当在 PRD 里列表说明**（改写失败 → 用归一化问题；意图分类失败 → 空意图走全局搜索；歧义确认失败 → 触发引导），而不是散在代码里各自决定。

- **引导短路仍然要写链路记录。** 这一轮虽然没有检索、没有生成，但它是一次完整的用户提问，[CONTEXT.md](../../../CONTEXT.md) 里的「链路记录」应当能查到"这次提问在歧义检测处短路了、候选是哪几个"。**否则线上出现"引导太频繁"的投诉时无从统计**——而调 `threshold` / `margin` 这两个参数恰恰只能靠这类统计。

## 值得注意的设计取舍/坑

- **"宁可多问不可答错"这条原则在这里被用了两次**（LLM 失败降级、灰色地带偏保守），但它有隐藏成本：**每多问一次就多一轮完整的 pipeline**（会话记忆 + 改写 + 意图分类都要重跑）。第二轮的成本并不比第一轮低，只是省掉了一次可能错误的检索与生成。如果引导触发率偏高，总成本反而上升。**这条原则值得保留，但必须配上引导触发率的监控**，否则没人知道它是不是过头了。

- **多选（"1,2"）与"全部"这两个选项把复杂度推给了下一轮的查询改写。** 用户回"1,2"时，改写要基于上一轮的引导文案把它还原成两个子问题，然后再走一遍拆分与意图分类。这条路径**依赖会话记忆完整保留了上一轮的选项列表**——如果记忆压缩（第 3 篇）恰好把那条引导消息摘要掉了，"1,2"就彻底失去了指代对象。**摘要压缩的水位线策略与引导消息的保留策略之间存在耦合，原文没有提。**

- **两道防线（分数拉开 / 字符串命中）都不是硬保证。** 用户回"1"，改写成"3C 数码的退货政策"之后，三个品类的退货政策**理论上仍可能给出接近的分数**（毕竟节点描述里都写着"退货"）。此时靠的是通道二的字符串匹配——而通道二匹配的是 **DOMAIN 名称**，电商单域名场景下压根不命中。**也就是说：电商场景下"避免重复引导"实际上只剩分数这一道防线。** 原文说"两道防线确保不再引导"是过于乐观的表述。xrag 若做这个功能，应当加一条硬防线：**同一会话中对同一主题已引导过一次，则不再引导**。

- **`Collectors.toMap` 的合并函数用了 `>=` 而不是 `>`**（`(a, b) -> a.getScore() >= b.getScore() ? a : b`）。同分时保留先出现的那个——而"先出现"取决于上游 `candidates` 的顺序，这个顺序来自封顶算法的排序结果。**同分场景下品类代表是谁，是由一条隐式的、跨了三个方法的顺序约定决定的**，改动上游排序就会静默改变这里的行为。

- **灰色地带的 LLM 调用没有走前面第 6 篇那套五层容错**，只有一个 `try-catch` + `getAsBoolean()`。如果 LLM 返回的 JSON 里 `ambiguous` 字段缺失，`obj.get("ambiguous")` 返回 null，`.getAsBoolean()` 抛 NPE，被 catch 兜住降级为 `true`——**结果是对的，但走的是异常路径，日志里看起来像是"LLM 调用失败"，实际是"LLM 返回了不合规格的 JSON"**。这两件事的排查方向完全不同。同一个仓库里两处解析 LLM JSON 用了两种严谨程度，**说明容错逻辑没有收敛成一个共用组件**——这正是第 6 篇笔记里提到的、xrag 应当避免的问题。

- **比值法在最高分很低时会失真。** 0.36 / 0.38 ≈ 0.95，落在"明确歧义"区间，系统会郑重其事地请用户在两个都只有 0.36 分的方向里选一个。实际上这时更合适的动作是**兜底全局搜索或直接澄清"没太理解你的问题"**。原文的 `shouldSkipGuidance` 只检查了 `top <= 0`，没有检查 `top` 是否低到不值得引导。xrag 应当补一条最低分下限。
