# 《AI大模型Ragent项目》——工具调用稳定性与安全保障

> 原文链接：https://t.zsxq.com/FG5YI
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

生产级工具调用需要四层保障：调用层做校验与超时，容错层做有边界的重试、降级与熔断，安全层做授权、防注入、脱敏和审计，可观测层用日志、指标、追踪、告警与测试把故障变成可发现、可定位、可恢复的事件。

## 核心内容提炼

### 1. 稳定性从错误分类开始

所有工具都应有截止时间，避免第三方服务或内部任务无限占用线程和连接。文章按查询、写操作、复杂计算给出不同超时量级，但真正参数应由业务 SLO 和历史延迟分位数决定。

重试只适合瞬时且可能恢复的故障，例如连接错误、超时、503 和部分 429；参数错误、权限拒绝、资源不存在和确定性业务失败不应重试。重试需要次数上限与指数退避，最好加入随机抖动，避免大量请求同时再次压垮下游。

### 2. 降级与熔断解决不同问题

- 降级回答“依赖不可用时还能给用户什么”：可返回诚实的兜底说明、在明确标注时效的前提下使用缓存，或引导到受支持的替代渠道。
- 熔断回答“持续失败时是否还继续请求依赖”：关闭态正常调用，打开态快速失败，半开态用少量探测判断恢复，避免故障依赖拖垮调用方。

降级结果不能伪装成实时成功数据；缓存必须说明时间和来源，写操作失败也不能轻率改走可能产生另一份副作用的渠道。

### 3. 安全边界必须在执行端

- 权限判断以认证后的用户、角色、租户和资源关系为依据，在工具执行前完成，不能依赖模型判断“用户应该能访问”。
- 所有模型参数都视为不可信输入。数据库使用参数化查询；文件访问要规范化路径并限制在允许根目录；输出到 Web 页面时按实际渲染上下文进行编码。
- 工具返回、模型上下文、应用日志和追踪属性都要遵守同一套最小披露与脱敏原则。
- 高风险工具需要审计“谁、何时、通过哪个会话调用了什么能力、结果类别、耗时与追踪标识”，但参数和结果中的敏感值仍需脱敏或摘要化。

### 4. 可观测性覆盖完整工具回路

文章提出四个基础指标：

- 调用量：总量及按工具维度的流量变化。
- 成功率：按工具和错误码分解，避免总平均掩盖单工具故障。
- 延迟：重点看 P50/P95/P99，而不是只有平均值。
- 错误分布：区分超时、参数、授权、限流、依赖和系统故障。

链路追踪应覆盖“用户请求 → 第一轮模型 → 工具选择与执行 → 下游依赖 → 第二轮模型 → 响应”，使团队能区分模型慢、工具慢还是依赖慢。日志、指标和 Trace 应共享稳定的工具名、错误分类和相关标识。

### 5. 测试对象不只是工具函数

测试至少分三层：

1. 单元测试验证参数边界、权限、业务逻辑、异常映射与安全输入。
2. 集成/评测验证模型是否选对工具、参数是否正确、工具失败后是否生成合适回复，以及模糊和多工具场景是否会澄清。
3. 压力与故障测试验证真实并发下的吞吐、尾延迟、错误率、连接池、熔断恢复和降级容量。

工具描述优化后的效果应使用固定问法集、线上灰度或 A/B 实验验证，不能凭感觉认定“描述更长就更好”。

## 关键概念/术语

- 截止时间（Deadline）：一次工具调用允许消耗的总时间预算，比单个客户端 socket timeout 更接近业务语义。
- 指数退避：每次重试前增加等待间隔的策略，通常还应增加随机抖动。
- 降级：依赖失败时返回受限结果、缓存或替代路径的策略。
- 熔断器：根据近期失败情况在关闭、打开、半开状态间转换，保护调用方和故障依赖。
- 最小权限：工具只获得完成当前动作所需的最小身份、数据和操作范围。
- 审计日志：面向追责与安全调查记录主体、动作、对象和结果的不可随意更改记录。
- 黄金指标：调用量、成功率、延迟分位数和错误分布等最小可用运行信号。
- 分布式追踪：用 Trace/Span 关联一次请求跨模型、工具和依赖服务的执行链路。

## 与 xrag 项目的关系

当前 xrag 没有工具执行模块，现阶段应沉淀约束而不是提前引入 Resilience4j、OpenTelemetry 或一套抽象框架。

- 未来工具执行入口应统一承接身份上下文、超时预算、错误映射、审计字段和观测标签，避免每个工具各写一套且口径漂移。
- 知识检索工具会接触用户问题、文档片段和元数据；日志及 Trace 不能默认记录完整 Prompt、检索文本和工具结果。
- 流式问答中的客户端取消需要传播到工具和模型调用；否则浏览器已断开，后端重试、降级或下游调用仍可能继续消耗资源。
- 只有在真实工具、依赖 SLO 和故障数据出现后，才应确定超时、重试次数、熔断阈值和告警线。

## 值得注意的设计取舍/坑

- **文章中的数值是示例，不是 xrag 默认值**：5～30 秒超时、3 次重试、50% 熔断率、95% 成功率等必须经本项目负载与体验目标校准。
- **`CompletableFuture.get(timeout)` 不一定取消底层工作**：调用方超时返回后，任务或 HTTP 请求可能仍在运行；实现必须有可传播的取消能力。
- **429 重试必须尊重服务端信号**：优先使用 `Retry-After`，并纳入整体截止时间；盲目指数重试可能进一步恶化限流。
- **缓存降级有一致性风险**：余额、权限、库存等数据可能不允许旧读，能否使用缓存取决于业务语义。
- **安全编码必须匹配输出上下文**：在服务层预先做 HTML 转义可能造成双重转义，也不能防 SQL 或 Prompt 注入；应在数据进入具体危险解释器时使用对应防护。
- **可观测标签要控制基数**：用户 ID、原始错误消息和查询内容不宜作为指标标签，否则会造成指标系统高基数和隐私泄露。
- **工具链存在 Prompt 注入边界**：外部工具返回内容也属于不可信数据，不能因为来自“已授权工具”就让其中指令覆盖系统策略。
