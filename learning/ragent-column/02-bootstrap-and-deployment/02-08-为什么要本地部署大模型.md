# 《AI大模型Ragent项目》——为什么要本地部署大模型？

> 原文链接：https://t.zsxq.com/8VPnK
> 所属分组：02-bootstrap-and-deployment 本地开发与模型部署环境

## 一句话概括

本地模型不是默认的“高级方案”，而是在数据不能出域、稳定高负载可能摊薄固定成本、业务必须离线、需要掌控模型权重或供应商风险不可接受时才成立的部署选择；多数早期 RAG 项目先用云 API 更务实，成熟后再用数据决定云、本地或混合架构。

## 核心内容提炼

### 1. 云 API 是默认起点

云 API 提供开箱即用、按量付费、模型持续升级、弹性容量和免 GPU 运维等优势。对个人项目、验证阶段、初创团队和低频 RAG，固定投入低、试错速度快。

因此部署决策应从“云 API 能否满足业务”开始，而不是从购买硬件或安装 Ollama 开始。

### 2. 五类需求会推动本地化

1. **数据合规和合同边界**：医疗、金融、政务、企业机密等数据可能被要求不能离开受控网络。脱敏不一定消除所有可识别性和合同限制。
2. **成本结构**：云成本随 Token 量近似线性增长；自建以硬件、机房、电力和运维固定成本为主。只有流量足够稳定且利用率高时，本地边际成本优势才可能出现。
3. **稳定与控制**：本地化减少供应商限流、模型下线、价格调整、区域网络和上游故障的外部依赖，但把风险转移为自己的容量与运维责任。
4. **离线和边缘**：隔离产线、车载、涉密或弱网环境无法依赖持续公网连接。
5. **深度定制**：训练、LoRA/蒸馏、解码约束和硬件级优化需要模型权重及推理引擎控制权。

### 3. 混合架构常比二选一现实

可按数据敏感度、问题复杂度或流量形态路由：

- 敏感请求走本地，公开问题走云端强模型。
- 基线流量本地消化，峰值溢出到云端。
- 简单任务走小模型，复杂推理走能力更强的模型。

混合架构同时引入模型能力差异、数据分类、路由、回退和答案一致性问题，需要统一评测和观测，不能只把两个 Base URL 拼在一起。

### 4. 模型、权重格式和推理服务是不同层次

本地部署链路包括：

- 模型发布方与许可证。
- 权重托管平台。
- 权重/量化格式，如 safetensors、GGUF、GPTQ、AWQ。
- 推理引擎或服务层，如 llama.cpp、vLLM、SGLang，以及封装易用性的 Ollama、LM Studio、Xinference 等。

Ollama 偏向本地开发和低并发体验；vLLM 偏向 GPU 高并发服务。它们不能仅按流行度互换，选型取决于硬件、并发、延迟、格式和运维能力。

### 5. OpenAI 兼容降低接入成本，但不是完全等价

云平台和本地推理服务广泛提供 OpenAI 风格接口，Chat 请求、SSE 和消息结构可以复用；切换时至少仍要配置 Base URL、模型 ID、凭据、超时与能力。

兼容接口不保证：

- Function Call/结构化输出精度相同。
- 上下文长度与超限行为相同。
- Chat、Embedding、Rerank 的具体字段完全一致。
- 首 Token 延迟、吞吐、并发和错误语义相同。

每个目标组合都要重新跑功能和性能评测。

### 6. 本地部署的成本远不止显存

模型权重、KV Cache、上下文和并发共同决定内存/显存需求；MoE 即使每次只激活部分参数，也通常需要加载完整权重。

长期成本还包括模型版本管理、驱动/CUDA/框架兼容、监控、容量、温度与硬件故障、升级回滚、效果回归和专业运维人力。本地只减少数据出网风险，不自动解决访问控制、审计和内部泄露。

## 关键概念/术语

- 数据主权：数据在何处存储、处理并受谁控制的约束。
- 成本拐点：云端按量成本与自建固定/运维成本在特定负载下相交的位置。
- 混合模型架构：按数据、能力或流量在本地与云模型之间路由的部署方式。
- 开源权重：可按许可证下载并由自有推理引擎加载的模型参数。
- 量化：用较低数值精度表示权重以降低内存和计算成本，可能牺牲质量。
- 推理引擎：负责权重加载、调度、批处理和 Token 生成的底层运行系统。
- TTFT：Time To First Token，从请求到第一个生成 Token 的延迟。
- TPS：Tokens Per Second，生成阶段的 Token 速率。
- KV Cache：Transformer 推理中缓存注意力键和值的运行时内存，随上下文和并发增长。

## 与 xrag 项目的关系

xrag 当前尚未接入任何云或本地模型，现有 Compose 也不包含 Ollama/vLLM/GPU 服务。本篇不构成“Phase 1 必须本地部署”的决策。

- 首期应优先定义与 Provider 无关的最小 Chat/Embedding 边界和评测样本，再用实际数据选择运行方式。
- 当前没有明确合规、离线、稳定高负载或微调需求，直接增加本地模型会扩大环境和运维范围。
- 若为了开发验证使用 Ollama，应把它视作可选开发依赖，并保证无 Ollama 时文档/CI 基线仍清晰。
- 云/本地切换至少要验证模型能力、Embedding 维度、结构化输出、流式语义和性能，而非只验证 HTTP 200。

## 值得注意的设计取舍/坑

- **合规结论必须由具体法律、合同和数据分类确认**：课程场景说明风险，但不能代替 xrag 实际业务的合规评估。
- **成本模型要包含利用率和人力**：只比较 Token 单价与 GPU 价格会漏掉峰谷、冗余环境、机房和维护。
- **OpenAI 兼容不是强语义标准**：Provider 会在 usage、错误、工具调用、Embedding/Rerank 和流式终止上存在差异。
- **本地模型版本也会漂移**：标签更新、量化版本和推理引擎升级都可能改变回答，必须固定可追溯的模型 digest/版本。
- **混合路由可能违反数据边界**：在本地失败后自动回退云端前，必须再次检查请求内容是否允许出域。
- **文章中的型号、价格和“事实标准”具有时效性**：应把它们视作 2026-04 的参考快照，不写成 xrag 长期架构依据。
- **Embedding 切换比 Chat 切换更昂贵**：改变 Embedding 模型通常需要重建向量索引，不是简单改 Base URL。
