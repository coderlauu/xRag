# 《AI大模型Ragent项目》——RAG知识库管理宏观设计

> 原文链接：https://t.zsxq.com/tqP4O
> 所属分组：03-knowledge-base AI知识库建设

## 一句话概括

这是"从理论到实战"系列的开篇，讲的是把分块/向量化/检索这些单点技术组合成一个真正能落地的企业级知识库系统时会遇到的工程问题（格式多样、异步处理、失败重试、文档更新、多知识库隔离、成本控制），并给出三层架构 + 三个核心概念（知识库/文档/分块）+ 三张核心表的整体骨架设计。

## 核心内容提炼

- **理论到实战的鸿沟**：前面理论篇讲的分块、元数据、向量化、向量库、检索策略、生成策略都是"单点技术"，只回答"某个环节怎么做"；真要做一个完整系统（作者举例：电商智能客服），会撞上理论篇没讲过的工程问题——文档格式五花八门（含扫描版PDF）怎么统一处理、处理耗时长（几分钟级）怎么异步、失败了怎么重试、文档更新后旧chunk怎么处理、多个品类/多个知识库怎么隔离、Embedding API 调用成本怎么控制。

- **三层架构**：
  - **用户层**（前端交互）：创建知识库（起名+选 Embedding 模型）、上传文档（本地上传/URL抓取）、查看文档处理状态、触发分块、查看分块结果。设计原则是让用户不需要懂 RAG 原理。
  - **业务层**（核心逻辑，五大模块）：知识库管理、文档管理、分块管理（含去重）、文档解析（Apache Tika 统一多格式解析，扫描版PDF需OCR）、向量化（批量调用 Embedding API）。每个模块职责单一——文档管理只管接收上传和发任务，不关心怎么解析；解析模块只管解析，不关心怎么分块。
  - **存储层**（四组件）：PostgreSQL 存元数据（结构化、支持事务）；pgvector 存向量（选它而不是 Milvus 的理由：同库带来事务一致性更好、运维更简单、成本更低，HNSW 索引在百万级向量下性能够用，Milvus 部署复杂度和本地内存占用更高）；对象存储存原始文件（用 RustFS，但只依赖 S3 协议，理论上可无缝换其他 S3 兼容存储）；消息队列做异步任务（项目为了学习门槛默认用 Redis Stream，后续会出 RocketMQ 教程，包括如何用 RocketMQ 事务消息平衡数据库与三方组件间的事务性）。

- **三个核心概念（一对多关系：知识库→文档→分块）**：
  - **知识库**：文档的容器，类似文件夹。存在的必要性：品类隔离（问手机问题不该检索到服装文档）、模型隔离（不同知识库可以用不同 Embedding 模型）、配置独立（可以有不同分块策略/检索参数）。核心属性包括：唯一标识（雪花算法生成的分布式ID）、名称、`embedding_model`（绑定后不建议修改，否则已有向量全部失效——因为不同模型生成向量维度不同不能混用）、`collection_name`（向量库里隔离不同知识库数据的唯一标识，对应 pgvector 里的逻辑分割）。
  - **文档**：知识库的基本单元，一个上传文件对应一个文档，有生命周期（上传→处理中→成功/失败）。关键设计点：`processMode` 区分两种处理路径——`chunk`模式（按配置的分块策略直接处理，最常用）vs `pipeline`模式（关联预定义 Pipeline，由多个可单独配置的节点组成：获取→解析→清洗→分块→增强→索引，适合需要特殊清洗/chunk增强等复杂场景）；`chunkStrategy`/`chunkConfig` 允许**文档级别**定制分块参数（同一知识库里长文档和短FAQ需要不同的chunk大小，不能全局统一一套）；`scheduleEnabled`/`scheduleCron` 支持定时刷新（典型场景：URL导入的在线文档会持续更新，运营容易忘记手动重新上传导致答案过期）；状态流转只用了四态 `pending→running→success/failed`（比之前提示词设计里六态的 `pending→parsing→chunking→indexing→success/failed` 更简化，理由是解析/分块/向量化/入库在同一个异步任务里顺序执行，中间状态切换对用户没有意义，用户只关心整体成功或失败，失败详情走独立的分块日志表定位）。
  - **分块**：检索的基本单元。关键设计是**向量和元数据不放在 chunk 业务表里，单独存到向量数据库**——原因是职责分离（chunk表管业务数据，向量库管向量和相似度检索）、灵活性（向量库可独立换型，chunk表不用动）、性能（向量字段体积大，混进chunk表会拖累常规分页查询性能）。

- **三张核心表的设计要点**（字段设计只做提炼，具体 DDL 见原文）：
  - 知识库表：主键用雪花算法 ID；`collection_name` 加唯一约束保证向量库隔离；`embedding_model` 建议创建后不改；用软删除（`deleted` 标记）而非物理删除，因为删知识库是高危操作要留痕。
  - 文档表：`chunk_count` 是冗余字段（避免每次查列表都去 chunk 表 COUNT）；`chunk_config` 用 JSONB 存分块参数保持灵活；`enabled`（是否临时禁用）和 `deleted`（软删除）是两个独立维度；`kb_id` 建索引（按知识库查文档列表是高频查询）。
  - 分块表：`content` 用 TEXT 不限长度；`content_hash` 用于去重；`kb_id` 是从文档冗余下来的字段（避免按知识库查 chunk 时要 JOIN 文档表）；`doc_id` 建索引。

- **文档上传与处理的完整流程**（拆成"上传"和"触发分块"两个独立接口，而不是一个接口做完）：
  1. **上传接口**：校验知识库存在 → 保存文件到对象存储（本地上传直接存，URL抓取先下载再存）→ 插入文档记录（`status=pending`）→ 返回文档ID。只做存储和元数据记录，不触发分块处理，让用户有机会先确认文件信息无误再触发处理。
  2. **触发分块接口**：用 **CAS（Compare-And-Swap）** 把状态从非 running 原子性改成 running（已经是 running 就直接拒绝，防止手抖点两次或前端重复请求导致重复处理）→ 如果配置了定时刷新则创建/更新定时任务 → 发消息到队列 → 立即返回（不等处理完成）。
  3. **异步处理器**依次执行：解析（Apache Tika 统一多格式解析，扫描版PDF需OCR，失败则 `status=failed`）→ 分块（按文档级 `chunkStrategy`/`chunkConfig`，缺省则用知识库默认配置，通常是递归分块 chunkSize=500/overlap=50）→ 向量化（按知识库配置的 Embedding 模型调用对应API，批量处理每次10~20个chunk以降低请求数和延迟，成本高可换本地 Embedding 但需要 GPU）→ 入库（批量INSERT而非逐条插入、用事务保证要么全成功要么全回滚，完成后更新文档的 `status=success` 和 `chunk_count`）。
  4. **拆两个接口的原因**：上传和分块是不同粒度的操作——上传很快（存文件+记元数据），分块耗时（解析+向量化都是慢操作，必须异步）；用户可能想先看看文档信息再决定要不要处理；文档更新时也可以只重新触发分块而不用重新上传文件。

- **异常处理与重试**：区分"不可恢复"（文件损坏、Tika不支持的格式如加密PDF/特殊CAD——只能提示用户重新上传或转换格式）和"可重试"（Embedding API超时/限流/服务不可用）两类失败。重试策略：最多3次、指数退避（1s→2s→4s）、超过重试次数进死信队列等人工介入、且重试要保证幂等（处理前检查状态是否已是success则跳过，或先清理已有半成品数据再重新开始）。

## 关键概念/术语

- **知识库（Knowledge Base）**：文档的容器，一个知识库对应一个独立的 Embedding 模型配置和向量 Collection。
- **文档（Knowledge Document）**：知识库的基本单元，一个上传文件对应一条文档记录，有 `pending→running→success/failed` 四态生命周期。
- **分块（Knowledge Chunk）**：文档的片段、检索的基本单元，向量和元数据与业务数据分离存储。
- **collection_name**：知识库在向量库（pgvector）中的逻辑隔离标识，检索时只在指定 Collection 内搜索。
- **processMode（chunk / pipeline）**：文档两种处理路径，chunk 是直接按策略分块，pipeline 是走可配置的多节点流水线（ETL 的 AI 语义版：Extract→Transform(清洗+分块+增强)→Load）。
- **CAS（Compare-And-Swap）**：触发分块时用来防止重复处理的原子状态切换机制。
- **死信队列**：重试耗尽仍失败的消息的归宿，需人工介入排查。

## 与 xrag 项目的关系

- 这篇文章给出的三层架构和三张核心表设计，是 xrag 知识库模块设计 PRD/技术方案阶段的直接参考起点——尤其是"知识库/文档/分块"三个概念的一对多关系和状态机设计，与 `CONTEXT.md` 里已经定义的"知识库/源文档/文档版本/入库任务/文档分块"术语高度对应，可以在正式设计数据模型时逐条核对是否需要补充"文档版本"这个 xrag 术语体系里有但本文没单独建表的概念（本文的文档表似乎是"一个文件=一条记录"，没有显式的多版本并存机制，需要在 PRD 阶段明确 xrag 是否要支持同一文档的多版本共存/替换语义）。
- pgvector 而非 Milvus 的选型理由（同库事务一致性、运维简化、成本）与我们已经锁定的"pgvector 作为正式架构决策"完全一致，可以直接作为 ADR 里补充的论据来源。
- 对象存储用 RustFS 但代码面向 S3 协议编程、可无缝迁移的做法，与我们在脚手架修复阶段已经确认的"`StorageConfig` 用 AWS SDK v2 `S3Client` 面向通用 S3 API 编程、不绑定具体供应商"的设计完全吻合，说明这个决策方向是对的。
- "上传"和"触发分块"拆成两个接口、用 CAS 防重复触发、四态状态机而非六态——这些都是 xrag 知识库模块 API 设计时应该直接借鉴的具体模式，可以在技术方案文档里作为接口契约的起点。

## 值得注意的设计取舍/坑

- **状态机做减法是有意为之**：从六态简化到四态，是因为中间状态对用户没有实际意义，只有整体结果（成功/失败）才是用户关心的，细节走独立日志表——设计 xrag 的状态机时不要盲目追求"看起来更详细"，要问清楚谁会消费这个状态、消费者需要的颗粒度是什么。
- **向量与元数据分离存储**是这篇文章反复强调的关键设计，不要图省事把向量字段塞进业务表——会拖累所有不需要向量的常规查询（比如分页查看 chunk 列表）的性能。
- **embedding_model 绑定在知识库级别且创建后不建议修改**：如果 xrag 后续要支持"知识库升级 Embedding 模型"这类需求，必须显式设计"旧向量全部失效、需要重新生成"的迁移流程，而不是假设可以无缝切换。
- **chunk_count、kb_id（在分块表里）都是有意为之的冗余字段**，用来换查询性能（避免 COUNT 全表、避免多余 JOIN）——这类"业务上有点重复"的设计需要在技术方案里显式记录理由，避免后来者以为是设计失误想去"规范化"掉。
- **RocketMQ vs Redis Stream 的选择是教学优先，不是技术最优解**：项目为了降低学习者的环境搭建门槛默认用 Redis Stream，但明确说了 RocketMQ 才是更适合企业级场景的选择（支持延迟消息、死信队列、消息轨迹、事务消息）。xrag 做正式技术选型时不能简单照抄"项目默认用什么"，要重新评估：如果需要事务消息保证数据库和消息发送的一致性，Redis Stream 可能不够用。
- **重试必须幂等**这一点容易被忽略——不能假设"重试就是再跑一次一定安全"，必须显式设计"跑到一半的半成品数据"要怎么清理或跳过。
