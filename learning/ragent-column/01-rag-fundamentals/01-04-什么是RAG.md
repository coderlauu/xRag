# 《AI大模型Ragent项目》第4小节：什么是RAG？

> 原文链接：https://t.zsxq.com/wBsEm
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章从"大模型自身有哪些解决不了的局限"这个反问出发，系统讲清楚了 RAG（检索增强生成）为什么诞生、它的六步核心流程（ingest→chunk→embed→index→retrieve→answer）是怎么运转的，以及"做好 RAG"真正难在哪六个环节，是整个专栏后续所有具体技术小节（分块、Embedding、向量库选型、检索、重排序、会话记忆……）的总纲和路线图。

## 核心内容提炼

- **写作动机**：作者认为应用层开发者去死磕大模型微调、蒸馏、Transformer 原理性价比不高，真正该掌握的是 RAG、Agent 这类能落地、能应对面试的应用层技术；市面上 B 站/GitHub 的 demo 级项目和训练营（多为 Python 生态）与企业级 Java 落地之间存在明显差距，这是作者做 Ragent 实战项目、并先系统讲一遍 RAG 原理的原因。

- **大模型工作原理的两阶段模型**：训练阶段本质是让模型从海量文本里学到三类东西——语言规律、世界知识、推理能力；推理阶段本质是"自回归"地逐字预测下一个最可能的词（类似文字接龙）。关键结论：模型的知识全部在训练阶段被"灌入"，推理时只是在调用这些已固化的知识，没有能力在对话过程中主动获取训练之外的新信息。这个结论是后面"五大局限性"的根源。

- **大模型的五大局限性**（文章的第一层分析框架，逐条都对应到 RAG 要解决的问题）：
  - **幻觉问题**：本质原因是模型只是在预测"概率最高的下一个词"，并不真正理解事实；当它对答案不确定时，不会说"不知道"，而是会生成一个看起来合理但可能是编造的内容。
  - **知识时效性**：知识冻结在训练截止日期，企业的产品、政策、价格变化模型完全不知道。
  - **专业领域深度不足**：训练数据里垂直领域的专业内容占比有限，遇到公司内部型号、专属流程等问题会直接答不上来。
  - **私有数据无法获取**：模型训练用的是公开数据，天然访问不到公司内部文档、客户数据、未公开资料、个人隐私信息。
  - **黑盒不可追溯**：模型给不出"这个答案的依据是哪篇文档/哪条法规"，在医疗、法律、金融这类需要验证和追责的场景是硬伤。
  文章用一个"智能客服"场景把五个局限性逐一对应了实际表现（编造不存在的功能、不知道新品、技术问题回答肤浅、不知道退换货政策、答不出出处），说明这五点不是抽象罗列，而是会直接反映在业务效果上。

- **传统关键词检索为什么不够**：作者用 `LIKE '%打印机%'` 类比传统检索，指出它只能做字面匹配，理解不了语义——"这玩意儿怎么用"和文档里的"产品使用方法"字面完全不同，关键词检索匹配不上，但人能一眼看出说的是同一件事。这一步是引出 RAG 的关键铺垫：大模型懂语义但没有私有知识，传统检索有数据但不懂人话，RAG 就是把两者结合的方案。

- **RAG 概念与起源**：RAG（Retrieval-Augmented Generation，检索增强生成）概念最早由 2020 年 Meta（当时叫 Facebook AI）的研究团队提出，核心思路是让模型"先查资料，再回答"，类似开卷考试——模型不需要记住所有知识，只要能检索到并理解就行。基本链路是：知识先入语义化知识库→用户提问先检索相关内容→检索结果和问题一起交给大模型→大模型基于这些参考资料生成回答。

- **RAG 核心六步流程**（`ingest → chunk → embed → index → retrieve → answer`，前四步是离线准备阶段、跑一次或增量更新，后两步是在线运行阶段、每次提问都执行）：
  - **Ingest（导入）**：把 PDF、Word、网页、数据库等各种格式的数据源接入系统，目标只有一个——拿到干净的纯文本，不同格式需要不同的解析方式。
  - **Chunk（切块）**：长文档必须切成小块，原因是模型上下文窗口有限、且检索时希望定位到最相关的那一小段而不是整篇文章。切块的权衡很直接：切太大检索不精准、容易超出上下文限制；切太小语义不完整、上下文丢失。文章给出的经验值是每块 500~1000 字，相邻块之间重叠约 100 字，防止关键信息正好被切断。
  - **Embed（向量化）**：这是整个 RAG 的核心一步，把文本转换成几百到上千维的向量，语义相近的文字在向量空间里距离也相近，由此绕开关键词匹配的语义盲区。这一步由专门的 Embedding 模型完成，文章举例 Qwen3-Embedding-8B，以及开源的 bge、m3e。
  - **Index（入库）**：把向量存进向量数据库，向量数据库专门做"给一个向量、找出距离最近的 N 个"这类相似度搜索，区别于普通数据库的精确匹配。常见的重量级向量库有 Milvus、Pinecone、Weaviate，轻量级有 Faiss、Chroma；作者调研后认为 Milvus 迭代快、社区活跃、有较完善的可视化管理界面，决定用它作为后续课程的示例工具。存储时向量要和原文、元数据（可以理解成一段 JSON）一起存，元数据用于检索时做筛选过滤。
  - **Retrieve（检索）**：用户提问时把问题也转成向量，去向量库里找最相似的若干文档块，靠的仍然是"语义相近→向量距离相近"这条原理，所以"墨盒怎么换"能匹配到文档里的"墨盒更换步骤"。
  - **Answer（生成）**：把检索到的文档内容和用户问题打包组装进 Prompt 交给大模型生成答案，让模型基于给定资料回答而不是自己凭空编造。
  文章特别提醒，这六步只是给一个整体印象，实际落地时每一步都有讲究（切块策略、向量模型选择、是否做重排序等），后续章节会逐个拆开细讲——这也是这篇文章作为专栏总纲的定位所在。

- **RAG 的优点与缺点**：
  - 优点三条：①成本低、上手快——相比微调需要准备训练数据、算力、动辄数天，RAG 把文档灌进向量库当天就能跑起来；②知识更新方便——微调后知识固化，要更新得再微调一轮，RAG 只需重新处理变动的文档，甚至可以做到实时检索最新数据；③答案可追溯——能看到回答参考了哪些文档，便于在金融、医疗、法务等高准确性场景做验证和追责。
  - 缺点三条：①效果强依赖知识库质量，"垃圾进、垃圾出"，检索效果的上限取决于喂给系统的数据；②系统复杂度显著上升，链路从"直接调模型"变成"文档处理+向量存储+检索排序"，任何一环出问题都会打折扣，调试成本比单纯调模型高；③检索耗时不能忽视，文章引用了一个说法——检索环节可能占整个 RAG 流程耗时的 60% 以上——提示对延迟敏感的业务需要重点优化这一步（这个数字是作者引用的经验说法，没有给出可查证的原始来源）。

- **RAG 的四类典型应用场景**：
  - **企业内部知识库**：查询公司制度、产品手册、技术规范等文档并给出出处；进一步结合 MCP（Model Context Protocol）之类的工具调用能力，可以把知识检索和 HR、BI、订单、OA 等业务系统打通，从"只能查文档的知识库"升级为能查数据、能干活的"企业级智能助手"（文章举了考勤/年假、销售额环比、订单物流、待审批流程四个例子）。
  - **智能客服**：突破传统客服机器人"关键词匹配+预设问答对"覆盖不到就抓瞎的局限，把产品文档、FAQ、历史工单都灌进知识库后回答的范围和灵活度都能提升；文章顺带提到观察到某云厂商 AI 助理收敛了此前明显拟人化/角色扮演的输出风格，作者认为这类收敛是为了避免 ToC 场景下的风格漂移和严谨性问题，属于合理优化。
  - **专业领域助手**：法律（检索法条判例辅助写诉状、案情分析）、金融（基于研报财报回答投资问题）、医疗（检索文献和用药指南辅助诊断建议），这类场景对准确性和可追溯性要求都很高，是 RAG 价值最明显的领域。
  - **代码与技术文档助手**：把代码仓库、API 文档、技术文档接入后，新人问接口调用方式、业务逻辑归属模块，系统能直接检索给出答案；文章提到 GitHub Copilot、Cursor 这类工具背后也大量使用了类似的检索增强思路。

- **"做好 RAG 并不容易"——六大难点清单**（这是全文信息密度最高的部分，本质上是给后续专栏章节列了一份路线图）：
  1. **数据入向量库**：企业文档格式五花八门（PDF 表格、扫描件、双栏排版都是解析上的坑），光是拿到干净文本就是脏活累活；切块策略（按段落/固定字数/语义切）没有放之四海而皆准的答案，不同文档类型可能需要不同策略。
  2. **问题重写（Query Rewriting）**：用户原始问题往往不能直接拿去检索——口语化表达需要展开成完整表述才能提升检索效果；多轮对话里的省略/指代（比如接着问"怎么申请"）需要把上文信息（"年假"）补全才能检索到正确内容；一句话里包含多个意图（既要查知识库又要查业务数据）需要先拆开分别处理；复杂问题可能要拆成多个子问题分别检索再合并答案。本质是在弥补"用户怎么说"和"检索需要怎么问"之间的差距。
  3. **意图识别**：不是所有输入都要走 RAG 检索流程——闲聊类问题应该直接让模型回复而不查库；有些问题该查知识库、有些该调用业务系统接口，走错分支答案必然不对；企业里常有多个知识库（HR/产品/技术等），需要判断该路由到哪个库，每个库都搜一遍成本高噪音大，只搜一个又怕选错完全检索不到；还需要识别出敏感、超范围、恶意试探类问题并给出合适的拒绝或引导。意图识别一旦判断错，后面流程再完美也没用。
  4. **数据检索**：这是最容易出问题的核心环节——纯向量检索对精确匹配（编号、人名、型号、订单号）很弱，通常需要向量检索+关键词检索的混合方案，但两边结果怎么融合、权重怎么设是个开放问题；检索返回多少条（top-k）需要在"漏掉关键信息"和"引入噪音干扰模型"之间权衡；很多时候还要加一层 Reranking（重排序）用更精细的模型重新打分排序以提升精度，但这会增加延迟和成本；召回的内容也不一定该直接用，可能是过时版本、相关度不够、或用户没有权限查看，塞给模型前还需要一轮过滤筛选。
  5. **会话记忆**：多轮对话里历史上下文该带多少是个权衡——全带 Token 成本扛不住还容易被早期无关内容干扰，只带最近几轮又可能丢失重要信息；对历史做摘要压缩能省 Token 但可能丢细节；跨会话的长期记忆需要单独的持久化存储和检索机制；用户纠正信息后系统还要能更新记忆、遗忘过时信息。
  6. **其他配套能力**：问题太模糊时要能识别并引导澄清而不是直接检索或拒答；入口处要做请求风控过滤恶意/套取敏感信息的请求，涉及私有敏感数据的知识库还可能需要本地化部署大模型并配套限流风控；要支持用户中途"停止生成"并及时终止而不是继续傻输出；线上流量大时需要模型负载均衡，用第三方 API 还要处理限流、降级、多供应商切换；答案要能标注具体来自哪个文档的哪个部分，方便用户核实建立信任；上线后还需要收集用户反馈（点赞/点踩/纠正）、监控各环节指标，为持续优化提供数据支撑。
  作者强调这六类难点单独拎出来都不算特别难，但组合在一起会让复杂度指数级上升——这正是很多 RAG demo 跑得很顺、一到生产环境就翻车的原因；文中也说明这份清单是"高频难点"而非"问题已穷尽"，后续会针对具体场景持续补充。

- **后续课程路线图**：作者预告接下来会按 Spring AI 快速上手（先搭一个能跑的 RAG 建立直观感受）→ 向量数据库（Embedding 原理、怎么存怎么查）→ RAG 核心流程拆解（检索/重排/生成）→ 本地部署大模型（脱离外部 API 方便调试）→ Ragent 项目底层架构拆解 这五步展开，全程基于 Java 技术栈。

## 关键概念/术语

RAG（Retrieval-Augmented Generation，检索增强生成）：先从知识库检索相关内容、再把内容和问题一起交给大模型生成回答的架构，用于弥补大模型没有私有知识、易幻觉、不可追溯的短板。
Embedding（向量化）：把文本转换成能表达语义的高维数值向量的技术/模型，语义相近的文本对应的向量在空间中距离也相近。
向量数据库：专门存储向量并支持"给定一个向量、找出最相似的 N 个"这类相似度搜索的数据库，区别于做精确匹配的传统数据库。
Chunk / 切块：把长文档切分成较小片段的预处理步骤，用于适配模型上下文窗口限制并提升检索定位精度。
Reranking（重排序）：在初步检索结果基础上，用更精细的模型对结果重新打分排序以提升最终相关性的环节，会增加延迟和成本。
混合检索：把向量检索（擅长语义匹配）和关键词检索（擅长精确匹配编号/人名等）结合使用的检索策略。
意图识别：在真正走检索/生成流程之前，先判断用户输入应该闲聊直答、走知识库检索、还是调用业务工具接口的分类步骤。
查询重写（Query Rewriting）：把用户口语化、省略指代、多意图或复杂的原始问题改写成更适合检索的完整表述的处理步骤。
幻觉（Hallucination）：大模型生成看起来合理但实际错误或编造的内容的现象，根源是模型本质是预测概率最高的下一个词而非真正理解事实。

## 与 xrag 项目的关系

这篇文章目前看主要是概念地基和顶层路线图，还没有到可以直接抄落地代码的程度，但它给出的两套框架对 xrag 的模块划分和优先级判断有直接指导作用：

- **RAG 六步流程可以直接映射为 xrag 的模块边界**：`ingest/chunk/embed/index` 四步对应 xrag 的知识库/文档管理模块（负责把各种格式文档变成向量并入库），`retrieve/answer` 两步对应 xrag 的检索问答运行时链路（负责每次提问的实时处理）。这个划分和 `learning/ragent-column/INDEX.md` 里已经拆出的 `03-knowledge-base`（对应 ingest/chunk/embed/index）、`05-qa-pipeline`（对应 retrieve/answer 及其复杂化）分组是吻合的，可以作为后续设计 xrag 系统架构图时模块划分的一致性检查依据。
- **"六大难点清单"本质上就是 xrag 05-qa-pipeline 分组后续文章要逐一细化的内容**——查询重写、意图识别、混合检索/top-k/重排序、会话记忆、澄清与兜底、风控/停止生成/负载均衡/答案溯源/效果监控，几乎一一对应 `INDEX.md` 里 05-qa-pipeline 分组列出的具体篇目标题。这说明这篇文章的价值不在于给出答案，而在于提前把 xrag 检索问答链路需要覆盖的能力清单列全了，方便后续设计阶段做覆盖度检查（避免漏做某个环节）。
- **向量数据库选型不能只看这篇文章的结论**：文章推荐 Milvus 作为示例工具（理由是迭代快、社区活跃、有可视化界面），但专栏 `07-interview` 分组里明确有一篇《Ragent为什么从Milvus换成Pgvector？》，说明作者在实际项目推进中把选型从 Milvus 改成了 Pgvector。这提示 xrag 做向量数据库选型时要等看到那篇文章给出的迁移理由后再定，不能仅凭这篇入门文章的推荐就直接拍板，尤其要评估是否已经在用 PostgreSQL（如果是，Pgvector 能省一套独立中间件的运维成本）。
- **技术栈契合度**：xrag 后端是 Java/Spring 技术栈（`backend/pom.xml`），文章强调的"走 Java 生态而不是 Python 训练营套路"和"用 Spring AI 但要留意版本迭代快、低版本功能缺"这两点，和 xrag 当前的技术选型方向是一致的，说明后续把这套 RAG 流程落地到 xrag 时，可以直接对照 Spring AI 生态的现成组件（如 `VectorStore`、`EmbeddingModel` 抽象）去实现，不需要额外做语言/生态层面的转译。

## 值得注意的设计取舍/坑

- **"检索环节占 60% 以上耗时"是作者引用的经验说法，没有给出可查证的原始数据来源**，xrag 做性能预算或立性能目标时不能把这个数字当成精确基准，需要针对自己的检索链路（向量库延迟、网络往返、重排序模型调用等）实测后再定优化优先级。
- **Milvus 的选型理由本身就是一个会被后续推翻的取舍**：文章给出的"迭代快、社区活跃、有可视化界面"三条理由都是功能和生态维度的考量，没有涉及运维成本、与现有基础设施的整合难度；专栏后续标题暗示作者实际把项目从 Milvus 换成了 Pgvector，说明向量数据库选型除了看功能，还要看是否会引入独立中间件的运维负担——这是一个容易在"选型初期只看 demo 好不好用"时忽略的坑。
- **Chunk 的"500~1000 字、重叠 100 字"只是经验值，不是理论最优**，文章自己也承认切块策略没有银弹、需要按文档类型定制，xrag 后续设计分块策略时不能直接套用这个数字了事，要结合实际文档类型（制度文档 vs 代码文档 vs 聊天记录）单独验证。
- **"检索准确性"和"检索到但不该用"是两个独立的问题**，文章明确把"结果重排序（提升相关性排序）"和"过滤掉过时/低相关/无权限内容（决定能不能用）"分开描述——这提示检索模块设计时不能只优化召回率和排序，还需要一层独立的后置过滤/权限校验逻辑，这一层很容易在只关注"检索准不准"时被忽略，尤其是权限过滤（检索到了但用户没权限看的内容）在企业知识库场景是刚需而非可选项。
- **RAG 不是普适方案**：文章明确指出 RAG 效果的上限取决于知识库质量（"垃圾进、垃圾出"），且会显著增加系统复杂度和响应延迟，适用场景被限定为"知识密集、更新频繁、需要可追溯"；如果业务场景不满足这三个特征（比如知识量很小且几乎不变），引入 RAG 反而是不必要的复杂度，这一点在做 xrag 功能取舍时值得作为前置判断标准。
