## 1. 背景与动机

xrag 目前只有健康检查接口和存储/数据库连接骨架，知识库能力完全空白。知识库是整个 Agentic RAG 系统的地基——没有"把文档变成可检索内容"的能力，后续的大模型调度、知识问答、评测体系都无从谈起。

本 PRD 基于知识星球专栏《Ragent AI》"AI 知识库建设"分组共 11 篇文章（[学习整理见此](../../learning/ragent-column/03-knowledge-base/)）提炼而来，按 [ADR 0001](../adr/0001-build-xrag-independently.md) 的约束：课程内容和参考仓库 `nageoffer/ragent` 只作为设计参考，不直接照抄其代码/Schema/模块结构；每项能力是否纳入、怎么落地，都要结合 xrag 自己的定位（**单用户个人学习与作品集项目**，已在 Phase 0 对齐检查点中确认）重新判断。

## 2. 目标与非目标

### 目标（Goals）

1. 用户能创建知识库、上传文档（本地文件 / 远程 URL 两种来源），文档能被解析、分块、向量化，进而支撑后续问答模块的检索。
2. 文档和分块具备完整的生命周期管理能力（查看、更新、删除、启用/禁用），且这些操作在数据库和向量库之间保持一致。
3. 文件上传具备基本的安全防护（大小限制、内存安全、并发限流），不会因为一次上传拖垮整个应用。
4. URL 来源的文档支持定时同步，知识库内容能跟随源文档持续更新，而不是一次性导入后就过时。
5. 全部能力有对应的技术方案、任务书、测试验收标准，作为可展示的企业级 SDLC 产出物的一部分。

### 非目标（这一版明确不做）

- **多租户/权限体系**：已在 Phase 0 对齐检查点确认——xrag 是单用户项目，不做租户隔离、不做基于角色的访问控制。
- **复杂鉴权的远程文档源**（飞书文档、钉钉文档、Confluence 等需要 OAuth 授权或平台专属 API 的场景）：只支持完全公开的 URL 或 URL 参数携带 Token 的简单鉴权，参考文章明确把复杂平台适配排除在核心链路之外，本 PRD 沿用这个边界。
- **Pipeline 模式（可编排的多节点 ETL 处理流程）**：课程内容里 CHUNK 模式（固定流程）和 PIPELINE 模式（可自定义节点编排）并存，但 PIPELINE 模式的复杂度（节点定义、编排引擎）明显超出"知识库建设"这一个模块该有的范围。第一版**只做 CHUNK 模式**，PIPELINE 模式作为明确记录的未来扩展点，不在本轮设计和开发范围内。
- **精确 Token 计数**：分块的 `tokenCount` 走启发式估算（中文≈1字/token，英文≈4字符/token），不接入具体模型的 Tokenizer，仅供管理界面展示参考，不参与任何检索/生成逻辑判断。
- **消息队列的选型和事务消息机制**：课程用 RocketMQ 事务消息保证"状态更新"和"异步任务触发"的原子性，这是一个具体的技术实现方案而非产品需求，本 PRD 只要求"上传和分块解耦为两个独立操作、分块异步执行、支持失败重试"，具体走 RocketMQ / Redis Stream / 或 Spring 自带的异步机制，留给技术方案阶段决策。

## 3. 用户场景

xrag 是单用户项目，"用户"就是 liuqiang 本人，但产品设计上仍按"知识库管理员"这个角色的完整操作闭环来设计（这也是"企业级/可展示"定位的一部分）：

- **场景一：导入一批本地文档建知识库**——创建一个知识库，批量上传 PDF/Word/Markdown 文件，逐一触发分块，几分钟后这些内容就能被检索到。
- **场景二：追踪一份持续更新的在线文档**——把一个远程 Markdown 文档的直链配置进知识库，开启定时同步（比如每天检查一次），文档更新后知识库内容自动跟着刷新，不需要手动重新上传。
- **场景三：修正分块质量问题**——检索效果不理想，管理员定位到某个分块把一句完整的政策条款切断了，手动编辑合并这个分块的内容，而不需要重新调整全局分块参数、重跑整份文档。
- **场景四：临时下线有问题的内容**——发现某份文档内容有误，需要立即让它不再出现在检索结果里，但暂时不想删除（可能改完还要用），用"禁用"而不是"删除"。

## 4. 功能需求

### 4.1 知识库管理

| 功能 | 说明 |
|---|---|
| 创建知识库 | 指定名称、Embedding 模型（当前只支持云端 API，见 §6 非功能需求） |
| 查看知识库列表/详情 | 展示知识库基本信息，后续可扩展文档数/分块数等统计 |
| 修改知识库 | 可改名称、描述；Embedding 模型不可改（见下） |
| 删除知识库 | 仅允许删除空知识库；仍有文档或活动入库任务时拒绝 |

- 每个知识库对应向量库里一个独立的 collection（用于按知识库隔离向量数据、支持不同知识库使用不同 Embedding 模型）。
- Embedding 模型一经选定，不支持事后修改（模型变更会导致已有向量全部失效，是一个需要用户主动发起的"重建"操作，不属于本轮范围）。

### 4.2 文档管理

**上传**
- 支持两种来源：本地文件上传（`FILE`）、远程 URL 抓取（`URL`）。
- 上传只做两件事：把文件存到对象存储（RustFS）、把文档元数据存到数据库，状态设为"待处理"。**不在上传接口里触发分块**——上传和分块是两个独立操作（原因见 §7 关键设计决策）。
- URL 来源的地址必须是文件的直接下载链接，不能是网页地址（前端交互上应给出提示/校验，避免用户误填网页 URL 导致抓取到 HTML 源码）。

**查看**
- 分页查看知识库下的文档列表，支持按启用/禁用状态过滤。
- 查看单个文档详情（状态、分块数、来源信息、定时同步配置等）。
- **查看源文档**（`2026-07-26` 增补，见下方说明）：用户能重新打开/下载当初上传或抓取到的那份原始文件。范围限定为**下载或在新标签打开**，不做在线预览渲染、也不做"分块 ↔ 原文位置对照"。
  - `URL` 来源打开的是**对象存储里的快照**（上次抓取到、且真正被切分过的那一份），不是实时重新抓取——否则源站已经变了的话，用户看到的原文与现有分块对不上。界面需同时给出快照的抓取时间，并另给一个跳转到原始链接的入口。

> **为什么补这一条。** 此前的设计里，原始文件进了对象存储之后用户就再也打不开了——§7.6 保留它只是为了"逻辑删除可恢复"，不是为了给人看。但 §4.4 手动干预分块这个能力，恰恰要求用户能判断"原文到底怎么写的"：在分块页看到一段被切坏的内容，没有原文可对照时他只能凭记忆改。这是实现完成后回看界面才发现的缺口，不是需求变更。

> **明确不做的两件事**，各有理由：**在线预览**要引 PDF 渲染库，而 `.docx` 在浏览器里没有像样的免费方案，投入与收益不成比例；**分块与原文位置对照**要求分块记录保留其在原文中的字符偏移量（数据模型变更），且对 PDF 这类"提取后文本与原排版对不上"的格式，高亮位置未必准。两者都推迟到有真实使用反馈之后再评估。

**触发分块**
- 独立于上传的操作，用户主动点击后异步执行：解析文本 → 按配置的分块策略切分 → 生成向量 → 写入分块表和向量库 → 更新文档状态。
- 前端可轮询文档状态获知处理进度（待处理/处理中/成功/失败）。
- 失败后用户可以直接重新触发分块，无需重新上传文件。
- 处理中的文档不允许被删除、更新配置或再次触发分块（并发保护）。

**更新配置**
- 可修改文档名称、分块策略与参数。
- 仅 URL 来源的文档可修改来源地址和定时同步配置。
- 更新配置**不会**自动触发重新分块，需用户显式再次触发（保持"配置变更"和"处理触发"两个动作的独立性）。

**删除**
- 逻辑删除文档本身，并级联逻辑删除其下全部分块（详见 §7.6 全局逻辑删除约束）。
- 向量数据是**例外**：必须物理删除，否则文档删了内容还会出现在检索结果里，"删除"就没有实际效果（和禁用文档必须清理向量是同一条道理）。
- 对象存储里的原始文件**保留不删**——逻辑删除意味着"可恢复"，把源文件删了就恢复不回来了。真正释放存储空间是一个独立的运维动作，不在本轮范围内（作为已知的存储增长代价被显式接受）。

**启用/禁用**
- 禁用：文档的内容应立即从检索结果中消失（意味着必须同步清理向量库中的对应数据，而不只是打个标记位）。
- 启用：重新计算并写回向量数据，文档重新参与检索。
- 用于"临时下线有问题的文档，但保留恢复的可能性"这个场景（区别于删除）。

### 4.3 定时同步（仅 URL 来源）

- 用户可为 URL 来源的文档配置定时刷新周期（cron 表达式），系统按周期检查远程文件是否有变化，有变化才重新拉取、重新分块。
- **必须先判断"值不值得刷新"，再决定要不要真正拉取和重新分块**——不能每次定时触发都无脑重新处理整份文档（会造成不必要的下载、解析、Embedding API 调用成本）。
- 定时周期有最短间隔限制（避免用户配置过于频繁的同步造成资源浪费）。
- 需要能应对"处理到一半、进程异常退出"这类情况——文档不能永久卡在"处理中"状态，需要有超时后自动恢复的机制。
- 定时刷新和用户手动触发分块可能撞在一起，两者不能同时处理同一份文档。

### 4.4 分块（Chunk）管理

自动分块无法覆盖所有情况（原文切割位置不理想导致语义被截断、或者关键短句被淹没在大段文字里），因此提供手动干预入口，**作为永久性的兜底能力，不是临时功能**：

| 功能 | 说明 |
|---|---|
| 查看分块列表 | 按文档原文顺序展示，支持按启用/禁用状态过滤 |
| 新增分块 | 手动插入一段内容作为新分块，可指定插入位置 |
| 编辑分块内容 | 修改后需要重新生成该分块的向量；内容未变化时不应触发任何实际操作（避免不必要的 Embedding API 调用） |
| 删除分块 | 逻辑删除单个分块并物理删除其向量，不影响同文档的其它分块 |
| 单条启用/禁用 | 只影响这一个分块的检索参与状态 |
| 批量启用/禁用 | 对一批指定的分块 ID 做批量状态切换，需要限制单次操作规模 |

- 新增/启用分块前必须确认所属文档处于启用状态——不允许一份已禁用的文档"漏出"某个被单独启用的分块，造成数据库状态和向量库检索结果矛盾。

## 5. 交互要点（供 Step C 技术方案 / 前端设计细化）

- 文档列表需要清晰展示"待处理/处理中/成功/失败"四种状态，处理中的文档相关操作按钮（删除/编辑/重新触发）应禁用或给出明确提示。
- 分块编辑应该是知识库管理界面里一个相对独立的子页面/弹层，因为需要展示分块在原文中的顺序上下文，方便用户判断"这段内容是不是该合并/拆分"。
- URL 来源文档的定时同步配置应该有明显的状态展示（下次执行时间、上次执行结果、是否有失败历史），而不是配置完就"看不见"。
- 批量操作（分块批量启用/禁用）需要给用户明确的操作范围反馈（比如"已选中 N 个分块，其中 M 个将发生状态变化"）。

## 6. 非功能需求

### 6.1 文件上传安全（学习收获直接转化为需求）

- 单文件大小限制、单次请求大小限制必须显式配置（当前脚手架的 `application.properties` 尚未配置，是本模块开发时的第一个具体待办）。
- 大文件上传不能因为内存问题拖垮应用——需要验证 xrag 使用的 AWS SDK v2 `S3Client`（`StorageConfig` 已实现）直接 `putObject` 是否存在学习笔记 03-03 里记录的内存放大问题，技术方案阶段需要明确采用预签名 URL 流式上传还是其它方案。
- 并发上传数量需要有限流保护，避免大量并发上传拖垮磁盘/IO；限流应该拦截在尽量早的处理环节（技术方案阶段结合 xrag 实际是否引入网关来决定具体拦截层）。

### 6.2 数据一致性

- 数据库记录与向量库数据必须保持一致：写入/删除/状态变更等操作要么都成功要么都不生效；耗时的外部调用（文件上传、Embedding API）不能包在数据库事务里，避免长事务占用连接池。
- 允许接受"文件系统操作"这类无法参与事务的环节采用最终一致性（清理失败留下的孤儿数据，可以后续用定时任务清理，不追求强一致）。

### 6.3 性能

- Embedding 走云端 API（已确认决策）；批量操作要考虑单次操作规模上限，避免接口响应时间不可控。
- 分块处理是异步的，接口层面不应让用户等待处理完成。

## 7. 关键设计决策（提炼自学习内容，供技术方案阶段直接采纳或调整）

以下结论来自 03-knowledge-base 分组的学习整理，建议技术方案阶段直接沿用，除非有明确理由调整：

1. **上传和分块是两个独立接口/操作**，不是一个耗时的大接口——职责分离、支持失败重试、支持批量上传后再统一触发。
2. **知识库/文档/分块是一对多的三层数据模型**，分块的向量数据与业务内容分离存储（分块表存文本和元数据，向量库单独存向量），职责分离且便于向量库单独选型/迁移。
3. **禁用文档必须同步清理向量库数据**，而不是只在数据库打标记——检索是直接查向量库的，数据库状态和向量库状态必须同步，否则"禁用"没有实际效果。
4. **手动分块管理是永久能力**，服务于"自动分块无法覆盖所有情况"这个客观现实，不是过渡方案。
5. **定时同步前必须先判断"值不值得刷新"**（比对远程文件是否真的变化），不能每次触发都无脑重新处理，需要设计变更检测机制。

### 7.6 全局约束：业务数据统一逻辑删除

`2026-07-25` 用户确认的**全系统级**约束（不限于本模块，后续所有模块同样适用）：**所有业务数据的删除都是逻辑删除，不做物理删除。**

- 知识库、源文档、文档分块三类业务实体的删除接口，一律只打删除标记，不执行 `DELETE` 语句；所有查询默认过滤掉已删除记录。
- 删除具备级联语义：删除知识库 → 其下全部文档和分块一并标记删除；删除文档 → 其下全部分块一并标记删除。
- **两类例外**（必须在技术方案中显式说明，否则逻辑删除会破坏系统正确性）：
  1. **向量数据物理删除**——向量库是从分块内容派生出来的检索索引，不是业务主数据。给它打逻辑删除标记既没有业务意义，还会让被删数据继续占用索引、拖慢检索、甚至污染召回结果。因此凡是"内容不再应参与检索"的场合（删除、禁用、重新分块），向量记录都物理删除，需要时从分块内容重新生成。
  2. **对象存储原始文件保留**——不删除，以保留恢复可能性。
- 这条约束带来的已知代价：数据库和对象存储只增不减，长期会持续增长。个人项目的数据量级下可接受；如果将来确实需要回收空间，应设计成一个显式的、独立于业务删除的"归档/清理"运维能力，而不是把业务删除改回物理删除。

## 8. 验收标准（对应 Step E 测试环节的输入）

- [ ] 能创建知识库、上传本地文件、触发分块，几分钟内该文档内容可以在数据库和向量库中查到对应记录。
- [ ] 能配置 URL 来源文档，验证定时同步在文件未变化时不会触发重新分块，文件变化后能正确刷新。
- [ ] 上传超过配置大小限制的文件被正确拒绝，且不会导致内存/磁盘异常增长。
- [ ] 删除文档后：文档和其分块在所有列表/详情接口中不再可见（逻辑删除生效），向量数据被物理删除，定时同步不再对它执行。
- [ ] 禁用文档后，其内容不应出现在任何检索结果中（需要在问答模块打通后联调验证，本模块先保证向量数据被正确清理）。
- [ ] 手动编辑/新增/删除分块后，向量库数据与数据库分块记录保持一致。
- [ ] 处理中的文档拒绝并发的删除/更新/重复触发分块请求。
