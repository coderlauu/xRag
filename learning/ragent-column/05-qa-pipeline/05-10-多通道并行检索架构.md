# 《单次提问同时查三个知识库——多通道并行检索架构》

> 原文链接：https://t.zsxq.com/dWyw9
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

第 9 篇讲"查什么"，本篇讲"怎么查"：`MultiChannelRetrievalEngine` 分两阶段（并行跑通道 → 串行跑后处理链），通道用 `SearchChannel` 统一契约 + Spring 列表注入，**并行嵌套三层配三个独立线程池**（子问题 / 通道 / Collection），每层都有 try-catch 兜底——把串行 450ms 压到 165ms。

## 核心内容提炼

- **两阶段职责切得很干净**：阶段 1 `executeSearchChannels` 并行收原始结果，阶段 2 `executePostProcessors` **必须串行**——去重与精排之间有依赖（先去重再精排），不是没能力并行。

- **`SearchChannel` 五个方法**：`getName()`（日志/监控）、`getPriority()`（去重优先级，定向=1、全局=10）、`isEnabled(context)`、`search(context)`、`getType()`。**`isEnabled` 接收 `SearchContext` 而不是无参**，这是关键——同一个通道对不同请求可以有完全不同的表现。

- **`SearchChannelResult.channelType` 不只是日志字段**：后处理器去重时靠它判优先级，同一条 chunk 被两个通道同时命中时**保留定向检索的版本**（基于意图的精准匹配可信度更高）。`latencyMs` 用来定位是哪个通道拖了后腿。

- **`getMainQuestion()` 优先用改写后的问题**——检索用改写版本效果更好，这是第 4 篇成果的兑现点。

- **通道按 `getPriority()` 排了序，但排序不影响执行顺序**（全部 `supplyAsync` 并行）。排序只影响日志与结果列表的稳定性。**这是一个容易读错的地方。**

- **两级线程池是为了避免嵌套并行的自阻塞**。共用一个池的失败路径讲得很具体：池子最大 4 线程，两个通道各占一个跑 `search()`，`search()` 内部又往同一个池提交 Collection 任务，只剩 2 个线程；全局要查 5 个 Collection，后 3 个排队——**外层线程在 `.join()` 等内层，内层在等外层释放线程**，形成拥塞。

  | 参数 | 外层（通道级） | 内层（Collection 级） |
  |---|---|---|
  | 核心线程 | CPU 核数 | 2×CPU |
  | 最大线程 | 2×CPU | 4×CPU |
  | 队列 | `SynchronousQueue`（无缓冲直交） | `LinkedBlockingQueue(100)` |
  | 并发度来源 | 通道数（2） | Collection 数（可能 10+） |

  内层更大的理由：向量检索是 IO 密集（主要在网络等待），CPU 利用率不高，可以承载更多并发。两个池都用 `CallerRunsPolicy`——**极端情况退化为串行而不是丢任务**。

- **`TtlExecutors` 包装解决的是 `ThreadLocal` 在线程池下丢上下文的问题**。不包装的话内层任务拿不到 `traceId`，日志里看到一条"检索耗时异常"却不知道属于哪次请求。

- **`AbstractParallelRetriever<T>` 是标准的模板方法模式**：`executeParallelRetrieval` 用 `final` 修饰锁死骨架（提交 → join → 收集 → 统计），子类只实现 `createRetrievalTask` / `getTargetIdentifier` / `getStatisticsName` 三个抽象方法。方法内用了**局部 `record RetrievalFuture<T>`** 把目标与 Future 绑在一起——比 `Pair` 语义清晰、编译期类型安全，且作用域只在方法内。

- **`IntentParallelRetriever` 的四参数重载是绕开模板方法限制的手法**。父类骨架假设所有目标共用一个 `topK`，而意图检索需要每个目标独立 `topK`。做法是**先把 `topK` 预计算好塞进 `IntentTask` record**，再调父类三参数方法——`createRetrievalTask` 里父类传下来的 `topK` 参数直接命名为 `ignoredTopK` 忽略掉。

- **两层容错各自兜一层**：通道级（`channel.search()` 外的 try-catch，失败返回空 `SearchChannelResult`）与 Collection 级（`createRetrievalTask` 内的 try-catch + `future.join()` 外的 try-catch 双重保险）。核心原则：**宁可少返回一部分结果，也不让整个请求挂掉**——少一个 Collection 的 chunk 比返回 500 好得多。

- **失败是静默的但可观测**：某个 Collection 超时时，统计日志会打 `总目标数: 5, 成功: 4, 失败: 1`，用户拿到的答案里少了那部分内容但请求正常完成。

- **三层并行 × 三个池的耗时账**：通道级取最慢（~65ms）+ 后处理串行（~100ms）= ~165ms；全串行则是 7 个 Collection × 50ms + 100ms = 450ms。**省了约 63%。**

## 关键概念/术语

- **`MultiChannelRetrievalEngine`**：多通道检索的编排者，两阶段执行。
- **`SearchContext`**：所有通道共享的只读上下文（原问题 / 改写问题 / 子问题 / 意图 / topK / metadata）。
- **`SearchChannelResult`**：通道输出（类型 / 名称 / chunks / 耗时 / metadata）。
- **两级线程池**：外层管通道并行，内层管 Collection 并行，物理隔离。
- **模板方法模式**：`final` 骨架 + 三个抽象钩子。
- **TTL 透传**：`TransmittableThreadLocal`，让线程池里的子任务继承父线程的上下文。

## 与 xrag 项目的关系

- **xrag 的 pgvector 形态会让这一整层架构塌缩掉一半，这是本组笔记里最大的实现差异。** 原文的三层并行里，最内层（Collection 级）的存在理由是 **Milvus 的物理集合隔离**——查 5 个知识库就是 5 次独立检索，必须并行再合并。xrag 是一张 `document_chunk_embedding` 表加一个 HNSW 索引：
  - **全局检索 = 一条不带 `where kb_id` 的 SQL**，索引直接给出全局最近邻。不需要并行、不需要合并、不需要内层线程池，**而且结果比"N 路各取 TopK 再合并"更正确**（后者是近似的分组 TopK，前者是真正的全局 TopK）。
  - **定向检索 = `where kb_id in (...)` 一条 SQL，或 N 条并行**——取决于第 9 篇笔记里记的那个选择题（全局排序 vs 每库保底）。

  也就是说：**`AbstractParallelRetriever`、`CollectionParallelRetriever`、内层线程池这三样东西在 xrag 里可能一个都不需要**。Step C 写技术方案时不要因为原文有就照着搭一遍——**这是照搬会引入纯负担的典型位置**。

- **真正的并发上限在 xrag 是数据库连接数，不是线程池大小。** `ChunkVectorRepository.search` 标了 `@Transactional(readOnly = true)`（因为要 `set local hnsw.iterative_scan = strict_order`），每个并行检索任务都要独占一条连接。而 [`application.properties`](../../../backend/src/main/resources/application.properties) 没有配 Hikari 池大小，**默认 `maximumPoolSize` 是 10**。原文的三层嵌套在 8 核机器上内层线程池最大 32 个线程——**32 个线程抢 10 条连接，多出来的会阻塞在连接获取上，看起来像"向量检索变慢了"，实际是连接池排队**。而这个症状与 CLAUDE.md 里记的那个坑（IDE 后端抢任务导致成片超时）一样具有欺骗性。**Step C 必须把"并行度 ≤ 连接池大小"写成一条硬约束**，并且这个约束还要和第 17~18 篇的全局并发许可一起算。

- **`SearchChannelType` 里预留的 `KEYWORD_ES` / `HYBRID` 两个枚举值，xrag 不应照抄。** 这正是"不预留永远走不到的分支"要拦的东西——枚举值存在但没有任何实现，读代码的人会以为系统支持关键词检索。xrag 若确定本期只做定向 + 全局两个通道，枚举里就只写这两个。**注意：CLAUDE.md 明确说"检索策略尚无 ADR，不要假设已有定论"，所以"要不要做混合检索"本身是 Step A 该提交给所有者的问题**（当前待决策项 D-02 只写了"意图树、多通道检索、结果融合的选型"，应当细化到"是否含 BM25/关键词通道"）。

- **`SearchChannel` 接口 + Spring 列表注入这个扩展点，对 xrag 是"值得保留但要有第二个实现才建立"的东西。** 只有一个实现时接口是负担；有两个（定向 + 全局）时它就开始还本。**但要注意 xrag 的定向与全局在 pgvector 下差别只有一个 where 子句**——两个"通道"是否值得做成两个类，还是同一个方法的两种参数，这是 Step C 的一个真实设计判断。倾向于保留通道抽象，理由不是扩展性而是**它们的激活条件、topK 倍率、去重优先级都不同**，这些差异需要一个地方安放。

- **`TtlExecutors` 在 xrag 大概率用不上，但它指向的问题必须解决。** 如果按 [ADR 0004](../../../docs/adr/0004-reactive-streaming-runtime.md) 走 Reactor，上下文透传用的是 Reactor `Context` 而不是 `ThreadLocal`，`TransmittableThreadLocal` 这个依赖不需要引入。**但"链路记录要能把三层并行里的每一次检索关联回同一次提问"这个需求是一样的**——[CONTEXT.md](../../../CONTEXT.md) 的「链路记录」要落地，就必须有一个跨异步边界的关联 ID。`com.app.ai.model` 已经有 `RequestId`，问答链路是复用它还是另起一个，Step C 要定。

- **`SearchContext` 是个 `@Data @Builder` 的可变对象且带 `Map<String, Object> metadata`，xrag 应当做成不可变记录。** 它被多个并行通道共享读取，可变对象 + 可变 Map 在并发下是隐患（虽然当前没人写它）。`com.app.ai.model` 下的领域类型全是 record，问答链路应当保持同样的风格。`metadata` 这种 `Map<String, Object>` 口袋字段尤其要警惕——**它是"以后可能有用"的具象化，等价于预留一个类型不安全的扩展点**。

- **"宁可少返回也不整体失败"这条原则，xrag 要配上可见的降级信号。** 原文的失败只体现在 `log.info` 的统计里。xrag 的问答界面若某个知识库检索失败，用户看到的是一个内容不全的答案而**没有任何提示**——这与知识库模块反复强调的"界面状态要如实反映实际行为"冲突。至少链路记录里要能查到"本次检索有 N 个目标失败"，界面上是否提示是 Step B 的 ui-spec 该决定的事。

## 值得注意的设计取舍/坑

- **`CallerRunsPolicy` 在嵌套并行里是个隐蔽的风险，原文把它当成纯粹的好事。** 外层池满时调用者线程自己跑 `channel.search()`——而调用者线程是 pipeline 主线程。此时主线程会同步执行整个通道检索，**包括它内部往内层池的提交与 join**。如果内层池也满了，内层同样降级为 CallerRuns，那么"两级隔离"在压力下会退化成完全串行，且是在**最需要并行的高负载时刻**发生。这不是错误，但"极端情况下退化为串行而不是丢任务"这个描述掩盖了一个事实：**退化的时机恰好是延迟最不能忍受的时候**。

- **全局检索每次都查一遍数据库拿 Collection 列表**，原文自己承认可以加缓存但选了简单可靠。这个取舍在 xrag 里**直接消失**——不需要知识库列表，一条不带过滤的 SQL 就够了。这是个很好的例子：**原文的一个"待优化项"在另一种存储形态下根本不成立**。照抄架构会连带把不存在的问题一起抄过来。

- **`createRetrievalTask` 的第三个参数被命名为 `ignoredTopK`，这是模板方法模式绷不住了的信号。** 父类骨架假设"所有目标共用一个 topK"，子类的真实需求是"每个目标独立 topK"，于是用 `IntentTask` 预绑定 + 忽略父类参数绕过。原文夸它"巧妙"，但**一个抽象方法的参数在一半实现里必须被忽略，说明抽象抽错了地方**——正确的做法是让泛型 `T` 自带 topK（就像 `IntentTask` 做的），父类骨架根本不传 topK。xrag 若真要抽这个父类，别把这个签名一起抄过来。

- **`SearchChannelType` 参与去重优先级，意味着通道类型是有序的，但这个序与 `getPriority()` 是两套。** 一个通道有 `getPriority()`（数字，用于排序）和 `getType()`（枚举，用于去重优先级），**两者语义重叠但不是一回事，且没有任何机制保证它们一致**。新增通道时很容易出现"priority 排在前面但去重时被判为低优先级"的矛盾。**去重优先级应当直接用 `getPriority()`，不需要第二套。**

- **耗时账里"后处理器 ~100ms"这一项，比整个并行检索还慢。** 全部并行优化省下的是 285ms，而串行的后处理链就占了 100ms——**其中主要是 Reranker 的 Cross-Encoder 推理**。这提醒一件事：**在 Reranker 面前，检索层的并行优化收益是有限的**。xrag 当前没有可用的 Rerank 能力，一旦接上，检索侧这些并行设计的相对收益会立刻下降。**优化顺序应当是先把 Rerank 的延迟摸清楚，再决定检索层值不值得做三层并行。**

- **两个通道可能从同一个知识库搜到同一条 chunk，这在 xrag 里的表现不同。** 原文里定向查 `kb_3c_return`、全局也查 `kb_3c_return`，**同一条 chunk 被查了两次**——纯粹的重复劳动，只能靠后处理去重收拾。xrag 若两个通道都是同一张表上的查询，重复更是必然（定向的结果是全局结果的子集，只要 topK 够大）。**这引出一个 xrag 特有的简化机会：既然定向 ⊂ 全局，"两个通道同时激活"是否还有意义？** 原文的价值在于定向能保证小库的 chunk 不被大库淹没（分组 TopK 的效果），xrag 若用 `IN` 一次查就没有这个保证。**这个问题必须在 Step C 想清楚，否则会做出一个"两条通道查同一份数据、去重后等于只查了一次"的架构。**
