# 《10 个人同时提问只有 3 个坑位》

> 原文链接：https://t.zsxq.com/m4blA
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

RAG 请求长耗时 + 资源敏感 + 体验敏感，QPS 限流挡不住并发存量、本地 Semaphore 在多机下没有全局视角、HTTP 429 会把用户逼成重试风暴——于是改用**排队**：Redis 五件套（可过期信号量 + ZSET 队列 + 自增 seq + entry 存活标记 + Pub/Sub）配 `Ticket` 状态机，走"先 Lua claim 队头位置、再抢真实许可"的两阶段抢占。

## 核心内容提炼

- **QPS 限流挡的是速率，打爆下游的是存量**。同样 10 req/s：单次 60 秒的场景稳态并发 600，单次 100 毫秒的场景任意时刻只有 1 个。**两者 QPS 完全相同，对下游的压力差 600 倍。**

- **三种朴素方案的适用边界**：

  | 方案 | 适合 | RAG 是否合适 |
  |---|---|---|
  | HTTP 429 直接拒绝 | 短请求、能快速重试 | 否，用户已按下回车并在等 |
  | 令牌桶 | 短请求 + 突发但均速可控 | 否，令牌发出后被长期占用，速率算不准 |
  | 排队 + 信号量 | 长耗时 + 资源敏感 + 体验敏感 | 是 |

  拒绝的真正代价原文说得很直白：**用户会刷新再问、刷新再问，制造更多请求把系统继续打爆。**

- **本地 `Semaphore` 在多机下的三个具体失效点**：两台各配 N 则总并发 2N；按 `N / 节点数` 分配又受扩缩容影响；即使分对了，负载均衡随机分发会让 A 满载而 B 的许可闲置。

- **两层拆分的理由是复用**：`FairDistributedRateLimiter` 封装通用的"信号量 + ZSET + Lua claim + entry 标记 + Pub/Sub"，跟 SSE 和聊天没关系；`ChatQueueLimiter` 只做 SSE 特有的事（绑 emitter 生命周期、超时被拒时写会话记忆并推事件）。

- **五个 Redis 数据结构各自解决一个具体问题**：

  | 结构 | 解决什么 |
  |---|---|
  | `RPermitExpirableSemaphore` | 集群总并发上限，租约到期自动回收防泄漏 |
  | ZSET 队列 | 等待者 FIFO，支持 `ZRANK` 查位次与 `ZREM` 随时退出 |
  | `RAtomicLong` 自增 seq | 做 score，**时间戳会毫秒级撞车从而破坏 FIFO** |
  | entry 存活标记（带 TTL 的 KV） | **ZSET 存的是排队凭证，entry 存的是排队者还活着的证明**；凭证在人不在就是僵尸 |
  | `RTopic` Pub/Sub | 许可释放时跨节点唤醒等待者 |

- **`onAcquire` 回调是整个设计的支点**——它把"业务执行"变成可延迟、可异步、可丢给线程池的对象。业务代码看起来还是直接调用，中间实际插了"排队 → 抢占 → 异步执行"。

- **`setEntryMarker` 必须在 `queue.add` 之前**。反过来会有一个极短窗口：别的节点的 Lua 扫到这个 ZSET 条目却看不到 entry key，直接当僵尸 `ZREM` 掉。

- **`Ticket` 状态机把三条竞态路径收拢**：`PENDING` 单次 CAS 转 `GRANTED` / `TIMED_OUT` / `CANCELLED` 之一，保证业务回调最多触发一次。**`cleanup()` 在 `GRANTED` 下不释放许可**——此时许可已由 `grant()` 内的 `try/finally` 接管，重复释放等于让另一个请求拿到同一个 slot，直接突破并发上限。

- **四阶段抢占，每阶段都不能省**：
  1. 查 `isPending()` 最早短路（用户可能刚入队就关了浏览器）；
  2. `availablePermits()` 轻量预判，**高峰期绝大多数请求在这里被挡住，省掉 Lua 开销**；
  3. Lua 原子 claim 队头窗口（顺带清僵尸）；
  4. `tryAcquire(0, lease, SECONDS)` 拿真实许可。

  **阶段 2 是优化不是判定**，最终以阶段 4 为准；claim 成功但 acquire 失败时，**按原 score 重入队并补写 entry 标记**，保留 FIFO 位次。

- **Lua 里的 `slack = 16`**：只取前 `maxRank` 个成员的话，若队头全是僵尸，存活请求永远进不了窗口。多取 16 个给推进留缓冲。

- **拿到 permit 后还要再查一次状态**。从阶段 1 到这里隔了三次 Redis 往返、少说几十毫秒，前端可能已经断连——**否则就是把许可发给一个不存在的连接，LLM 照跑、token 照烧，而人早就走了。**

- **`grant()` 里先 `permitRef.set` 再 CAS 状态，顺序关键**：CAS 若失败（被 cancel/timeout 抢先），`cleanup()` 能从 `permitRef` 看到值并释放，避免泄漏。

- **`RPermitExpirableSemaphore` 而非 `RSemaphore` 的三个理由**：租约兜底进程崩溃（否则许可永久泄漏，泄漏 N 次总并发就永久降 N）；`permitId` 让重复释放安全失败（普通版 `release()` 只是计数 +1，会让并发虚高）；`permitId` 可跨线程传递，契合异步释放。

## 关键概念/术语

- **并发存量 vs 流量速率**：限流要限的是"同时在跑多少"，不是"每秒进来多少"。
- **两阶段抢占**：Lua claim 队头位置（公平性）与 acquire 真实许可（容量）分离，两步都成才算抢到。
- **entry 存活标记**：排队者还活着的证明，缺失即判定为僵尸条目。
- **`Ticket` 状态机**：`PENDING` → `GRANTED`/`TIMED_OUT`/`CANCELLED`，单次 CAS 转终态。
- **租约（lease）**：许可的自动回收期限，覆盖持有者崩溃的场景。

## 与 xrag 项目的关系

- **这套分布式机制 xrag 整体不做，而且这是同一个判例的第二次适用——[ADR 0002 §4](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 已经拒绝过 `RPermitExpirableSemaphore` 一次了。** 更巧的是仓库里已经有一个几乎同构的实现：[`UploadConcurrencyFilter`](../../../backend/src/main/java/com/app/knowledge/web/UploadConcurrencyFilter.java) 用的就是 `new Semaphore(maxConcurrent, true)`，类注释里写着"单实例下两者能力等价"。ADR 0002 的论证可以逐字复用到这里：**`RPermitExpirableSemaphore` 存在的意义就是防止持有者崩溃导致许可永久泄漏，而本地信号量在 `finally` 里释放即可，进程崩溃时整个信号量随进程一起消失，泄漏问题根本不存在。** 原文自己也承认了这一点——"如果你只部署一台机器，这套方案确实能工作"。**xrag 正好就是那一台机器**，于是 ZSET、自增 seq、entry 存活标记、Lua claim、Pub/Sub 唤醒、租约回收这六样全部不需要。

- **但不能因此把整篇跳过——"排队而不是拒绝"这个产品决策与实例数无关，而 xrag 现有的先例恰好选了相反的策略。** `UploadConcurrencyFilter` 是 `tryAcquire` 带 5 秒超时、拿不到返回 429。原文的核心论证正是**对 RAG 而言 429 是错的**：用户已经按下回车、已经看到"思考中"的圈圈，此时告诉他"系统繁忙"，他会刷新重试制造更多请求。**上传与问答的体验模型不同**——上传是一次性动作，失败了重传很自然；问答是有状态的对话，被拒等于对话断了。**所以 xrag 的正确形态是"本地 `Semaphore` + 排队语义"：拿掉分布式那一层，保留有界等待与超时反馈。** 这两个决定必须分开做，不要因为拒绝了 Redisson 就顺手把排队也一起拒绝了。

- **这一篇正面回答了检查点 [D-04](../PHASE-3-STEP-A-CHECKPOINT.md) 的一半。** D-04 问的是"对话历史与并发许可的存储形态：Postgres / Redis / 进程内"。**并发许可这一半的答案是进程内**，理由就是上面 ADR 0002 那条等价性论证。对话历史是另一半，属于第 2、3 篇的范畴，两者不该被同一个决策绑在一起——**许可是易失的运行态（进程没了就该没了），对话历史是持久业务数据（进程没了必须还在）**，把它们放进同一个存储只会让两边都别扭。这与 [ADR 0005](../../../docs/adr/0005-separate-model-runtime-state.md)"分离模型配置、熔断运行态与诊断历史"是同一种分层直觉。

- **QPS 限流那段论证与部署形态无关，是可以直接采纳的通用洞见**，而且它给 xrag 提供了一个具体的配置依据：**许可数应当按下游模型的并发上限来设，而不是拍脑袋**。xrag 的 catalog 里已经有 `quota-domain`（如 `volcengine-ark-account`）这个概念，**但要注意它与入口排队不是同一层东西**：`QuotaDomain` 解决的是"429 该算到哪个账号头上"（用于熔断归属），入口排队解决的是"同时允许多少个问答在跑"。**前者是事后归因，后者是事前闸门**，两者都需要，不要用一个顶替另一个。

- **等待预算与模型调用 deadline 必须分开设，且相加不能超过 SSE 超时。** Phase 2 工单 08 已经给整条逻辑调用建立了共享 Deadline，那管的是**模型调用**这一段。本篇的 `max-wait-seconds`（建议 20~30 秒）管的是**入队到抢到许可**这一段，发生在模型调用之前。**两段串行相加才是用户实际等待的时间**，而 `SseEmitter` 的超时必须大于这个和——否则会出现"排队 25 秒 + 生成 40 秒"把 SSE 超时撑爆、连接先断的情况。**这三个超时值的关系要在 Step C 的技术方案里画出来，不能各配各的。**

- **`onAcquire` 这个"把业务包成 `Runnable` 交给限流器"的形状，xrag 应当谨慎采纳。** 它确实优雅，但代价是**业务执行的调用栈被彻底切断**——异常不再沿调用链上抛，而是落到线程池的 `UncaughtExceptionHandler` 或被 `try/finally` 吞掉。xrag 已经有 `ApiExceptionHandler` 统一错误响应体的纪律，而这类回调化的执行会绕过它。**若采纳，onAcquire 内部必须有自己的完整异常出口**（映射成 SSE 的错误事件），而不是指望外层兜住。第 15 篇笔记里"流式错误也应当走同一套翻译"是同一个要求。

- **单实例下"排队"的实现可以简单到一个 `Semaphore` + 有界等待，但公平性要显式打开。** `new Semaphore(n)` 默认是非公平的，高并发下可能出现后到先得甚至饥饿。`UploadConcurrencyFilter` 已经写了 `new Semaphore(maxConcurrent, true)`——**`true` 那个参数就是原文用 ZSET + 单调 seq 费尽力气实现的 FIFO**，在单 JVM 内它是免费的。这是一个很好的对照：**同一个语义，分布式下要五个数据结构加一段 Lua，单进程内是构造函数的第二个参数。**

## 值得注意的设计取舍/坑

- **本篇开头"Tomcat 默认 200 个工作线程会被这些 SSE 长连接占满"与第 15 篇的结论直接矛盾，而第 15 篇是对的。** 第 15 篇写得很清楚：Controller 返回 `SseEmitter` 后请求转异步，**Tomcat 线程当场释放**，"长时间占用的是 NIO 连接，不是线程"。本篇却把线程耗尽列为需要排队限流的理由之一。**两篇对同一个机制给出了相反的描述**，而排队限流真正的理由只有下游模型并发上限与业务线程池容量这两条——**Tomcat 线程这一条是错的，不该被当作论据**。若照着这个错误理由去调 Tomcat 线程数，会白花力气还掩盖真正的瓶颈。

- **`chatEntryExecutor` 与信号量是两个管同一件事的闸门，而且它们必须手工保持一致。** 线程池核心/最大线程数设为 `maxConcurrent`、队列用 `SynchronousQueue`，与信号量许可数相同。原文自己说"理论上不会超"、"如果频繁出现说明配置和许可数不匹配"——**也就是说系统的正确性依赖两个独立配置项永远相等，却没有任何代码或启动校验来保证它。** `grant()` 里那条 `RejectedExecutionException` 降级路径，本质上是为这个配置漂移准备的补丁。**更干净的做法是让线程池成为唯一的闸门，或者让信号量许可数从线程池配置派生**，而不是并列两份。

- **`grant()` 提交失败后走的是 `onTimeout` 回调，于是用户收到的提示是"系统繁忙"，而实际发生的是"你已经抢到许可了但我没线程跑你"。** 这两件事在监控上完全不可区分——`onTimeout` 既统计真正等超时的请求，也统计这类内部降级。**排队系统最需要看的指标（等待超时率）被一个不相干的失败混入了**，一旦线程池配置出问题，表现出来的是"等待超时率上升"，会把排查方向引到 `max-wait-seconds` 上去。

- **`Ticket.cancel()` 里 `state.compareAndSet` 的返回值被丢弃了，而 `timeout()` 检查了。** `timeout()` 写的是 `if (!state.compareAndSet(...)) return;`，`cancel()` 写的是 `state.compareAndSet(...)` 然后无条件 `cleanup()`。**也就是说 `cancel()` 在任何状态下都会执行 `cleanup()`**，包括已经 `GRANTED` 的情况。原文解释了 `cleanup()` 在 `GRANTED` 下不释放许可，所以不会出安全问题；但它仍然会执行"从 ZSET 移除、删 entry 标记、注销 poller、取消 future"这几步。**两个终态转换方法用了不同的防护写法，而这种不对称没有任何注释说明是有意的**——读代码的人无法判断这是深思熟虑还是遗漏。

- **entry 标记的 TTL 是"等待预算 + 5 秒缓冲"，但 claim 成功后会 `DEL` 掉它，而重入队时又要 `setEntryMarker(剩余时间)`。** 于是同一个请求的 entry key 在一次排队中可能被写、删、再写多次，**每次重写的 TTL 都基于当时的剩余时间**。这条链路上任何一个环节漏写（比如重入队分支抛异常），条目就会在下一轮 Lua 扫描时被判为僵尸清掉——**而请求本身还活着，还在等**。原文对这个分支写了 `if (!ticket.isPending())` 的补救，但**没有覆盖"重入队成功但 setEntryMarker 失败"**（两个操作不是原子的，且 `setEntryMarker` 在前）。

- **`publishQueueNotify()` 在四个地方被调用，其中"我自己刚拿到许可也要广播"这条的理由是站不住的。** 原文的解释是"可能还有许可剩，让等待者更快进入下一轮"。但**拿走一个许可是让可用数减少的事件**，它不会让任何等待者的处境变好——被唤醒的等待者跑完四阶段只会在阶段 2 被挡回来。**这是一次纯粹浪费的全集群唤醒**，而下一篇要专门讲"防惊群"。**为防惊群设计一个 `PollNotifier`，同时又在减少许可时主动惊群，这两件事是对冲的。**

- **Lua 脚本的僵尸清理是一个不受限的写操作，混在读判定里。** `ZRANGE` 取 `maxRank + 16` 个成员，逐个 `EXISTS`，不存在就 `ZREM`。正常情况下开销很小，但**在"大量节点同时崩溃"这个 entry 标记机制本就是为之设计的场景下**，队头会积压大量僵尸，每个请求的每一轮 claim 都要重复扫描并清理它们。**故障时刻恰恰是这段脚本最重的时候**，而 Redis 执行 Lua 期间是全局阻塞的。`slack = 16` 限制了单次扫描的规模，但没有限制"每个等待者每 200 毫秒都跑一次"的总量。

- **`nextQueueSeq()` 每次入队都是一次独立的 `incrementAndGet()` 往返，与后面的 `queue.add()` 不是原子的。** 若在两者之间进程崩溃，seq 被消耗但没有对应的队列成员——这本身无害（score 只需单调不需连续）。**真正的问题是这两步与前面的 `setEntryMarker` 一起构成了三次独立的 Redis 往返**，任何一步之间崩溃都留下不同程度的残留：只有 entry 标记（会自然过期，无害）、entry + 队列成员但没人推进（靠 TTL 变僵尸后被清，延迟一个等待预算）。**入队这个看起来最简单的动作，实际是整个流程里唯一没有被原子化保护的部分**，而 claim 那一步反而用 Lua 做到了原子。

- **"VIP 用户给更小的 score"这个被当作 ZSET 隐性好处提出的扩展，会直接破坏 entry 标记与等待预算的假设。** 一个 score 为负的 VIP 持续插队，普通用户的 `liveRank` 永远压不进 `maxRank` 窗口，它的 entry 标记会在 `max-wait + 5 秒` 后过期，然后**被 Lua 当作僵尸 `ZREM`**——而这个用户其实还活着、还在等。此后它靠 `scheduleQueuePoll` 重入队还是彻底掉队，取决于下一篇的实现细节。**FIFO 是这套机制里很多不变量的隐含前提，"顺序控制权"不是免费的。**
