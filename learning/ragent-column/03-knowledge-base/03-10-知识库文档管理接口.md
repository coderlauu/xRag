# 《AI大模型Ragent项目》——知识库文档管理接口

> 原文链接：https://t.zsxq.com/eGdy4
> 所属分组：03-knowledge-base AI知识库建设

## 一句话概括

讲文档生命周期管理的三个"事务型"接口——`delete`（删除）、`update`（更新配置）、`enable`（启用/禁用）——看起来简单，实际都涉及多表联动、事务边界设计和幂等性；核心共性是都要禁止对 RUNNING 状态的文档操作，都要保证数据库和向量库的一致性；`enable` 接口最值得学习，把耗时的 Embedding 重算移到事务外、用编程式事务把数据库+向量库操作压缩到几十毫秒。

## 核心内容提炼

- **三接口横向对比**（HTTP方法/路径/破坏性/事务范围/幂等性/关联清理/调度同步/状态校验）：`delete`（DELETE，破坏性高，需清理chunk/schedule/log/vector/file五类关联数据，非严格幂等——重复删会抛异常）；`update`（PUT，破坏性中，同步调度配置，部分幂等）；`enable`（PATCH，破坏性低，同步调度状态，**严格幂等**——先检查当前状态，已是目标状态直接返回）。

- **三接口的共同点**：① 都用事务保护多表操作（`delete`/`update` 用声明式 `@Transactional`；`enable` 用编程式事务 `TransactionOperations`，为了把耗时的 embedding 调用移出事务）；② **都检查 `status != RUNNING`**——因为分块是异步的，如果允许在分块运行时删除/修改文档，会出现"分块任务找不到文档记录""分块任务用的还是旧配置导致chunk和配置不一致""向量库和数据库不一致（正在写向量库时数据库记录被删）"这几类问题；③ 都涉及多表联动（不只是改 document 表，还联动 chunk/schedule/chunk_log 表）。

- **事务边界的通用原则**：数据库表操作 + 向量库操作（因为 pgvector 就是 PostgreSQL 表，`JdbcTemplate` 自动加入 Spring 事务，和业务表强一致）都在事务内；**文件删除永远在事务外**（`deleteStoredFileQuietly`——方法名里的 `Quietly` 就是"静默失败"：文件删除失败不抛异常只记日志，因为文件系统不支持事务，且文件删除失败不影响核心业务，数据库/向量都已经删了，文件最多占点空间，可以靠定时任务清理，为此回滚整个事务代价太大）。

- **`delete` 的六步流程**：① 查文档校验存在+非RUNNING；② 依次删除三类关联数据（chunk记录、schedule定时任务、chunk_log分块日志）；③ **逻辑删除**文档本身（`deleted=1`，MyBatis Plus 的 `deleteById` 在配置了逻辑删除后会自动转成 `UPDATE ... SET deleted=1` 而非真正 DELETE）；④ 删除向量库中的向量；⑤ 静默删除对象存储文件。**为什么用逻辑删除而不是物理删除**——四个理由：数据审计（谁在什么时候删了什么，物理删除后无法追溯）、误删恢复（手抖删错了还能恢复，把 `deleted` 改回0）、关联数据追溯（虽然chunk/log这些关联表是真删了，但文档本身的历史记录还在，方便排查"这个文档为什么分块失败过10次"这类问题）、合规要求（金融/医疗行业常有数据保留期规定）。代价是数据库会越来越大、查询都要加 `deleted=0` 条件，可以靠定时任务归档/物理删除超保留期数据来缓解。

- **`update` 的关键设计——CHUNK/PIPELINE 两种处理模式的字段互斥**：切换到 CHUNK 模式时更新 `chunkStrategy`+`chunkConfig`、**同时清空 `pipelineId`**；切换到 PIPELINE 模式时校验并更新 `pipelineId`、**同时清空 `chunkStrategy`+`chunkConfig`**。**为什么必须清空互斥字段**：如果不清空，切换模式时旧字段残留，下次切回原模式时系统不知道该用新配置还是旧配置——这保证"任何时候文档的处理配置都是完整且唯一的"。调度相关字段（`sourceLocation`/`scheduleEnabled`/`scheduleCron`）**只有 URL 来源的文档才能更新**，且cron同样要做格式合法性+最小间隔（60秒）校验。更新调度任务时用的是 **`upsertSchedule`（不存在则创建）而非 `syncScheduleIfExists`（只更新已有的）**——因为用户可能是第一次给已上传的文档配置定时同步。

- **`update` 明确不自动触发重新分块**（呼应 03-06/03-07 反复强调的"接口职责分离"原则）：三个理由——职责分离（update管配置，startChunk管触发，混在一起职责就乱了）；用户可能只是想改个名称，不想触发耗时分块（自动触发会让用户困惑"我只改了名字怎么又开始分块了"）；避免意外的耗时操作拖慢体验。是否重新分块，由用户手动决定、显式调用 startChunk。

- **`enable` 是三个接口里"看起来最轻但实际最重"的一个**，核心流程：① 查文档校验存在+非RUNNING；② **幂等性检查**——已是目标状态直接 `return`，避免重复触发数据库更新/调度同步/chunk更新等一整套操作（但作者提醒这不能替代防重复提交机制，因为并发场景下这个检查规避不了真正的同时执行）；③ 提前查一次知识库信息（`collectionName`），启用/禁用两个分支都要用，避免重复查询；④ **启用时把 Embedding 计算提前到事务外**——从数据库读出 chunk 内容，调 Embedding API 计算好向量存在内存里（这一步对内容多的文档可能耗时十几秒），再开一个只做数据库写入的短事务；⑤ **编程式事务**里原子提交四件事：更新 `document.enabled` 字段、`syncScheduleIfExists` 同步调度任务状态（禁用暂停/启用恢复）、批量更新 chunk 表的 `enabled` 字段（保证检索时chunk状态和文档状态一致）、向量库写入或删除（禁用删向量、启用重建向量索引）。**为什么禁用时必须删除向量**：检索是直接查向量库的，如果只在数据库层面标记禁用而不动向量库，向量库里的内容照样会被检索到，禁用形同虚设——作者还提到一个备选方案（在向量元数据里加 `enabled` 字段，检索时过滤）但认为"每次查询都要带这个必查条件，没必要"，选择了更直接的"删了重建"方案。

- **`enable` 事务缩短的量化效果**：把耗时的 Embedding 调用移出事务后，"事务持有时间从十几秒降低到几十毫秒"——这是一个非常具体的性能优化说明，直接对应 03-06/03-07 反复强调的"事务内不做耗时操作"原则的具体量化案例。

- **`enable` 的三个典型应用场景**：临时下线有问题的文档（不想删除，修复后再启用）、A/B测试不同文档集合的检索效果、定时文档控制（比如促销活动文档只在特定时间段生效）——相比 delete，`enable` 更轻量、可随时恢复，适合临时性状态控制。

## 关键概念/术语

- **逻辑删除（logical delete）**：用 `deleted` 标记位代替真正的 DELETE，MyBatis Plus 原生支持自动转换。
- **字段互斥设计**：CHUNK 与 PIPELINE 两种处理模式各自的配置字段互斥，切换时必须清空对方字段以保证配置的完整唯一性。
- **`upsertSchedule` vs `syncScheduleIfExists`**：前者不存在则创建（适合 update，用户可能首次配置），后者只更新已有的不创建新的（适合 enable，只改启用状态不该凭空建调度任务）。
- **编程式事务（`TransactionOperations`）**：相比声明式 `@Transactional` 注解，能精确控制"只有这一小段代码在事务里"，用于把耗时的外部调用移出事务范围。

## 与 xrag 项目的关系

- **`enable` 接口的"Embedding计算移出事务+编程式事务收敛数据库操作"这个模式，应该作为 xrag 所有涉及外部API调用+数据库写入的接口的标准写法**——这是 03-06（upload不加事务）、03-07（runChunkTask不加事务只有persist操作用事务）之后，第三次遇到同一个原则的不同应用场景，说明"外部耗时调用绝不能包进数据库事务"是这个项目从头到尾贯彻的架构约束，xrag 技术方案应该把这条原则显式写成一条通用设计规范，而不是每个接口分别决策。
- **"禁用时必须同步删除向量，否则检索层面看不出区别"这个坑，是 xrag 知识库模块设计时必须提前想到的**——如果只在业务表打个enabled标记就以为完事了，检索链路（Step E，05-qa-pipeline分组会详细讲）如果直接查向量库而不联查业务表状态，就会出现"文档已禁用但还能被检索到"的真实bug。这提示 xrag 的检索设计需要明确：向量库本身要么不含被禁用文档的数据（本文方案），要么检索时必须联查业务状态过滤（本文提到但放弃的备选方案）——两者必须二选一，不能假设"业务表标了禁用，向量库自然也生效了"。
- **CHUNK/PIPELINE 字段互斥设计**，应该在 xrag 的知识库文档数据模型设计阶段就纳入约束（比如用数据库 CHECK 约束或应用层校验强制"两组字段不能同时非空"），而不是仅靠代码里"记得清空"来维持一致性。
- **逻辑删除 vs 物理删除的四点论证**，可以直接作为 xrag 数据模型设计 ADR 的参考——考虑到 xrag 是单用户学习项目，合规/审计要求不强，但"误删恢复"和"关联数据追溯"这两条理由依然成立，值得对文档表采用逻辑删除。

## 值得注意的设计取舍/坑

- **幂等性检查（"已是目标状态直接返回"）不能替代并发控制**——原文明确提醒这一点：单纯的状态判断规避不了真正的并发同时执行（两个请求同时查到"未是目标状态"然后都往下执行），需要配合防重复提交机制（比如幂等token、分布式锁）才能真正杜绝并发问题，不能想当然认为"检查了当前状态就够了"。
- **`update` 接口不自动触发分块，是刻意的产品决策而非疏漏**——如果在其它项目里看到类似"只改配置不触发重新计算"的设计，不要默认这是没做完的功能，先确认是不是这里同样的"职责分离+避免意外耗时操作"的考量。
- **文件删除失败静默处理（`deleteStoredFileQuietly`）会产生"孤儿文件"，这是刻意接受的风险**，和 03-06 篇"上传成功但DB插入失败"产生孤儿文件是对称的取舍——一个是"DB删了文件没删干净"，一个是"文件传了DB没插成功"，两种孤儿数据的治理思路应该统一（都是靠定时任务扫描比对+清理），不要针对每种孤儿数据单独发明一套清理机制。
- **"向量库里删向量 vs 元数据加enabled字段过滤"这个二选一**，作者选了前者但也诚实交代了后者的存在和放弃理由（每次检索都要带必查条件，认为没必要）——这提醒在做类似技术选型时，即使选了更简单的方案，也应该像这样明确记录"考虑过的替代方案+放弃理由"，方便后来者理解决策背景而不是重新纠结一遍。
