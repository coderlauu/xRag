# 《AI大模型Ragent项目》——Ollama安装与模型调用实战

> 原文链接：https://t.zsxq.com/frBrF
> 所属分组：02-bootstrap-and-deployment 本地开发与模型部署环境

## 一句话概括

本篇用“安装服务、选择并拉取 Chat/Embedding 模型、分别验证原生 API、再切换 Ragent 候选配置”的路径跑通本地模型；对 xrag 而言，可借鉴的是分层验证方法，而不是直接照搬模型、维度或“只改配置即可无缝切换”的结论。

## 核心内容提炼

### 1. 安装后先验证服务边界

Ollama 在 macOS、Windows 和 Linux 上分别可通过桌面安装包、包管理器或官方安装脚本部署。Linux 安装通常还会注册 systemd 服务，服务环境变量需要通过 systemd override 配置。

安装完成后的最小验证顺序是：

1. `ollama --version` 确认 CLI。
2. 请求 `http://localhost:11434` 确认服务监听。
3. `ollama list` 确认模型清单可访问。

把监听地址改为 `0.0.0.0` 会允许其他机器访问，但同时扩大攻击面；这必须与网络隔离、认证和访问控制一起设计。

### 2. 选模型要同时看能力、资源和许可证

Ollama 模型页面提供参数规模、量化格式、磁盘体积、上下文长度、输入类型、工具调用能力和许可证等信息。选择模型不能只看参数量或下载热度：

- 显存/统一内存决定可加载的权重规模。
- 上下文窗口还会通过 KV Cache 增加运行内存。
- Chat、Embedding、视觉和工具调用是不同能力，不能凭模型家族名称推断。
- 企业使用前必须核对目标 tag 对应的真实许可证。
- `latest` 是可变指针；需要复现时应固定 tag 和 digest。

文章示例为 Chat 与 Embedding 各拉一个 8B fp16 模型，合计约 31GB 磁盘，并可能需要 30GB 以上运行内存。这只是课程环境的选择，不是 xrag 的推荐基线。

### 3. 先独立验证 Chat 与 Embedding API

在接入应用前，先绕过业务代码直接请求：

- `/api/chat`：检查模型能否生成、消息结构和同步/流式行为。
- `/api/embed`：检查输出数组、向量维度和批量输入行为。

这样能把“模型服务故障”与“应用路由或解析故障”分开。应用集成测试还需要验证超时、取消、错误码、模型不存在、资源不足和并发请求。

### 4. Ragent 通过候选模型配置切换 Provider

参考 Ragent 已有 Ollama 专用 Chat/Embedding 客户端、候选模型选择器和路由服务。示例通过修改 Chat 与 Embedding 的 `default-model`，将本地 Ollama 候选提到队首，并保留云端候选作为失败回退。

该描述绑定课程文章版本。对参考仓库 `60e49e1`（2026-07-23）的复核显示，其 Ollama 配置已改为 `/v1/chat/completions` 和 `/v1/embeddings`，不再是文章中的 `/api/chat` 和 `/api/embed`；后续引用 Ragent 行为必须同时记录所检查的提交。

这里有三个不同标识：

- Provider：服务类型，如 Ollama。
- Candidate ID：应用内部的候选配置标识。
- Model ID/Tag：Provider 实际接收的模型名称。

`default-model` 指向 Candidate ID，而非 Ollama 模型 Tag；混淆它们会导致流量仍走原候选。

### 5. 配置切换后要用双重证据验流量

仅看到问答成功不能证明流量走了本地，因为候选路由可能回退云端。文章建议同时查看：

- `ollama ps` 中目标模型是否已加载。
- 应用 Trace/日志中是否命中 Ollama Provider 节点。

Embedding 链路也应有等价的可观测证据。文章所示版本对 Embedding 缺少对应 Trace，这是参考实现的观测缺口。

### 6. Chat 与 Embedding 的资源竞争需要实测

两类模型可能同时驻留，也可能因显存不足相互驱逐。频繁卸载会让每次切换都产生冷启动。量化模型、模型规模、keep-alive、最大驻留数和实际业务时序需要一起评估。

“延长 keep-alive 能减少卸载次数”只在资源足够且工作负载允许时成立；显存不足时，延长驻留时间不能让两个模型凭空同时容纳。

### 7. 向量维度相同不代表可混用

文章示例通过 Ollama `dimensions` 参数把模型原生向量输出调整为 1536 维，并据此认为可以与原有 1536 维云模型向量混用。这个结论不能直接成立。

不同 Embedding 模型即使输出维度相同，坐标空间、归一化方式和相似度分布仍可能完全不同。查询向量与库内文档向量必须来自同一且可追溯的 Embedding 配置；更换模型、模型版本、量化方式或输出维度时，默认应重建全部文档向量，并通过离线评测确认迁移效果。

## 关键概念/术语

- Candidate ID：应用内部用于选择模型候选的稳定标识。
- Model Tag：Provider 侧的具体模型变体名称。
- Chat Model：面向消息输入生成文本或结构化结果的模型。
- Embedding Model：把文本映射到向量空间以支持相似度检索的模型。
- 向量空间：Embedding 模型学习得到的语义坐标体系；维数相同不代表空间相同。
- 原生 API：Provider 自己定义、可暴露特有参数和指标的接口。
- Provider 回退：当前模型调用失败后按候选策略转向其他服务。
- 模型驻留：权重加载到内存/显存并保持可立即推理的状态。
- 模型驱逐：因空闲策略或资源竞争而从内存/显存卸载模型。
- 分层验证：按服务、模型 API、应用路由和端到端业务逐层定位问题的方法。

## 与 xrag 项目的关系

xrag 当前没有 Ollama Provider、模型候选路由和向量入库链路，因此本篇命令不应直接成为当前启动前置条件。

- Phase 1 若接入 Embedding，应把 Provider、模型 ID、版本/digest、输出维度、归一化和距离度量共同记录为“向量配置版本”。
- 每个 Document Chunk 应能追溯其向量配置版本，禁止查询时静默混用不同空间的向量。
- Provider 验证宜按“服务可达 → Chat/Embedding 原生调用 → xrag 客户端 → 端到端链路”分层执行。
- 本地 Provider 若保留云端回退，必须显式记录实际命中的 Provider；敏感数据也不能未经判断自动回退到云端。
- Ollama 应保持可选，不下载 30GB 级课程模型作为普通开发或 CI 的默认步骤。
- xrag 后续若实现 Embedding 路由，需要补齐调用指标和 Trace，不能只观测 Chat。

## 值得注意的设计取舍/坑

- **同维向量不可默认混用**：这是本篇最重要的纠偏；切换 Embedding 模型通常意味着全量重建索引。
- **课程模型规格不是系统需求**：8B fp16、1536 维和具体 Qwen tag 都应由 xrag 数据集与硬件评测决定。
- **回退可能掩盖本地失败**：最终回答成功时仍要记录实际 Provider、候选、重试和回退原因。
- **本地失败回退云端可能造成数据出域**：必须在路由前施加数据策略，而不是失败后无条件回退。
- **模型能力标签需要实测**：页面标注支持 tools/vision，不代表目标提示、语言和量化版本下质量可用。
- **下载与安装命令有供应链风险**：生产环境不应未经校验直接执行远程安装脚本；应固定版本、校验来源并纳入制品管理。
- **监听所有网卡不等于团队服务就绪**：还缺认证、TLS、限流、审计和网络策略。
- **效果判断不能只靠一次对话**：文章对小模型质量的主观观察只能作为线索，xrag 需要固定评测集比较质量、延迟和资源成本。
- **原生与兼容 API 是明确取舍**：原生接口获得特有参数和指标，但增加 Provider 专用代码；兼容接口降低实现量，但仍要处理行为差异。
