# 《AI大模型Ragent项目》第10小节：向量检索策略与召回优化

> 原文链接：https://t.zsxq.com/Sx4gA
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

纯向量检索对精确关键词（订单号、型号、专有名词、数字编号）天生不敏感，容易把关键信息淹没在语义相似度里；本文讲解如何用 BM25 关键词检索、向量+关键词的混合检索（RRF 排名融合）、以及基于 Cross-Encoder 的重排序三层手段，把召回和排序质量逐级补齐，并给出 Milvus 2.5+ 原生实现的 Java 代码示例。

## 核心内容提炼

1. 纯向量检索的结构性短板
   - 电商客服场景举例：用户问"订单号 2026012345 的物流状态是什么"，向量检索会把整句话理解成"物流/订单"这一类泛化语义，返回一批语义相关但不包含该具体订单号的通用规则文档，真正命中订单号的那一条反而排不到前面。
   - 三类典型翻车场景：(1) 精确关键词/型号丢失，如"iPhone 16 Pro Max"被泛化成笼统的"退货"语义；(2) 专有名词和缩写，如 RMA 这种业务缩写，向量模型倾向于把它理解成通用退货语义，而不是直接命中专门讲 RMA 流程的文档；(3) 数字和编号，如"2026 年春节发货安排"，因为历年记录语义都相近，向量检索不一定优先返回当年那条。
   - 根本原因：Embedding 模型的优势是语义泛化、同义词、跨语言理解，但对"精确的、离散的 token"（数字、编号、专有名词）天然不敏感，容易把它们融进整体语义而丢失区分度；反过来关键词检索擅长精确匹配但无法处理同义词和语义相近的表达，两者是互补而非替代关系。

2. BM25 关键词检索算法
   - BM25（Best Matching 25）是经典的、纯统计的关键词相关性算法，是 Elasticsearch 等搜索引擎的默认排序算法，不做语义理解，只统计词频和文档频率。
   - 三个核心因子：
     - 词频 TF：词出现次数越多相关性越高，但做了饱和处理——出现次数从 1 涨到 10 分数涨得快，10 涨到 100 涨得很慢，目的是避免长文档靠堆砌关键词占便宜。
     - 逆文档频率 IDF：一个词在全部文档中出现得越少（越稀有），区分度越高、权重越大；"的""是"这类常见词几乎没有权重。
     - 文档长度归一化：长文档天然更容易命中查询词，BM25 对超过平均长度的文档打折、短文档提权，避免长文档系统性占便宜。
   - BM25 计算成本远低于向量检索（不需要调用 Embedding 模型，只需统计词频），但完全无法处理同义词和语义相近但措辞不同的查询。
   - Milvus 从 2.5 版本开始原生支持 BM25：建表时给 VarChar 字段开启 analyzer（分词），Milvus 自动生成倒排索引和稀疏向量做 BM25 检索，不需要额外部署 ES。若 Milvus 版本低于 2.5，或对中文分词要求更高（自定义词典、同义词扩展），可以改用 ES 做关键词检索、Milvus 做向量检索、应用层融合两路结果——架构更复杂但全文检索能力更强。

3. 混合检索（Hybrid Search）与 RRF 分数融合
   - 基本思路：同一个 query 同时跑向量检索和 BM25 检索两路，再把两路结果融合成一个最终排序。
   - 两种落地架构：
     - Milvus 原生方案（本文采用）：架构简单，不需要维护两套系统、不存在数据双写一致性问题，Hybrid Search API 原生支持 RRF 融合，运维成本低；代价是全文检索能力和中文分词能力弱于 ES（分词器插件、复杂布尔/短语查询、聚合等能力有限）。
     - ES + Milvus 双系统：ES 做关键词检索、Milvus 做向量检索、应用层做融合；全文检索能力强、中文分词生态好（IK 分词器等）、查询语法丰富；代价是运维两套系统、数据双写一致性风险、融合逻辑要自己写、故障面扩大。
     - 选型建议：多数 RAG 场景直接用 Milvus 原生方案；只有对中文分词/复杂查询语法有硬性要求，或者已有 ES 基础设施时才考虑双系统。
   - 分数融合的核心难题：向量检索输出余弦相似度（0~1），BM25 输出的相关性分数值域是 0 到正无穷，两者量纲完全不同，不能直接相加；简单归一化后相加也有问题，因为归一化会因分数分布集中或分散程度不同而扭曲真实差异。
   - 解决方案是 RRF（Reciprocal Rank Fusion，倒数排名融合）：不看分数本身，只看每个候选在各路检索里的排名。公式为 RRF(d) = Σ 1/(k + rank_i(d))，k 是平滑常数（业界惯例取 60），对每一路检索的排名取倒数后求和；某候选在两路检索里排名都靠前，RRF 分数就越高。
   - 文章用一个 7 条候选的手算例子演示融合过程：向量检索排序 [A,B,C,D,E]、关键词检索排序 [C,A,F,B,G]，融合后最终顺序是 A、C、B、F、D、E、G——因为 A 和 C 在两路里排名都靠前，拿到了最高的复合分数。RRF 的价值在于不需要复杂的分数归一化、对分数尺度差异不敏感、鲁棒性强，是当前混合检索融合策略的事实标准。
   - 一个基于 6 条示例数据的实测对比（query 为"订单号 2026012345 的物流状态"）：纯向量检索返回全部 6 条（Top-1 相似度 0.840，但语义相关却不含订单号的"订单查询入口"这条也拿到 0.816 高分，体现向量检索高召回但会把语义相关的非精确匹配内容排得很高）；纯 BM25 只返回 1 条结果（其余 5 条因关键词重叠太少被 drop_ratio_search=0.2 的阈值过滤掉），体现 BM25 高精度、低召回的特性；混合检索 Top-1 的 RRF 分数（0.0328）显著高于 Top-2（0.0161），因为 Top-1 在两路检索里都排第一拿到双倍加分。作者指出在这个 6 条数据的小样例里三种模式的 Top-1 恰好一致，混合检索的互补优势不算明显，但在数万到数百万条 chunk 的真实生产环境下这个优势会更显著。
   - Milvus 原生混合检索的 Java 实现要点：Collection schema 里除了 dense 向量字段（FloatVector），还要建一个 SparseFloatVector 字段和一个 BM25 Function（inputFieldNames 指向原文 text 字段，outputFieldNames 指向 sparse 字段，由 Milvus 自动生成稀疏向量，不需要手工计算）；索引层面 dense 字段用 COSINE 度量，sparse 字段用 BM25 度量；检索时分别构造 dense、sparse 两个 AnnSearchReq（各自的 topK，示例里都设为 20）传入 HybridSearchReq，ranker 参数指定 RRFRanker(k)（示例 k=60），最终返回融合后的 finalTopK（示例设为 8，实际展示取了 6）结果。

4. 重排序（Reranking）
   - 为什么需要：召回阶段（向量/BM25/混合检索）追求的是尽量不漏掉相关结果，但排序未必精准；而最终喂给 LLM 的上下文窗口很小，真正决定答案质量的是 Top-3/Top-5 这几条排序是否正确——如果 Top-1 不相关，LLM 很容易被带偏生成错误答案。
   - 基本流程：先用向量/混合检索快速召回一批候选（比如 Top-20 或 Top-50），再用重排序模型逐个给候选和 query 的相关性打分，按新分数重排后取最终 Top-K（比如 Top-5）给 LLM。
   - Bi-Encoder 与 Cross-Encoder 的本质区别：Bi-Encoder（Embedding 模型的工作方式）把 query 和 chunk 分别独立编码成向量再算相似度，速度快、可以提前把 chunk 向量算好存起来，但因为两者是独立编码的，捕捉不到两者之间细粒度的交互信息，精度有限；Cross-Encoder 把 query 和 chunk 拼接后一起输入模型，能看到两者完整的交互关系，精度更高，但每个 (query, chunk) 对都要单独跑一次模型推理，速度慢。
   - 为什么不能全程用 Cross-Encoder 做检索：如果知识库有 100 万条 chunk，每次查询都要对 100 万个 (query, chunk) 对分别做一次 Cross-Encoder 推理，延迟和成本都不可接受。所以工程上必须分两阶段：先用便宜的 Bi-Encoder 做粗召回（延迟低、覆盖面广），再用精确但慢的 Cross-Encoder 对缩小后的候选集（20~50 个）做精排序。
   - 文中横向对比了几款主流 Reranker（截至 2026 年 2 月）：BAAI/bge-reranker-v2-m3（轻量、中文效果稳定、部署灵活，适合预算敏感且要中文效果的场景）；Qwen/Qwen3-Reranker-8B（长文本能力强、支持 instruction 定制，适合行业问答和复杂意图排序）；Cohere rerank-v4.0（商业 API 成熟，适合海外或多语言产品化场景）；jina-reranker-v2-base-multilingual（多语言支持好，适合跨语言场景）。本文示例调用 SiliconFlow 提供的 Reranker API。
   - Java 实现要点：把混合检索候选（documents 数组）连同 query 一起 POST 给 /v1/rerank 接口，指定 model、top_n、return_documents=true；如果用 Qwen3-Reranker 还可以额外传一个 instruction 参数（比如让模型优先排序包含订单号与时间状态的文档）来定制排序偏好；接口返回每个候选的 relevance_score，按分数降序即为最终排序。
   - 效果对比示例（query 为"iPhone 16 Pro Max 拆封后还能退吗"）：混合检索未重排时 Top-1 是笼统的"七天无理由退货说明"；重排后 Top-1 变成精确匹配型号的"iPhone 16 Pro Max 退货政策"，同时把提到"拆封"这个关键限定词的条目也提到了前面。这说明重排序的价值不在于多召回几条，而在于把真正该进上下文窗口的那几条排到最前面。

5. 完整检索策略的选型与调优
   - 四种策略（纯向量、纯 BM25、混合检索、混合检索+Rerank）在召回覆盖、Top-3 精度、延迟、成本上依次递增：纯向量最省但精度一般，混合检索+Rerank 最贵但精度最高。
   - 选型对照：数据量小且 query 基本是自然语言，用纯向量检索就够；query 经常包含订单号/型号/专有名词，用混合检索补上精确匹配能力；对答案准确率要求高、能接受一点延迟，用混合检索+重排序；成本敏感、不想额外调用 Reranker API，只用混合检索（RRF 融合本身效果已经不错）；已有 ES 基础设施且对中文分词要求高，用 ES+Milvus 双系统。
   - 给出一组可直接上线试跑的经验参数：Dense topK=20（漏召回就加大、延迟高就减小），Sparse topK=20（query 关键词多时可升到 40），融合 RRF 常数 k=60（两路结果波动大时优先保持默认值），Rerank 候选数=30（精度不够可升到 50，但要盯延迟），最终返回 K=5（结合 LLM 上下文窗口调整）。
   - 强调一个容易被忽略的调优顺序：应该先确认召回阶段真的把相关 chunk 都召回进了候选池（用 Recall@20 / Recall@50 衡量），再去优化排序精度（用 MRR、nDCG@10 衡量），最后才看人工标注准确率、用户追问率、答非所问率这类业务指标。很多团队反过来直接死磕 Reranker 参数，但如果召回阶段已经把关键 chunk 漏掉了，后面无论怎么重排都补不回来。

## 关键概念/术语

BM25（Best Matching 25）：基于词频、逆文档频率和文档长度归一化的经典关键词检索算法，不理解语义，只做统计匹配。
TF（词频）：一个词在文档中出现的次数，BM25 对其做饱和处理防止长文档靠堆词占便宜。
IDF（逆文档频率）：衡量一个词在全部文档中的稀有程度，越稀有权重越高，越有区分度。
Hybrid Search（混合检索）：同时执行向量检索和关键词（BM25）检索，再把两路结果融合成一个最终排序的检索策略。
RRF（Reciprocal Rank Fusion，倒数排名融合）：只依赖候选在各路检索中的排名（不依赖原始分数）做融合的排序算法，对每路排名取 1/(k+rank) 后求和，k 通常取 60。
Bi-Encoder（双编码器）：query 和文档分别独立编码成向量再算相似度的模型结构，速度快但精度受限，是常见 Embedding 模型的工作方式。
Cross-Encoder（交叉编码器）：把 query 和文档拼接后一起输入模型联合编码、直接输出相关性分数的结构，精度高但推理慢，常用于 Reranker。
Reranker（重排序模型）：对粗召回候选集用 Cross-Encoder 做二次精细打分排序的模型，用于提升最终 Top-K 的排序质量。
drop_ratio_search：Milvus BM25 检索里的过滤阈值参数，相关性分数低于该阈值的候选会被丢弃，是纯 BM25 检索"高精度低召回"现象的直接原因之一。
Recall@K / MRR / nDCG@10：分别衡量召回覆盖率、第一个相关结果排名倒数的均值、Top-10 排序质量的三个检索评估指标。

## 与 xrag 项目的关系

这一节直接对应 xrag 检索模块的核心架构决策：
- 检索层需要同时具备向量检索和关键词（BM25）检索两条通路，不能只依赖 Embedding 相似度，否则订单号、工单号、型号等精确标识符类查询会系统性漏召回。
- 如果 xrag 基于支持原生全文检索的 Milvus 版本（2.5+）构建，优先采用"Milvus 原生混合检索 + RRFRanker"的架构，避免引入 ES 带来的双写一致性和多系统运维负担；只有在中文分词要求很高或团队已有 ES 基础设施时才需要评估 ES+Milvus 双系统方案。
- 检索链路应设计成"向量+BM25 各自粗召回（topK 约 20）→ RRF 融合 → Rerank 精排（候选 30~50 条）→ 最终 TopK（约 5 条）"的多阶段结构，而不是把所有工作都压在一次向量检索上；这套参数可以作为 xrag 检索模块的初始默认配置。
- 调优和线上监控应按"先看召回覆盖（Recall@20），再看排序质量（MRR/nDCG@10），最后看业务指标"的顺序推进，这一顺序建议可以直接写入 xrag 检索模块的调优 SOP 或验收清单，避免团队一上来就调 Reranker 参数而忽视召回阶段的问题。
- 重排序模型选型上，如果 xrag 面向中文场景且预算有限，可优先评估 BAAI/bge-reranker-v2-m3；如果需要复杂意图排序或想用 instruction 定制排序偏好，可评估 Qwen3-Reranker-8B。

## 值得注意的设计取舍/坑

- 两种分数（余弦相似度 vs BM25 相关性分数）量纲完全不同，直接相加或简单归一化后相加都不可靠——归一化本身会因为分数分布集中或分散而扭曲真实差异，这是容易被忽略的一个坑；RRF 通过只看排名而不看原始分数规避了这个问题。
- BM25 在候选词汇重叠度低的场景下会出现"过滤阈值把大部分候选都过滤掉，只剩个别结果"的现象，即高精度但极端低召回，这是 BM25 的固有特性而不是配置错误，需要结合混合检索来弥补。
- 不能因为 Cross-Encoder 精度更高就直接拿它做全量检索——在百万级 chunk 规模下逐个做 Cross-Encoder 推理的延迟和成本不可接受，必须坚持"Bi-Encoder 粗召回 + Cross-Encoder 精排"的两阶段架构。
- 调优顺序容易本末倒置：如果召回阶段已经漏掉了关键 chunk，后续无论怎么调 Reranker 参数都无法把它找回来，必须先确保召回覆盖率达标，再去优化排序精度，最后再看业务指标。
- Milvus 原生 BM25 方案架构简单、一致性好，但中文分词能力和查询语法（布尔查询、短语查询、聚合等）弱于 ES，如果业务对这些有强需求，选择原生方案会在后期遇到能力天花板，需要提前评估是否要切换到 ES+Milvus 双系统。
