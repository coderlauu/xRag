# 《AI大模型Ragent项目》——工具调用架构设计指南

> 原文链接：https://t.zsxq.com/cj66k
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

Function Call 和 MCP 只解决“如何调用”，工具定义本身才决定模型能否选对工具、传对参数和利用返回结果；高质量工具应职责单一、参数最少、写操作幂等、描述明确，并以信息适中的结构化契约返回成功或错误。

## 核心内容提炼

### 1. 工具是一份面向模型的业务接口

模型并不理解工具背后的代码，只能根据名称、描述、参数 Schema 和历史调用结果做选择。把年假、病假、工资、考勤都塞进 `getUserInfo(infoType)`，会额外要求模型正确选择枚举值，也会把不同数据源、权限和变更节奏耦合在一起。

工具设计质量会直接反映为四类线上问题：选错工具、参数格式错误、失败后无从修正，以及不必要的重复调用。问题不能都归因于模型能力。

### 2. 四项工具定义原则

1. **单一职责**：一个工具只表达一个清晰业务动作。与其提供一个带大量模式参数的通用工具，不如拆成 `getUserAnnualLeave`、`getUserSickLeave` 等边界明确的工具。
2. **参数最小化**：只让模型提供没有上下文就无法推导的参数。`topK`、阈值、是否重排、排序方式等系统策略通常应由工具实现或配置决定，而不是每次要求模型填写。
3. **写操作幂等**：查询天然适合重试，创建订单、提交报销、发邮件等操作必须使用 `requestId` 等幂等键，防止网络重试、模型重试或用户重复提问造成重复副作用。
4. **返回结构化**：成功结果应提供足够回答当前问题和合理追问的字段；错误结果应有稳定错误码、可理解消息和必要细节。纯文本限制模型二次组织，返回整张业务对象则浪费 Token 并泄露无关数据。

### 3. 描述决定模型的路由质量

一个有效的工具描述至少包含：

- 功能：工具具体做什么，结果包含什么。
- 场景：用户用哪些常见说法表达这个需求。
- 参数：含义、格式、范围和示例。

相似工具必须写出差异和边界。例如年假与病假都属于“假期”，描述里要分别强调“带薪休假”和“因病请假”；无法从用户表达中判断时，应允许模型追问，而不是赌一个工具。

“优先使用”“仅当……”可作为路由提示，但不能代替真正清晰的业务边界。描述应使用主动、肯定、具体的语言，避免宽泛词和容易被模型反向理解的否定句。

### 4. 参数 Schema 需要真实约束

- 必填参数只保留工具执行不可缺少的值；有合理默认值的参数保持可选。
- 默认值应覆盖主流场景，避免极端值或模糊的 `null`/空字符串语义。
- 工具实现必须重新执行类型、格式、范围、权限和业务规则校验，不能因为模型通过了 JSON Schema 就信任输入。
- 参数命名应语义化且风格一致；枚举必须提供准确可选值，不能只在自然语言描述里暗示。
- 校验错误需要告诉调用方“哪个字段不对、允许什么值、如何修正”，使模型有机会进行一次有依据的纠错。

### 5. 统一结果契约并控制信息密度

文章使用的基线结构为：

```json
{"success": true, "data": {}}
```

或：

```json
{
  "success": false,
  "errorCode": "PERMISSION_DENIED",
  "errorMessage": "您没有权限查询该资源",
  "details": {}
}
```

错误码使用 `INVALID_PARAMETER`、`PERMISSION_DENIED`、`RESOURCE_NOT_FOUND`、`BUSINESS_ERROR`、`SYSTEM_ERROR`、`RATE_LIMIT_EXCEEDED` 等业务语义，而不是只返回 403/500。HTTP 状态描述传输结果，工具错误码描述模型下一步该如何处理，两者职责不同。

返回值的信息密度要以“能回答当前问题及紧邻追问”为尺度：只返回剩余年假天数可能不足以回答“总共有多少天”，但附带邮箱、手机号和完整请假历史又明显过量。

## 关键概念/术语

- 工具定义：暴露给模型的名称、描述、输入 Schema 和输出约定的组合。
- 工具选择：模型根据用户意图和工具描述决定是否调用以及调用哪个工具的过程。
- 参数 Schema：约束工具输入字段、类型、必填项、枚举和格式的机器可读契约。
- 幂等键：用于识别重复写请求并复用已有结果的唯一标识，如 `requestId`。
- 结构化结果：使用稳定字段表达成功数据或错误信息的返回对象，而非不可解析的自由文本。
- 信息密度：工具返回中对当前回答有用的信息与无关冗余之间的比例。
- 语义错误码：描述参数、权限、资源或业务失败类别的稳定代码，可指导模型采取不同后续动作。

## 与 xrag 项目的关系

当前 xrag 尚未实现 Function Call、MCP 工具注册或工具执行层，因此本文首先是未来接口设计的验收清单。

- 知识检索若被包装成模型可调用工具，不应把 `topK`、阈值、重排开关等内部检索策略全部暴露给模型。模型提供查询意图，检索层负责默认策略与治理边界。
- 用户身份、租户、授权范围和追踪信息应由可信服务上下文注入，不能让模型通过参数自由指定“当前用户”或权限。
- 将来若引入写操作工具，必须先确定幂等键归属：幂等键由请求编排层生成通常比要求模型凭空生成更可靠。
- 工具成功和失败契约应与 xrag 的可观测性关联，但不能直接复制文章示例；需要结合项目统一错误模型、日志脱敏和 API 协议再定。

## 值得注意的设计取舍/坑

- **拆分不是越细越好**：单一职责能降低单个工具复杂度，但工具数量过多会增加模型路由难度和上下文 Token。应按业务能力与权限边界拆分，再通过分层发现或意图路由缩小候选集。
- **默认值会隐藏产品决策**：不让模型传 `topK` 是好事，但默认值必须由可评测的数据支持；把示例中的 5、0.7、启用重排直接写死，会把课程经验误当成 xrag 决策。
- **描述关键词不是稳定分类器**：堆叠用户可能说法可以提升匹配，但也可能造成相似工具描述相互污染。工具选择需要用真实问法做回归评测。
- **幂等控制不能只“先查再写”**：文章示例便于理解，但并发请求下仍可能双写；真实实现需要数据库唯一约束或原子幂等记录。
- **错误细节可能泄露数据**：返回给模型的 `details` 也会进入提示上下文，不能包含无必要的用户标识、内部异常栈、SQL 或敏感配置。
- **模型参数永远是不可信输入**：JSON Schema 能减少格式错误，不能替代服务端授权、业务校验、注入防护和资源限制。
