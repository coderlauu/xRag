# 《用户点了停止生成集群里发生了什么》

> 原文链接：https://t.zsxq.com/dqWjK
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

停止请求可能落在 A 节点而推理跑在 B 节点，于是 `StreamTaskManager` 用 **Redis Bucket 写标记 + Pub/Sub 广播**做跨节点中转、**本地 Guava Cache**扛高频 `isCancelled()` 轮询、**CAS** 保证只取消一次、**标志位 + `call.cancel()` 双通道**确保读流线程一定停得下来，并在两个时序竞争点（先取消后注册、先取消后绑定）各补一次检查。

## 核心内容提炼

- **前端不直接断连**，而是先 `POST /rag/v3/stop?taskId=xxx`，等后端推回 `cancel` 事件再关 `EventSource`。**这样后端才有机会保存半截内容并回一个 `messageId`**，前端据此展示"已中断"的部分回复而不是一片空白。

- **两层存储各管一件事**：

  | | 存什么 | 解决什么 |
  |---|---|---|
  | 本地 Guava Cache | `StreamTaskInfo`（`cancelled` / `handle` / `sender` / `onCancelSupplier`） | 高频 `isCancelled()` 轮询，纯内存纳秒级 |
  | Redis `RBucket` | `ragent:stream:cancel:{taskId} = true`，TTL 30 分钟 | 持久化标记，兜底"取消先于注册" |
  | Redis `RTopic` | 广播 `taskId` | 实时通知已注册的节点 |

  选 Guava Cache 而非 `ConcurrentHashMap` 的理由是两个 `HashMap` 没有的能力：`expireAfterWrite(30min)` 防异常路径漏清理造成的内存泄漏，`maximumSize(10000)` 防堆积撑爆内存。

- **Pub/Sub 与 Bucket 是互补的短板组合**：Pub/Sub 即时但不持久（fire-and-forget，且真正会"丢"的不是网络，而是**消息到达时 `taskId` 还没走到 `register()`**）；Bucket 持久但不通知（只能靠轮询发现）。所以 `cancel()` **先写标记再广播**，顺序不能反。

- **`cancel()` 不碰本地 Cache**，即使停止请求正好打在跑任务的机器上，也是广播一圈再由监听器回到本地执行——**本地直调与远端调用不走两条路径**。

- **`cancelLocal()` 四步**：查本地 Cache（查不到直接 return，这正是广播的特点——所有节点都收到，只有持有任务的那个处理）→ `compareAndSet(false, true)` 保证只执行一次 → `handle.cancel()` 中断 LLM 流 → 保存内容 + 推 `cancel`/`done` + 关连接。**中断在前、保存在后**：中断为了尽快止住 Token 消耗，保存放后面是因为此时内容已不会再增加。

- **两个时序竞争点各有一道检查**：

  | 竞争场景 | 检查位置 | 检查方式 |
  |---|---|---|
  | 取消早于 `register()` | `register()` 内 | 查 Redis 标记 |
  | 取消晚于 `register()` 早于 `bindHandle()` | `bindHandle()` 内 | 查本地 `cancelled` |

  加上回调里的 `isCancelled()`，一共**三道防线**：前两道是入口拦截，第三道是过程拦截。

- **双通道中断**：`cancelled.set(true)` 让 `while (!cancelled.get())` 协作退出（适用于线程正在两行之间）；`call.cancel()` 从底层断 TCP（适用于线程阻塞在 `readUtf8Line()` 上等下一个 Token——**光设标志位没用，线程根本走不到条件判断**）。`AtomicBoolean once` 保证 `cancel()` 幂等。

- **`doStream()` 的 catch 块区分取消与真异常**：`cancelled == true` 时的 `IOException` 是 `call.cancel()` 的预期产物，只打 info 不调 `onError()`。**否则会与 `cancelLocal()` 已在进行的取消流程重复推事件、重复关连接。**

- **取消路径不走 `unregister()`**，Cache 条目与 Redis 标记都靠 TTL 自然过期。这是有意的——**取消后保留条目一段时间，让延迟到达的回调仍能查到 `isCancelled() == true`**，否则查到 `null` 会被当成正常状态而把内容推出去。

- **超时 / 推送报错 / 客户端断连三种场景统一由 `closed` 标志兜底**，发送方不需要区分原因。但原文明确指出：**这些场景下没有人调 `handle.cancel()`，LLM 流继续跑、Token 继续烧**，与用户主动取消有本质区别。作者猜测这样设计是为了给前端重连留下结果。

## 关键概念/术语

- **跨集群取消**：停止请求与推理任务落在不同节点时的信号传递问题。
- **标记 + 广播双写**：Bucket 保证不丢，Pub/Sub 保证及时，顺序为先写后播。
- **协作式取消**：读循环主动检查标志位退出，与强制中断 IO 互补。
- **三道防线**：`register()` 查 Redis、`bindHandle()` 查本地标志、回调里 `isCancelled()`。
- **部分回复（Partial Answer）**：取消时已生成的内容，落库后带 `messageId` 回给前端。

## 与 xrag 项目的关系

- **原文这一整套跨集群机制，在 xrag 当前的部署形态下应当整体不做——而这正是 [ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 已经立过的判例。** ADR 0002 面对的是同一类诱惑（课程用 RocketMQ 事务消息、Redisson 租约锁、分布式信号量），结论是"**xrag 单实例部署，不预先为多实例付复杂度**"，同时**显式记录多实例下的失效点与升级路径**。取消机制适用同样的判断：单实例下 `cancel()` 就是"在本地 map 里找到任务、调一次取消"，**Redis Bucket、Pub/Sub、订阅/退订生命周期、广播回到本机的统一路径——这四样全都不需要**。Step C 应当照 ADR 0002 的格式写下来：单实例下怎么做、多实例下这个做法会怎么失效、届时怎么升级。

- **但有一处必须先想清楚再照搬 ADR 0002 的思路：取消不是入库任务，数据库任务表那套替代方案在这里不适用。** ADR 0002 的核心手法是"用数据库任务表 + 状态字段 CAS 替代消息队列与分布式锁"，前提是入库任务的时间尺度是秒到分钟，轮询数据库完全够用。**取消信号是亚秒级的实时通知**，靠轮询数据库会引入肉眼可见的延迟（用户点了停止，答案还在往外蹦）。所以**单实例下的正确做法不是"用数据库替代 Redis"，而是"根本不需要跨进程通道"**——进程内一个 `ConcurrentHashMap` 加 `CancellationToken` 就够了。**这条要写清楚，否则很容易机械套用 ADR 0002 而得出"那就把取消也建张表"的错误结论。**

- **xrag 的取消原语已经存在，而且比 `StreamCancellationHandle` 强。** [`CancellationToken`](../../../backend/src/main/java/com/app/ai/model/CancellationToken.java) 有 `isCancelled()`、`onCancel(Runnable)` 和可关闭的 `CancellationRegistration`，通过 `CallOptions.cancellation` 传进每次调用。原文的 `StreamCancellationHandle` 只有一个 `cancel()` 方法，**没有订阅取消事件的能力**——所以它才需要 `bindHandle` 里那次补检。xrag 的 `onCancel` 监听器让"绑定时已取消"这类竞争可以用注册回调解决，而不是每个绑定点手工补一次 `if`。

- **原文的"双通道中断"在 xrag 由 Reactor 免费提供。** [ADR 0004](../../../docs/adr/0004-reactive-streaming-runtime.md) 写明"**订阅取消必须传播到当前 WebClient 请求，所有终态汇合到同一清理路径**"。也就是说：取消 `Flux` 订阅 → Reactor 传播 cancel 信号 → WebClient 关闭在途 HTTP 请求。**协作式标志位与强制断连这两条通道，在响应式栈里是同一个 cancel 信号的两端**，不需要自己造 `AtomicBoolean` + `call.cancel()` 的组合，也不需要 `once` 幂等保护（Reactive Streams 规定 cancel 之后不再有信号）。同理，原文 `doStream()` 里"取消引起的异常不上报"那段判断也不需要——**Reactor 的 cancel 是独立于 `onError` 的终态**，天然不会走错分支。

- **有一条默认行为在 xrag 恰好与原文相反，必须显式决策。** 原文说客户端断连时**不会**中断 LLM 流（没人调 `handle.cancel()`，Token 继续烧），并猜测这是为重连留结果。而 xrag 若按 ADR 0004 正确实现——**浏览器断连 → SSE 连接关闭 → 推送层取消对 `Flux` 的订阅 → 上游 WebClient 请求被关掉**——"断连即停止计费"会是**默认行为**。这个默认更省钱也更符合直觉，但它意味着**"断连后继续生成、允许重连拿结果"在 xrag 反而是需要额外实现的功能**（要把 Flux 从 SSE 连接的生命周期上解耦，比如 `cache()` 或投递到一个独立的会话缓冲）。**产品要哪种行为得在 Step B 定，别让它由实现方式默默决定。**

- **Redisson 与 Guava 在 xrag 都不存在，`backend/pom.xml` 里 Redis 相关只有 `spring-boot-starter-data-redis`。** 真要做跨节点广播，用的是 Spring Data Redis 的 `RedisMessageListenerContainer` 与 `StringRedisTemplate`，不是 `RTopic`/`RBucket`；真要做带 TTL 与容量上限的本地缓存，得先决定引不引 Caffeine。**读这篇时不要把 `RBucket`/`RTopic`/`CacheBuilder` 当成可直接落地的 API**，它们一个都不在依赖树里。

- **`taskId` 与 `conversationId` 要进 [CONTEXT.md](../../../CONTEXT.md) 的统一语言表。** CONTEXT.md 已经定义了「对话」「回答」「链路记录」，但没有"一次生成任务"这个层级的术语。原文用 `taskId` 标识一次生成、`conversationId` 标识一轮对话，而 xrag 的模型调度侧还有 `logicalCallId` 与 `RequestId`（见 `ExecutionInfo`）——**四个 ID 各是什么粒度、谁包含谁，必须在 Step C 之前统一命名**，否则日志和 API 里会同时出现四个含义相近的字段。

- **停止接口的越权校验，原文完全没有，xrag 不能跟着漏。** 见下方"设计取舍"第一条。这是本篇唯一一处**必须比原文做得更多**而不是更少的地方。

## 值得注意的设计取舍/坑

- **`POST /rag/v3/stop?taskId=xxx` 没有任何归属校验——知道 `taskId` 就能停掉别人的生成。** `stop()` 直接把 `taskId` 转给 `taskManager.cancel()`，`cancel()` 里只有写 Bucket 和 publish 两行，**从头到尾没有一处检查这个任务属于当前用户**。而 `taskId` 是 Snowflake ID，同一毫秒段内的取值高度可预测。`@IdempotentSubmit` 防的是同一用户连点，不是越权。**任何需要按 taskId 操作的接口都必须校验归属**，xrag 做这个端点时要在 `ui-spec`/`api.md` 里把它写成硬性要求，而不是等实现时想起来。

- **顺带一个放大面：`cancel()` 对不存在的 `taskId` 同样会写一个 30 分钟 TTL 的 Redis Key。** 刷这个接口就能往 Redis 里灌 key，每次一个，且 `@IdempotentSubmit` 拦不住不同 `taskId` 的请求。**"先写标记再广播"这个为正确性做的设计，同时也是一个无界写入点**——原文没有讨论过这里需要限流或存在性校验。

- **`buildCompletionPayloadOnCancel()` 里的 `String.valueOf(messageId)` 是一个真实的 bug。** `messageId` 声明为 `String messageId = null`，只有落库成功才被赋值。返回时写的是 `new CompletionPayload(String.valueOf(messageId), title)`——**`String.valueOf(null)` 返回的是字符串 `"null"`，不是 `null`**。而 `CompletionPayload` 上标了 `@JsonInclude(NON_NULL)`，本意正是"没有 messageId 就不要这个字段"。结果是：**取消时若没有内容或落库失败，前端收到的是 `{"messageId": "null"}`**，而文中给前端的判断规则是"`messageId` 不为空就展示这条消息"——**判断成立，前端会去展示一条 id 为 `"null"` 的消息**。对比 `onComplete()` 里是 `new CompletionPayload(messageId, title)`，没有 `String.valueOf`。**两条路径对同一个字段的处理不一致，正常路径是对的，取消路径是错的**，而且错法很隐蔽：字段存在、非空、看起来完全正常。

- **`isCancelled()` 在每个 `onContent` / `onThinking` 回调里查一次，这是把"低频事件"实现成了"高频轮询"。** 第 15 篇笔记已经记过一次，本篇给出了它的完整代价：Guava Cache 的 `getIfPresent` 虽然是内存操作，但仍有哈希计算与可能的 TTL 检查，而且**每个 token 块都要做一次**。取消信号明明已经通过 Pub/Sub 主动送达了，**主动通知与被动轮询两套机制并存，却只用了轮询那套的结果**。更自然的写法是让 `cancelLocal()` 直接置一个 handler 自己的 `volatile boolean`，热路径只读一个字段。

- **"取消后靠 TTL 回收而不主动清理"的理由成立，但 30 分钟这个数量级与它要解决的问题差了四个数量级。** 保留 Cache 条目是为了让**延迟到达的回调**还能查到 `cancelled == true`——这个延迟窗口的实际尺度是毫秒到秒（流中断后残留在途的几个事件）。为此保留 30 分钟，意味着一台机器上每个被取消的任务都要占 30 分钟的条目。`maximumSize(10000)` 是兜底，但在取消频繁的场景下**有效缓存会被大量已死任务挤占**，反而影响活跃任务。**这个 TTL 是从 Redis 标记那边照搬过来的**（两者都是 30 分钟），可它们要解决的根本不是同一个问题。

- **`register()` 里执行取消时不检查 `sender` 是否已被使用，也不走 CAS。** `cancelLocal()` 有 `compareAndSet` 保证只执行一次，但 `register()` 发现 Redis 标记为 true 后，是**直接** `onCancelSupplier.get()` + `sendCancelAndDone()` + `complete()`，中间只在 `isTaskCancelledInRedis()` 里做了 `cancelled.set(true)`——**`set` 不是 `compareAndSet`**。若此刻 Pub/Sub 广播也到了，`cancelLocal()` 的 CAS 会因为 `cancelled` 已是 true 而失败并返回，看起来没事；但反过来若 `cancelLocal()` 先抢到 CAS，`register()` 这边的 `isTaskCancelledInRedis` 走的是"本地标志已为 true"的快路径，**依然会再执行一遍保存与推送**。也就是说**内容可能被落库两次、`cancel` 事件可能推两次**。`SseEmitterSender` 的 CAS 会挡住第二次 `complete()`，但挡不住第二次 `sendEvent()` 和第二次 `memoryService.append()`。**幂等保护只做在了两个方法中的一个上。**

- **三道防线看起来周密，但它们守的是同一件事的三个阶段，而不是三个独立的失效模式。** 真正没有被任何一道防线覆盖的是：**取消发生在 `cancelLocal()` 执行的同时，`onComplete()` 也正好走到了一半**。`onComplete()` 开头查 `isCancelled()` 返回 false 于是继续，随后 `cancelLocal()` 置位并推 `cancel` 事件——**前端会先后收到 `finish` 和 `cancel` 两个终态事件**。原文的对比表把"正常完成"与"用户取消"列成了互斥的两栏，**但代码里没有任何机制保证它们互斥**。

- **`SseEmitter` 超时后 LLM 流继续跑，这个"兜底"其实是一个静默的成本泄漏。** 原文自己说得很清楚——推送通道关了，Token 还在烧，而且**没有任何日志或指标记录"这次生成的结果没人要"**。深度思考模式下模型长时间不吐 token 恰恰最容易触发 SSE 超时，于是形成一个很坏的组合：**越贵的调用越容易被静默丢弃**。作者给的解释是"前端可能重连"，但代码里并没有重连拿结果的机制——**结果既没推给前端，也没有落库入口**（`onComplete()` 里 `sender.complete()` 会因 CAS 失败跳过，但落库在它之前，这一步还是会执行）。**要么实现重连取结果，要么在超时回调里主动取消，现在这个中间态两头不靠。**
