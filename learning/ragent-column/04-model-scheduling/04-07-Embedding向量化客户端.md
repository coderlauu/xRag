# 《Embedding向量化客户端》

> 原文链接：https://t.zsxq.com/k0zXf
> 所属分组：04-model-scheduling 大模型调度引擎

## 一句话概括

Embedding 可以复用同步调度骨架，但它的核心不变量是“模型身份固定、批量输入与返回严格一一对应、维度和数值合法”；故障转移只能发生在同一向量模型制品的等价部署之间，不能因维度相同就切换模型。

## 核心内容提炼

- 原文同样划分 `EmbeddingService`、`EmbeddingClient` 和 `RoutingEmbeddingService` 三层。业务接口提供单条、批量和维度查询，Provider 客户端增加 `ModelTarget`。
- OpenAI 风格客户端的固定流程是：构造 `model + input + dimensions` 请求、分批调用、解析 `data[].embedding`、合并批次。不同 Provider 通过是否需要 Key、请求体字段和最大批次覆盖差异。
- 批量分片是 Provider 能力：硅基流动示例限制为每批 32 条，Ollama 有自己的协议和字段。上层不应写死一个所有 Provider 共用的批次上限。
- 整体结果列表应保持输入全局顺序。单批请求失败时，原文按整个批次失败处理，不返回缺少一部分向量的“部分成功”。
- 指定模型时只为该模型生成单候选；不指定时由默认候选路由。原文也强调查询向量和已入库向量必须使用同一模型。
- 同步 Embedding 可复用通用执行器，但批次切分、顺序恢复、维度校验和向量合法性属于 Embedding 自己的协议逻辑。

## 关键概念/术语

- **向量空间**：某个模型及版本定义的语义坐标系；维度相同不代表空间兼容。
- **等价部署**：运行同一模型制品、版本、预处理和输出配置的不同端点。
- **按 index 恢复**：根据响应项的 `index` 重排，而不是假定 Provider 按请求顺序返回。
- **批次能力**：Provider/模型对条目数、token 总量、单条长度和维度参数的限制。
- **全批失败**：一批结果不完整或非法时整批拒绝，避免静默写入错位向量。

## 与 xrag 项目的关系

- xrag 的 Phase 1 实现已优于原文的教学代码：
  - `EmbeddingClient.embed(List<String>)` 明确长度和顺序严格一致；
  - 按响应 `index` 重排并校验越界、重复；
  - 校验返回条数和向量维度；
  - 串行分批，只对 429 指数退避；
  - 中断后恢复线程中断标志；
  - 外部 HTTP 调用不进入数据库长事务。
- Phase 2 必须保留这些接口和自动化回归。推荐新增 `RoutedEmbeddingClient` 实现现有端口，把协议编解码迁到 Provider 适配器，而不是修改知识库调用点。
- 路由候选不仅要维度相同，还必须绑定同一 embedding 模型、版本、预处理和 dimensions 配置。不同模型之间的自动故障转移会让新向量无法与旧向量正确比较。
- 当前 Ark 的每批 10 条、间隔和重试是已验证的供应商配置，不应变成所有 Provider 的公共常量；Phase 2 应把它们迁为 Provider/模型元数据。
- 当前缺口包括：`Retry-After`、抖动、共享总预算、Provider 请求 ID、限流余量，以及对向量元素 `NaN`/无穷值的校验。

## 值得注意的设计取舍/坑

- **原文声称保序，但示例按响应数组顺序读取，忽略了 `index`。** xrag 已正确处理，迁移时不能回退。
- **同维度不是可替换证明。** 例如两个 1024 维模型的坐标轴含义不同，混用会产生无报错但质量完全错误的检索。
- **指定模型不能只存在于单次请求参数。** 知识库应持久化模型身份/版本，并在查询、补向量和重建时强制一致。
- **分批故障转移必须以完整语义为单位。** 如果前半批来自模型 A、后半批来自模型 B，即使维度一致也不可接受；换等价端点时也应记录每批实际目标。
- **外部调用与诊断写库都不能扩大事务范围。** 先得到并校验全部向量，再在短事务内写入数据库与派生索引。
