# 《AI大模型Ragent项目》第12小节：理解函数调用Function Call

> 原文链接：https://t.zsxq.com/Sd930
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章指出纯 RAG 系统的能力边界是"只能查知识库、干不了活"，进而系统讲解了 Function Call（函数调用）协议——模型不真正执行函数，只输出"该调哪个函数、传什么参数"的调用意图 JSON，由业务代码去执行并把结果回传给模型——并配合 Java + OpenAI 协议的完整两轮请求示例、在 RAG 系统中的应用方式，以及该协议在维护成本、跨语言集成、权限安全、可观测性四方面的局限性，为下一篇 MCP 协议做铺垫。

## 核心内容提炼

- **问题的引入：RAG 的能力边界**。RAG 的完整链路（用户提问→向量检索→召回文档→生成答案）数据来源只有知识库，所以只能回答"知识库里有什么"。但企业场景里用户经常问的是实时数据（我还剩几天年假）、业务状态（订单物流到哪了）、甚至要求执行操作（帮我请假、提报销），这些答案根本不在知识库里，必须调用业务系统的接口或数据库。文章用"年假余额"和"订单物流"两个例子说明：知识库里有制度文档不代表能查到具体用户的实时数据，这是两类完全不同的信息源。

- **两种传统方案及其问题**：
  - 方案一，在 Prompt 里写死兜底话术（如"请访问 HR 系统查询"），本质是让系统承认自己做不到，体验差，等于放弃了"智能助手"该有的能力。
  - 方案二，用关键词/规则匹配用户意图后再调接口（`if (userQuestion.contains("年假"))...`），问题是自然语言表达方式太多（"假期余额""还有多少天假"等）规则永远写不全，且判断意图的逻辑硬编码在代码里，每加一个新工具都要改代码、加规则、重新部署，维护成本随工具数量线性甚至更快增长。

- **Function Call 的本质：模型只输出"调用意图"，不真正执行**。这是全文最核心的一句话——模型分析完用户问题后，输出的是一段 JSON（字段名 `tool_calls`），里面写明"应该调用哪个函数、参数是什么"，但模型本身没有能力也不会去真的调这个函数；真正解析这段 JSON 并执行对应函数、拿到结果的，是使用方自己的业务代码。文章用"服务员拿着菜单帮你下单，但服务员不会做菜、做菜的是厨房"这个比喻来说明模型（服务员）和执行代码（厨房）的分工边界。

- **完整流程是一次两轮对话，而不是一次调用**：
  1. 定义工具（函数名、功能描述、参数结构）；
  2. 把工具列表和用户问题一起发给模型（第一轮请求）；
  3. 模型判断需要调用某个工具，返回 `tool_calls`（不生成最终文本答案，此时 `content` 字段为 `null`，`finish_reason` 为 `tool_calls`）；
  4. 业务代码解析 `tool_calls`，按函数名路由到具体实现并执行，拿到结果；
  5. 把函数执行结果作为新的一条消息（`role: tool`）追加进对话历史，连同前面用户问题、模型的 `tool_calls` 响应，一起发起第二轮请求；
  6. 模型基于函数结果生成最终的自然语言答案（这次 `finish_reason` 为 `stop`）。
  文章特别强调第二轮请求的消息顺序不能乱：必须是 用户消息(user) → 模型的 tool_calls 响应(assistant) → 函数执行结果(role=tool，且 `tool_call_id` 要和上一条 assistant 消息里 `tool_calls[].id` 对应)，顺序错了或缺了一条，模型可能生成不出正确答案。

- **为什么选 Function Call 而不是另外两种方案**：相比"Prompt 兜底"，Function Call 让模型动态判断是否需要调工具，用户无感知；相比"传统规则匹配意图"，模型理解自然语言，能覆盖各种同义表达而不用穷举关键词；相比"让模型直接生成可执行代码"（第三种一般不会采用但值得对比的方案），Function Call 输出的是结构化 JSON，易解析、参数有类型约束，比直接生成代码更安全可控。核心分工：判断"要不要调、调哪个"交给模型（模型擅长的自然语言理解），"具体怎么执行"留给业务代码（代码擅长的确定性逻辑）。

- **OpenAI Function Call 协议的具体字段**（文章称这是"事实标准"，OpenAI/Anthropic/Google/通义千问/智谱/DeepSeek 等主流服务商都兼容）：
  - 工具定义：`{"type": "function", "function": {"name", "description", "parameters"}}`，其中 `parameters` 用 JSON Schema 描述（`type: "object"` + `properties`（每个参数的 `type`/`description`）+ `required` 必填列表）。
  - **`description` 是模型选工具的关键依据**：文章举例，若两个工具分别是"查年假余额"和"查病假余额"，描述写清楚了模型才能选对；如果写成笼统的"查询用户信息"，模型很可能选错工具。这是实践中最容易踩坑、也最容易被忽视的一点。
  - 请求里的 `tool_choice` 参数控制模型是否/如何调工具：`auto`（模型自行判断，默认也是最常用值）、`none`（强制只生成文本，不调工具）、`required`（强制必须调用某个工具）、或直接指定 `{"type": "function", "function": {"name": "xxx"}}` 精确点名调用某个工具。
  - 响应里 `message.tool_calls` 是一个数组，说明**模型可能一次输出多个工具调用**（并行调用多个工具）；`function.arguments` 字段是**JSON 字符串而不是 JSON 对象**，业务代码拿到后必须自己再做一次 JSON 解析，这是一个容易被忽略的实现细节。

- **Java 实战示例的关键工程细节**（示例用 OkHttp + Gson 调用 SiliconFlow API，模型为 Qwen2.5-7B-Instruct / DeepSeek-V3，定义了 `getUserAnnualLeave` 和 `getOrderStatus` 两个工具）：
  - 用系统消息（`role: system`）把"当前登录用户 ID"注入对话（如 `"当前登录用户的ID是: user_12345"`），让模型在生成 `tool_calls` 参数时能带上正确的用户身份，而不是让用户自己在提问里报 ID——这是一个实用的工程技巧，用系统消息传递上下文身份信息。
  - 函数路由目前示例用简单的 `if-else` 按函数名分发，文章提到实际项目里可以用策略模式或反射做动态路由，避免 `if-else` 链无限增长。
  - 工具定义手写 Gson JSON 比较繁琐，文章建议实际项目里封装一个 `FunctionTool` 工具类来生成标准 JSON 结构。

- **Function Call 在 RAG 系统里的三种应用方式**：
  1. **意图识别/路由**：把"查知识库"本身也包装成一个工具（如 `searchKnowledgeBase`，描述里写清楚"适用于查询公司制度、产品文档等静态知识"），和业务工具（`getUserAnnualLeave` 等）平级放进 `tools` 列表，让模型自己判断该走知识库检索还是调业务接口——用 Function Call 机制统一承担了"该不该做 RAG 检索"这个路由决策，不用额外写一层意图分类器。
  2. **混合场景（知识检索 + 工具调用同时需要）**：例如"我的订单能退货吗"需要先查订单信息（购买时间、商品类型）再查退货政策文档，模型可能一次输出多个 `tool_calls`，或者分多轮依次调用；工程实现上要写一个循环，每轮把所有工具调用结果都追加进消息历史，直到模型的 `finish_reason` 不再是 `tool_calls` 才结束。
  3. **多工具优先级控制的三种手段**：①在 `description` 里写优先级提示语（如"优先使用此工具查询公司制度…"）；②用 `tool_choice` 显式指定要调用的工具（适合业务上已经明确知道该调哪个工具的场景）；③分阶段调用——先用一个轻量级工具做粗粒度意图分类，再根据分类结果选具体工具。

- **Function Call 协议本身的四类局限性（是全文承上启下、引出下一篇 MCP 的关键部分）**：
  1. **工具定义维护成本高**：每个工具的 JSON Schema 都要手写，参数一多就很繁琐；如果工具是从数据库表结构自动生成的（比如每张表对应一个查询工具），手写 Schema 完全不现实。
  2. **跨语言/跨系统集成问题**：Function Call 协议本身只规定了"工具怎么描述、模型怎么响应"，不解决"Java 写的工具、Python 写的工具、纯 HTTP API 怎么被统一调用"这个问题——这部分需要自己搭一个工具注册与调用框架（统一描述格式 + 跨语言 RPC，如 gRPC/HTTP + 各系统自己的认证鉴权）。
  3. **权限与安全控制需要自己实现**：模型可能被诱导调用不该调的工具或传入不合法参数（如用户 A 让模型查用户 B 的年假、或参数里塞 SQL 注入/路径穿越字符串），协议本身没有权限校验机制，必须在执行函数前自己加一层"当前用户是否有权限操作该资源"+"参数格式/合法性校验"的逻辑。
  4. **可观测性不足**：调用了哪个工具、传了什么参数、执行结果和耗时是多少，都需要自己记日志、埋点追踪；如果调用链很长（工具 A 内部又调工具 B、工具 B 再查数据库），排查起来会很麻烦，协议没有内置的追踪机制。

- **引出下一篇 MCP**：文章把上述四类局限性明确定位为"MCP（Model Context Protocol）要解决的问题"——统一工具描述与调用协议、支持工具动态发现和注册、提供标准的权限安全机制、内置可观测性支持。作者的定位很清楚：Function Call 是"协议"，解决了"让模型学会喊工具"这一步；MCP 是在此之上的"企业级标准化方案"，解决"工具怎么管理、怎么发现、怎么鉴权、怎么可观测"这几个 Function Call 没管的问题。

## 关键概念/术语

Function Call（函数调用）：让大模型根据用户输入判断是否需要调用外部函数/工具，并输出结构化调用意图（工具名+参数）的机制；模型本身不执行函数，执行由调用方代码完成。
tool_calls：模型响应中表示"我判断需要调用工具"的字段，是一个数组（可能包含多个工具调用），每项含调用 id、工具类型、函数名和 JSON 字符串形式的参数。
tool_choice：请求参数，控制模型是否/如何调用工具，取值包括 `auto`（自行判断）、`none`（禁止调用）、`required`（强制调用）、或指定具体工具名。
finish_reason：响应中标识本轮结束原因的字段，`tool_calls` 表示模型要求调用工具（未生成最终答案），`stop` 表示已生成最终文本答案。
JSON Schema（用于 function.parameters）：描述函数参数结构的标准格式，含 `type`/`properties`/`required` 等字段，模型据此理解参数类型和是否必填。
MCP（Model Context Protocol）：下一篇要讲的协议，定位为在 Function Call 协议之上补齐工具发现注册、权限安全、可观测性等企业级能力的标准化方案。

- 这篇文章讨论的"查知识库 vs 调工具"的路由决策，直接对应 `INDEX.md` 里 `05-qa-pipeline` 分组后续会细讲的《意图识别与多路由调度策略》一文；本篇给出的具体实现思路（把 `searchKnowledgeBase` 包装成一个和业务工具平级的 tool，让模型统一路由）可以作为 xrag 检索问答链路设计意图识别模块时的一个可选实现方案，而不必单独再造一套基于规则或分类模型的意图识别器。
- 文章列出的四类局限性（工具定义维护成本、跨语言集成、权限安全、可观测性）在专栏后续目录里能找到对应的专门文章：`01-24-工具调用架构设计指南.md` 和 `01-25-工具调用稳定性与安全保障.md`。这说明本篇是"提出问题"，具体"怎么解决"要等看到那两篇再落地到 xrag 的工具调用模块设计里，本篇的定位更多是让 xrag 在设计工具调用框架时提前预留这四个关注点的扩展位（工具注册/描述生成、跨语言适配层、执行前权限校验钩子、结构化调用日志），不必等到问题出现才补。
- xrag 后端是 Java/Spring 技术栈，本篇的 Java 实战示例（OkHttp + Gson 手动拼装 `tools` JSON、手动解析 `tool_calls`）给出的是"协议层原生做法"；实际接入 xrag 时应优先看 Spring AI 是否已经封装了等价的 `ToolCallback`/`FunctionCallback` 抽象（覆盖 Schema 生成、参数反序列化、多轮编排），如果有现成抽象，没必要照抄示例里手写 Gson 拼 JSON 的方式，那部分示例代码的价值是理解协议底层结构，不是照搬工程实现。
- 本篇里"用 system 消息注入当前登录用户 ID，让模型在生成参数时带上正确身份"的技巧，以及"执行函数前做权限校验（用户 A 不能查用户 B 的数据）"的提醒，是 xrag 未来如果要做"个人数据查询类工具"（如查看自己的用量/配额/历史记录）时必须落地的安全前提，需要在设计工具执行层时就把"当前请求用户身份"作为强制传入参数，而不是完全信任模型从对话里推断出的参数。

## 值得注意的设计取舍/坑

- **`function.arguments` 是 JSON 字符串，不是 JSON 对象**，拿到 `tool_calls` 后必须先对这个字段单独做一次 JSON 解析才能取到具体参数值，这是接协议时最容易漏掉的一个实现细节，直接当对象取字段会出错。
- **第二轮请求的消息顺序和字段完整性是硬约束**：必须严格保持"用户消息→模型的 tool_calls 响应（assistant，`content` 为 null）→ 函数结果（role=tool，`tool_call_id` 对应上一条消息里的 id）"这个顺序，少一条或错一条模型可能给不出正确答案；这个约束在自己实现多轮工具调用循环时容易在重构代码时不小心破坏。
- **`description` 写得模糊会直接导致模型选错工具**，这是一个"看起来是小事、实际影响调用正确率"的坑——文章举的反例是把两个功能不同的工具都写成"查询用户信息"这种笼统描述，模型会失去区分依据；工具描述应该清楚写明功能、适用场景、参数含义三部分。
- **权限校验和参数合法性校验不是协议自带的能力，必须自己在执行函数前手写**，文章明确指出模型可能被诱导调用不该调的工具或传入非法参数（如查询别人数据、SQL 注入类参数），如果误以为"模型会自己把关"就省略这层校验，是一个直接的安全隐患。
- **Function Call 只是"协议"，不是"框架"**：工具的维护、跨语言集成、权限安全、可观测性这四件事协议都不管，需要项目自己搭配套设施；如果照着文章的 Demo 直接原样搬进生产系统而不补齐这四块，短期能跑通，长期工具数量增多后维护成本会迅速失控——这也是文章刻意把这四点作为局限性单独列出、并借此引出 MCP 的原因，说明作者认为这是从"Demo 可用"到"生产可用"之间的关键缺口。
