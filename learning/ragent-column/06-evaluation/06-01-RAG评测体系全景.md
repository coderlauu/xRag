# 《RAG 做出来了，但效果怎么衡量？》

> 原文链接：https://t.zsxq.com/0mYZD
> 所属分组：06-evaluation RAG 评测体系

## 一句话概括

评测不是上线前抽几条问题看答案，而是把“初始化数据 → 录制一次真实执行 → 分层评分 → 面向不同受众出报告”做成可重复流水线，并用确定性业务指标与 LLM-as-judge 语义指标互补。

## 核心内容提炼

- 课程把评测拆成 `init → run → score → report` 四段；最有价值的设计是“录制一次，评分 N 次”，避免每次改指标都重新调用被评系统。
- 被评 Java 系统与 Python 评测项目分仓：前者负责真实问答，后者保存评估集、运行器、指标和报告。分仓是课程方案，不是必须照搬的架构结论。
- 自建指标覆盖意图、文档命中、排序、行为和时延，计算快且确定；RAGAS 补充忠实度、切题度、正确性和上下文语义质量，但更慢、更贵且有方差。
- 总分会掩盖退化来源。报告至少要按意图、检索、生成、行为、性能分别展示，并能从总体下钻到意图切片和单条失败样本。
- 课程用生产 SSE 与评测旁路两个请求拼出答案和检索证据，明确承认两次独立检索可能漂移。

## 关键概念/术语

- **评测录制（run）**：冻结一次被评执行的输入、证据、输出和性能事实。
- **确定性指标**：集合或数值运算得到的指标；同一输入重复计算应一致。
- **语义指标**：依赖模型理解文本的评分，必须绑定 judge、Prompt 和运行参数。
- **切片（slice）**：按意图、难度、风险或其他维度分组观察指标。

## 与 xrag 项目的关系

- xrag 已有同一 `turn` 下的意图 revision、检索来源、工具结果、生成任务及模型诊断，评测应优先从同一次执行事实构造记录，避免课程“双请求旁路”的证据错配。
- Phase 4 的不可变评测身份至少要能追到：数据集版本、样本 ID、知识库输入 revision、意图树 revision、模型实际身份、Prompt 版本和代码版本；具体 Schema 留到 Step C。
- 默认 CI 只能跑有界、确定性、零付费或假 Provider 检查；真实生成和 judge 评测必须显式守门。

## 值得注意的设计取舍/坑

- 课程给出的绝对阈值只是教学起点，不能直接成为 xrag 的发布线；先跑 baseline，再结合业务风险和人工判定校准。
- “评测逻辑不侵入生产代码”不能绝对化。若完全不记录同一次执行的版本和证据，评测虽隔离却不可复现。
- 课程关于 RAGAS 方差、调用次数和成本的数字受版本、模型与样本长度影响，必须实测，不能当稳定事实。
