# 《AI大模型Ragent项目》——分布式限流选业务层还是网关层？

> 原文链接：https://t.zsxq.com/kJVbI
> 所属分组：03-knowledge-base AI知识库建设

## 一句话概括

上一篇讲了"用信号量限流"，这篇讲"限流代码该放在请求处理链路的哪一层"——从 Tomcat 处理上传请求的实际流程出发，证明 Service/Controller 层限流完全无效（临时文件早已写盘、线程早已被占用），Filter 层能防住临时文件但防不住 Tomcat 线程被占满，只有 Gateway 层（基于响应式非阻塞IO的流式透传）能同时防住两者；结论是单体应用用 Filter、微服务架构用 Gateway。

## 核心内容提炼

- **问题背景**：假设单文件限50MB、Tomcat最大线程200，如果200个请求同时涌入（集中上传/批量导入/客户端重试放大），即使 Service 层做了信号量限流，是不是 200×50MB=10GB 的临时文件已经产生了？答案取决于限流代码放在哪个环节。

- **Tomcat 请求处理流程里的三个关键时机（很多人有误解）**：
  1. **线程分配**发生在 Filter 之前（Tomcat Acceptor 接到连接后就从工作线程池分配一个线程），即使 Filter 里立刻返回 429，这个线程也已经被占用了。
  2. **multipart 解析**（也就是把文件真正读出来写临时目录）发生在 **Filter 链执行完之后、DispatcherServlet 内部、Controller 之前**——具体是 Spring Boot 的 `StandardServletMultipartResolver` 调用 Servlet 3.0 的 `request.getParts()` 时触发。HTTP 请求体在此之前是"懒读取"的，还躺在 socket buffer 里没被消费。
  3. 三个常见误区都要澄清：Tomcat 收到请求不会立刻解析 multipart；Filter 里直接 `return`（不调用 `chain.doFilter()`）确实能阻止文件被写入磁盘；`HandlerInterceptor` 是在 DispatcherServlet **内部**执行的，此时 multipart 已经解析完，用它限流和 Controller 里限流本质一样，都太晚了。

- **三层方案的实测/推演对比**（核心结论表）：
  - **Service/Controller 层**：进入业务代码时文件已经解析完、临时文件已经落盘，信号量只能挡住"后续上传到对象存储"，挡不住磁盘和IO已经发生的问题——**完全不推荐**。
  - **Filter 层**：在 multipart 解析之前拦截，`chain.doFilter()` 不调用则请求根本不会到 DispatcherServlet，不会触发文件读取和临时文件写入。极端场景下：200个请求到达 Tomcat（**200个线程还是被占用**，这个避免不了），但只有许可数（比如10个）能真正触发 multipart 解析，临时文件从10GB降到10×50MB=500MB，磁盘IO可控。**局限性很明确**：线程分配在 Filter 执行之前发生，无法通过 Filter 层的逻辑挽回。
  - **Gateway 层**：Spring Cloud Gateway 基于 Netty+WebFlux 的响应式非阻塞IO，处理方式和 Tomcat 本质不同——不会为每个请求独占一个工作线程，而是从 socket 读一小块数据（如8KB）封装成 `DataBuffer` 立刻转发给后端，循环往复直到传完，全程只持有少量 buffer（几十KB量级），是真正的"流式透传"，不会像 Servlet 容器那样把整个文件落到本地临时文件。如果限流判断只需要请求头/路由/用户标识等信息就能做，Gateway 可以在**请求根本没有转发到后端服务之前**就直接拒绝——后端 Tomcat 的线程完全不受影响。极端场景下：200个请求到 Gateway，只有10个被转发到后端，后端只有10个线程被占用、10×50MB=500MB临时文件；其余190个在网关侧就被拒绝，网关自身只占用少量 DataBuffer 和 Netty 事件循环线程。

- **一个重要澄清**：Spring Cloud Gateway 自带的 `RequestRateLimiter` 控制的是"单位时间请求速率"（限速语义），**不等于**"当前正在上传的并发数"控制——如果目标是控制并发上传数，需要自定义 `GatewayFilter`，复用和 Filter 层同样的分布式信号量逻辑（识别上传请求→转发前尝试获取许可→失败直接429→成功转发+请求结束释放）,不能直接拿 `RequestRateLimiter` 当并发控制用。

- **一个隐含前提**：Gateway 层"自身只占用少量buffer"这个结论，成立的前提是网关只做路由和限流、没有额外启用会缓存/改写请求体的过滤器；如果网关侧主动读取缓存了 body，资源占用模型就完全不同了。

- **选型建议**：
  - **单体应用**（没有微服务网关）→ **Filter 层限流**是性价比最高、最稳妥的方案，实现位置离业务最近、配置和观测都直接，通常没必要专门为这件事再引入一层网关。
  - **微服务架构**（已经有 Gateway）→ **Gateway 层限流**，因为所有请求本来就要经过网关，能在业务服务收到请求之前就拦截。
  - **Filter 和 Gateway 不是互斥关系**：即使用了 Gateway，业务服务内部有时仍会保留一层 Filter 兜底（比如上传链路里有绕过网关的入口，或者需要更细粒度的按用户/按知识库/按文件类型限流——这类细粒度逻辑通常还是要在应用层实现，Gateway 更适合做入口级/服务级的总量控制）；两者都支持从配置中心动态调整参数。
  - 如果要追求极致，理论上还能把这件事前移到 Nginx 层（连 Gateway 都不用做无意义转发），但文章明确这不是"内部知识库"这个场景下的默认推荐。

## 关键概念/术语

- **懒读取（Lazy Loading）**：Tomcat 收到请求后先只读请求头，请求体等应用代码真正调用 `getParts()`/`getInputStream()` 时才会被消费。
- **DispatcherServlet**：Spring MVC 核心分发组件，在 Filter 链之后执行，是 multipart 真正被解析（触发临时文件写入）的地方。
- **流式透传**：Gateway（Netty+WebFlux）处理请求体的方式——不整体缓冲/落盘，而是一小块一小块地读取并立即转发，`Flux<DataBuffer>` 是这种处理模式的代码体现。
- **`RequestRateLimiter`**：Spring Cloud Gateway 自带的限速组件，控制的是速率而非并发数，容易被误用成并发控制。

## 与 xrag 项目的关系

- **xrag 目前的架构决策直接决定了答案**：已确认是单体 Java/Spring Boot 后端、没有独立网关层（也没有计划引入微服务架构），按本文结论应该**直接选 Filter 层限流**，把上一篇（03-04）设计的 `RPermitExpirableSemaphore` 信号量逻辑挂在一个 `OncePerRequestFilter` 上，而不是塞进 Controller/Service 方法里。
- **这条结论应该写进知识库模块的技术方案，作为明确的接口设计约束**：文档上传接口的限流拦截点 = Filter（`@Order(Ordered.HIGHEST_PRECEDENCE)`，判断请求路径命中上传接口时才介入，其余请求直接放行），不是 Service 方法内部的一段信号量代码——这和 03-04 篇里 Ragent 项目示例代码里"在 Service 方法体内 acquire/release"的写法看似矛盾，需要在 xrag 自己的技术方案里明确采用哪种（本文的结论更全面，建议以本文为准，把限流逻辑从 Service 移到 Filter）。
- 由于 xrag 是单用户个人学习项目，线程池被占满的风险本来就很低（不会有200个并发请求），但"把限流放在正确的层"这个架构原则本身值得在技术方案里体现，作为学习和演示"企业级设计思维"的一部分——这也符合"任务书定位=还原企业级全流程、可作品集展示"的既定目标。

## 值得注意的设计取舍/坑

- **最容易被误解的一点**：以为"信号量限流"本身就够了，忽略了"限流代码放在哪一层"同样重要——同一套 `RPermitExpirableSemaphore` 逻辑，放在 Service 层和放在 Filter 层，实际防护效果天差地别（10GB vs 500MB 临时文件），这是本文最核心的教训。
- **`HandlerInterceptor` 是一个常见的伪解决方案**：很多人以为拦截器可以在 multipart 解析前介入，但实际上它在 DispatcherServlet 内部执行，此时文件早已经落盘——这是一个容易被文档/直觉误导的坑，选型时要认准"是否在 DispatcherServlet 调用 `getParts()` 之前"这条硬标准，而不是看组件名字听起来像不像"拦截"。
- **Filter 层限流无法解决线程占用问题，这是一个必须接受的局限，不是实现疏漏**：即使方案选对了（Filter层），仍然有"200个线程被占满"这个残留风险，只是通过 Filter 里快速返回429把占用时间缩到最短。如果未来真的要支持大规模并发访问（超出当前"单用户个人项目"的范围），需要重新评估是否要引入网关层。
- **`RequestRateLimiter` 的误用是一个具名的坑**：原文特别强调不要把它当并发控制用，如果 xrag 未来真的引入网关，要留意这类"名字像限流但语义是限速"的组件，不能想当然套用。
