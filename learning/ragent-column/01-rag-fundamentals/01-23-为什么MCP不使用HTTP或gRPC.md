# 《AI大模型Ragent项目》——为什么MCP不使用HTTP或gRPC？

> 原文链接：https://t.zsxq.com/oacL6
> 所属分组：01-rag-fundamentals RAG与大模型基础概念（加餐）

## 一句话概括

这篇加餐回答一个容易被忽略的协议选型问题：MCP 没有直接指定用 HTTP 或 gRPC 作为调用方式，而是选了 JSON-RPC 2.0 作为消息格式规范，根本原因是 MCP 要解决的是"如何统一描述一次工具调用"，而不是"如何传输数据"——HTTP 只管传输、不管调用语义，gRPC 调用语义完整但太重，JSON-RPC 2.0 恰好卡在两者中间，用最小的规范换来跨语言、跨传输、易调试的互操作性。

## 核心内容提炼

- **先厘清问题本质，再谈选型**：文章开篇把讨论焦点从"用什么协议传数据"扭转到"怎么表达一次调用"。MCP 的目标是让 Python/Java/Node.js 写的 Server 都能被同一个 Client 调用、让不同厂商的模型都能用同一套方式调工具，这是一个"调用语义标准化"问题，不是传输层问题——这个前提决定了后面为什么 HTTP、gRPC 都不够合适，而看似"性能更差"的 JSON-RPC 2.0 反而是对的选择。

- **HTTP 的问题：它是传输协议，不是调用协议**。HTTP 规定了怎么建连、怎么发请求（GET/POST 等）、怎么给状态码和 Header，但完全不规定"方法名放哪、参数怎么传、错误怎么表达、不需要响应的通知怎么处理"这几件事。后果是同样基于 HTTP，RESTful、RPC-style（`POST /api` 带 `{method, params}`）、GraphQL 可以长成完全不同的样子——如果 MCP 直接说"用 HTTP"，各语言实现照样会各自发明一套调用约定，等于什么都没统一。

- **gRPC 的问题：调用语义足够完整，但代价对 MCP 场景太高**。gRPC 有强类型接口（Protocol Buffers）、HTTP/2 传输、流式调用、多语言代码生成，性能和类型安全都好，但对应四个成本：①每个工具都要先写 `.proto` 再生成代码，开发成本上升；②客户端和服务端都依赖代码生成，不利于"运行时动态发现工具"这种 MCP 需要的场景；③二进制协议没法直接用 curl/浏览器调试，出问题排查门槛高；④强依赖 HTTP/2，浏览器和部分代理环境支持不完整。这四点合起来，让 gRPC 在"轻量、灵活、易调试"这个 MCP 最看重的维度上处于劣势。

- **JSON-RPC 2.0 的定位：只管消息格式，不管传输**。它跟 HTTP、gRPC 不是同一维度的东西——只定义了四种消息对象（请求、成功响应、错误响应、通知），完全不绑定具体传输通道，理论上能跑在 HTTP、WebSocket、stdio，或任何能传 JSON 的通道之上。这一点直接解释了为什么 01-13 里提到的 Stdio 和 Streamable HTTP 两种 MCP 传输方式可以共享同一套调用语义：传输层和消息格式在 MCP 里是分开设计的两层，stdio 传的是 JSON-RPC 文本行，Streamable HTTP 传的是装在 HTTP body/SSE 帧里的 JSON-RPC 消息，上层的方法名、参数、错误结构完全一致。

- **MCP 选 JSON-RPC 2.0 的六个具体理由，每一条都对应 MCP 的实际痛点**：
  1. **消息结构统一**：请求/成功响应/错误响应的字段都是固定的（`jsonrpc`/`method`/`params`/`id` 等），不同语言实现的 Server 和 Client 按同一套结构解析和构造消息，不会出现"各家协议方言"。
  2. **规范极简，不需要工具链**：完整规范只有四个核心概念（Request/Response/Notification/Error Object），任何语言只要会解析和构造 JSON 就能实现完整的客户端或服务端，不需要 IDL、不需要代码生成器——这直接对应 MCP 要求"随便一个 Python 脚本就能当 Server"的低门槛诉求，是 gRPC 做不到的。
  3. **纯文本、人类可读**：可以直接用 curl 发请求、在浏览器 DevTools 里看报文、用文本编辑器改、在日志里直接读，不需要反序列化工具；这一点是相对 gRPC 二进制 Protocol Buffers 格式的直接对照。
  4. **不绑定传输层**：能同时覆盖 MCP 的三种真实部署形态——本地进程用 stdio、远程服务用 HTTP、需要保持长连接的场景用 WebSocket。gRPC 因为强依赖 HTTP/2，天然没法用在 stdio 这种场景里，这是一个硬性排除项，不是"优化空间"层面的差距。
  5. **原生支持 Notification（无 id 请求）**：工具向模型上报日志、汇报任务进度这类不需要等确认的单向消息，JSON-RPC 2.0 直接有对应的消息形态（请求里不带 `id`，服务端处理后不返回响应）。HTTP 和 gRPC 都没有这种一等公民的单向消息概念，要做等价效果得自己额外设计（HTTP 可能要单独开一个"回调"接口，gRPC 得靠流式 API 模拟）。
  6. **原生支持批量请求（Batch）**：可以把多个请求对象塞进一个 JSON 数组一次发出去（例如同时请求 `tools/list`、`resources/list`、`prompts/list`），服务端并发处理、减少网络往返——这对模型一次性拉取多种工具/资源信息的场景直接有用，而 HTTP/gRPC 同样需要额外设计或用流式 API 才能达到类似效果。

- **JSON-RPC 2.0 本身也有四点明确的局限性，MCP 需要在协议层或实现层自己补**：
  1. **不管传输层细节**：连接怎么建立、超时重试、负载均衡、服务发现，JSON-RPC 规范完全不涉及，这些必须由 MCP 的传输规范或具体 SDK/框架实现来补齐——换句话说，"选了 JSON-RPC"本身并不会自动带来这些能力。
  2. **不含鉴权机制**：认证要么放到传输层（比如 HTTP Header），要么放到应用层（比如在 `params` 里塞一个 `auth` 字段），JSON-RPC 规范对这件事保持沉默。
  3. **不含类型系统**：参数和返回值都是动态 JSON，类型错误只能在运行时发现，编译期完全查不出来。MCP 的补偿方案是在协议层给每个工具附带 `inputSchema`（一份 JSON Schema），让工具自己声明期望的参数结构，但这终究是运行时校验，不是真正的编译期类型安全。
  4. **性能不如二进制协议**：JSON 的序列化/反序列化开销比 Protocol Buffers 大，但文章判断这点损耗对"大模型调用工具"这种调用频率和数据量级的场景基本可以忽略。

- **总结性判断：这是一次明确的三方权衡，不是技术不知道 gRPC 更快**。文章最后把 HTTP、gRPC、JSON-RPC 2.0 在定位、消息格式标准化、实现复杂度、可读性、传输层灵活性、通知支持、批量支持、类型安全、性能九个维度上逐一对比，结论是 JSON-RPC 2.0 既不是最快的（gRPC 性能更好），也不是最灵活的（HTTP 可以随意设计），但在"标准化 + 简单 + 好调试 + 跨语言"这组 MCP 真正在乎的目标上综合得分最高。MCP 需要的是让不同语言、不同厂商的实现之间能无缝对话，不是把单次调用的延迟压到最低。

## 关键概念/术语

JSON-RPC 2.0：只定义请求、成功响应、错误响应、通知四种消息对象结构、不绑定任何传输层的轻量级远程调用消息格式规范，可运行在 HTTP、WebSocket、stdio 等任意能传输 JSON 的通道之上。
Notification（通知消息）：JSON-RPC 2.0 中不带 `id` 字段的请求，服务端处理后不返回响应，用于日志上报、进度汇报等无需确认的单向消息。
Batch Request（批量请求）：把多个 JSON-RPC 请求对象放进一个 JSON 数组一次性发送，服务端可并发处理，减少网络往返次数。
Protocol Buffers（protobuf）：gRPC 使用的二进制序列化格式，需要预先编写 `.proto` 接口定义文件并生成对应语言的代码。
inputSchema：MCP 在协议层为每个工具附带的 JSON Schema，用来声明该工具期望的参数结构，弥补 JSON-RPC 本身没有类型系统的缺陷，但本质仍是运行时校验。
IDL（接口定义语言）：用于预先描述接口结构、驱动代码生成的语言，gRPC 用 Protocol Buffers 作为其 IDL；JSON-RPC 2.0 不需要 IDL。

## 与 xrag 项目的关系

- 这篇把"传输层"和"消息格式层"拆成了两件独立的事，正好补全了 01-13《MCP协议入门与实践》里 Stdio / Streamable HTTP 选型讨论缺的那一层解释：xrag 后续接入 MCP 时，Spring AI 的 MCP Server/Client Starter 已经把 JSON-RPC 2.0 这层消息编解码实现好了，团队不需要手写 JSON-RPC 解析逻辑；但排查问题时要有意识地分层定位——连不上、超时属于传输层问题（stdio 进程没启动/HTTP 端口不通），返回 `-32602` 之类的错误码或响应结构不对才是 JSON-RPC 消息层的问题，两类问题的排查路径不一样。
- xrag 规划中把知识检索能力封装成 MCP 工具对外提供（01-13 里 `MCPToolRegistry` + `MCPToolExecutor` 的思路），工具方法本身只需要返回业务数据，Spring AI 框架会负责把返回值包装成 JSON-RPC 的 `result` 结构、把异常包装成 `error` 结构（含错误码）——这意味着 xrag 侧的工具实现代码不需要、也不应该自己去拼装 JSON-RPC 响应格式，避免和框架的封装逻辑重复或冲突。
- 本篇明确 JSON-RPC 2.0 不含鉴权机制，认证必须在传输层或应用层自行实现；这与 01-13 里"生产环境选 Streamable HTTP、但认证方式还没有统一标准"的结论是同一个问题的两个说法。xrag 如果要把知识检索工具通过 Streamable HTTP 开放给内部多个客户端（运营后台、开发者 IDE），必须显式设计一套认证方案（网关鉴权或在 HTTP Header / MCP 请求 `params` 里带凭证），不能假设接入 MCP 协议后鉴权问题会被协议自动兜底。
- 类型安全的局限提醒 xrag 在定义自己的 MCP 工具时，`inputSchema`（或 Spring AI 注解自动生成的等价物）只是声明性的契约，不是编译期保证；对外暴露的工具方法仍应在方法体内做显式参数校验（比如 Bean Validation 或手写检查），否则一个格式不对但恰好通过了框架层粗校验的请求，可能会在业务逻辑内部才暴露问题，排查成本更高。

## 值得注意的设计取舍/坑

- **JSON-RPC 2.0 故意不管的四件事（传输细节、鉴权、类型、性能），恰恰是后续容易被追问"MCP 怎么解决"的地方**：这四点局限性不是协议设计者没想到，而是有意排除在 JSON-RPC 规范之外，留给 MCP 的传输规范和具体 SDK/框架去补。理解这一点能解释 01-13 里提到的"MCP 权限模型还比较基础、远程认证还没有统一标准"这类现状——根源就是消息格式层选型本身就没打算覆盖这层，不是实现得不够好。
- **"inputSchema 弥补了类型安全"这句话容易被过度解读**：文章的原意是协议层用 JSON Schema 做运行时参数校验，去部分缓解无类型带来的问题，但这终究是运行时行为，效果依赖具体 SDK/框架是否真的在调用前严格执行了 Schema 校验。不能把"工具定义了 inputSchema"直接等同于"这个调用是类型安全的"，两者不是一个强度的保证。
- **gRPC 被排除的一个关键原因是它在 stdio 场景完全用不了（强依赖 HTTP/2）**，这一点比"gRPC 太重"更硬——如果 MCP 的使用场景里没有"本地进程通过标准输入输出被调用"这个需求，针对 gRPC 的评估结论未必会一样。这提示技术选型的结论是绑定具体场景的：换成一个不需要 stdio、追求高吞吐的纯内部微服务通信场景，同样的比较维度大概率会得出"选 gRPC"的相反结论，不能把"MCP 选了 JSON-RPC"泛化成"JSON-RPC 通常比 gRPC 更优"的通用结论。
- **文章明确承认 JSON-RPC 2.0 不是最快、也不是类型最安全的方案，这是主动接受的代价，不是没意识到问题**：如果后续讨论中有人质疑"为什么不用 gRPC/protobuf 提升性能"，正确的回应角度是"MCP 场景下互操作性和调试效率的优先级高于吞吐量和类型安全"，而不是暗示协议设计者没有比较过这些方案。
