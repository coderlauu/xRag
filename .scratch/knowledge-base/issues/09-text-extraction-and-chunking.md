# 09 — 文本提取与分块算法

**What to build:** 给定一个文件，得到一串分块。纯本地字符串处理，没有 UI、没有数据库、没有网络调用——因此可以被单元测试**完整**覆盖，这是本模块唯一能做到这一点的部分，值得把测试写扎实。

**Blocked by:** 03（Tika 依赖）

**Status:** done（`2026-07-25`）

- [x] Tika 文本提取，支持 `.txt` `.md` `.pdf` `.docx` 四种格式
- [x] `FIXED_SIZE` 策略：按字符数硬切，相邻分块重叠 `overlap` 个字符
- [x] `RECURSIVE` 策略：按分隔符优先级递归切分（默认 `["\n\n", "\n", "。", ". ", " "]`），先用最高优先级切，超长片段再用下一级切，最终仍超长的硬切
- [x] 每个分块算出 `charCount`、`tokenCount`（启发式：中文 1 字≈1 token、英文 4 字符≈1 token、其他 2 字符≈1 token）、`contentHash`（SHA-256）
- [x] `tokenCount` **只用于展示**，不参与任何逻辑判断
- [x] 单元测试覆盖边界：空文档、只有空白字符的文档、单字符文档、长度恰好等于 `chunkSize`、长度等于 `chunkSize + 1`、`overlap = 0`、`overlap = chunkSize - 1`
- [x] 单元测试验证 `RECURSIVE` 真的在段落边界切分（构造一段有明确段落结构的文本，断言切点落在 `\n\n` 处而不是中间）
- [x] 单元测试验证一个没有任何分隔符的超长字符串也能被切开（递归到最后必须硬切，不能返回一个超长分块或死循环）
- [x] `overlap >= chunkSize` 的参数组合被拒绝（否则会无限循环或产生无意义的重复分块）
- [x] `./mvnw -q -B verify` 通过

## 完成记录

产出 `com.app.knowledge.ingestion` 的 `TextExtractor` / `TextChunker` / `TokenEstimator` / `TextExtractionException`，以及 `model` 里的 `ChunkConfig` / `TextChunk`。**24 条单测全绿**，纯本地处理确实做到了完整覆盖。

**写实现时发现并修掉的一个真 bug**（测试先写出来才暴露的）：`RECURSIVE` 的合并阶段在收口一块之后，会保留末尾若干片段作为重叠。原来的回退条件只有"尾巴缩到 `overlap` 以内"，但**保留的重叠 + 下一个片段仍可能超过 `chunkSize`**——实测切出过一个 53 字符的分块（上限 50）。修复是把回退条件加成两个：尾巴要 ≤ `overlap`，且必须给下一个片段腾出位置。取舍是明确的：**超长是硬约束，重叠只是锦上添花**，冲突时丢重叠。

**几处需要说清的设计决定**

- **空白文档切出 0 个分块是正常结果，不是错误。** 扫描版 PDF、空文件都会走到这里，ui-spec 为它设计了专门的空态（`revision>0` 却没有分块）。
- **`FIXED_SIZE` 不修剪空白，`RECURSIVE` 修剪。** 前者的全部价值是行为完全可预测（第 n 块一定是 `[n*step, n*step+chunkSize)`），修剪会破坏这个性质；后者的片段末尾带着分隔符，不修剪的话每块都以 `\n\n` 结尾，展示和编辑都碍事。
- **递归切分时分隔符保留在前一个片段末尾**，这样片段拼起来能还原原文，切点也必然落在分隔符边界而不是词中间。
- **`overlap >= chunkSize` 在 `ChunkConfig` 构造时就拒绝**，不留给算法自己发现。这不是"效果不好"而是不终止：固定长度的步进 ≤ 0 会原地打转。
- **`BodyContentHandler` 必须显式传 -1。** 无参构造默认只写 100,000 字符就抛异常，一份几百页的 PDF 直接撞上。为此专门写了一条 15 万字符的用例守住它——这是最容易在重构中被改回去的一行。

**一条测试的前提写错了，已改。** 原本断言"内容是纯文本但文件名是 .pdf → 抛异常"，实际 Tika 按**内容**探测类型而不是扩展名，会正常提取。这是对的行为（误命名的文件仍能用），改成了两条：损坏的 PDF（`%PDF-` 头 + 垃圾字节）抛带文件名的异常；误命名的纯文本正常提取。格式白名单是上传接口的职责，不是提取器的。

PDF/DOCX 样本在测试里用 pdfbox / poi 现场生成（已随 `tika-parsers-standard-package` 进入 classpath），不往仓库塞二进制夹具。
