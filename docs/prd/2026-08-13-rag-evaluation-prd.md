## 1. 背景与动机

Phase 3 已形成完整知识问答链路：会话理解、意图路由、混合检索、RRF、精排、工具协议、Prompt 隔离、
流式生成、排队、停止和断连恢复均有自动化或浏览器证据。但这些证据主要证明协议、状态机和接线正确，
不证明“答案质量已经达标”。

当前任何 Prompt、Embedding、分块、意图描述、TopK 或 Rerank 改动，都可能一边修好某类问题、一边让另
一类问题退化。如果继续靠抽几条问题目测，结果不可复现、样本覆盖不清楚，也无法判断问题来自意图、检索、
生成还是性能。

Phase 4 建设可重复的质量证据闭环：冻结评估数据与被评配置，录制同一次真实执行，分别计算确定性与语义
指标，输出机器和人都能消费的报告，并把确认过的 bad case 回流为长期回归样本。

## 2. 产品定位

### 2.1 服务对象

1. **开发者**：改动检索、Prompt 或模型配置后，知道哪些样本变好、哪些变坏以及先查哪个阶段。
2. **项目所有者**：在进入发布或下一阶段前，看到可解释的基线、风险样本和费用边界，而不是一个总分。
3. **CI / 守门任务**：读取机器可读结果，对确定性回归、执行失败和预算越界做自动判断。
4. **人工 Reviewer**：复核自动低分、高风险样本和 Judge 分歧，保留可审计的人工结论。

第一版不面向普通问答用户，也不提供独立评测控制台。使用者通过 CLI/受控 API 发起运行，通过版本化
JSON/JSONL、Markdown 和 CSV 产物查看结果，并从报告跳转到既有 turn/trace 诊断事实。

### 2.2 产品承诺

一次可比较评测应做到：

> 选择不可变数据集 revision 和运行模式 → 校验知识夹具及费用预算 → 每条样本只录制一次真实 turn，
> 让答案与实际证据同源 → 按资格计算分层指标 → 显式保存成功、失败、跳过与不可评 → 输出逐样本、
> 聚合和 A/B 报告 → 对高风险与争议样本保留人工复核轨迹。

系统承诺提供可复现、可解释的证据，不承诺任何自动指标等同于事实真理，也不承诺第一版自动完成发布审批。

## 3. 目标与非目标

### 3.1 目标

1. 建立不可变的样本、数据集和评测运行身份，使两个分数先能判断“是否可比”。
2. 提供受控的评估集生命周期：起草、校验、发布 revision、废弃；已发布 revision 不原地修改。
3. 从同一个 Phase 3 turn/trace 录制问题、实际阶段结果、有序证据、回答、终态与性能事实。
4. 分别评估意图/动作、检索、生成、端到端行为、性能、费用和可靠性，不产生单一 RAG 总分。
5. 默认 CI 运行确定性、无付费的回归守门；真实被评模型和 Judge 通过显式、有预算的离线任务运行。
6. 输出机器可读结果、研发报告、逐样本明细、失败样本和 A/B diff。
7. 支持自动分与人工复核并存，保留原始值、复核结论、理由和责任人。
8. 用小型中文人工校准集验证 Judge/RAGAS 候选是否适合 xrag，再决定哪些语义指标可进入守门。

### 3.2 非目标

- 专用评测页面、可点击原型、多人在线标注平台或审批工作流。
- 在 Step B 锁定 RAGAS、Python sidecar、数据库表、消息队列或具体报告库。
- 用评测工作顺手实现多实例部署、SSE 重放、WebSocket、再生成、流式 Markdown或真实工具执行器。
- 自动修改 Prompt、意图树、知识库、TopK 或模型配置；第一版只评估和报告，不自动调参。
- 用一个综合分自动替项目所有者作发布决策。
- 默认采集线上用户问题、知识库正文或工具结果作为评估集。
- 模型排行榜、公开 Benchmark、计费结算后台或多租户评测服务。

## 4. 统一语言

| 术语 | 定义 |
|---|---|
| 样本 revision | 一条问题、标签、reference、gold 证据与 provenance 的不可变版本 |
| 数据集 revision | 一组有序样本 revision、split 与权重的不可变清单 |
| 知识夹具 | 为评测准备、可重建并经过就绪校验的知识库/文档/意图树输入 |
| 运行 manifest | 绑定数据集、知识夹具、代码、Prompt、被评模型、Judge、指标实现和预算的不可变身份 |
| 录制 | 执行样本并冻结同一次 turn 的阶段事实、证据、回答和性能数据 |
| 评分 | 在已录制事实之上计算指标；改评分逻辑不重新调用被评系统 |
| 确定性指标 | 基于 ID、枚举、数值或协议事实计算，同一输入重复结果一致 |
| Judge 指标 | 依赖 LLM/Embedding 对文本做语义判断的指标，存在方差、偏置和费用 |
| 人工金标 | 按标注规范由人审并完成冲突裁决的 reference、gold 或 rubric 结果 |
| 弱标注 | 由 LLM、规则或单人初标产生、尚未达到发布金标等级的标签 |
| 不可评 | 样本缺少某指标的必要证据，或评分过程无法产生有效值；不是普通低分 |
| 主力集 | 日常改动使用的有代表性回归集 |
| 校准集 | 用于比较 Judge 与人工结论、校准 Prompt/阈值的小型中文金标集 |
| 发布保留集 | 不参与日常调参，只在正式守门时打开的独立样本集 |

## 5. 第一版评估数据产品

### 5.1 数据来源与业务覆盖

第一版使用**受控的 xrag 能力夹具**，不直接复制课程电商数据，也不默认抽取线上内容。夹具使用无个人信息、
可提交仓库或受控 artifact 的原创/授权短文档，覆盖 Phase 3 已实现的行为：

| 场景组 | 必须覆盖的样本类型 |
|---|---|
| 意图与路由 | 单一明确意图、相邻意图混淆、低置信无匹配、歧义需澄清 |
| 问题理解 | 指代追问、术语归一、双子问题；最多三子问题边界另做协议用例 |
| 检索 | 语义改写、精确编号/关键词、混合召回、重复 chunk、Rerank 噪声、多证据问题 |
| 生成 | 单事实、多个必要事实、证据不足应兜底、证据含干扰信息、不得补造 |
| 非 RAG 行为 | SYSTEM 直答、业务外问题、该答却误拒、不该检索却过召回 |
| 工具 | 工具白名单、参数结构、确认语义和稳定失败夹具；不声明真实业务执行质量 |
| 可靠性/性能 | 成功、模型失败、超时、取消、部分回答、未保存、排队等待 |

首批数据分三层建设，规模作为产品上限而非必须一次填满：

| 数据集 | 首版目标 | 用途 |
|---|---:|---|
| 中文人工校准集 | 12 条 | 双人独立判断 + 冲突裁决；验证 Judge 指标、中文、数字/否定/多证据 |
| 主力回归集 | 36 条以内 | 日常确定性回归和有界真实模型评测；上述六类质量场景均有代表 |
| 发布保留集 | 12 条以内 | 不参与日常 Prompt/阈值调优；正式 baseline/release gate 使用 |

这 60 条是第一版容量边界，不是假装具有统计代表性的行业 Benchmark。Step E 先完成校准集和不少于
24 条的主力集即可形成初始 baseline；后续只在发现真实覆盖缺口时增量扩充。

### 5.2 样本最低信息

每条样本在产品语义上至少包含：稳定样本 ID、revision、用户输入、场景/split、标签来源、是否应检索、
期望意图/动作、must/nice 文档或 chunk 证据、自然语言 reference 或 rubric、风险等级和适用指标。

规则：

- 不同路径只填写适用字段；SYSTEM/拒答样本不伪造 gold 文档。
- reference 必须是自然语言可接受答案或明确 rubric，不写“应回答……”式元指令。
- gold 使用跨环境稳定业务码；运行时内部 ID 只能作为本次 trace 事实。
- 修改问题、标签、reference、gold、split 或风险等级都会产生新 sample revision。
- 标签 provenance 必须区分 `human_gold`、`expert_adjudicated`、`synthetic`、`llm_judged`、
  `heuristic` 与 `production_unlabeled`。

### 5.3 防污染与隐私

- `development`、`main`、`release_holdout` 的样本 ID 集互斥；保留集答案不进入业务 Prompt、few-shot、
  合成器或知识库。
- 新样本与已有 split、业务 Prompt 和知识 corpus 做内容 hash/近重复检查；具体算法留 Step C。
- 线上 bad case 必须先确认授权、脱敏、重写和复标，才能进入固定集。
- 未授权用户问题、文档正文、工具结果和答案不得发送给外部 Judge，也不得复制进长期报告。
- 人工修订不覆盖历史 revision；已引用旧 revision 的运行继续可追溯。

## 6. 核心用户旅程

### 6.1 建立第一个 baseline

1. 开发者选择已发布的数据集 revision 和已就绪的知识夹具。
2. 系统生成运行预览：样本数、运行模式、实际模型约束、最大调用/Token/金额/时间预算及敏感数据检查。
3. 开发者显式确认付费运行；系统为每条样本创建独立会话/turn，录制同源答案与证据。
4. 确定性评分完成后保存结果；Judge 启用时继续计算语义指标，单项失败不抹掉前面结果。
5. 系统生成 manifest、汇总报告、逐样本明细和 failures，项目所有者将该 run 标记为初始比较基线。

### 6.2 日常改动回归

1. 开发者改动意图描述、检索策略或 Prompt。
2. 默认 CI 对固定夹具运行假 Provider/确定性检查，验证协议、gold ID 指标计算和报告契约，无真实费用。
3. 需要质量结论时，开发者显式运行主力集真实模型评测。
4. A/B 报告先检查两次 manifest 是否可比，再展示 paired delta 和变好/变坏样本，不只比较 overall。

### 6.3 人工复核争议样本

1. Reviewer 从 failures/CSV 找到自动低分、高风险、重复评分不一致或不可评样本。
2. 读取受控的用户输入、reference、实际 contexts、response 和 Judge 原始理由。
3. 填写人工分项结论、原因和 reviewer 身份；原始自动分保持不变。
4. 重算“采用人工优先”的报告，同时显示 override 数量和策略；历史报告仍可重建。

### 6.4 Bad case 回流

1. 评测或授权线上观察发现新问题。
2. 先判断是标注错误、知识缺口、意图、检索、生成还是执行问题。
3. 修复后，把能代表一类风险且不泄漏敏感信息的 case 重新标注为新样本 revision。
4. 样本先进入 development/main，不直接泄露进发布保留集。

## 7. 功能需求

### FR-01 数据集生命周期

- 支持校验草稿、发布不可变 revision、列出 revision 与废弃旧 revision；不提供原地修改已发布版本。
- 发布前校验稳定 ID、split 唯一归属、字段资格、gold 业务码解析、reference/rubric、provenance 和敏感内容。
- 数据集 manifest 保存有序样本 revision 清单、内容 hash、创建者、时间和说明。
- 第一版可以通过仓库文件/CLI 管理，不要求 CRUD 页面；技术落位由 Step C 决定。

### FR-02 知识夹具初始化与就绪检查

- 评测运行不得依赖开发数据库里的偶然内容；必须选择明确的 fixture/snapshot identity。
- 初始化后检查文档 revision/content hash、分块、向量、Embedding 身份、意图树 revision 和启用状态。
- 未就绪时阻止录制并列出具体缺口，不能跑出一批零分后再猜原因。
- 重建/清理只允许作用于明确评测命名空间，默认 dry-run；不得删除共享业务知识库。

### FR-03 运行创建与可比性 manifest

- 创建 run 时冻结数据集、知识夹具、代码/build、配置、Prompt、被评模型、指标实现、Judge/Embedding、
  运行策略和价格版本。
- 同时记录请求模型和 Provider 实际返回的模型身份；别名不能替代实际身份。
- 任何缺失的关键身份都让 run 标为“不可作严格 A/B”，但已产生事实仍保留。
- 运行开始后 manifest 不随配置变化；重跑产生新的 run ID。

### FR-04 单次同源录制

- 每个样本只以一个真实 Phase 3 turn 作为答案、意图、检索、工具、生成和终态的共同事实源。
- 不通过第二次独立检索拼接“近似 contexts”作为默认证据。
- 录制保存模型实际消费的有序证据 identity；正文是否保留遵守授权与保留策略。
- 执行失败、拒答、取消、超时和部分回答同样形成记录，不从分母中静默消失。
- 录制与评分解耦；改指标、Judge 或报告时可复用冻结录制。

### FR-05 运行模式与费用守门

第一版定义三种模式：

| 模式 | 被评 Provider | Judge | 默认触发 |
|---|---|---|---|
| `DETERMINISTIC_CI` | 假 Provider/固定夹具 | 无 | 每次 CI，可自动 |
| `REAL_BASELINE` | 真实 Provider | 无或少量校准 | 手动显式触发 |
| `JUDGED_RELEASE` | 真实 Provider | 固定 Judge，多轮按策略 | 手动显式触发 |

- 真实模式启动前展示并要求样本、请求、Token/金额和总截止时间上限；缺一项不得启动。
- 达到任一上限后停止新工作，保留已完成结果并标记 `BUDGET_EXHAUSTED`，不得无界自动重试。
- Judge 某项失败不影响确定性指标落盘；整次 run 可为部分成功。
- 默认 CI 永远不因环境里碰巧存在真实 Key 就升级为真实模式。

### FR-06 指标分层与资格

第一版必须提供或预留以下产品级结果；具体算法参数在 Step C 冻结：

| 层 | 第一版指标/事实 |
|---|---|
| 意图/动作 | 子问题级 Top-1、gold action 覆盖、歧义/拒答正确性、confusion 明细 |
| 检索 | Doc/Chunk Hit@K、Recall@K、MRR；Rerank applied/degraded 切片 |
| 工具 | 工具选择、参数结构、确认语义与夹具终态；不声称真实业务结果质量 |
| 生成 | 引用/兜底规则；经校准后候选的 faithfulness、relevance、reference correctness |
| 端到端行为 | 成功、正确拒答、误拒、过召回、失败、取消、部分回答 |
| 性能 | 排队、accepted、客户端正式回答 TTFT、阶段耗时、总耗时、输出速率 |
| 费用/可靠性 | 请求、重试、Token、金额、超时、解析失败、Provider 失败与降级 |

- 每个指标声明 required evidence、分母、聚合方式、单位、版本和 `does not prove`。
- `not_applicable`、`missing_evidence`、`evaluation_failed` 与有效数值分开。
- 聚合报告显示有效样本数、失败/跳过数和逐样本值；不只显示百分比。
- 不输出跨层加权“RAG 总分”。

### FR-07 Judge 与 RAGAS 候选验证

- RAGAS 不作为 PRD 依赖；若 PoC 采用，必须精确 pin 版本并位于框架无关适配器后。
- Judge 记录模型实际身份、Prompt artifact/hash、参数、语言适配、Embedding、重复序号、原始 verdict/理由、
  解析/重试、Token、费用和耗时。
- 先对 12 条中文校准集做双人金标，比较 Judge 一致性、分歧类型和费用，再决定指标是否进入报告/门禁。
- Judge/Prompt/框架版本变化产生新 metric revision，旧新分数不得直接拼成同一历史曲线。
- 多轮均值只能降低部分随机方差，不能被描述为消除系统性偏置。

### FR-08 报告产物

每个 run 至少产生：

1. `manifest`：可比性身份、预算、环境和状态；
2. 机器可读聚合结果：供 CI/守门程序读取；
3. sample-level 结果：原始事实、指标资格、各轮分数与人工覆盖；
4. `report.md`：总体、分层切片、终态、性能/费用和已知证据边界；
5. `failures`：一条样本可有多个失败原因，并关联 turn/trace；
6. A/B diff：可比性检查、before/after/delta、改善/退化/不变样本。

Markdown/CSV/JSON/JSONL 是产品要求的可消费形态，具体目录和字段由 Step C 定义。第一版不要求
`slides.html`，也不建设专用页面。

### FR-09 人工复核

- 支持导出待复核样本，并导入/记录 reviewer、时间、分项结论、理由和采用值。
- 自动原始值、人工值与最终采用值三者共存；不得覆盖或删除原始 Judge 结果。
- 高风险样本、自动低分、重复不一致、数字/日期/否定/多证据以及 Judge 失败进入复核候选。
- 报告显示人工覆盖数量、覆盖策略和未完成复核数。
- 第一版人工流程使用受控 CSV/Markdown 或 API/CLI，不提供在线协作页面。

### FR-10 基线、比较与守门

- 项目所有者可把一个完整、身份齐全的 run 标记为某数据集 revision 的 baseline。
- A/B 先比较 manifest；数据集、知识夹具、Judge 或指标 revision 不同，报告必须突出“不严格可比”。
- 确定性指标允许绝对阈值和 paired regression 规则；Judge 指标在完成中文校准前只报告、不硬阻断。
- 任何执行失败率、不可评率或预算耗尽超过产品阈值时，不能用剩余成功样本均值宣告通过。
- 发布结论包含 `PASS`、`FAIL`、`REVIEW_REQUIRED`，其中自动系统不能绕过人工要求自行给 PASS。

## 8. 隐私、安全与数据保留

- 评测系统沿用单用户边界，但不因此放宽敏感数据最小化原则。
- run manifest、ID、阶段、耗时、错误、Token、费用和指标可长期保留；正文类 artifact 受单独授权和期限控制。
- 报告默认使用 query/response 摘要或受控引用，不复制完整知识库正文和工具结果。
- 外部 Judge 调用前做数据资格检查；不合格样本标记跳过，不因“需要分数”而越权发送。
- API Key、Authorization、原始 Provider 错误体和模型思维链不得进入评测 artifact。
- 第一版默认保留最近 20 个完整 run 的正文 artifact 或 30 天，先到者清理；manifest、聚合指标和人工审计
  记录保留。该默认值可在 Step C 根据存储量细化，但不得无期限积累正文。

## 9. 非功能需求

### 9.1 可复现与可审计

- 同一录制输入的确定性评分可离线重复执行并得到相同结果。
- 任何分数都能追到 sample revision、required evidence、metric revision 和原始观测。
- 报告生成失败不删除已有录制或评分结果；可从上一个完整阶段重跑。

### 9.2 可靠性

- 单样本失败不拖垮整批；run 最终状态准确反映完整、部分成功、取消或预算耗尽。
- 取消后不再创建新 Provider/Judge 请求，已完成结果仍可读取。
- 重试有界且计入调用、费用和截止时间预算。

### 9.3 性能与成本

- 确定性 score/report 对主力集应为本地秒级任务，不能依赖真实模型。
- 真实运行支持受控并发，但不得突破 Phase 3 排队边界或污染性能基线。
- 每个真实 run 输出实际用量；无法获得价格或 usage 时明确标为未知，不能估成 0。

### 9.4 可测试性

- 假 Provider 能稳定构造命中、miss、降级、超时、取消、部分回答与 Judge 解析失败。
- 时间、价格表、运行身份和 metric adapter 可替换，确保 CI 结果确定。
- 真实 Provider/Judge 测试必须由专门开关和固定样本上限守门。

## 10. 验收标准

| ID | 场景 | 验收结果 |
|---|---|---|
| AC-01 | 发布数据集 revision | manifest/hash 固定；修改 gold/reference 产生新 revision，旧 run 仍可读取 |
| AC-02 | 评测夹具未完成分块或向量化 | 运行在录制前失败并列出缺口，不生成误导性的零分报告 |
| AC-03 | 同一样本执行问答 | 答案、意图、实际有序证据和终态关联同一 turn/trace，没有第二次检索拼接 |
| AC-04 | 默认 CI 环境存在真实 API Key | 仍只运行 `DETERMINISTIC_CI`，不产生真实模型费用 |
| AC-05 | 显式真实运行缺少金额或时间上限 | 拒绝启动并指出缺少的预算字段 |
| AC-06 | Judge 中途失败 | 确定性指标和成功样本保留，run 标记部分成功并列出失败/不可评数量 |
| AC-07 | Rerank 降级 | 报告单独切片 `rerank_applied=false`，不与完整精排样本静默混为同类 |
| AC-08 | SYSTEM/正确拒答样本 | 不进入检索 gold 分母，行为指标能判断正确拒答与过召回 |
| AC-09 | 取消/超时/部分回答 | 作为独立终态计数，不从性能和可靠性报告中消失 |
| AC-10 | A/B 数据集或 Judge revision 不同 | 报告标记不严格可比，不输出无说明的胜负结论 |
| AC-11 | 人工修正 Judge 误判 | 原始分保留；人工分、reviewer、理由和采用策略可审计，聚合可重算 |
| AC-12 | 达到 Token/金额/时间预算 | 停止新调用，已完成结果保留，run 标记 `BUDGET_EXHAUSTED` |
| AC-13 | 某指标只有部分样本具备证据 | 报告显示有效、不可评、失败和跳过数，不把缺失默认为 0 或静默排除 |
| AC-14 | 输出报告 | manifest、机器聚合、逐样本、Markdown、failures 与 A/B diff 均可生成和互相追溯 |
| AC-15 | 中文 Judge 校准 | 12 条双人校准集有分歧裁决、逐指标一致性与误判清单；未通过前不作硬门禁 |
