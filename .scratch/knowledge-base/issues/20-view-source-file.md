## 进行记录

### 范围是用户定的：只做下载 / 新标签打开

摆出来的四个选项里选了最小的那个。另外两个更大的选项各自的代价写进了 PRD，免得以后重新讨论一遍：

- **在线预览**：要引 PDF 渲染库，而 `.docx` 在浏览器里没有像样的免费方案，投入与收益不成比例。
- **分块 ↔ 原文位置对照**：要求分块记录保留其在原文中的字符偏移量，**这是数据模型变更**（`document_chunk` 加两列 + 分块算法输出偏移）；且对 PDF 这类"提取后文本与原排版对不上"的格式，高亮位置未必准。

### 三处设计判断

- **`inline` 而不是 `attachment`**。PDF 与纯文本让浏览器直接显示，`.docx` 这类渲染不了的格式它自己会退化成下载。写死 `attachment` 则连 PDF 都要先存到本地再打开，多一步且没有收益。
- **不校验 `enabled` 也不拦 `RUNNING`**。禁用针对的是"参与检索"，与"能不能看原件"无关——禁用一份文档之后连原文都打不开，用户就没法判断该不该重新启用它。`RUNNING` 同理：它是只读操作，而文档正在重新处理时恰恰是用户最想看看原文的时候。
- **两种 404 的 `message` 必须分开**。"文档不存在或已被删除"是用户自己删的；"源文件已不可用，可能已被清理"是存储侧的状况，只有后者需要找运维。PRD §4.2 明说了空间回收不在本轮范围，但它迟早会做，届时这条提示就是用户唯一能理解发生了什么的线索。

### URL 来源看到的是快照，这点界面上必须说

对象存储里存的是**上次抓取到、且真正被切分过的那一份**，不是实时重新抓取。不说清楚的话，源站已经变了的时候用户会困惑"原文明明是这样，分块怎么是那样"。

原型里 URL 来源的分块页页头是两个并列入口，语义不同：

```
查看源文件（2026-07-25 03:00 抓取的快照）  ·  打开原始链接 ↗
```

想核对分块点前者，想看源站更新了什么点后者。FILE 来源只显示前者，没有快照说明——已在原型里分别验过。

### 入口为什么是两个

文档行那个是顺手确认"我传上去的到底是哪一版"；**分块页页头那个才是主战场**——ui-spec §6 的手动干预要求用户判断原文怎么写，没有对照就只能凭记忆改。两处都是新标签打开，不在当前页跳走：用户正在编辑分块，把他带走会丢掉滚动位置和展开状态。
