# 《抢不到许可请求该等还是该拒？》

> 原文链接：https://t.zsxq.com/mOutN
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

抢不到许可的请求进入异步等待：**`scheduleAtFixedRate` 周期轮询 + Pub/Sub 即时唤醒**双路径驱动同一个 poller，`PollNotifier` 用三层防御把 N 次广播压成 1~2 轮遍历，等满 `deadline` 则走**超时拒绝**（把问题与"系统繁忙"一并写进会话记忆再推 `reject`），许可释放由 `Ticket.cleanup()` / `try/finally` / `lease` 三道防线兜底。**本篇同时为 05 组 18 篇收尾。**

## 核心内容提炼

- **poller 三个分支对应三个出口**：非 `PENDING` 就注销走人；超过 `deadline` 就 `timeout()`；否则跑一次 `tryAcquireIfReady`。`deadline` 在 `Ticket` 构造时就算成**绝对时间戳**，比每次比较"已等待时长"更直观。

- **`scheduleAtFixedRate` 的 `initialDelay` 也设成 `interval` 而不是 0**——同步路径的 `tryAcquireIfReady` 刚失败过，立刻再跑一次是浪费。

- **同一个 poller 注册到两条触发路径**（scheduler 周期任务 + `PollNotifier`），重复调用安全，因为 poller 内部三个分支都是状态判断。

- **为什么 Pub/Sub 之外还要轮询**——Redis Pub/Sub 是 fire-and-forget，四种场景会丢：主从切换期间、订阅连接断开重连之前、新节点启动时 listener 还没注册完、GC 卡顿期间回调线程处理不了。**只靠广播会让等待者卡死（明明有许可却没人通知）**；只靠轮询则响应慢且 Redis 调用密度高。**快路径 + 慢路径兜底**，与 Nacos 的 watcher + 定期拉取、K8s Informer 的 watch + list 是同一个模式。

- **`PollNotifier.fire()` 二十多行藏三层防御**：
  1. **CAS 串行化**——`firing.compareAndSet(false, true)` 保证同一时刻最多一个扫描任务；抢不到的直接返回，但它加的 `pendingNotifications` 不会丢；
  2. **`pendingNotifications` 火上加柴**——do-while 结构，跑完发现期间有新通知就抢回执行权再跑一轮，**5 次广播最终只触发 2 轮遍历**；
  3. **空轮次跳过**——进循环先查一次 `availablePermits()`，为 0 直接 `break`。**在 fire 这一层查 1 次，省掉 N 个 poller 各查一次的 N 次查询。**

- **`pendingNotifications.set(0)` 必须在循环体开头而不是末尾**，这是最容易写错的地方。放末尾会把"遍历期间到达的通知"一起清掉，那条通知本该触发新一轮。语义是：**`set(0)` 是"我承诺这一轮会消化掉之前所有通知"的那一刻，在此之前的归我，之后的归下一轮**——是划清新旧边界，不是擦掉边界。

- **超时拒绝写会话记忆是产品决策**，原文列了三种实现对比：A 直接关连接（前端只能显示"网络错误"，用户立刻刷新重试，雪上加霜）；B 推 reject 但不写记忆（刷新后这次失败像没发生过）；**C 既推事件又写记忆**（刷新后历史里仍有"我问了什么、系统回了什么"，还能统计哪些用户/时段常被限流，作为扩容依据）。

- **拒绝路径复用正常路径的事件框架**：`META` → `REJECT` → `FINISH` → `DONE`，前端只需多认一个 `reject` 类型，其余逻辑不变。

- **许可释放三道防线**：`Ticket.cleanup()` 管排队中的（`PENDING`/`TIMED_OUT`/`CANCELLED`）；`grant()` 的 `try/finally` 管已执行的（**`cleanup()` 在 `GRANTED` 下绝不释放，否则业务还在跑就把 slot 让给了别人，直接突破并发上限**）；`lease` 管不可预期的灾难（进程被杀、机房断电）。

- **`lease` 的上下界都有硬约束**：太短会导致业务还在跑许可被回收、并发实际超限；太长则崩溃后长时间降配。调优原则是 **`max-wait-seconds × 3 < lease-seconds`**。

- **`stop()` 的顺序是从外到内**：先摘 Pub/Sub 监听器（不再接新事件）→ 再 `scheduler.shutdown()` + 最多等 3 秒 → 最后清空 poller 注册表。**反过来会让监听器向已关闭的 scheduler 提交任务抛 `RejectedExecutionException`。**

- **daemon 线程为什么还要主动关**：JVM 退出是粗暴杀——poller 可能正好停在"`tryAcquire` 拿到 `permitId` 但还没 `permitRef.set`"的那一瞬间，**Redis 里许可被占着而 Java 侧不知道 permitId 是什么**，只能等 600 秒 lease 回收。

## 关键概念/术语

- **双路径驱动**：同一个 poller 由周期调度与广播唤醒共同触发，前者兜底后者提速。
- **惊群（Thundering Herd）**：一次释放唤醒全部等待者，集体涌向 Redis。
- **去抖（Debounce）**：把短时间内的多次通知压成一次处理。
- **火上加柴**：跑的过程中来了新通知就续一轮，而不是另起一个任务。
- **租约兜底（lease）**：持有者彻底失联时由存储侧自动回收许可。

## 值得注意的设计取舍/坑

- **拒绝路径新建了第二个 `SseEmitterSender`，把第 15 篇那套 CAS 幂等保护整个架空了。** `sendRejectEvents()` 第一行是 `new SseEmitterSender(emitter)`，而正常路径的 sender 是 `StreamChatEventHandler.initialize()` 里创建的**另一个实例**。两个实例包着同一个 `SseEmitter`，**各自持有独立的 `AtomicBoolean closed`**——第 15 篇反复强调的"`emitter.complete()` 不是幂等的，重复调用会抛异常，所以要用 CAS 保护"在这里完全失效：A 实例的 CAS 挡不住 B 实例去调 `complete()`。**保护的前提是"同一个 emitter 只有一个 sender"，而这条不变量没有任何机制维持。**

- **同一条链路上还会推出两个不同的 `taskId`。** 按第 17 篇的 `streamChat()`，`callbackFactory.createChatEventHandler(emitter, conversationId, taskId)` 是在 `chatQueueLimiter.enqueue()` **之前**调用的，而 `StreamChatEventHandler` 构造时立即 `initialize()`——**推一个 `META` 事件并把 `taskId` 注册进 `StreamTaskManager`**。若这个请求随后在队列里超时，`recordRejectedConversation()` 内部又 `IdUtil.getSnowflakeNextIdStr()` 生成了一个**新的** `taskId`，`sendRejectEvents()` 再推第二个 `META`。于是前端先后收到两个 `META`、两个不同的 `taskId`，**而它存下来用于调停止接口的那个（第一个）已经没有任何东西与之对应**；同时第一个 `taskId` 在 `StreamTaskManager` 里注册了却永远不会 `unregister`，只能等 30 分钟 TTL。**这是第 15、16、17 三篇的组件各自正确、拼在一起却错位的典型**——排队限流是后加的一层，它被插在了回调实例创建之后，而那个实例已经产生了对外可见的副作用。

- **`String.valueOf(rejectedContext.messageId)` 又出现了一次。** 第 16 篇 `buildCompletionPayloadOnCancel()` 里同样的写法把 `null` 变成了字符串 `"null"`，绕过 `@JsonInclude(NON_NULL)`。同一个模式在两个不同的类里各出现一次，**说明它不是笔误而是习惯**。`recordRejectedConversation` 可能返回 `null`（`question` 或 `userId` 为空时直接 `return null`），此时 `sendRejectEvents` 只推 `DONE`——这条分支是对的；但只要 `RejectedContext` 存在而 `messageId` 因落库失败为 `null`，前端就会拿到 `"null"` 字符串。**代码审查时值得全局搜一遍 `String.valueOf(` 的用法。**

- **`fire()` 里的 `break` 会连同已累积的通知一起丢弃，而原文把这说成是刻意的。** 第三道防线查到 `availablePermits() <= 0` 就 `break`，跳过 `while` 条件检查，**期间累积的 `pendingNotifications` 不会触发下一轮**。原文的辩护是"许可为 0 时再跑一轮也是白跑，等下一次 release 重新驱动"。但这与它自己刚论证过的"Pub/Sub 会丢"直接冲突——**如果那次"下一个 release 的广播"恰好落在会丢的四种场景里，这些等待者就只能靠 200ms 周期轮询发现许可**。也就是说：第三道防线在优化掉开销的同时，把一部分等待者从"快路径"降级回了"慢路径"，而这正是 Pub/Sub 存在的意义。**降级本身可接受（轮询兜底还在），但它不该被描述成没有代价。**

- **`fire()` 遍历的是 `pollers.values()`，一个 `ConcurrentHashMap` 的弱一致视图。** 遍历期间新注册的 poller 可能被看到也可能看不到，取决于时序。对"新入队的等待者"来说，漏掉这一轮问题不大（它自己的同步路径刚跑过 `tryAcquireIfReady`）。**真正微妙的是遍历顺序完全不确定**——`fire()` 触发全部 poller 的顺序与 ZSET 的 FIFO 顺序无关。公平性完全依赖 Lua 里的 `liveRank` 判定，**广播这一层是彻底无序的**。这个设计是对的（顺序在 Redis 侧裁决），但它意味着**本地看到的唤醒顺序对排查问题毫无参考价值**，日志里 poller 的执行先后不代表任何东西。

- **`awaitShutdown` 等 3 秒然后 `shutdownNow()`，而原文承认 poller 里没有显式的中断检查点。** 它的论证是"`tryAcquireIfReady` 内部有 Redis 调用，Redisson 的 `tryAcquire` 会响应 `InterruptedException`"。**但这条路径只覆盖了四个阶段中的一个**——阶段 2 的 `availablePermits()`、阶段 3 的 Lua `eval`、以及 `cleanup()` 里的一串 Redis 操作，是否响应中断取决于 Redisson 各 API 的实现，原文没有逐个核实。**"3 秒够它们跑很多遍了"这个理由才是真正起作用的那个**，中断响应只是纸面上的第二保险。

- **`recordRejectedConversation` 里 `memoryService.append(USER)` 会触发 LLM 生成会话标题——在系统已经过载到需要拒绝请求的时刻。** 拒绝路径的本意是快速止损，结果它内部（通过 `conversationService.createOrUpdate`）藏了一次 LLM 调用。**系统越忙，被拒的请求越多，这条路径上的 LLM 调用就越多**。而且这次调用不受排队限流保护（它不在 `onAcquire` 里）——**限流器保护了正常路径，却给拒绝路径开了一个不受限的后门**。`buildFallbackTitle` 的兜底说明作者知道这次调用可能失败，但没有意识到它的时机有多糟。

- **`Ticket.cancel()` 在 `GRANTED` 状态下仍执行 `cleanup()`，而 `cleanup()` 会 `queue.remove` 并据此广播。** 业务正常完成时 `emitter.complete()` → `onCompletion` → `cancel()` → `cleanup()`：此时该请求早已不在队列里（claim 时就 `ZREM` 了），`remove` 返回 false，`releasedPermit` 也是 false（`GRANTED` 守卫），于是不广播——**恰好正确**。但这个"恰好"依赖两个返回值同时为 false，而真正该在此刻广播的事件（许可被 `releaseHeldPermit()` 归还）是由 `try/finally` 那边单独广播的。**两条清理路径在同一个终态上并行跑，靠各自的返回值判断才没有重复广播**，这种正确性很难在代码里一眼看出，也很难写测试保证。
