# 《性能指标的口径选择》

> 原文链接：https://t.zsxq.com/jrYMw
> 所属分组：06-evaluation RAG 评测体系

## 一句话概括

流式问答的等待体验主要由首个正式回答到达时间决定，但完整耗时、输出速率和各阶段耗时仍是定位瓶颈所需的独立指标；分位数是否可信取决于样本量和采集口径。

## 核心内容提炼

- 完整流耗时随答案长度增加，不能单独代表“卡顿”；课程把 TTFT 作为主要体感指标、总耗时作为参考。
- TTFT 只记录第一个非空 `response` delta，不记录 thinking；这个定义必须与实际产品是否展示 thinking 保持一致。
- 小样本下 P95/P99 接近极值，易受一次网络抖动影响。课程在 20~150 条时选择 P50 + 均值，并用两者差距识别长尾。
- 性能指标应保留逐样本值，才能按意图、检索路径、模型或复杂度定位最慢样本。
- 课程对老数据缺 TTFT 时回退到总耗时，虽方便兼容，但两种口径不可直接作为同一时间序列比较。

## 关键概念/术语

- **TTFT**：从定义好的请求起点到首个正式回答 token 的时间。
- **Total latency**：从请求起点到流终止的完整时间。
- **尾延迟**：分布慢端的体验，通常用分位数而非均值观察。
- **删失样本**：因拒答、错误、取消或超时而没有 TTFT 的执行。

## 与 xrag 项目的关系

- xrag 存在排队、accepted、生成订阅和断连恢复，至少应区分提交到 accepted、排队等待、模型 TTFT、首个 SSE 可见字节和完整结算；不能笼统叫 TTFT。
- `ai_route_event` 与 `qa_turn_stage` 可提供服务端阶段耗时，浏览器/runner 可提供端到端体感，两者配合才能定位网络、排队、检索或模型慢。
- 取消、拒绝和失败没有正式回答首字，必须单独报告成功率/终态分布；只统计有 TTFT 的成功样本会产生幸存者偏差。
- 输出长度和 tokens/sec 应与总耗时一起保存，否则长答案天然更慢会被误判为回归。

## 值得注意的设计取舍/坑

- “TTFT 是唯一卡点”过于绝对：首字很快但后续 token 停顿、速率过低或最终永不结束同样损害体验。
- P95 并非按固定样本数自动失效；是否稳定要看目标、采样分布和置信区间。首版可报告但不宜用小样本 P95 做硬门禁。
- 缺失 TTFT 回退总耗时会混淆定义。xrag 应显式标记 `measurement_kind` 或拒绝跨口径比较。
