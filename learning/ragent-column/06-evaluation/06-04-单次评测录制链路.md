# 《单次问答背后的全链路》

> 原文链接：https://t.zsxq.com/jCALF
> 所属分组：06-evaluation RAG 评测体系

## 一句话概括

一次评测录制要同时保存用户实际看到的答案、产生该答案的证据、阶段身份和性能时间点；若这些事实来自两次独立执行，就只能视为近似证据。

## 核心内容提炼

- 课程让每条 query 调生产 SSE 获取答案/TTFT，再调检索旁路获取文档、分块、上下文和意图，合并为一条 JSONL 记录。
- 旁路复用改写、意图和检索服务但跳过生成，以配置开关在生产环境禁用。
- 文档级去重 ID 用于 Hit/Recall/MRR；与 contexts 一一对应的 chunk/doc 列表用于语义检索指标，两种粒度不能混用。
- TTFT 定义为请求发出到第一个非空正式回答 delta 到达，不把 thinking 或空 delta 当首字。
- runner 产物同时包含静态 gold、SSE 输出和旁路证据，使后续评分不再调用被评系统。

## 关键概念/术语

- **同源录制**：答案和证据来自同一次执行、同一个 turn/trace。
- **旁路漂移**：评测旁路与生产链路随代码演进出现行为差异。
- **双检索不一致**：同一 query 两次执行因改写、ANN、缓存或配置变化返回不同证据。
- **TTFT**：正式回答首个可见 token 的到达时间。

## 与 xrag 项目的关系

- xrag 的 `qa_turn`、`qa_intent_match`、`qa_retrieval_source`、`qa_tool_call`、`qa_generation_task` 与 AI 诊断已经能围绕同一 turn 关联；首选方案应从该事实链录制，不新增一条会漂移的复制链路。
- 课程旁路直接返回 chunk 正文；xrag 需要先裁决评测数据的权限、保留期限和外部 judge 发送边界，不能默认把用户与知识库正文长期落入报告。
- 客户端观测 TTFT 与服务端阶段耗时回答的问题不同，应分别命名和记录，不能用一个 `latency_ms` 混在一起。
- 录制失败也必须保留终态、失败码和已完成阶段，才能区分系统错误、正确拒答与不可评样本。

## 值得注意的设计取舍/坑

- 课程承认双请求只是“足够近似”。对于需要比较 Prompt 或生成质量的 xrag，这种近似可能把未实际喂给模型的 contexts 当作证据，导致 faithfulness 结论失真。
- 自写 SSE 解析器有协议维护成本；xrag 已有生产 SSE 契约，评测客户端应复用经过契约测试的事件语义。
- 多子问题只取第一个意图会丢失事实，不能用于 xrag 已支持的拆分链路。
