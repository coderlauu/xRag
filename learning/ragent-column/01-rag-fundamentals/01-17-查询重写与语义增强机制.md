# 《AI大模型Ragent项目》——查询重写与语义增强机制

> 原文链接：https://t.zsxq.com/d5ini
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

会话记忆解决了模型"听得懂上下文"的问题，但检索系统拿到的仍是用户原始的、可能含糊不清的一句话；这篇文章讲的是 Query 改写（Query Rewrite）——在检索之前用大模型把原始 query 改写成一个独立、完整、对检索友好的查询，并系统梳理了改写要解决的五类问题、Prompt 设计方式、成本时机权衡，以及改写在整条多轮对话 RAG 链路中的确切位置。

## 核心内容提炼

- **问题的引入：模型有记忆，但检索系统没有**。多轮对话里模型能看到完整历史，知道"它"指代什么，但检索系统在向量化之前拿到的仍然是那句带代词的原始问题。文章举例："那它的保修期呢"和"iPhone 16 Pro 保修期"两句话向量化后的距离可能相差很大，检索召回的很可能是无关内容（如笔记本电脑保修政策）。解法是在检索前先把原始 query 改写为语义完整的检索查询，这一步插入在"会话记忆读取之后、检索之前"。

- **改写要解决的不只是代词问题**，文章用电商客服场景列出四类典型情况：
  - **省略上下文**：连续聊了某个产品后突然问"还有别的颜色吗"，产品主体缺失，直接检索会召回所有产品的颜色信息。
  - **口语化表达**：用户说人话（"东西坏了咋整"），知识库文档写书面语（产品故障报修流程），两者语义有鸿沟，检索效果打折扣。
  - **多意图混合**：一句话里包含两个独立问题（退货流程+运费承担方），一次检索很难同时命中两个主题的 chunk。
  - **模糊描述**：如"那个很贵的手机"，检索系统无法理解这种相对性描述。
  这些问题的共性是：用户原始表达对检索系统不友好，改写的目标就是把它转成"独立、完整、检索友好"的查询。

- **五种改写策略及其取舍**：
  1. **指代消解（Coreference Resolution）**：把代词（它/这个/那个/上面说的等）替换成对话历史中的具体实体，是多轮对话里最高频的改写场景，**必须依赖对话历史**，实现复杂度低但影响是"不做检索基本失败"级别的。文章特别提到一个边界情况：如果历史里同时出现了多个实体（比如同时聊过 iPhone 16 Pro 和 AirPods Pro），代词指代会有歧义，改写模型的通常做法是取**最近一次被提到的实体**。
  2. **上下文补全（Context Completion）**：补全用户在多轮对话里自然省略的主体/条件信息（如"价格呢"缺产品名），同样依赖历史、复杂度低、属于必做项。文章指出它经常和指代消解同时出现（"价格呢"既省略了主体又省略了指代对象），实际改写时大模型会一起处理，不需要工程上单独区分两种情况。
  3. **口语化转正式（Colloquial to Formal）**：把用户口语转成更接近知识库文档措辞的正式表达，**不依赖对话历史**——哪怕是单轮对话（第一轮提问）也有改写价值，这点和前两种策略的适用范围不同。文章强调这一步的本质是"意图提取"而不是"字面翻译"：例如"能不能便宜点"的真实意图是"查询有没有优惠"，不是字面上的"要求降价"，改写模型需要理解真实意图再落笔。
  4. **多意图拆分（Intent Decomposition）**：把一句话里的多个独立意图拆成多个子查询，各自检索后再合并结果。文章给出明确的拆分判断标准：**不是所有涉及多个方面的长 query 都要拆**，只有当两个意图很可能分布在不同 chunk 里时才需要拆（例如"退货流程+运费承担方"通常是两个文档主题，但"iPhone 16 Pro 的价格和颜色"通常同一个产品介绍 chunk 就能覆盖，不用拆）。这是五种策略里复杂度最高的一种——拆分后每个子查询都要走一次完整检索，**成本直接翻倍**，如果业务场景里多意图问题不多，可以先不实现。
  5. **关键词扩展（Keyword Expansion）**：给原始 query 补充同义词和相关术语（如"屏幕碎了"扩展为"屏幕碎裂 屏幕破损 屏幕维修 碎屏险"），目的是提高召回率。文章明确指出这个策略主要对**关键词检索（BM25）**有用，因为 BM25 按词匹配，同义词扩展能直接提高命中率；对**向量检索帮助有限**，因为向量检索本身已经能捕捉语义相似性（"屏幕碎了"和"屏幕破损"的向量本来就很接近）。只有在混合检索（向量+BM25）架构下，这个策略在 BM25 那一路才有明显收益。

- **优先级结论**：指代消解和上下文补全是多轮对话场景下的必做项（不做的话多轮检索基本不可用）；口语化转正式建议做（投入产出比高，且单轮场景也适用）；多意图拆分和关键词扩展按业务需要决定，不是通用必需项。

- **用大模型统一实现改写，而不是给每种策略单独写规则**：一个 Prompt 就能同时覆盖指代消解、上下文补全、口语化转正式三类场景。文章给出两版 Prompt：
  - **基础版**：输入对话历史 + 用户最新问题，输出改写后的单条查询文本。关键约束是明确告诉模型"如果问题已经足够清晰，请原样输出，不要画蛇添足"——这条指令直接决定改写会不会"用力过猛"。
  - **进阶版**：输出格式改为 `{"queries": [...]}` 的 JSON 数组，用来支持多意图拆分（一句话拆成多条子查询）。文章的取舍建议很直接：JSON 解析增加了工程复杂度，且模型偶尔会输出格式不规范的 JSON；**除非业务确实需要多意图拆分，否则基础版更稳**。

- **改写质量取决于三个因素**：① **对话历史/摘要的质量**——如果会话记忆的摘要压缩得太狠、把关键实体名丢了，改写模型就没有素材可用（这一点直接把这篇文章和上一篇"会话记忆"的摘要质量挂钩，两者是上下游依赖关系）；② **Prompt 设计**——必须显式声明"已经清晰的 query 不改写"，否则模型倾向于过度补充；③ **模型能力**——改写任务本身对模型要求不高，文章给出的经验结论是 Qwen2.5-7B-Instruct 级别的小模型就能覆盖大部分场景，没必要用大模型做这一步。

- **三类典型改写失败模式**（这是文章里少见的"反面案例"部分，实操参考价值高）：
  - **过度改写**：用户问"它多少钱"，模型自己脑补出"iPhone 16 Pro 256GB 沙漠色钛金属版在京东平台的售价"——平台、颜色、容量都是用户没提过的，模型自己加的。
  - **改写不足**：代词完全没被替换，改写前后一模一样。
  - **偏离原意**：把"能不能便宜点"错误改写成"如何投诉商品定价过高"——完全误判了用户的真实意图。
  文章给出的直接对策是在 Prompt 里加一条"不要添加用户没有提到的信息"来抑制过度改写。

- **改写的成本与何时可以跳过**：每次改写调用一次大模型 API，大约增加 **200~500ms 延迟**+一点 token 成本。文章给出一个可跳过改写的简单启发式（Java 方法 `needsRewrite`：无历史且 query 长度>15 大概率不用改写；含代词必须改写；query 很短且有历史大概率要改写），但同时指出更稳妥的生产实践是：**只要有对话历史，就一律改写**，用小模型压低单次成本，避免规则覆盖不到边界情况导致漏改。

- **改写在 RAG 全链路里的确切位置和两个容易忽略的细节**：改写发生在"会话记忆读取之后、检索之前"。两个关键细节：① **检索用改写后的 query，但生成答案时喂给大模型的 Prompt 应该用用户的原始问题**，不是改写后的版本——改写的目的只是让检索更准，不是替用户改变提问本身（文章提到保守做法是把原始问题和改写问题都放进 Prompt）；② 改写这一步的输入是对话历史，输出是检索用的 query，这个先后关系决定了它必须排在会话记忆读取之后。

- **生产环境的三个工程要点**：
  1. **改写质量监控**：记录每次改写的完整信息（session_id、原始 query、改写后 query、历史长度、改写耗时、时间戳），并跟踪三个指标——**改写率**（触发改写的请求占比，过低说明判断规则太严）、**过度改写率**（人工标注后发现的画蛇添足比例，过高需要调 Prompt）、**改写后检索提升率**（对比改写前后的检索命中率）。文章特别提醒：改写效果差是一个"容易默默出错"的环节——用户只会觉得"AI 不够聪明"，不会意识到问题出在改写这一步，所以必须靠主动监控而不是等用户反馈。
  2. **改写失败兜底**：API 超时、模型服务不可用、返回格式异常时，直接**回退用原始 query 去检索**，不能让整条 RAG 流程因为改写失败而报错中断。文章用一句话定位改写的角色："改写是锦上添花，不是雪中送炭"——即使改写失败，用原始 query 检索也能有基本效果，只是精度打折。
  3. **改写缓存**：用 `sessionId + 原始query哈希` 做缓存 key，避免同一 session 内重复问题反复调用改写 API。文章特别强调缓存粒度必须包含 sessionId——因为同一句"价格呢"，在聊 iPhone 的上下文里和聊 AirPods 的上下文里，改写结果应该完全不同，缓存 key 如果只用 query 本身会导致跨话题串结果。

- **Java 实战代码的关键工程细节**：示例 `QueryRewriter` 用 OkHttp + Gson 调 SiliconFlow 的 `Qwen/Qwen2.5-7B-Instruct`，`temperature=0.1`（改写任务需要稳定输出，低温度合理）、`max_tokens=256`（改写结果通常很短，不需要大预算）。`rewrite(history, currentQuery)` 方法把历史拼成"用户：xxx\n助手：xxx"的文本块塞进 Prompt 模板，无历史时用占位符"（无历史对话）"，避免模板里出现空字符串导致歧义。`safeRewrite` 包一层 try-catch + 基本校验（非空、长度<500）做兜底，失败直接返回原始 query。

## 关键概念/术语

Query 改写（Query Rewrite）：在检索之前，把用户可能含糊、不完整的原始提问改写为独立、完整、对检索系统友好的查询的处理步骤，位于会话记忆读取之后、检索之前。
指代消解（Coreference Resolution）：把对话中的代词（它、这个、那个等）替换成其在历史中指代的具体实体。
上下文补全（Context Completion）：补全用户在多轮对话中省略的主体、条件等信息。
口语化转正式（Colloquial to Formal）：把用户口语化的表达转化为更接近知识库文档措辞、更利于检索命中的正式表达，本质是意图提取而非字面翻译，不依赖对话历史。
多意图拆分（Intent Decomposition）：把一句话中的多个独立意图拆分为多个子查询分别检索，判断是否要拆的标准是两个意图是否可能落在不同的 chunk 里。
关键词扩展（Keyword Expansion）：为原始 query 补充同义词/相关术语以提高召回率，主要对 BM25 关键词检索有效，对向量检索帮助有限。
过度改写：改写模型脑补出用户未提及的具体信息（如平台、颜色、型号细节），使改写结果偏离用户真实提问范围。

## 与 xrag 项目的关系

- 这篇是 `INDEX.md` 里 `05-qa-pipeline` 分组第 4 篇《用户说的话 ≠ 该搜的词》的前置基础概念版本——本篇讲的是"为什么要改写、有哪些策略、怎么权衡"，那一篇大概率会讲 xrag 项目里 Query 改写模块的具体工程实现。设计 xrag 检索问答链路时，本篇的五种策略分类（必做两项+推荐一项+按需两项）可以直接作为模块功能范围的决策依据：xrag 至少要落地指代消解和上下文补全，口语化转正式看知识库文档风格与用户提问风格的差异程度决定是否投入，多意图拆分和关键词扩展留到有明确业务信号（多意图占比高、或采用混合检索）时再加。
- 文章明确指出的"改写用小模型即可（Qwen2.5-7B-Instruct 级别）"这一结论，对 xrag 后续设计模型调度层（`04-model-scheduling`）有直接指导意义：Query 改写可以路由到轻量模型/低成本模型池，不需要占用主问答用的大模型配额，这是一个可以和"多模型路由与智能选择"那篇结合起来落地的具体场景。
- 改写"锦上添花、失败要兜底用原始 query"的设计原则，以及"检索用改写 query、生成用原始问题"的双轨用法，是 xrag 检索问答核心链路（`05-qa-pipeline`）在实现层必须遵守的硬约束——如果 xrag 的实现里把改写做成阻塞式且无兜底的强依赖，一旦改写服务异常会直接拖垂整条问答链路，这是设计时要提前预留的降级路径。
- 文章末尾把本篇和上一篇《多轮对话记忆设计》串联成"会话记忆→Query改写→检索"的顺序依赖关系，并预告下一篇是《意图识别与多路由调度策略》（即 `01-18`）。这提示 xrag 在设计问答主链路时，Query 改写应该作为一个独立、可插拔的处理阶段插在"读取会话历史"和"检索/路由"之间，而不是和检索逻辑耦合在一起写，方便后续接入意图识别时两个阶段能独立演进。

## 值得注意的设计取舍/坑

- **改写 Prompt 里"不要画蛇添足"这条约束容易被忽略，但后果很直接**：如果 Prompt 没有明确告诉模型"已经完整的 query 请原样输出"，模型倾向于过度补充用户没说过的细节（平台、颜色、型号），文章反复强调"过度改写比不改写更危险"——不改写只是精度打折，过度改写可能直接把检索导向错误方向。
- **进阶版（JSON 输出、支持多意图拆分）不是默认更优的选择**：JSON 解析增加工程复杂度，且模型偶尔输出格式不规范的 JSON，文章明确建议除非业务确实需要多意图拆分，否则基础版 Prompt 更稳——这是一个"功能更强不代表默认该用"的典型权衡。
- **关键词扩展策略对向量检索基本没用**，容易被误当作"通用召回提升手段"照搬进纯向量检索系统；只有在有 BM25 一路的混合检索架构下才值得做，用错场景等于白做工。
- **缓存粒度必须包含 sessionId 这一点看似简单，但读者评论区里出现了更细的争议**：有读者提出"改写缓存的 key 不能只由 sessionId+query 组成"，理由是同一 session 内用户也可能对不同的东西提出相同的问题；另一位读者回复认为"相同的 query 存一份就够了"。这两种立场分别对应"缓存 key 应该更细粒度（纳入当前话题/最近提到的实体）"和"缓存 key 保持粗粒度（只按字面 query 去重）"两种设计取向，文章正文本身给出的是后一种（sessionId+query 哈希），但评论区的分歧提示：如果 xrag 的实际场景里同一 session 内话题切换频繁（比如客服一次会话里连续问多个不同产品），字面 query 命中缓存可能会返回上一个话题的改写结果，这是实现缓存时需要留意的边界情况，不能照抄文章方案时忽略这个前提。
- **是否应该把 Query 改写做成一个由模型自主决定是否调用的工具（MCP/Function Call），而不是固定的管道步骤**：评论区里另一位读者提出这个设计思路，作者的回应是"改写是一个通用的步骤"——暗示作者倾向于把它当作每轮固定执行的管道环节，而不是交给模型按需判断调用的工具。这其实是两种架构哲学的分歧：固定管道步骤简单、行为可预测，但对所有请求都有额外延迟开销；工具化调用能省掉不需要改写场景下的开销，但把"是否改写"这个判断也交给了模型，多了一层不确定性。xrag 在设计这个模块时需要明确选边，不能两种思路混着实现。
