# 《知识问答在后端经历了哪八个阶段？》

> 原文链接：https://t.zsxq.com/pVQt8
> 所属分组：05-qa-pipeline AI知识问答核心链路

## 一句话概括

一次知识问答被编排成八个线性阶段（记忆 → 改写 → 意图 → 歧义引导 → 系统直答 → 检索 → 空结果兜底 → 生成），其中三个是**短路点**——歧义时反问、纯闲聊时跳过检索、检索为空时坦诚告知；短路的价值不在省算力，而在于**拒绝在信息不足时假装能回答**。

## 核心内容提炼

- 编排类 `StreamChatPipeline.execute()` 只有 20 行，是整个问答系统的骨架。每个阶段是一个私有方法，返回 `boolean` 表示"我已处理完，不用往下走了"：

  ```text
  阶段 1：loadMemory            — 加载会话记忆
  阶段 2：rewriteQuery          — 查询改写与子问题拆分
  阶段 3：resolveIntents        — 意图识别
  阶段 4：handleGuidance        — 歧义引导        [短路点 #1]
  阶段 5：handleSystemOnly      — 系统直答        [短路点 #2]
  阶段 6：retrieve              — 多通道检索（KB + MCP）
  阶段 7：handleEmptyRetrieval  — 空结果兜底      [短路点 #3]
  阶段 8：streamRagResponse     — Prompt 组装 + 流式生成
  ```

- **阶段顺序不是随意排的，每一步都被前后依赖钉死**：改写要消解代词（"那它能退货吗"里的"它"），必须先有对话历史；意图识别要对每个子问题分别分类，必须先有拆分结果；检索要知道查哪个库、查多少条，必须先有意图分数。

- **三个短路点的触发条件与意图各不相同**：

  | 短路点 | 阶段 | 触发条件 | 行为 | 意图 |
  |---|---|---|---|---|
  | #1 歧义引导 | 4 | 多个意图高分命中且互相冲突 | 推送引导选项，**不调 LLM** | 与其猜错不如问清楚 |
  | #2 系统直答 | 5 | 全部意图都是 SYSTEM 类型 | 跳过检索，**仍调 LLM** | 不需要检索就不要检索 |
  | #3 空结果兜底 | 7 | KB 与 MCP 都没返回结果 | 推固定文案，**不调 LLM** | 与其让模型编造不如坦诚告知 |

- **意图分三类**：`KB`（知识库检索）、`MCP`（工具调用）、`SYSTEM`（系统直答）。意图体系是一棵树而非扁平分类，每个子问题会命中若干带分数的叶子节点，并由一个"封顶算法"控制保留数量——保证每个子问题至少留最高分意图，再按全局分数分配剩余配额。

- **阶段 6 的两条路径并行**：KB 意图走多通道并行向量检索 + 去重 + 精排；MCP 意图走工具执行链取实时数据。两者合并进一个 `RetrievalContext`（含 `kbContext` 与 `mcpContext`）。

- **阶段 8 做四件事**：意图聚合 → Prompt 组装 → 参数调整（纯 KB 场景 `temperature=0.0` 尽量忠于原文，混入 MCP 数据时 `0.3` 允许整合发挥）→ 流式生成并注册取消句柄。

- **数据总线是一个 `StreamChatContext`**，不靠方法参数层层传递。字段分两类：不可变输入（`question`/`conversationId`/`taskId`/`userId`/`callback`，`final` 修饰，天然线程安全）与流水线中间状态（只有三个可变字段，分别由阶段 1/2/3 填充，后续阶段只读）。

- **Pipeline 之外还有三层前置设施**：幂等提交拦截（防连点导致记忆写入冲突）、队列式并发限流（Redis 信号量控制并发坑位，超时则拒绝而非干等）、全链路 Trace 初始化（`traceId`/`taskId` 跨线程池传递）。它们不属于八阶段，但决定请求能否进入 Pipeline。

## 关键概念/术语

- **短路点（short-circuit）**：Pipeline 中允许提前终止的阶段。判据是"已经能确定答案，或已经能确定无法回答"。
- **子问题拆分**：把复合问题拆成多个可独立检索的问题（"iPhone 和 AirPods 的退货政策分别是什么" → 两个子问题）。
- **意图树**：分层的意图分类结构，叶子节点对应具体意图并携带类型（KB/MCP/SYSTEM）与打分。
- **封顶算法**：在"意图多样性"与"检索开销"之间取平衡的配额分配策略。
- **歧义引导**：多个意图高分冲突时反问用户而非猜测，用户选择后带着明确意图重新进入 Pipeline。
- **空结果兜底**：检索为空时推送固定文案，拒绝把空上下文交给模型自由发挥。
- **数据总线 Context**：贯穿全流程的单一上下文对象，阶段间通过它读写而不互相调用。

## 与 xrag 项目的关系

- **这是 Phase 3 的全景地图**，八个阶段对应本分组后续 17 篇。xrag 的 Phase 3 要建的正是这条链路，但**必须独立设计**——按 [ADR 0001](../../../docs/adr/0001-build-xrag-independently.md)，课程配套仓库的 Schema、配置与模块结构都不是 xrag 的基线，只能作为对比参考。

- **前两个 Phase 的产出正好是这条链路的两端**：知识库（`com.app.knowledge`）提供阶段 6 要检索的分块与向量；模型调度（`com.app.ai`）提供阶段 2/3/5/8 要用的 Chat 与流式 Chat、阶段 6 精排要用的 Rerank。Phase 3 是把两端接起来的中间层。

- **调用纪律已经定死**：Phase 3 不得绕过 `com.app.ai` 直接碰 Provider SDK，只能面向四个能力端口（[ADR 0003](../../../docs/adr/0003-separate-model-capability-ports.md)）；且 Rerank 可能返回 Noop 降级，阶段 6 的后处理必须区分 `rerankApplied=false` 与普通成功。

- **原文的三处并发/分布式设计与 xrag 的既有决策有张力，不能照搬**：

  | 原文方案 | xrag 现状 | 处理方式 |
  |---|---|---|
  | `@IdempotentSubmit` + 分布式锁 | [ADR 0002](../../../docs/adr/0002-knowledge-base-async-and-concurrency.md) 明确不引入 Redisson，用状态字段 CAS 替代分布式锁 | Phase 3 需重新论证，不直接引入 |
  | Redis 信号量控并发坑位 | 同上，且 ADR 0002 假设**单实例部署** | 单实例下进程内信号量即可，多实例才需要 Redis |
  | `TransmittableThreadLocal` 跨线程池传 Trace | Phase 2 已有诊断表与 Trace Console，但走的是**完成态异步写入**而非线程上下文透传 | 优先复用 `com.app.ai.diagnostic` 的既有模式 |

- **阶段 8 的 `temperature` 分场景取值**（纯 KB 0.0 / 混合 MCP 0.3）需要落到 `CallOptions`，这是 Phase 2 能力端口已有的位置，不需要新增机制。

- **检索策略尚无 ADR**（见 CLAUDE.md），阶段 6 的多通道并行、去重、精排方案是 Phase 3 Step C 要形成决策的地方，现在不要假设已有定论。

## 值得注意的设计取舍/坑

- **短路不是性能优化，是正确性设计。** 三个短路点里有两个（歧义引导、空结果兜底）根本不调用 LLM，省下的算力是副作用；真正的目的是**在信息不足时拒绝作答**。电商场景下编造的退货政策比"没找到"危险得多——这一点决定了空结果兜底不能改成"让模型基于常识回答"。

- **Context 的可变字段只有三个，这是有意的。** 前三个阶段各填一个，后续阶段只读。可变字段一多，"这个字段到底谁写的、写了几次"就无从追溯，阶段间的解耦也就名存实亡。

- **意图命中多不等于回答得更好。** 意图越多，后续检索通道和工具调用越多，开销与噪声同步上升。封顶算法的存在说明"召回更多"在这一层是负担而不是收益，需要显式设上限。

- **`boolean` 返回值做短路控制读起来直白，但语义是"我处理完了"而不是"成功了"。** 阶段 4 返回 `true` 表示已推送引导，阶段 7 返回 `true` 表示已推送兜底——都是正常路径而非失败。命名与文档要写清楚，否则很容易被后来者误读成错误标志。

- **前置三层设施容易被当成"和 RAG 无关的工程细节"跳过。** 但幂等拦截缺失会导致同一用户两次请求并发写记忆，Trace 缺失会让"这次慢了 3 秒卡在哪"无从查起——它们是链路可运维的前提，不是可选项。

- **本篇自述的"18 篇地图"是旧版目录，与实际发布篇目对不上。** 原文地图把第 17 篇列为"这次回答慢了 3 秒，到底卡在哪个环节？"（Trace 追踪）、第 18 篇为队列式并发限流；而实际发布的 17/18 是"10个人同时提问只有3个坑位"与"抢不到许可请求该等还是该拒？"——两篇都在讲限流排队，**Trace 追踪没有独立成篇**。已对 18 篇全部抓取核对，本仓库 [INDEX.md](../INDEX.md) 的记录与实际发布一致，不需要更正。

  这条差异本身值得留意：全链路 Trace 在本篇被列为三层前置设施之一、后文却没有专门篇幅展开，说明**这一块的设计要靠 xrag 自己补**。好在 Phase 2 已经有了诊断表与 Trace Console，问答链路的可观测性可以沿用那套模式而不是从零设计。
