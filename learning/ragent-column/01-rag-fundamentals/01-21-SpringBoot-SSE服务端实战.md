# 《AI大模型Ragent项目》——SpringBoot-SSE服务端实战

> 原文链接：https://t.zsxq.com/l9Xki
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章讲清了 Spring Boot 如何同时充当上游大模型的 SSE 客户端和前端浏览器的 SSE 服务端：用 `SseEmitter` 释放请求线程并逐 Token 转发，同时补齐事件契约、超时、心跳、断连清理、线程池、反向代理缓冲和前端消费方式等生产约束。

## 核心内容提炼

### 1. 后端中间层不是多余转发

前端不应直连大模型 API，主要有三类硬约束：

- API Key 放在浏览器中会直接暴露，无法保护模型额度和账单。
- 第三方模型 API 的跨域策略不受业务系统控制。
- 鉴权、限流、敏感内容处理、会话记录和审计等业务逻辑必须由后端承接。

因此完整链路应是“前端 → Spring Boot → 大模型 API → Spring Boot → 前端”。Spring Boot 面向上游消费 SSE，面向下游生产 SSE。

### 2. `SseEmitter` 的异步模型

- Controller 创建并返回 `SseEmitter` 后，HTTP 连接保持打开，但 Tomcat 请求线程可以立即释放。
- 真正的模型调用和事件推送由独立执行线程承担，通过 `emitter.send()` 持续写事件，以 `complete()` 或 `completeWithError()` 结束。
- `onCompletion`、`onTimeout`、`onError` 构成连接生命周期回调，其中资源清理应尽量收敛到最终都会触发的 `onCompletion`。
- 如果仍在 Controller 线程里完成全部模型调用和推送再返回，虽然使用了 `SseEmitter`，但没有获得跨线程异步的价值。

活跃连接不会长期占用 Controller 线程，却仍会占用一个 `SseEmitter`、一个推送任务、一个上游 HTTP 连接和一个 Tomcat NIO 连接，因此不能把“异步”误解为“没有资源成本”。

### 3. 明确前后端事件契约

文章建议至少区分三类事件：

| 事件 | 含义 | 典型数据 |
|---|---|---|
| `token` | 一段增量内容 | `{"content":"..."}` |
| `done` | 本次生成完成 | Token 用量或完成信息 |
| `error` | 流内错误通知 | 错误码和可展示消息 |

后端从上游响应中提取 `delta.content` 后发送 `token`；遇到 `[DONE]`、结束原因或独立 usage chunk 时发送 `done` 并关闭连接；HTTP 失败、异常 EOF 或解析链路错误则发送 `error` 或异常完成。

### 4. 生产化需要四类治理

1. **超时分层**：`SseEmitter` 超时限制整条下游连接的生命周期，文中建议 3～5 分钟；OkHttp `readTimeout` 限制上游两个 chunk 之间的最大等待间隔，文中建议 30～60 秒。二者不能混为一谈。
2. **心跳保活**：模型长时间没有新 Token 时，定期发送 SSE 注释心跳，避免 Nginx、负载均衡器或 CDN 把空闲连接关闭；文章建议 15～20 秒一次。
3. **断连与取消**：用户关闭页面后，`send()` 会失败；后端不仅要停止推送和心跳，还应尽可能取消仍在计费的上游模型请求。
4. **受控执行器**：示例里的 `new Thread()` 只用于解释机制。生产环境应使用专门且有界的线程池，控制并发、队列和拒绝策略，避免无限制创建线程。

### 5. 前端接入方式决定接口形态

- 浏览器原生 `EventSource` 使用简单并支持自动重连，但只支持 GET，且不能自定义 `Authorization` 等请求头；收到 `done` 后必须主动 `close()`，否则会把正常结束误判为断线并重新请求。
- `fetch` + `ReadableStream` 可以使用 POST、复杂 JSON 请求体和自定义请求头，更适合真实问答请求，但前端需要自行解析 SSE 行、事件边界和不完整缓冲区。

接口不能先固定成 GET 或 POST 再让前端迁就，应根据请求体复杂度、鉴权方式和客户端实现共同确定。

### 6. 反向代理配置是流式效果的一部分

Nginx 默认响应缓冲会把多个 Token 攒在一起再转发，表现为“等待数秒后一次出现一大段”。SSE 路由需要关闭代理缓冲和缓存、设置足够长的读取超时并保持 HTTP/1.1 长连接；后端也可发送 `X-Accel-Buffering: no` 和 `Cache-Control: no-cache`。

因此“后端逐 Token 调用 `send()`”并不能独立证明端到端流式成功，必须从浏览器跨过反向代理观察到持续增量到达。

## 关键概念/术语

- `SseEmitter`：Spring MVC 提供的异步响应对象，可在 Controller 返回后由其他线程持续推送 SSE 事件。
- 推送线程：负责上游模型调用和下游事件写入的执行线程，与短生命周期的 Controller 请求线程分离。
- 生命周期回调：`onCompletion`、`onTimeout`、`onError`，用于识别连接结束并释放心跳、上游请求等资源。
- SSE 事件契约：前后端对 `token`、`done`、`error` 等事件名称及数据结构的共同约定。
- 心跳注释：以 `:` 开头、客户端忽略但中间代理可感知的 SSE 数据，用于维持空闲长连接。
- 代理缓冲：反向代理为提高普通响应吞吐而暂存数据的机制；对实时 SSE 路由必须关闭。
- `EventSource`：浏览器原生 SSE 客户端，只支持 GET 且不能自定义请求头。
- `ReadableStream`：前端通过 `fetch` 读取响应流的接口，可承载 POST 和自定义鉴权头，但需自行解析协议。

## 与 xrag 项目的关系

当前 xrag 后端只有健康检查接口，尚未实现问答 API、上游流式模型客户端或下游 SSE 服务端；本文应作为未来问答传输层的设计输入，而不是对现状的描述。

- xrag 若选择流式问答，需要先定义稳定的事件契约，至少分开增量、完成和错误，避免前端靠内容形态猜测流状态。
- `deploy/nginx/web.conf` 和 `deploy/caddy/Caddyfile` 是端到端验证的一部分；实现后必须验证代理不会缓冲流式响应。
- 上游模型请求、下游客户端连接、心跳任务和推送执行器应共享一个可取消的请求生命周期。用户停止生成或断连时，只关闭浏览器连接而不取消上游请求会继续消耗模型配额。
- xrag 当前没有足够的并发与延迟数据，文章中的线程池数字只能作为示例，不能直接固化为项目参数。

## 值得注意的设计取舍/坑

- **Spring MVC 与 WebFlux 是架构选择，不是语法替换**：`SseEmitter` 适合保留 Spring MVC 模型并用受控执行器桥接阻塞式上游客户端；若未来选择全链路响应式客户端和背压模型，才值得评估 WebFlux，不能只因为“SSE 是流”就混用两套并发模型。
- **`CallerRunsPolicy` 不是无损的免费兜底**：队列满时让 Controller 线程执行长时间模型调用，会重新占用请求线程并放大拥塞。是否接受这种退化，需要结合“排队、快速拒绝还是同步降级”的产品策略决定。
- **完成事件必须与连接关闭配套**：只关闭连接会触发 `EventSource` 自动重连；只发 `done` 却不释放服务端资源也会泄漏。前后端都要把 `done` 当作显式终止协议。
- **异常完成不等于错误事件一定到达**：连接已经断开时，向客户端再发送 `error` 很可能失败，服务端仍需保留日志和可观测状态。
- **双重超时容易误配**：连接总寿命和上游静默间隔属于不同维度；设得过短会误杀慢生成，设得过长会延迟故障回收。
- **端到端测试不可缺少代理层**：只用 Controller 单测或直连后端验证，无法暴露 Nginx/Caddy 缓冲、网关超时和连接头配置问题。
