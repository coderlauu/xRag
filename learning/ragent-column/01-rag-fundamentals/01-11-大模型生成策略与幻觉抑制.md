# 《AI大模型Ragent项目》第11小节：大模型生成策略与幻觉抑制

> 原文链接：https://t.zsxq.com/3v399
> 所属分组：01-rag-fundamentals RAG与大模型基础概念

## 一句话概括

这篇文章讲的是 RAG 流程里"检索之后"的最后一公里问题：即便混合检索 + 重排序已经拿到了高质量的 Top-K chunk，只要 Prompt 设计不到位，大模型仍然会用自己的预训练知识覆盖、篡改甚至无视检索结果，本文给出了一套三段式 Prompt 结构、幻觉抑制技巧、引用对齐机制和答案约束方法，并配上完整的 Java 生成链路代码，来保证"检索对了"能真正转化为"回答对了"。

## 核心内容提炼

- **问题引子**：作者用电商退货场景做示范——用户问 iPhone 16 Pro Max 拆封后能否退货，检索命中的 chunk 明确说不支持七天无理由退货，但作者实测千问 Qwen3-Flash 模型时，模型仍回答"可以无理由退货"。这说明模型会用训练时学到的通用常识（大部分商品支持七天无理由退）覆盖检索到的具体业务规则，检索质量再高也保证不了生成质量。

- **三类典型翻车场景**（生成阶段幻觉的具体表现）：
  - **凭空捏造细节**：chunk 只说了"质量问题退货运费由商家承担"，模型自己加上了"3-5 个工作日退款到账"这类 chunk 里完全没有的信息，一旦实际时效不符就会引发用户投诉。
  - **张冠李戴**：检索到两个 chunk（AirPods Pro 默认保修 1 年；AppleCare+ 可延保至 2 年），模型把两者信息拼接成"保修期 2 年，自购买之日起计算"，这种幻觉每个信息点单独看都对，但组合方式错了，比整段编造更隐蔽、更难发现。
  - **答非所问**：chunk 里明确写了"48 小时内发货"，模型却跑去介绍物流合作商和次日达能力，完全没有对齐用户实际提问的点。

- **生成阶段三大核心挑战**：幻觉（编造或篡改 chunk 内容，后果是错误答案、客诉甚至法律风险）、答非所问（没聚焦问题，导致用户体验差需反复追问）、缺乏可追溯性（用户不知道答案依据，企业级场景无法通过合规审计）。文章指出这三个问题的根源都指向 Prompt 设计，因此后续内容全部围绕 Prompt 展开。

- **RAG Prompt 的三段式结构**：System Prompt（定义模型角色、行为边界、不能做什么）+ Retrieved Context（把 Top-K chunk 组装成上下文喂给模型）+ User Query（用户原始提问）。三段各司其职：System Prompt 相当于新员工的岗位手册，Context 相当于参考资料，User Query 相当于客户来电。
  - **System Prompt 基础模板的 6 条规则**，每条对应解决一个具体问题：①只基于参考资料回答（防止预训练知识覆盖检索结果，对应"篡改事实"）；②信息不足时明确告知固定话术（给模型一个兜底出口，对应"凭空捏造"）；③禁止编造数字/日期/金额等具体细节（这些是幻觉高发区）；④回答需标注参考资料编号 `[1]`（解决可追溯性问题）；⑤多条资料冲突时指出冲突、以更新时间新的为准（对应"张冠李戴"）；⑥语气要求（间接影响答非所问的体验）。
  - **常见设计误区**：太短则等于没约束，模型会自由发挥；太长则规则互相冲突（比如同时要求"详细"和"简洁"），模型表现反而不稳定——经验法则是核心规则控制在 5~8 条，但作者特别指出，复杂场景下 5~8 条往往不够，需要大量测试排查规则之间是否存在"左右互搏"；缺兜底指令是最致命的误区，没有兜底模型会默认"尽力回答"也就是开始编造。

- **检索上下文的组装细节**：推荐格式是每个 chunk 带编号 `[1][2][3]`、来源、更新时间，用空行分隔避免相邻内容混在一起理解。来源和更新时间取自 chunk 的元数据（Metadata），更新时间的作用是当多条资料冲突时供模型判断哪条更权威。
  - **上下文窗口限制**：即便模型支持 128K 甚至更长上下文，塞太多 chunk 也不是好事——关键信息会被稀释、噪音变多；还会触发"迷失在中间"（Lost in the Middle）现象，模型对上下文中间位置内容的关注度更低；同时输入 token 越多成本和延迟越高。
  - **chunk 数量的经验法则**：简单事实问答（如退货政策）推荐 3~5 个；复杂对比类问题推荐 5~8 个；总结类问题（覆盖某品类全部规则）推荐 8~10 个但要注意去重。如果已经用了 Reranker，Top-K 质量本身已经很高，通常 3~5 个就够——原则是宁可少给几个高质量的，也不多给低质量的。

- **User Query 处理**：多数场景直接用用户原始问题即可；但遇到语义模糊的提问（比如"退货怎么弄"，无法判断是问流程、条件还是运费）需要 Query 改写（Query Rewriting）来澄清，文章明确把 Query 改写列为一个独立话题，本篇不展开，留给后续文章。

- **幻觉抑制的五个实用技巧**：
  1. 明确限定知识来源——反复强调"只基于参考资料回答"，让模型把 chunk 当唯一依据而不是仅供参考。
  2. 加兜底指令——明确告诉模型信息不足时该怎么回答，这是抑制"凭空捏造"最关键的一条，不能省略。
  3. 禁止编造具体细节——针对数字、日期、金额这类模型最容易"顺手补全"的信息重点约束。
  4. 要求先引用再回答——让模型为每句话找到对应 chunk，找不到就不敢说，这是引用规则对幻觉的间接抑制作用。
  5. 降低 Temperature 参数——从采样层面减少模型的"自由发挥"空间。

- **Temperature 与 Top-P 参数机制**：Temperature 控制输出的随机程度，值越低越倾向选择概率最高的词（0 表示几乎总选最高概率词，输出最保守；0.7 是常见默认值，适合创意写作；1.0 以上输出很随机，适合头脑风暴）。Top-P（核采样）是另一种控制随机性的方式，比如 0.9 表示只从累计概率达到 90% 的候选词里采样，排除掉概率很低的长尾选项。**RAG 场景推荐设置**：Temperature 取 0~0.3，Top-P 取 0.9~0.95；且两者通常不需要同时调，大多数情况下只设置 Temperature 就够，同时设置两者时不同模型的行为可能不一致，建议先只调 Temperature。

- **兜底回答的设计原则**：兜底不是简单说"我不知道"，好的兜底应做到三点——承认信息不足、给出替代方案（如联系人工客服）、如果能部分回答就先给出已知部分。文章给了三种模板：完全无法回答、部分可以回答（分段说明已知/未知部分）、问题超出知识库范围。

- **引用对齐（Citation Alignment）的作用与实现**：类比新闻报道标注数据来源，用户看到答案后的第一反应是"这个答案靠谱吗"，标注引用来源比模型自称"我的回答是准确的"更有说服力。企业级场景（金融、医疗、法律）引用对齐是合规审计的刚需，也是问题追溯（定位是知识库问题还是模型问题）和建立用户信任的基础。
  - 实现思路：上下文每个 chunk 带编号 + Prompt 要求模型在回答时标注 `[1]`、`[2]`（一句话多个来源可同时标注多个编号，如 `[1][3]`；只引用真正用到的资料，不引用无关资料）+ 后端用正则 `\[(\d+)\]` 解析模型输出中的引用标记，关联到对应 chunk 元数据，渲染成可点击链接供前端展示，用户点击后可跳转原文自行验证。

- **答案约束：控制输出格式与边界**——除了抑制幻觉和引用对齐，Prompt 还要控制输出的形式：
  - **格式约束**：纯文本（客服场景默认）、JSON（下游程序消费场景，字段一般包含 answer/citations/confidence，作者特别提醒要在 Prompt 里给输出示例，否则模型可能自己发明字段名，另外部分大模型 API 支持 `response_format` 参数强制 JSON 输出，比纯 Prompt 约束更可靠）、编号列表（知识卡片场景）。
  - **长度约束**：简短回答（1-2 句话，适合聊天机器人）、详细回答（适合知识库查询/报告生成）、限定字数。RAG 客服场景推荐中等长度——覆盖核心要点+必要注意事项，不展开无关背景知识。
  - **边界约束**：限定模型只回答知识库范围内的问题（如售后、退换货、物流），遇到超出范围的问题（天气、写诗、品牌对比）要礼貌拒答并引导回话题范围，同时明确禁止回答涉及品牌对比、价格预测、主观观点等争议性话题。

- **生产级 System Prompt 的完整结构**：按"角色与边界 / 回答规则 / 引用规则 / 格式要求"四个分组组织，比基础版内容更多但依然保持清晰分组，好处是模型更容易理解每条指令的优先级，也方便后续针对某一维度单独调优。

- **Java 完整生成链路实现**（对应 TinyRAG 项目 `com.nageoffer.ai.tinyrag.retrieve` 目录）：整体分四步——① Milvus 混合检索 + Reranker 重排序拿到 Top-K chunk（复用上一篇成果）；②把 chunk 组装成带编号、带元数据的上下文（`buildContext`）；③拼接 System Prompt + 上下文 + 用户问题，调用大模型 Chat API（`callLlm`，示例用 SiliconFlow 的 `Qwen/Qwen2.5-7B-Instruct`，temperature 设为 0.1，max_tokens 1024）；④解析模型回答中的引用编号并关联到 chunk 元数据（`parseCitations`，用正则 `\[(\d+)\]` 提取，并做了 `index >= 1 && index <= chunks.size()` 的边界检查，防止模型引用了不存在的编号）。
  - **关键设计点**：System Prompt 放在 `role: system` 消息里，检索上下文和用户问题放在 `role: user` 消息里分开传递，作者认为这样模型能更清楚区分"行为指令"和"参考内容"，效果优于把两者塞进同一条消息；Temperature 特意设为 0.1 而不是 0，因为完全确定性输出有时会显得过于生硬，0.1 保留一点灵活性同时几乎不产生幻觉；引用解析的边界检查是防止模型"引用幻觉"（引用了实际不存在的 chunk 编号）的代码层兜底手段。
  - **实测结果与局限**：用 iPhone 退货+运费的组合问题跑通全流程，模型正确引用了 3 个 chunk 并区分了不同退货情形下的运费归属，还基于两个 chunk 的对比做出了"iPhone 16 Pro Max 是特殊商品不适用通用规则"的合理推理（作者强调这属于合理推理不算幻觉）。但作者也如实记录了局限：多次测试中，其中一个 chunk（"通用退货规则"）偶尔会出现该被引用却没被引用的情况，说明即便低温度，引用行为仍带有一定随机性，不是绝对可靠的硬保证。

- **Prompt 迭代优化的实用流程**：①收集 bad case，至少记录用户问题、检索到的 chunk、模型的错误回答三项信息；②把每个 bad case 归类到固定类别（篡改事实/凭空捏造/张冠李戴/答非所问/格式不对/超出边界），每个类别对应明确的优化方向；③针对性修改 Prompt（文章给了三个真实 bad case 示例：多 chunk 数字混淆→要求区分不同资料的适用条件和主体；chunk 信息不足时自补细节→强化兜底指令让其更具体地说明"哪些能答哪些不能答"；回答了非售后问题→在角色边界里加入针对"商品功能/参数"类问题的专门拒答话术）；④用所有历史 bad case 做回归测试，确保新修改没有引入老问题。文章强调 Prompt 调优是持续过程，不存在一次性写对的完美版本。

- **全链路定位**：文章末尾用一张全景图把 RAG 系列所有环节串联——文本提取（Tika）→数据分块（Chunking）→元数据管理（Metadata）→向量化（Embedding）→向量数据库（Milvus）→混合检索+重排序（检索策略篇）→Prompt 组装+大模型生成（本篇）。本篇是整条链路里"检索之后、交付之前"的最后一环。

- **核心结论**：检索决定答案的上限（能不能找到对的信息），生成决定答案的下限（找到了对的信息能不能说对），两者都要抓、都要硬——这是文章反复强调的一句话总结。

## 关键概念/术语

三段式 Prompt 结构：System Prompt（角色与行为边界）+ Retrieved Context（编号化的检索上下文）+ User Query（用户问题）组成的 RAG Prompt 骨架。
幻觉（Hallucination）：模型生成的内容读起来流畅合理，但实际是脱离检索依据的编造，本质是"不知道自己不知道"，无法完全消除只能通过 Prompt 和参数设计压低概率。
幻觉三种表现：篡改事实（chunk 说 A 模型说反义的 B）、凭空捏造（补充 chunk 完全没提到的细节）、张冠李戴（把不同 chunk 的信息错误拼接到同一主体上）。
Lost in the Middle（迷失在中间）：模型对长上下文中间位置内容的关注度低于开头结尾，容易忽略排在中间的 chunk。
Temperature：控制模型输出随机程度的采样参数，值越低越保守确定，RAG 场景推荐 0~0.3。
Top-P（核采样）：只在累计概率达到设定阈值的候选词范围内采样、排除低概率长尾选项的随机性控制方式，常与 Temperature 配合但不建议随意叠加。
引用对齐（Citation Alignment）：要求模型在回答中标注所依据的参考资料编号，使答案可被用户和审计流程追溯验证的机制。
兜底回答：当检索上下文不足以支撑回答时，模型应给出的诚实、结构化（承认不足+替代方案+已知部分）的应答模板，而非强行编造答案。
response_format 参数：部分大模型 API 提供的用于强制结构化（如 JSON）输出的参数，比纯 Prompt 层约束更可靠。

## 与 xrag 项目的关系

本篇是 xrag "检索结果 → 最终答案"这一环（问答生成/生成策略模块）的直接设计依据，紧接在检索与重排序模块之后：

- xrag 的问答生成接口应采用三段式消息结构：System Prompt（角色边界+回答规则+引用规则+格式要求四个分组）放在 `system` 消息里一次性定义，检索到的 Top-K chunk 组装出的上下文与用户当前问题放进 `user` 消息按请求动态拼装——这与上一篇（`01-03-Prompt工程入门.md`）落地的消息分层思路一致，本篇进一步给出了针对生成质量本身（幻觉/引用/格式）的规则内容。
- chunk 组装到上下文时必须带稳定编号、来源、更新时间三个字段，并用空行分隔，这是 xrag 检索模块输出对接生成模块时的接口约定；这三个字段直接来自 xrag 元数据管理模块的产出，是元数据能力在生成阶段的实际落地点。
- xrag 默认调用大模型 API 的参数应参照本文推荐值：Temperature 设在 0~0.3（示例代码用 0.1），一般不必同时叠加 Top-P；如果 xrag 使用的模型 API 支持 `response_format` 强制 JSON，结构化输出场景应优先用该参数而不是纯靠 Prompt 约束。
- 引用解析逻辑（正则提取 `[数字]` 编号 + 边界检查 `index >= 1 && index <= chunks.size()`）应作为 xrag 答案后处理层的标配代码，用来防御模型"引用幻觉"（引用了实际不存在的编号），不能只依赖 Prompt 层的自律约束。
- xrag 需要在生成模块里内置三层兜底回答模板（完全无法回答 / 部分可回答 / 超出知识库边界），作为模型没有把握时的显式出口，而不是依赖模型自己判断"要不要编"。
- xrag 默认下发给生成模块的 Top-K chunk 数量可以参照本文的场景化经验值——简单事实类问题 3~5 个、复杂对比类 5~8 个、总结类 8~10 个，作为检索模块和生成模块之间默认 Top-K 参数的设计起点，同时结合 Reranker 的效果做调整。
- xrag 后续如果要建立自己的 Prompt 迭代和质量保障机制，可以直接复用本文给出的 bad case 驱动流程（记录→分类→针对性改 Prompt→历史 bad case 回归测试），把它做成 xrag 的 Prompt 版本管理和上线前体检的一部分。

## 值得注意的设计取舍/坑

- System Prompt 规则数量"5~8 条"只是经验起点，作者明确指出复杂业务场景下这个数字不够用，需要大量测试排查规则之间是否互相矛盾（"左右互搏"），不能把这个数字当成硬性上限直接套用。
- 引用规则能大幅降低但不能完全杜绝幻觉：作者自己的实测里，即便 Temperature 只有 0.1，某个实际被使用的 chunk 仍偶尔没有被正确引用，说明"要求模型引用"是概率性的行为约束，不是代码级别能强制保证的硬约束，工程上仍需要靠边界检查等代码逻辑做兜底。
- Temperature 特意选 0.1 而非 0：完全确定性输出（Temperature=0）有时会让回答显得生硬机械，作者认为保留一点点随机性反而更自然，这是准确性和表达自然度之间的权衡，不是"越低越好"。
- Temperature 与 Top-P 不建议随意同时调整——两者叠加后不同模型的行为可能不一致，本文建议先只调 Temperature，效果不满意再考虑加 Top-P，避免过度调参引入不可预期的行为差异。
- JSON 等结构化输出如果纯靠 Prompt 约束，模型可能自创字段名或格式不一致，必须配合输出示例，若模型 API 支持 `response_format` 参数应优先使用它而不是完全依赖 Prompt 层约束。
- Query 改写（Query Rewriting）被明确排除在本文范围之外，本文的三段式结构默认直接使用用户原始问题，遇到语义模糊的提问时的处理方案要等后续文章展开，不能假设本文已经覆盖了这部分。
