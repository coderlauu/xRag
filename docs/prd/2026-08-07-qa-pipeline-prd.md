## 1. 背景与动机

Phase 1 已能把文档转成可检索的分块和向量，Phase 2 已提供 Chat、流式 Chat、Embedding、Rerank
四个稳定能力端口，但 xrag 仍没有“用户问一句话，系统结合历史理解他真正想问什么”的业务链路。

如果直接把用户原话交给向量检索，会同时遇到四类问题：指代依赖前文、复合问题没有拆分、多个知识库
缺少可运营的路由规则、相似意图无法安全判断。错误路由比没有路由更危险——系统可能从错误知识库找到
看似合理的内容并自信作答，用户无法察觉来源方向已经错了。

3A 因此先建设问答链路的“理解层”：持久化历史、压缩长期记忆、改写问题、维护意图树、匹配意图、
识别歧义并生成检索动作。它不伪造尚未实现的检索结果或最终答案。

## 2. 产品定位

### 2.1 服务对象

1. **知识问答用户**：在对话页连续提问，系统应理解“它”“刚才那个规则”等依赖历史的表达；不确定时先问清楚。
2. **意图树运营者**：维护系统应该把什么问题路由到哪个知识库，能看见并修正含糊的描述与错误绑定。
3. **后续 3B/3C 编排**：消费 3A 产出的规范化子问题、意图候选、歧义结果和检索动作，不重复实现理解逻辑。
4. **项目验收者**：在 3A 尚无最终生成能力时，通过明确标为验收信息的“本轮处理”区域验证真实中间结果。

### 2.2 产品承诺

一次 3A 问题处理应做到：

> 保存用户消息 → 加载摘要与近期历史 → 把问题改写成可独立理解、数量有界的子问题 → 对启用的叶子意图
> 做匹配并全局封顶 → 歧义时如实请用户选择方向 → 无歧义时生成检索动作 → 保存可追溯的处理结果。

系统不承诺每次都能猜中意图；承诺的是不静默丢问题、不把低置信度包装成确定结果、失败时给出保守且
用户可理解的下一步。

## 3. 阶段边界

### 3.1 3A In Scope

- 对话创建、列表、切换、标题、消息历史与逻辑删除。
- 摘要压缩、水位线、近期原始轮次保留和摘要失败降级。
- 查询改写、指代消解、术语归一和最多三个子问题的拆分。
- 意图树的查看、创建、编辑、启停、逻辑删除和父子一致性处理。
- 意图叶子的匹配描述、示例、类型、知识库 ID 绑定与 `promptSnippet`。
- 意图评分、结果容错、跨子问题总量封顶和低置信度处理。
- 单子问题的跨品类歧义引导，以及用户选择后的第二轮闭环。
- 意图到“定向知识库 / 后续全局兜底 / SYSTEM 短路候选”的动作映射描述。
- 问答对话页与意图树管理页的 3A 界面基线。

### 3.2 3A Out Of Scope

- 真实知识库检索、全文/BM25 通道、结果融合与 Rerank；属于 3B。
- MCP 工具执行与工具结果展示；属于 3B。
- 最终答案生成、逐字流式输出、停止、断连、排队和限流；属于 3C。
- 让运营者直接编辑评分 Prompt、阈值组合或供应商采样参数。
- 意图树拖拽排序、任意换父节点、版本回滚、批量导入导出和多人协同编辑。
- 意图匹配质量评测与自动调参；属于 Phase 4。
- 多租户、RBAC 与对话分享；xrag 继续沿用单用户边界。

## 4. 统一语言

| 术语 | 定义 |
|---|---|
| 对话（Conversation） | 一组有顺序的用户/助手/引导消息；3A 已持久化，后续阶段继续扩展 |
| 本轮（Turn） | 从用户提交一条消息开始，到系统产生引导或可供 3B 使用的检索动作结束 |
| 摘要（Summary） | 对已滑出近期窗口的历史做结构化压缩；只保存用户目标、约束与状态，不保存历史答案事实 |
| 水位线（Watermark） | 摘要已经覆盖到的最后一条消息标识，防止重复或漏压缩 |
| 规范化问题 | 消除指代、补足上下文且适合检索的独立问句 |
| 子问题 | 复合问题拆分出的独立问题；第一版单轮最多三个 |
| 意图树 | 组织路由规则的可变深度树；中间节点用于组织，只有叶子参与匹配 |
| 意图叶子 | 可执行的末端节点，携带匹配信息并绑定知识库或系统类动作 |
| 匹配描述 | 给模型判断“什么问题应该来这里、与兄弟节点如何区分”的描述，不等同于知识库的人类简介 |
| 歧义引导 | 系统无法可靠区分多个品类时，先请用户选择方向而不是猜测 |
| 检索动作 | 3A 产出的声明式结果，描述后续应查哪些知识库及是否需要兜底；3A 本身不执行检索 |
| 本轮处理 | 3A 验收用的中间状态视图；不是最终答案，也不是面向普通用户长期暴露的模型思维链 |

## 5. 核心用户旅程

### 5.1 连续追问

1. 用户先问“海外仓的入库时效是什么？”
2. 下一轮只问“那超时了怎么办？”
3. 系统加载近期历史，把问题改写为“海外仓入库超过时效后如何处理？”
4. 匹配“物流与配送 > 跨境物流 > 海外仓”叶子，形成定向知识库动作。
5. 3A 验收态显示真实改写与匹配结果；最终产品在 3B/3C 接着检索和回答。

### 5.2 复合问题

1. 用户问“退货要什么材料，退款多久能到账？”
2. 系统拆成两个独立子问题，并分别保留至少一个最相关意图。
3. 如果模型拆出超过三个主题，系统不静默忽略第四个，而是请用户拆开提问。

### 5.3 歧义引导

1. 用户问“退货政策是什么？”
2. “3C 数码”“家电”“服装”三个品类得分接近且用户没有指定品类。
3. 系统如实提示“这个问题可能涉及以下几个方向”，最多展示三个单选项和“都不是这些”。
4. 用户选择“3C 数码”，下一轮结合完整引导消息改写成明确问题，不重复触发同一歧义。

### 5.4 运营者新增意图

1. 运营者在树中选择“物流与配送 > 跨境物流”，新增“清关流程”叶子。
2. 填写名称、匹配描述、正向示例，绑定一个现有且启用的知识库。
3. 保存前系统校验兄弟节点区分度提示、必填项与叶子绑定。
4. 保存成功后新叶子可参与后续请求；当前正在处理的请求不被中途改写。

## 6. 功能需求

### FR-3A-01 对话生命周期

- 首次提交问题时自动创建对话，不要求用户先填写表单。
- 对话标题默认取首条问题的精简文本；用户可以重命名。
- 列表按最近活动时间倒序，展示标题、更新时间与最近一条消息摘要，不展示内部评分。
- 删除对话使用逻辑删除并二次确认；删除后不再出现在列表，不影响 AI 调度诊断事实。
- 新建、切换、重命名或删除对话不能丢失当前已成功保存的消息。

### FR-3A-02 消息提交与本轮状态

- 空白消息不可提交；同一对话同一时刻只允许一个活动本轮。
- 用户消息必须先可靠保存，再进入理解链路；保存失败不能表现为“已发送”。
- 3A 内部状态至少区分：`已保存`、`加载历史`、`改写中`、`匹配意图`、`等待澄清`、
  `已形成检索动作`、`处理失败`。
- 普通聊天区域只显示用户可理解的消息；原问题、规范化问题、子问题、候选意图和降级原因放在明确标为
  “3A 验收信息”的本轮处理区，不伪装成助手答案。
- 刷新页面后能恢复已保存消息及本轮稳定终态；瞬时动画状态无需恢复。

### FR-3A-03 历史与摘要

- 上下文由“已有摘要 + 水位线之后的近期原始消息”组成，不能把同一轮重复放入两处。
- 摘要只保存用户目标、约束、偏好、指代对象和“当时”的处理状态；不得保存历史回答中的事实结论、
  chunk 正文或工具结果。
- 只有完整助手轮次结束后才允许触发摘要，不能压出半轮对话。
- 摘要是增强项：失败、超时或并发冲突时保留旧摘要并继续当前问题，不能清空已有成果或拒绝用户提问。
- 歧义引导消息及其选项在用户完成选择前不得被摘要掉，否则“1”将失去指代对象。

### FR-3A-04 查询改写与子问题拆分

- 改写必须保留用户原意、实体、限定条件和否定关系，不能补造用户没说过的前提。
- 指代依赖历史时补足上下文；本身已经独立的问题可保持原意，不追求文风重写。
- 改写失败时使用经过最小归一化的原问题继续，不向用户显示技术错误。
- 一个本轮最多产生三个子问题；超过上限时不静默截断，返回用户可见提示：
  `这个问题包含较多主题，请拆成不超过 3 个问题后重试。`
- 子问题顺序保持用户表达顺序，不能只按模型置信度重排。

### FR-3A-05 意图树管理

- 树允许两层和三层分支并存；中间节点不参与匹配，叶子参与匹配。
- 节点必须展示名称、完整路径、节点角色、启用状态、更新时间；叶子还展示类型与绑定目标。
- 创建节点时只能在选中的父节点下新增；3A 不支持拖拽换父节点。
- 匹配描述和正向示例是运营必填/重点字段；界面必须解释它们会直接影响路由准确率。
- KB 叶子绑定一个现有知识库 ID；知识库简介不能代替匹配描述。
- `promptSnippet` 是后续生成时追加的节点规则，不得替换系统安全规则；3A 可编辑但不执行。
- 删除为逻辑删除。根节点不可删除；删除父节点必须明确处理整个子树，不能留下孤儿或仍启用的后代。

### FR-3A-06 启停与父子一致性

- 停用父节点时必须先展示将受影响的启用后代数量，并提供“停用整个子树”确认；不允许只停父节点。
- 启用父节点只启用当前节点；若要恢复后代，用户必须显式选择“启用整个子树”，避免意外恢复旧规则。
- 启用叶子前必须确认所有祖先均启用、绑定知识库存在且可用、必填匹配字段完整。
- 并发修改或服务端一致性校验失败时，保留用户编辑内容并提示刷新差异，不把失败显示为成功。

### FR-3A-07 意图评分与总量封顶

- 一次模型调用对当前启用叶子评分；模型返回的节点 ID、分数和结构必须由代码复核。
- 默认每个子问题保留一个核心意图；确有歧义时单个子问题最多保留三个候选。
- 多子问题汇总时优先保证不同子问题各有代表，再让剩余名额按分数竞争。
- 总意图上限不得小于允许的子问题上限；两者冲突时启动失败，不运行一套会静默丢问题的配置。
- 所有候选置信度过低时返回空意图，不勉强路由到看似接近的知识库。

### FR-3A-08 歧义与无匹配

- 歧义只在单子问题、多个 KB 品类分数接近且用户未提供品类线索时触发。
- 低分候选即使彼此接近，也不生成“请从这些低相关方向选择”的假精确引导。
- 引导最多给三个单选方向，展示人类可读的完整路径；第一版不支持多选或“全部”。
- 用户可以选择“都不是这些”，系统随后请用户补充产品、业务域或知识库方向。
- 灰色地带确认失败时保守地触发引导；引导增加一轮交互但避免错误路由。
- 引导文案必须说“可能涉及以下方向”，不得谎称“已在知识库检索到”。

### FR-3A-09 检索动作产出

- 每个规范化子问题都要产生可解释的动作：定向知识库、需要全局兜底、SYSTEM 候选或等待澄清。
- 动作记录原问题/子问题的稳定关联、意图路径与配置快照标识；不保存模型思维链。
- 3A 不执行知识库查询，也不展示伪造来源或答案。
- 动作阈值之间必须保持“保留 ≤ 定向 ≤ 全局兜底 ≤ 单意图补充”的顺序约束；具体数值留给 Step C。

### FR-3A-10 导航与双界面

- 顶部导航增加 `问答` 和 `意图树`，与既有 `知识库`、`诊断` 并列。
- 建议正式路由：问答 `/chat`，意图树 `/intent-tree`。
- 问答是默认业务入口；是否把根路径从知识库改到问答，待本 Step B 确认。
- 两个页面都必须有独立规格和可点击原型，并在任何 Phase 3 前端代码之前一起确认。

## 7. 降级与用户反馈矩阵

| 失败点 | 系统行为 | 用户可见反馈 | 是否中断本轮 |
|---|---|---|---|
| 历史摘要加载失败 | 仅用近期原始历史 | 不打扰用户；验收信息标记“未使用摘要” | 否 |
| 近期历史加载失败 | 仅用已有摘要和当前问题 | 克制提示“本轮可能未结合最近对话” | 否 |
| 摘要生成失败/冲突 | 保留旧摘要，下轮重试 | 不打扰用户 | 否 |
| 查询改写失败 | 使用最小归一化原问题 | 验收信息标记“使用原问题” | 否 |
| 单个子问题意图失败 | 该子问题进入无匹配 | 需要用户补充该问题的方向 | 仅该子问题 |
| 全部意图失败/低分 | 不猜测知识库 | `我还不能确定应该从哪个方向查找，请补充产品或业务范围。` | 是 |
| 歧义灰区确认失败 | 保守触发引导 | 展示方向单选 | 是，等待用户 |
| 意图树保存校验失败 | 不应用修改，保留表单 | 展示具体字段/父子冲突 | 是，仅管理操作 |
| 消息持久化失败 | 不启动理解链路 | `消息未保存，请重试。` | 是 |

## 8. 隐私、安全与可观测

- 对话和消息是业务数据，按全系统逻辑删除约束管理；AI 调度诊断仍不得保存正文。
- 问答链路记录可以保存阶段、耗时、节点 ID、分数区间、是否降级和稳定请求 ID；不得保存模型思维链。
- 意图树的 `description`、示例和 `promptSnippet` 都是不可信运营输入；3A 只保存，3C 必须在进入 Prompt 时隔离。
- 页面不得向普通聊天消息暴露原始 Prompt、供应商错误体、内部调用栈或 API Key。
- 意图树变更至少保留更新时间；完整审计历史是否本期建设留给 Step C 数据模型权衡。

## 9. 非功能需求

### 9.1 可用性与无障碍

- 两个页面在 375px 和 1440px 宽度下可完成核心任务。
- 所有树节点和歧义选项可用键盘操作；颜色不是唯一状态信号。
- 编辑未保存时切换节点、对话或关闭页面必须提醒。
- 失败文案说清“什么没成功、用户现在能做什么”，不能只显示错误码。

### 9.2 性能边界

- 对话首屏与意图树首屏不得一次加载无限历史或全部大型树数据；分页/分段策略留给 Step C。
- 多子问题意图调用必须有总量上限，不能让单次用户问题无限扇出模型请求。
- 摘要、改写和意图都是增强/理解步骤，各自失败不能造成资源或任务永久占用。

### 9.3 一致性

- 用户消息、处理终态和意图树修改必须有可重放的稳定结果；刷新不能把失败显示成成功。
- 节点启停/删除后，新请求读取一致的树快照；已开始请求采用哪个快照由 Step C 冻结，不能中途混用。

## 10. 3A 验收标准

- [ ] 首次提问自动创建对话；刷新后对话、消息和稳定处理终态仍存在。
- [ ] 依赖历史的追问能被改写为独立问题；改写失败时显式记录降级但不中断。
- [ ] 复合问题最多拆成三个；超过上限时用户能看到拆分提示，不静默丢弃。
- [ ] 摘要水位线避免重复压缩，摘要失败保留旧摘要，未完成的歧义选项不会被压掉。
- [ ] 意图树能完成增删改、启停、KB 绑定和父子一致性失败提示。

- [ ] 低置信度不勉强路由；歧义时最多展示三个真实方向，用户选择后不会重复引导。
- [ ] 3A 产出检索动作但不伪造检索结果、来源或最终答案。
- [ ] 两套界面均通过桌面与窄屏走查，并在前端实现前获项目所有者确认。

## 12. 3B 范围与产品语义（Step B，2026-08-08）

### 12.1 范围裁决

- 检索通道：**定向向量 + 全局向量 + BM25 关键词**三路混合。
- MCP 工具：**含有副作用的工具**，配二次确认流。

两项均由项目所有者裁决，理由与后果见 [Phase 3 计划 §8](../exec-plans/active/2026-08-07-qa-pipeline-phase-plan.md)。

### 12.2 检索来源展示

用户能看到答案依据了哪些内容，且**看得出它来自哪个知识库**。每条来源展示：知识库名称、
文档名、可定位的片段位置。

- 同一片段被多条通道命中时，**只展示一次**，不因为"命中两次"就显得更可信。
- **不展示任何原始分数。** 余弦相似度与 BM25 分数量纲不同（0.82 与 12.5 不可比），把它们并列
  展示会让用户以为后者更相关。3A 已确立的"强/中/低区间"惯例延续到这里。
- 来源顺序即系统认定的相关性顺序，但不标注名次数字。

### 12.3 无结果

检索一无所获时，助手明说"没有在知识库里找到相关内容"，**不得用模型常识补一段看起来像答案的话**。
同时给出可操作的下一步（换个说法、指定知识库、检查该知识库是否已入库）。

这与 3A 的 `NO_MATCH` 是两件事：3A 是"没匹配到方向"，3B 是"方向对了但库里没有"。两者文案必须
可区分，否则用户无法判断该改问法还是该补资料。

### 12.4 部分知识库失败

多路检索中一部分失败时，**如实告知"结果不完整"并点名哪个知识库没查成**，而不是拿剩下的结果
当完整结果呈现。用户可以选择重试或就现有结果继续。

判断依据必须是显式状态，不能靠"结果条数少"倒推。

### 12.5 未重排

Rerank 不可用（无 Key、供应商故障、Noop 降级）时，检索照常返回，但**标明结果未经精排**。

- 未重排是一个**用户可见的事实**，不是内部细节：它直接影响结果可信度。
- **Rerank 返回不足 topN 时，不用原始候选补齐。** 补进来的正是 Rerank 判定为不相关的片段，
  却会被摆在"已精排"的位置上——这比结果少几条更有害。

### 12.6 工具请求 / 执行 / 失败

工具调用对用户是三段可见状态：**请求（要调什么、带什么参数）→ 执行中 → 结果或失败**。

- **工具未注册或不在白名单时，必须明确告知**，不能静默跳过后当作"没有工具可用"——那会让用户
  以为系统不支持，而实际是配置缺失。
- **失败原因只展示归一化后的稳定文案**，绝不透传异常 message：它可能带内部主机名、端口和堆栈片段。
- 参数由模型从对话中抽取，**抽取结果对用户可见**——这是他确认前唯一能核对的东西。

### 12.7 副作用确认

**有副作用的工具在用户确认前一律不执行。** 确认卡必须展示：工具做什么、用哪些参数、影响什么。

- **参数抽取失败时，禁止用默认值继续执行。** 这条对只读查询尚可商榷，对有副作用的工具是不可
  接受的——用户问"张三上季度的排名"而系统查了"本季度"只是答错，换成提交工单或发起退款就是
  真实损失。抽取失败即中止并请用户补充。
- **必填参数缺失时不得调用工具。** 不允许出现"参数被过滤掉后工具照常执行"。
- 参数校验不只看字段名，**还要按 Schema 校验值**；字段名对但取值非法（枚举外的值）同样拒绝。
- 确认卡的默认焦点不落在确认按钮上（沿用 3A 危险操作惯例）。

### 12.8 留给 Step C 的技术决策

产品语义已冻结，以下实现选择在 Step C 决定，**不得在此默认**：

1. **候选融合策略**（RRF 或加权）。跨通道分数不可直接比较，这是 §12.2"不展示分数"的成因。
2. **中文分词方案**。Postgres `to_tsvector` 不切中文，BM25 通道需要 zhparser / pg_jieba 一类
   扩展——**这是一个新的外部依赖**，须显式决策并进部署基线。
   → **Step C 已决（2026-08-08）：应用侧分词 + `tsvector('simple')`**，不引入数据库扩展、
   不自建镜像。同时更正本条的两个错误前提：**Postgres 内置全文检索没有 BM25**（排序是
   `ts_rank_cd`），**`pgvector/pgvector:pg16` 也不含那两个扩展**。因为融合选了 RRF（只吃排名），
   "拿不到真 BM25"不影响跨通道可比性。见 [ADR 0008](../adr/0008-hybrid-retrieval-and-rrf-fusion.md)。
3. **并行度上限**。真正的约束是数据库连接池而非线程池：向量检索独占只读事务连接，
   Hikari 默认池仅 10。并行度必须 ≤ 池大小，且与 3C 的全局并发许可一起核算。
4. **去重键**。不得用 `text.hashCode()` 兜底：int 碰撞虽罕见，一次碰撞就会丢掉一条真实证据。
5. **是否保留通道抽象**。pgvector 下定向与全局仅差一个 `where` 子句，但两者的激活条件、
   topK 倍率与去重优先级不同——差异需要一个安放处，这不是扩展性问题。

## 13. 3C 范围与产品语义（Step B，`2026-08-12`）

3C 是 Phase 3 的最后一段：**生成答案 + 流式推送 + 任务管控 + 排队限流**。
3A 交付了理解、3B 交付了依据，3C 才第一次真的回答用户。

本节冻结用户可见的语义。技术形态（SSE 事件闭集、任务状态机、信号量、Prompt 预算算法）
留给 Step C，但**不得与本节冲突**。

### 13.1 范围裁决

- **传输**：单向 SSE。不引入 WebSocket——3C 只需要服务端推，双向通道会把连接管理与鉴权
  复杂度提前引入。
- **并发控制**：全局许可 + 排队等待 + 超时拒绝。
- **停止**：用户可主动停止生成；停止是**用户意图**，不是错误。
- **不做**：多轮并行生成、生成结果编辑、答案重新生成（re-generate）。三者都会引出
  "同一轮多个答案"的数据形态，不在本期。

### 13.2 状态闭集

一次提交从进入系统到终结，用户可见的状态只有这些：

| 状态 | 用户看到 | 输入区 | 可做 |
|---|---|---|---|
| `排队中` | `排队中…` | 禁用 | 停止（取消排队） |
| `生成中` | 逐字出现的回答 | 禁用 | 停止 |
| `已完成` | 完整回答 | 可用 | 追问 |
| `已停止` | 已生成的部分 + `已停止` 标记 | 可用 | 追问（不提供"继续生成"） |
| `失败` | 归一化原因 + `重试` | 可用 | 重试 |
| `等待超时` | `当前排队较多，本轮未开始生成` + `重试` | 可用 | 重试 |
| `未保存` | 正交标记，见 §13.5 | 可用 | 追问，但禁用依赖 messageId 的操作 |

**没有 `停止中` 这个用户可见状态。** 点下停止后界面直接进 `已停止`——服务端的取消传播
可能要几百毫秒，但那是实现细节；给用户一个"正在停止"的中间态只会让他怀疑停止没生效。
若取消期间又流出了几个字，它们照常追加进那条部分回答，不回滚。

### 13.3 排队只说"排队中"（裁决）

**不给队列位置，不给预计等待时间。**

理由不是省事：位置会因公平调度与重入队而**非单调变化**（可能变大），预计时间在流式场景下
几乎必错。两者都属于"看起来精确、实际不准"的信息，用户据此做的决定（继续等还是放弃）会被
系统误导。只说"排队中"配一个可用的停止，让用户自己决定等多久，是更诚实的表达。

排队期间**必须能停止**。等待中的请求还没消耗模型额度，此时放弃对系统和用户都是纯收益；
一个不能取消的等待队列会让用户直接关页面，而那时服务端仍在为他排队。

### 13.4 部分回答保存并标注"已停止"（裁决）

停止、断连、生成中失败三种情况下，**已经流出的部分回答落库成一条真实消息**，带不完整标记。

理由：用户已经读到了那些内容。不保存意味着刷新后他看到自己刚读过的东西消失——这个行为无法
向用户解释。保存并标注，是"你看到什么就有什么"。

**接受的代价，需要在 Step C 正面处理**：部分回答会进入后续轮次的对话历史与摘要。一句半截的
话作为上下文可能误导下一轮的改写与意图匹配。Step C 必须决定它以什么形式进入历史
（原文、截断标注、还是摘要时跳过），**不能默认当成完整回答喂回去**。

不提供"继续生成"。断点续写要求把上一次的部分输出重新塞进 Prompt 并保证接得上，那是另一套
语义（也是另一份成本）；用户想要完整答案，重新问一次更可靠也更容易理解。

### 13.5 落库失败必须显式提示"未保存"（裁决）

回答完整流完、但持久化失败时：**回答照常显示，同时给一条明确提示**
`本条回答未能保存，刷新后将不可见`，并**禁用所有依赖 messageId 的操作**（复制引用、反馈、
后续引用该条）。

这条是针对一个具体的错误做法定的：只记日志、照常发完成事件、`messageId` 为空——用户看到一个
完整答案，系统里它不存在，而界面上没有任何异常。**那是最糟的中间态**：既没有"成功"的实质，
也没有"失败"的提示。

也不选"当作错误整轮标失败"：一次完整生成已经付费了，把它从屏幕上抹掉是第二次损失。让用户
先把内容拷走，比替他决定"这次不算"更合适。

### 13.6 断连重连能看到结果，但不继续流（裁决）

刷新或断线重连后**不重建 SSE**。轮次在服务端继续跑到终态，前端用普通读接口拿最终结果。

即：**断连不取消生成**。手机切后台、地铁里网络抖动都会断连，若断连即取消，用户会丢掉等了
很久的回答，而他并不觉得自己停过。

不做"重连后继续推剩下的"：那要求服务端保留已推事件序列与断点位置，并处理同一任务多个连接与
幂等重放。它是 3C 里成本最高的一项，而收益只是"重连瞬间也能看到逐字效果"。

代价要如实告诉用户：重连后那一轮显示为处理中，完成后才出现完整回答，**中间没有逐字过程**。

### 13.7 失败与重试

- 失败只展示**归一化原因**，绝不透传异常 message、base-url、上游错误体或堆栈片段。
  流式错误必须走与同步错误相同的翻译，不能把原始异常直接交给容器。
- `失败` 与 `等待超时` 都给 `重试`；`已停止` **不给**——它是用户自己的决定，摆一个重试按钮
  等于暗示他做错了。
- **等待超时与内部降级必须对用户区分开。** "队列真的等满了"和"抢到许可但没有线程跑"是两件
  不同的事，前者该说"排队较多"，后者是系统故障。把后者显示成前者会让用户以为是自己运气不好，
  也会让排查方向被带偏。
- 首包迟迟不来时，界面**必须有明确的等待表达**，不能只是空白。空屏无法区分"正在生成"、
  "卡住了"和"页面坏了"。

### 13.8 用户可见的诊断范围

3C 新增的可见信息**仅限**：本轮任务状态、是否排队过、生成是否被停止、是否未保存。

沿用 3A/3B 的既有纪律，**不新增**：Prompt 正文与消息数组、逐 token 推理或思维链、
供应商原始错误、模型/Provider/服务等级选择、队列位置与内部任务 ID。

`taskId` 属于内部标识。停止操作由界面自己持有它，不作为用户可见信息展示——**并且停止接口
必须校验任务归属**，只知道 ID 不足以停掉别人的生成。这条是安全要求，写在这里而不是等实现时
想起来。

### 13.9 不可信内容的界面纪律（延续 3B）

工具返回、chunk 正文、用户问题在 3B 已确立"一律纯文本渲染、不产生可点击目标"。3C 生成的
**答案本身同样是不可信输出**：模型可能被 Prompt 注入诱导产出链接或指令式文本。

答案渲染在 3C 首期**按纯文本处理**。要支持 Markdown 需要单独裁决，且必须先有链接与图片的
白名单策略——它不能作为"顺手加上"的呈现优化。

### 13.10 留给 Step C 的技术决策

1. **部分回答如何进入历史与摘要**（§13.4 的代价）——原文、截断标注还是摘要时跳过。
2. **SSE 事件闭集与终态优先级**：完成、停止、失败、超时在竞态下谁赢，以及事件顺序保证。
3. **流式专用 deadline**：不能沿用同步 Chat 的值；候选逐个重试时不得让首字延迟累加成
   候选数 × 单次超时。
4. **取消信号的传递方式**：低频事件不应实现成逐 token 的高频轮询。
5. **许可与线程池的关系**：两个管同一件事的闸门若必须并存，其一致性要有启动校验，
   而不是靠两份配置永远相等。
6. **拒绝路径与正常路径共用同一个推送实例**：两个实例包同一个连接会让幂等保护整体失效。
7. **`SseEmitter.send()` 的执行资源**：必须有界，且不得阻塞 Reactor Netty 的 event loop。
