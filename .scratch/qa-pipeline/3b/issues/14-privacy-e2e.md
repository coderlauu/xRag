## 执行记录（`2026-08-11`）

### 隐私审计（`Qa3bPrivacyAuditIntegrationTests`）

手法沿用 3A 的 `QaPrivacyAuditIntegrationTests`：标记串塞进每类正文，跑完链路再扫 3B 五张表、
3B 端点响应与 `ai_*` 诊断表。**每个标记串各有自己的允许范围**——工具参数值本来就该出现在
确认卡上，chunk 正文本来就该能在分块页看到；真正要守的是它们不该跨到哪里去。写成"全都不许
出现"会得到一个永远绿的假审计。

`priv03` 是反向断言：人为把异常 message 塞进 `qa_retrieval_target.failure_code`（该列无取值
check，而建表注释正写着"是归一化闭集，不是异常 message"——数据库拦不住的地方正是审计要盯的），
确认扫描器能报出来。没有这条，前两条随时可能因为"标记串压根没写进去"而假绿。

**工单 11 那个假绿陷阱又出现了一次，这次是正向断言抓到的**：白名单没配 → `definition` 为 null
→ 参数表为空 → "参数值不该跨到 `ai_*`"自然成立。补上白名单配置后才成为真断言。隐私测试必须
同时有正向与反向断言，只有反向的那一半永远绿。

### 无 Key 环境：Acceptance 的措辞把两层混在了一起

实测发现**无密钥时检索根本不会执行**：3A 的意图评分先拿不到候选
（`reasonCode=INTENT_SCORING_UNAVAILABLE`），动作退化成 `NO_MATCH`，而 `NO_MATCH` 不是可执行的
检索动作。所以"无 Key 时检索可用"在端到端这一层观察不到——不是检索坏了，是它没被要求做任何事。

因此拆成两条：
- `e2e04_无密钥时应用照常启动且检索不被触发`：如实断言端到端行为（`NO_MATCH` → `NO_RESULT`）。
- `e2e04_检索层在无密钥时退化为关键词召回且精排降级`：绕过 3A 直接 seed 动作再调编排，
  这才是"如果 3A 真产出了检索动作会怎样"的答案。

**顺带查证了工单 23 那句存疑记录**（"缺 Key 时重排直接失败而非降级"）：**不属实**。实测
`rerankApplied=false` 且 `degradation` 非空，是正常降级，与精排三态设计一致。

## 遗留

- **3B-E2E-02（一轮内同时产生来源与工具调用）未实现**：工具调用由 3A 的动作映射触发，而当前
  假 Chat 不产出工具调用意图——要造这个组合得先让 3A 能产出它，那属于工具触发链路的范围，
  不在本工单。已有的 `Qa3bPrivacyAuditIntegrationTests` 用 seed 方式覆盖了"来源与工具并存"
  的**数据形态**，但没覆盖"两者互不阻塞"的**时序**。
- **新发现的规格缺口，需要产品裁决**：无密钥环境的默认状态是
  **`status=RETRIEVAL_FAILED` 同时 `sources` 非空**。两者都符合现有规格——目标只由向量通道定义
  （架构 §19.6），向量全失败即"全部目标失败"；而关键词通道不产生目标、却真的召回了内容。
  于是界面会按 ui-spec §13.6 显示"没查成、可重试"，而来源区里躺着关键词召回的结果。
  这个组合在工单 08 写 `fail03` 时就被注意到并刻意绕开了，现在它成了无 Key 部署的常态。
  规格没有为它定义表达方式，**不在此擅自改实现**，测试如实断言当前行为。
