## 一句话概括

这篇文章从上一篇 Function Call 遗留的"工具一多就管不过来"的四大痛点（定义维护、跨语言集成、权限安全、可观测性）出发，系统讲解 MCP（Model Context Protocol）协议——它统一了大模型调用工具的接口标准（类比 USB），定义了 Host/Client/Server 三层架构和 Tools/Resources/Prompts 三大能力，并配合两种传输方式（Stdio、Streamable HTTP）与一个 Spring AI 实战案例，说明 MCP 不是取代 Function Call，而是在其之上补齐"怎么管理工具"这一层。

## 核心内容提炼

- **问题引入：工具规模化后 Function Call 管不住的四类痛点**。用企业知识库助手从 2 个工具（查年假、查订单）增长到 20 个工具的场景具体化：①**定义维护噩梦**——20 个工具每个 5~10 个参数，意味着几百行 JSON Schema 手写维护，参数改了忘同步就会传错参数出线上 bug；②**跨语言跨系统集成困境**——Java 工具、Python 工具、第三方 HTTP API 三种调用方式要写三套适配代码，认证方式（Token/API Key/OAuth）各不相同；③**权限安全黑洞**——协议本身没有权限机制，"用户 A 能否查用户 B 的年假""实习生能否调用删除订单"这类校验全部要自己写，且容易和业务代码混在一起留下漏洞；④**可观测性缺失**——调用次数、耗时、失败率、完整调用链路都要自己埋点，工具链一长（A 调 B、B 查库）排查就是大海捞针。文章明确定位：Function Call 解决了"模型判断是否调用工具＋标准化输出调用意图"这两件事，但没解决"工具怎么被管理"，MCP 就是补这一层的标准化工具管理协议。

- **MCP 的核心定位：大模型世界的 USB 接口**。MCP（Model Context Protocol，模型上下文协议）由 Anthropic 于 2024 年 11 月开源发布，是一个开放的协议规范而非具体产品/框架。核心思想：任何工具只要实现了 MCP 协议，就能被任何支持 MCP 的客户端调用，不需要关心对方的语言和平台。没有 MCP 之前，Java 工具只能被 Java 代码调、Python 工具只能被 Python 代码调，各系统是孤岛；有了 MCP，Java/Python/Node.js 写的工具与 Claude Desktop/Cursor/自建助手这些客户端可以任意组合、即插即用。

- **三层架构：Host → Client → Server**。
  - **Host（宿主应用）**：用户直接交互的应用，例如 Claude Desktop、Cursor、企业自建的知识库助手（比如 Ragent）。职责是接收用户输入→调用大模型→按模型指令通过 MCP Client 调用工具→把结果返给模型→展示最终答案。一个 Host 内部可以包含多个 MCP Client。
  - **Client（MCP 客户端）**：Host 内部的通信组件，负责和某一个 MCP Server 建连、发请求、收响应。关键约束：**一个 Client 只连接一个 Server**，但一个 Host 可以有多个 Client 连多个 Server（类比电脑有多个 USB 口，每口插一个设备）。职责还包括发现 Server 的工具列表、调用工具取结果、管理连接生命周期。
  - **Server（MCP 服务端）**：提供工具的一方，可以是本地进程（Stdio 通信）或远程 HTTP 服务（Streamable HTTP 通信）。职责是声明自己提供哪些工具（名称/描述/参数）、接收调用请求、执行并返回结果。
  - **关键机制——工具的动态发现**：Client 启动时会自动从 Server 拉取工具列表（含工具名、描述、参数定义），这意味着不需要在 Host 端手写 JSON Schema，Server 端定义好、Client 自动发现即可。这直接解决了 Function Call 的第一个痛点（工具定义维护）。

- **三大核心能力：Tools / Resources / Prompts**。
  - **Tools（工具调用）**：MCP 最核心的能力，和 Function Call 直接对应。区别在于工具定义的"位置"变了——Function Call 里工具定义写在客户端代码里（手写 JSON Schema，随请求一起发给模型）；MCP 里工具定义写在 Server 端，Client 通过协议动态获取。文章特别澄清：**MCP 协议本身只规定"工具定义在 Server 端、Client 动态获取"这件事，Server 端具体用注解/手写 JSON/配置文件哪种方式定义工具，是实现框架（如 Spring AI）的选择，不是协议本身的能力**。
  - **Resources（资源访问）**：Server 可以暴露资源供 Client 读取，如文件内容、数据库记录、API 返回数据。和 Tools 的区别：Tools 是执行操作（查年假、下单），Resources 是提供数据（读文件内容），更像是给模型补充上下文信息。
  - **Prompts（提示词模板）**：Server 可提供预定义的提示词模板，供 Client 构建和模型的交互，适合标准化场景（代码审查模板、文档总结模板）。文章说明本篇重点讲 Tools，Resources/Prompts 用得相对少、了解即可（后续第14篇《深入解析MCP中的Resources与Prompts》会专门展开）。

- **MCP 与 Function Call 的关系：增强而非替代**。MCP 底层仍依赖模型的 Function Call 能力——模型判断是否调用工具、输出 tool_calls JSON，这个能力还是 Function Call 提供的，MCP 不重新发明这个轮子。类比：Function Call 是"发动机"，MCP 是"整车"，发动机给动力，但上路还需要方向盘、刹车、仪表盘。文章用对比表总结两者差异（本质/工具定义/工具发现/跨语言支持/传输方式/权限控制/可观测性/生态八个维度），核心结论是 MCP 在工具发现（自动获取 vs 硬编码）、跨语言互通（协议统一 vs 各自实现）、传输标准化（Stdio/Streamable HTTP vs 依赖具体 HTTP API）三点上补齐了 Function Call 的空白，权限和可观测性"协议层面支持但还在完善中"。

- **澄清一个容易混淆的认知：MCP 协议层 vs 框架实现层（以 Spring AI 为例）**。协议层（标准制定者）定义了三件事：工具元数据的标准格式（name/description/parameters 的 JSON Schema）、Client-Server 通信协议（JSON-RPC over Stdio/HTTP）、工具发现机制（Client 启动时从 Server 拉取列表）——本质解决的是"工具定义从 Client 端转移到 Server 端，实现跨语言跨系统互通"。框架层（协议实现者，如 Spring AI）提供 `@Tool` 注解、自动扫描生成符合协议的元数据、处理 JSON-RPC 通信细节——本质解决的是"让 Java 开发者更方便地实现 MCP 协议"。类比 HTTP 协议与 Spring MVC 的关系：即使不用框架，纯手写 JSON 也能实现 MCP Server，只是更麻烦；MCP 协议真正的价值在于**一旦 Server 实现了协议，任何支持 MCP 的 Client（Claude Desktop、Cursor、Python 客户端等）都能直接调用，不需要为每个 Client 单独写适配代码**。这一点是理解全文的关键：代码量减少是框架带来的便利，跨客户端互通才是协议本身的核心价值。

- **两种传输方式：Stdio 与 Streamable HTTP**。
  - **Stdio（标准输入输出）**：Server 作为本地子进程运行，Client 通过 stdin/stdout 通信（类比在终端跑 `grep`，命令是输入、打印结果是输出），传输的是 JSON-RPC 格式的请求/响应。流程：Client 启动 Server 进程→往 stdin 写 JSON-RPC 请求→Server 从 stdin 读取、执行工具、把结果写入 stdout→Client 从 stdout 读响应。优点是简单、不需要网络配置、不暴露端口、通信只在本地进程间发生因而天然安全；缺点是只能本地调用，Server 和 Client 必须在同一台机器上。
  - **Streamable HTTP（可流式 HTTP）**：MCP 协议在 2025 年 3 月引入的传输方式，**替代了早期的 HTTP+SSE 方案**。Server 作为 HTTP 服务运行（监听端口），Client 发 HTTP POST 请求（JSON-RPC 格式），需要流式返回时 Server 通过 SSE 推送增量结果。优点是支持远程访问、支持多 Client 共享同一个 Server、支持流式响应、能利用 HTTP 生态的认证/负载均衡/监控基础设施；缺点是需要网络配置（端口/防火墙/HTTPS）、比 Stdio 多了网络开销。
  - **选型结论**：本地开发和个人工具用 Stdio；团队共享和生产环境用 Streamable HTTP，文章明确说企业级项目基本都是后者。

- **Java 实战：用 Spring AI 搭建一个 MCP Server**（延续企业知识库助手场景，提供 `getUserAnnualLeave`、`getOrderStatus` 两个工具，搭好后可被 Claude Desktop、Cursor 等任意 MCP 客户端直接调用）：
  - **三个 Starter，按传输方式选**：`spring-ai-starter-mcp-server`（Stdio，给 Claude Desktop/Cursor 这类本地工具用）、`spring-ai-starter-mcp-server-webmvc`（Streamable HTTP，基于 Spring MVC，远程/团队共享）、`spring-ai-starter-mcp-server-webflux`（Streamable HTTP，基于 WebFlux，响应式场景）。
  - **版本演进提醒**：Spring AI 1.0 版本用 `@Tool` 注解定义工具，2.0 版本改名为 `@McpTool`，文章明确说明后续文章统一以 `@McpTool` 为准（本篇示例代码用的是 `@Tool`，是较早版本）。
  - **定义工具**：一个 `@Service` 类里用 `@Tool(description=...)` 标注方法、`@ToolParam(description=...)` 标注参数，方法体直接返回业务数据（示例里是 mock 的 JSON 字符串）。相比 Function Call 手写 40+ 行 JSON Schema，这里只需要方法加注解。
  - **注册工具**：写一个 `@Configuration` 类，用 `MethodToolCallbackProvider.builder().toolObjects(...)` 把工具类实例传进去，框架会自动扫描其中所有 `@Tool` 方法、提取方法名/描述/参数注解，生成完整的工具元数据（JSON Schema）。
  - **关键配置及一个常见坑**：`application.yml` 里要设置 `spring.ai.mcp.server.name/version/type`（SYNC 同步或 ASYNC 异步执行模式），Stdio 模式下还要设 `spring.main.web-application-type: none`（不需要 Web 容器）和 `spring.main.banner-mode: off`。**坑点：Stdio 模式下 stdout 就是 MCP 协议的通信通道，任何非协议内容（Spring Boot 启动 banner、日志）一旦输出到 stdout 都会导致通信失败**，所以必须显式关闭 banner、把日志重定向到文件而不是 stdout。
  - **在 Cursor 中配置调用**：`mcpServers` 配置项里 `command` 填 `java`、`args` 填 `["-jar", "/path/to/xxx.jar"]`；如果本机默认 JDK 不是项目要求的版本（示例用 JDK 17），`command` 要换成具体 JDK 的绝对路径，并通过 `env.JAVA_HOME` 指定。
  - **切到 Streamable HTTP 只需两处改动**：Maven 依赖换成 `-webmvc` 版本；`application.yml` 里去掉 Stdio 相关配置、加 `server.port`。工具代码和注册配置完全不用改，仅传输方式从 Stdio 变为 HTTP。Client 配置从 `command+args` 变成 `{"url": "http://localhost:8080/..."}` 形式。
  - **代码量对比**：文章给出的估算是 Function Call 纯手写约 200 行（含 JSON Schema 构建）vs MCP+Spring AI 约 60 行（含工具实现），减少约 70%。但文章特别强调这个减少主要来自 Spring AI 框架的注解封装和自动路由，**不是 MCP 协议本身的功劳**；MCP 协议真正带来的核心价值是最后一项——任何支持 MCP 的客户端都能直接调用你的 Server，不用为每个客户端单独写适配代码。

- **MCP 在 RAG 系统中的应用**：
  1. **知识检索封装成 MCP 工具**：把上一篇 Function Call 里定义的 `searchKnowledgeBase` 直接改写成一个 `@Tool` 方法（内部走 Embedding→向量库检索→Reranking），好处是知识检索能力不再局限于自己的系统，任何支持 MCP 的客户端（比如团队成员在 Cursor 里写代码时）都能直接调用你的知识库。
  2. **多工具编排（多 Server 协同）**：比如"订单 #12345 能退货吗"需要同时查订单状态（业务系统）和退货政策（知识库），在 MCP 架构下这两个能力可以由两个独立的 MCP Server 分别提供，Host 根据模型判断并行调用多个 Server、综合结果生成答案。好处是职责清晰（每个 Server 独立开发部署维护）、灵活组合（加能力只需部署新 Server，不改现有代码）、团队协作（不同团队各维护自己的 Server，靠协议互通）。
  3. **Ragent 项目里的落地思路（简要）**：用 `MCPToolRegistry`（工具注册表，管理所有已注册的 MCP Server 和工具）+ `MCPToolExecutor`（工具执行器，按模型的 tool_calls 路由到对应 Server 并执行）+ 自动发现机制（系统启动时自动连接配置好的 MCP Server、拉取工具列表并注册进注册表）三个组件管理所有外部工具调用。文章明确说这只是简要架构思路，具体代码实现留给后续 Ragent 实战文章展开。

- **MCP 生态现状（发布约一年多后的快照）**：
  - **支持的客户端**：Claude Desktop、Cursor、Windsurf、Continue（VS Code 插件）、Cline（VS Code 插件）、Claude Code（CLI）、Spring AI（提供 Client/Server Starter）、Kiro，覆盖 AI 对话客户端、编程 IDE、CLI 工具、开发框架四类。
  - **社区 MCP Server 覆盖场景**：文件系统、数据库（MySQL/PostgreSQL/SQLite）、Web 搜索（Brave/Google）、代码仓库（GitHub 操作）、知识管理（Notion/Obsidian）、通信工具（Slack/Discord）、云服务（AWS/GCP），可以直接找现成的用，不必自己开发。
  - **五点局限性**：协议还在快速演进（传输层已从 HTTP+SSE 改成 Streamable HTTP，早期 Server 可能需要适配新版本）；部分客户端支持不完整（有的只支持 Stdio 不支持 HTTP，有的只支持 Tools 不支持 Resources/Prompts）；生产环境高并发下的稳定性和性能还需更多验证；权限模型（如基于角色的工具访问控制）还比较基础，企业级细粒度权限仍需自己实现；远程 Server 的认证方式（OAuth、API Key 等）还没有统一标准。文章类比 HTTP 协议从 0.9 到 3.0 的演进历程，认为标准化是大趋势，现在是学习和使用 MCP 的好时机。

## 关键概念/术语

MCP（Model Context Protocol，模型上下文协议）：Anthropic 于 2024 年 11 月开源的开放协议规范，统一大模型调用外部工具的接口标准，类比"USB 接口"。
Host（宿主应用）：用户直接交互的 AI 应用（如 Claude Desktop、Cursor、自建助手），内部可包含多个 MCP Client。
Client（MCP 客户端）：Host 内部负责与某一个 MCP Server 通信（建连、发现工具、调用、管理连接生命周期）的组件，一个 Client 只连一个 Server。
Server（MCP 服务端）：提供工具/资源/提示词的一方，可以是本地进程或远程 HTTP 服务，负责声明工具、接收请求、执行并返回结果。
Tools（工具调用）：MCP 三大核心能力之一，与 Function Call 直接对应，区别是工具定义放在 Server 端、由 Client 动态发现，而非写死在客户端代码里。
Resources（资源访问）：Server 暴露供 Client 读取的数据（文件、数据库记录等），用于给模型提供上下文而非执行操作。
Prompts（提示词模板）：Server 提供的预定义提示词模板，用于标准化交互场景。
Stdio（标准输入输出传输）：Client 启动 Server 本地子进程，通过 stdin/stdout 传输 JSON-RPC 消息通信，简单安全但只能本地调用。
Streamable HTTP：2025 年 3 月引入、取代早期 HTTP+SSE 方案的远程传输方式，Server 作为 HTTP 服务运行，支持多 Client 共享和流式响应。
JSON-RPC：一种轻量级远程过程调用协议，用 JSON 格式约定请求/响应结构，是 MCP 底层的消息格式。
@Tool / @McpTool：Spring AI 框架里用于标注方法为 MCP 工具的注解，1.0 版本叫 `@Tool`，2.0 版本改名为 `@McpTool`。
MethodToolCallbackProvider：Spring AI 提供的组件，扫描指定对象中所有 `@Tool` 注解方法并自动注册为 MCP 工具、生成元数据。

## 与 xrag 项目的关系

- 文章给出的 `MCPToolRegistry`（工具注册表）+ `MCPToolExecutor`（工具执行器）+ 自动发现机制这三个组件的架构思路，可以直接作为 xrag 设计"工具调用/MCP 接入层"模块时的骨架参考：注册表管理所有已连接的 MCP Server 和工具元数据，执行器负责按模型 tool_calls 路由到具体 Server 执行，自动发现机制在系统启动时批量连接配置好的 MCP Server 并拉取工具列表——这三块职责划分清楚，适合直接映射成 xrag 里对应的类/模块边界。

## 值得注意的设计取舍/坑

- **Stdio 模式下 stdout 是协议通信通道，任何非协议输出都会打断通信**：Spring Boot 默认会往 stdout 打印启动 banner，日志框架默认也可能输出到控制台，这些都必须显式关闭（`banner-mode: off`）或重定向到文件，否则 MCP 通信会失败。这是实际搭建 MCP Server 时最容易踩、也最隐蔽的坑（表现可能只是"客户端连不上/收不到响应"，很难第一时间联想到是 banner 输出干扰了 stdout）。
- **代码量减少 70% 是框架的功劳，不要误认为是协议本身的价值**：文章特别澄清这一点——Spring AI 的注解封装、自动路由带来的是开发体验提升，MCP 协议真正解决的核心问题是"一次实现、任何 MCP 客户端都能调用"，如果只看到代码变少就以为理解了 MCP 的价值，会忽略协议真正的意义（跨客户端/跨语言互通），后续做技术选型或对外介绍时容易讲错重点。
- **Spring AI 版本演进带来的实际接口兼容问题（评论区讨论证实）**：读者在 8.2 节测试 Streamable HTTP 时遇到本地配置需要用 `/sse` 后缀而不是文档写的 `/mcp` 后缀、Cursor 识别不了的问题；回复澄清是因为项目所用的 Spring AI 版本较早，支持 `/mcp` 路径的 MCP 协议实现是从 Spring AI 1.1.0-M1 版本才开始的，更早版本只支持 `/sse` 路径。这说明 Streamable HTTP 的具体端点路径不是一个稳定不变的协议细节，而是随框架版本变化的，接入时要先确认自己用的框架版本对应哪种路径约定，不能直接照抄教程里的固定 URL。
- **权限和认证目前协议层面并不兜底**：文章反复强调协议层面的权限控制"还在完善中"、认证标准化"还没有统一标准"，企业级的细粒度权限（基于角色的工具访问控制）和远程 Server 的认证方式都需要自己在应用层实现，不能假设"用了 MCP 协议，安全问题就自动解决了"。
- **Resources 的一种替代设计思路（来自评论区，值得记录）**：有读者指出文章示例里 Prompts 的用法完全可以用 Resources 订阅机制替代——把 Prompts 模板保存在 Client 本机（订阅 Server 端 Resource），拼接提示词时直接在本机完成，好处是减少网络往返开销、降低延迟，且当 Server 端模板变化时 Client 能通过订阅机制实时感知更新。这是对"Prompts 和 Resources 该怎么分工"的一个实用补充视角，供后续设计参考。
